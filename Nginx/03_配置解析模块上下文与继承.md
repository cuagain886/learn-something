# 配置解析、模块上下文与继承

## 1. 配置不是运行时逐行解释

启动/reload 时，Nginx lexer/parser 读取 token，指令由对应模块的 command table 处理，写入模块配置结构。

请求运行时通常读取已经合并好的配置，而不是重新解析文本。

```text
nginx.conf tokens
 -> ngx_command_t lookup
 -> directive set handler
 -> create main/srv/loc conf
 -> merge parent and child
 -> optimized runtime structures
```

## 2. 模块配置三层

HTTP 模块常提供：

```c
create_main_conf / init_main_conf
create_srv_conf  / merge_srv_conf
create_loc_conf  / merge_loc_conf
```

每个 http/server/location 上下文有模块配置指针数组。

`ngx_http_get_module_loc_conf(r, module)` 是按模块 index 取得当前请求 location 配置。

模块之间不能假定结构布局相同。

## 3. unset sentinel

创建子配置时不能直接填默认值，否则无法区分：

- 用户显式配置了某值。
- 子级未配置，应该继承父级。

因此常初始化为 `NGX_CONF_UNSET`、NULL 等 sentinel。

merge 时：

```text
child 未设置 -> parent
parent 也未设置 -> module default
child 已设置 -> child
```

## 4. “继承”不是统一语言规则

每个模块自己实现 merge。

可能是：

- 标量覆盖。
- 数组子级一旦出现就完全替换父级。
- 追加父子数组。
- 合并 hash。
- 根据其他字段生成派生结构。

因此不能用“子 location 自动继承父 location 所有指令”概括。

典型风险是子 location 新写一个 `add_header` 后，父级其他 header 不再按预期继承。

## 5. 配置上下文限制

`ngx_command_t.type` 声明指令可出现的上下文与参数形式。

同名看似合理的指令放错位置会在 `nginx -t` 报错。

上下文不是排版约定，它决定写入哪个配置对象以及请求阶段能否取得。

## 6. include 是文本展开

`include` 在解析时读取匹配文件。

风险：

- glob 顺序影响正则 location、map 等顺序语义。
- 重复 include 导致冲突或重复 listen。
- 自动化生成半个文件时 reload 读到不完整内容。
- 相对路径以 prefix/配置规则解析，不一定是当前 shell 目录。

部署应先原子写临时文件再 rename，并执行 `nginx -T` 审查展开后配置。

## 7. 配置 hash 构建

server_name、header、map 等可在配置期构建 hash、wildcard hash 或 regex 列表。

`server_names_hash_bucket_size` 等错误不是简单“域名太多”，还与最长 key、CPU cache line 和 hash 布局有关。

不要盲目把 bucket/max_size 调到极大；先查看错误提示与 key 集合。

## 8. 变量与 complex value

包含变量的指令不能在配置期得到最终字符串。

模块编译为 complex value：静态片段 + 变量取值脚本。

请求时执行得到值。

使用变量可能改变优化路径，例如动态 `proxy_pass` 可能需要 resolver 并无法使用静态 upstream 配置的所有行为。

## 9. map 优于复杂 if

`map` 在 http 上下文定义从输入变量到结果变量的映射，配置期构建高效查找结构。

适合：

- Host/URI/header 到标志。
- WebSocket Connection header。
- cache bypass 条件。
- 日志采样。

它是惰性求值：变量真正使用时才计算。

## 10. 配置 reload 的资源复用

`ngx_init_cycle(old_cycle)` 解析新配置并尝试复用：

- 未变化的监听 socket。
- 可兼容的共享内存 zone。
- 打开的文件等资源。

共享 zone 名称和大小变化可能无法原样继承。

reload 失败必须清理新 cycle 已打开资源，旧 cycle 继续工作。

## 11. 为什么共享区大小不能随意缩小

limit/cache/upstream zone 已包含运行状态。

新 cycle 尝试复用时，名称、tag 和大小必须符合模块约束。

直接缩小可能无法容纳已有 slab，导致配置失败或状态重建。

上线前在同版本进程验证 reload，而不仅是全新启动。

## 12. root 与 alias

`root` 通常把 URI 追加到根路径。

`alias` 用指定路径替换匹配 location 的 URI 部分。

```nginx
location /images/ { root  /data; }  # /data/images/a.png
location /images/ { alias /data/; } # /data/a.png
```

尾斜杠、正则 capture 和内部 rewrite 会改变结果。

安全上要检查 normalization 后路径，避免错误 alias 暴露目录。

## 13. 源码导航

- `src/core/ngx_conf_file.c`：token、指令查找、参数 setter。
- `src/core/ngx_cycle.c`：新旧 cycle 和资源。
- `src/http/ngx_http.c`：HTTP block、conf context、phase 初始化。
- 各模块 `ngx_command_t` 与 `create/merge_*_conf`。

## 14. 审查方法

```bash
nginx -t
nginx -T > expanded.conf
```

审查：

- 同一 listen 的 default_server。
- include 展开顺序。
- location 嵌套。
- 继承易错指令：headers、proxy headers、access rules。
- 动态变量是否需要 resolver。
- 共享区名称/大小。
- 证书、日志、临时目录权限。

## 15. 面试追问

问：为什么配置继承有时像覆盖、有时像追加？

答：Nginx core 只提供配置上下文，具体合并由每个模块的 merge 回调实现，没有统一的通用继承语义。
