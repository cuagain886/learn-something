# 限流、限连接、访问控制与安全边界

## 1. limit_req 是漏桶排队模型

共享 zone 按 key 记录请求速率状态。

`rate` 定义平均泄漏速度，`burst` 允许短时积累，`nodelay` 决定突发是立即放行还是排队延迟。

它不是固定窗口计数器。

## 2. key 设计

常见 `$binary_remote_addr`，比字符串 IP 节省共享内存。

但 CDN/NAT 后必须先正确 realip，否则所有用户共用代理 IP 被一起限流。

按用户 token 限流要防未认证/高基数 key 耗尽 zone，并避免把敏感 token 原文写共享状态/日志。

## 3. zone 容量

zone 满后新 key 无法正常记录，请求可能被拒绝。

容量取决于 key 长度、状态节点、IPv4/IPv6 和活跃 key 数。

共享区不会因配置 reload 自动无限扩展。

## 4. burst 语义

rate=10r/s、burst=20 不等于每秒允许 30 个永久持续。

burst 是超过稳定速率的队列/信用容量。

nodelay 可让这批突发立即通过，但之后请求要等待桶恢复或被拒。

## 5. limit_conn

按 key 限制并发连接/正在处理请求。

HTTP/2 一个 TCP connection 有多个 requests，模块计数语义需按版本文档理解，不能把 TCP 连接数与业务并发完全等同。

## 6. 多层限流

建议组合：

- 全局/边缘 DDoS 带宽保护。
- IP 连接限制。
- 登录/API 请求速率。
- 认证用户/租户配额。
- upstream 应用自身并发和队列保护。

Nginx 限流状态通常是节点本地共享内存，多实例间不全局一致。

## 7. real_ip 信任链

只有来自可信 LB/CDN 地址的 forwarded header 才能用于真实 IP。

若 `set_real_ip_from 0.0.0.0/0`，客户端可伪造 IP 绕过限流/ACL和污染日志。

递归解析时理解 header 链顺序与可信 hop。

## 8. Host 与 header 攻击

- 显式 default server 拒绝未知 Host。
- upstream Host 白名单/map，避免把客户端 Host 原样用于敏感内部路由。
- 限制 header 大小与非法字符。
- 清理客户端传入的内部身份 header。

## 9. 请求走私

前置代理与后端对 Content-Length/Transfer-Encoding、重复 header、URI normalization 解释不一致，可能造成 request smuggling。

保持各层更新，拒绝歧义请求，不随意开启兼容旧 header 的选项，并做端到端安全测试。

## 10. SSRF

变量 `proxy_pass http://$arg_host` 等动态代理可让攻击者访问内网/metadata。

必须使用 map 白名单、固定 upstream、DNS和网络 ACL；只校验字符串前缀不足以防编码、重绑定和 IPv6 绕过。

## 11. 方法与 body 限制

`limit_except`、`client_max_body_size`、body timeout 和 WAF共同约束攻击面。

返回 413 前是否已读取 body、前置 LB 的限制是否一致也需验证。

## 12. 面试追问

问：Nginx 多节点 limit_req 能否保证租户全局 100r/s？

答：默认共享 zone 只在单实例 workers 间共享；多节点各自计数，只能近似分担，需要全局限流服务或一致路由。
