# 负载均衡算法与健康判定

## 1. 默认 round-robin 不是简单取模

平滑加权轮询维护 peer 的 weight、effective_weight、current_weight。

每次选择累加 current weight，选最大者后减总权重。

这让权重分布更平滑，并能在失败时降低 effective weight、成功后逐步恢复。

运行状态在哪个 worker/共享 zone 中决定跨 worker 一致性。

## 2. least_conn

优先选择当前 active connections / weight 更小的 peer，再用轮询打破平局。

适合请求耗时差异明显。

限制：连接数不等于工作量；HTTP/2 后端、长连接、CPU差异和请求成本会使指标失真。

## 3. ip_hash/hash

hash 用 key 稳定映射 peer，可实现会话粘性或缓存亲和。

普通 hash 在节点变化时大量 key 重映射；consistent hash 减少迁移。

粘性不是状态可靠性：节点故障仍会重映射，应用 session 应外置或可恢复。

客户端 IP 在 NAT/CDN 后高度集中，ip_hash 可能严重倾斜。

## 4. random two choices

某些版本/构建支持 random 与 two least_conn 思路：随机抽少量 peer，再选负载更低者。

在大 upstream 集合中减少全量扫描和共享状态争用。

上线前确认开源/商业版本和具体指令支持。

## 5. passive health

开源常用被动失败：真实请求发生连接/超时/错误后，通过 `max_fails`、`fail_timeout` 暂时认为 peer 不可用。

它不是主动定时探测：

- 无流量时发现不了故障。
- 恢复通常由试探请求确认。
- 失败定义受 proxy_next_upstream 配置影响。

## 6. max_fails/fail_timeout

含义常被简化错误。

fail_timeout 同时参与失败统计窗口和暂时不可用时间；单 server upstream 的行为还有特殊性，避免唯一节点被永久屏蔽。

要按目标版本文档和源码验证。

## 7. slow_start 与主动健康检查

部分能力属于 Nginx Plus 或特定版本/模块。

开源配置不能直接照抄商业文档。

Kubernetes 中可由 readiness/endpoints 在 Nginx 外部完成健康摘除，但配置刷新存在传播延迟。

## 8. upstream zone

配置 `zone` 可让 upstream 运行状态在 workers 共享：

- peer counters。
- failure 状态。
- 动态解析后的地址等（取决版本能力）。

没有共享 zone 时，worker 各有自己的 peer 状态，可能对故障判断不同。

共享状态提高一致性，也引入锁和共享内存容量。

## 9. backup/down/drain

- backup：主 peer 都不可用时使用。
- down：静态禁用。
- drain 等能力需确认版本，通常避免新会话但允许已有绑定。

backup 机器必须有足够容量承接全部流量，否则主集群故障会把备机瞬间压垮。

## 10. keepalive 对算法的影响

选择 peer 后可能复用该 peer 的 idle connection。

keepalive cache 是 per worker，流量较低或 worker 分布不均时，各 worker 命中率不同。

DNS/IP变化后旧 keepalive 连接可能短期继续使用旧地址，需理解生命周期。

## 11. 排空发布

安全下线后端：

1. readiness 置失败/从 upstream 移除。
2. 等待配置/发现传播到所有 Nginx worker。
3. 停止新请求。
4. 等待应用 in-flight 完成。
5. 关闭实例。

仅先 kill 应用会让被动失败请求承担探测成本。

配置 reload 时旧 worker 可能仍持有旧 upstream 配置，长请求要纳入排空时间。

## 12. 热点与权重

weight 按请求/连接近似分配，不理解业务成本。

一个导出请求可能等于一千个 health 请求。

解决：

- 按 API 分类 upstream。
- 限制昂贵 endpoint。
- 应用报告负载/队列长度并使用更智能网关。
- 业务层分片。

## 13. 故障放大

一个 peer 变慢但未超时：least_conn 可能因连接堆积减少新流量，但 round-robin 继续分发。

超时过长会让连接和 worker_connections 被耗尽。

超时过短又会触发重试风暴，把剩余 peer 压垮。

容量必须保证 N-1 状态可承受降级流量，或快速限流。

## 14. 观测

按 peer 聚合：

- request rate/status。
- connect/header/response time。
- active connection。
- failure/retry count。
- upstream bytes。

access log 多尝试数组需按同一索引关联 addr/status/time。

## 15. 面试追问

问：least_conn 是否总比 round-robin 好？

答：不是。连接数只是负载代理，短连接、复用、HTTP/2 和请求成本会使它失真；还需共享状态和真实压测。
