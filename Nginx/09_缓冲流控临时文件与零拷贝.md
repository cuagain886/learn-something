# 缓冲、流控、临时文件与零拷贝

## 1. 两个方向

必须区分：

- `proxy_request_buffering`：客户端请求体到 upstream。
- `proxy_buffering`：upstream 响应体到客户端。

它们保护的方向和风险不同。

## 2. 请求缓冲开启

Nginx 先收完整 body，必要时写 client body temp file，再连接/发送 upstream。

优势：

- 慢客户端不长期占 upstream。
- body 可用于重试。
- upstream 快速连续读取。

代价：

- 上传首字节到后端更晚。
- 临时文件 I/O 和磁盘容量。
- Nginx 先承担完整 body。

## 3. 请求缓冲关闭

边收边转发，适合大文件流式上传。

代价：

- 慢客户端绑定后端连接。
- 开始发送后通常不能切换 peer。
- 上游更直接暴露于 slow upload。
- backpressure 跨两端传递。

## 4. 响应缓冲开启

Nginx 尽快从 upstream 读取到 buffer，超出内存部分可写 proxy temp file，再按客户端速度发送。

优势：后端连接更快释放，隔离慢客户端。

代价：每请求 buffer 内存、临时文件和磁盘写放大。

## 5. 响应缓冲关闭

适合 SSE、流式响应、低延迟 chunk。

上游产生速度超过客户端读取速度时，TCP 背压使 upstream write 变慢并长期占连接。

必须限制慢客户端、连接数和流持续时间。

## 6. buffer 参数关系

核心概念：

- `proxy_buffer_size`：响应首部初始部分。
- `proxy_buffers number size`：响应 body 缓冲集合。
- `proxy_busy_buffers_size`：正在向客户端发送的 busy buffer 上限。
- `proxy_temp_file_write_size`：单次临时文件写粒度。
- `proxy_max_temp_file_size`：单响应临时文件上限。

参数必须满足内部大小约束，过大乘以并发会耗尽内存。

## 7. 内存估算

```text
response_buffer_memory
≈ concurrent_buffered_requests
 × (proxy_buffer_size + allocated proxy_buffers + request pool overhead)
```

不是所有 buffer 必然立即分配满，但容量需压测峰值。

还要加 TLS、header、gzip、HTTP/2 stream、connection。

## 8. 临时文件

临时目录要考虑：

- 容量和 inode。
- 权限。
- 与 access/error/cache 日志的磁盘争用。
- 容器 ephemeral storage 限额。
- 清理异常退出残留。

磁盘写满可让原本健康 upstream 请求失败。

## 9. sendfile

静态文件 `sendfile` 可让内核在文件与 socket 间传输，减少用户态拷贝。

它不适用于所有动态 filter 场景；需要 gzip/修改 body 时通常必须进入用户态 buffer。

网络文件系统、虚拟化和特定内核可能有兼容/性能差异。

## 10. TCP cork/nodelay

`tcp_nopush` 常配合 sendfile 聚合响应头和文件数据。

`tcp_nodelay` 减少 keepalive 小响应的 Nagle 延迟。

它们作用于不同阶段，不能简单理解为互斥的“一个吞吐一个延迟”开关。

## 11. backpressure 链

```text
slow client
 -> Nginx write EAGAIN
 -> busy buffers accumulate
 -> temp file / stop reading upstream
 -> upstream send buffer full
 -> application write blocks/awaits
```

buffering 只改变背压出现的位置和可吸收容量，不能消灭速度不匹配。

## 12. chunked 与 Content-Length

上游响应未知长度时可能 chunked。

Nginx filter chain 可重新编码给客户端。

缓冲完整响应不一定意味着自动生成 Content-Length；协议版本、filter 和 header 决定。

请求 body chunked 到旧 upstream 时可能被强制缓冲以确定传输方式。

## 13. 客户端断开

临时文件或 buffer 中已有大量数据时客户端断开，应停止 upstream/清理文件。

但 upstream 业务副作用不回滚。

大下载断开率应监控 `$body_bytes_sent` 与 upstream response length 差异。

## 14. 实验

用限速客户端读取 1GiB upstream：

```bash
curl --limit-rate 10k https://host/file -o NUL
```

对比 buffering 开/关的：

- upstream 连接持续时间。
- Nginx RSS。
- temp path 大小。
- 磁盘 I/O。
- client 完成时间。

## 15. 面试追问

问：关闭 proxy_buffering 是否减少所有资源？

答：减少响应暂存内存/磁盘，但把慢客户端背压直接传给 upstream，增加后端连接占用和整个链路的并发状态。
