# 生产事故时间线与根因分析

## 1. 背景

4 workers，worker_connections=8192，代理 20 个应用实例。

配置 read timeout 60s、tries 无上限、buffering off，应用 P99 正常 200ms。

团队认为理论连接数 32768 足够。

## 2. T-10：数据库变慢

应用 P99 从 200ms 到 8s，仍持续返回。

Nginx upstream active 增长，Little 定律使并发约放大40倍。

buffering off 还让慢客户端继续占后端连接。

## 3. T-5：连接耗尽

每请求同时占 client+upstream，upstream keepalive idle也占 fd。

可用客户端数远低于32768。

新 accept 开始失败，handled/accepts 分离，前置 LB重试其他 Nginx。

## 4. T0：一个应用实例超时

Nginx 对多个 peer 重试。

每个原请求产生多次后端尝试，把剩余实例压垮。

部分 POST 已提交后 reset，被重试造成重复订单。

## 5. T+2：缓存和日志同盘写满

热点接口 stale 未配置，大量 MISS 回源。

proxy temp/cache/log 争用同盘，I/O延迟使 worker日志和文件操作进一步变慢。

## 6. T+5：错误 reload

值班调大 worker_connections 后 reload。

新旧 worker 共存使 RSS峰值，旧 WebSocket 不退出。

容器 OOM kill 一个 worker，连接再次断开。

## 7. 表象

- 499、502、504同时上升。
- 应用日志有重复 POST。
- Nginx CPU不高却无法接新连接。
- 总平均 upstream time 尚可，P99极差。
- reload 后旧 worker长期存在。

## 8. 根因链

```text
DB慢 -> 应用延迟 -> in-flight增长
-> 双端连接/fd耗尽 -> LB重试
-> Nginx upstream重试放大 -> 应用进一步过载
-> POST重复副作用
-> cache/log磁盘争用
-> reload内存双份 -> OOM和连接中断
```

不是单一“worker_connections 太小”。

## 9. 止血

1. 限制入口非关键流量。
2. 禁止非幂等自动重试。
3. 缩短有界 tries/timeout，但防止同步重试风暴。
4. 摘除真正故障实例并保留剩余容量。
5. 应用数据库熔断/降级。
6. 保护日志和 cache/temp 磁盘。
7. 暂停频繁 reload，排查旧 workers。

## 10. 整改

- 用 event_id/idempotency key 保护写请求。
- 按 endpoint 分 timeout/retry/upstream。
- 打开适合的 response buffering 隔离慢客户端。
- N-1容量和入口限流。
- cache lock/stale。
- fd/RSS/COW/reload峰值预算。
- 结构化多 upstream 尝试日志。
- 故障注入覆盖 DB慢+重试+reload组合。

## 11. 复盘证据

保留 expanded config、worker PID时间线、error/access log、upstream多值、ss/socket、fd、OOM、磁盘和应用幂等记录。

不要先重启清掉现场再猜。
