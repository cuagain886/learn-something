# 06 · HashMap 底层原理 ⭐⭐⭐

> Java 面试**出现频率最高**的集合题，逢面必考。核心一句话：
> **HashMap = 数组 + 链表 + 红黑树；用 hash 定位桶，冲突挂链表，链长超 8 且容量足够时转红黑树。**

---

## 1. 底层结构（JDK 8+）

```
table 数组（桶 bucket）
┌────┬────┬────┬────┬────┐
│ 0  │ 1  │ 2  │ 3  │... │
└─┬──┴────┴─┬──┴────┴────┘
  │         │
  ▼         ▼ 冲突时挂成链表，过长转红黑树
 Node      Node→Node→Node→...→（链表长度≥8 且 table≥64）→ TreeNode 红黑树
```

- **JDK 7**：数组 + 链表，链表用**头插法**（并发扩容会成环 → 死循环）。
- **JDK 8**：数组 + 链表 + **红黑树**，链表用**尾插法**（避免成环），冲突优化。

核心字段：
```java
transient Node<K,V>[] table;     // 桶数组，长度总是 2 的幂
transient int size;              // 实际键值对数
int threshold;                   // 扩容阈值 = capacity * loadFactor
final float loadFactor;          // 负载因子，默认 0.75
// 默认初始容量 16，树化阈值 8，退化阈值 6，最小树化容量 64
```

---

## 2. hash 扰动函数 ⭐——为什么不直接用 hashCode

```java
static final int hash(Object key) {
    int h;
    return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
}
```

- 定位桶用 `(n - 1) & hash`（因 n 是 2 的幂，等价于 `hash % n` 但更快）。
- 但 `(n-1) & hash` 只用到 hash 的**低位**，高位被浪费。
- **扰动**：把 hashCode 的**高 16 位异或到低 16 位**，让高位也参与定位，**减少冲突**，让分布更均匀。

> 为什么容量必须是 2 的幂？因为 `(n-1) & hash` 要等价于取模，n 必须是 2 的幂（n-1 全是 1）。即使你传 `new HashMap(17)`，它也会调整为 32（`tableSizeFor` 向上取最近的 2 的幂）。

## 3. put 全过程 ⭐⭐

```java
map.put(key, value);
```

1. 计算 `hash = hash(key)`（扰动）。
2. table 为空 → **resize() 初始化**（懒加载，首次 put 才建数组）。
3. 算桶下标 `i = (n-1) & hash`：
   - 桶为空 → 直接放新 Node。
   - 桶非空（冲突）：
     - 桶头 key 相同（hash 相同且 equals）→ **覆盖** value。
     - 是红黑树节点 → 走树的插入。
     - 是链表 → 遍历：找到相同 key 则覆盖；到尾部没找到则**尾插**新节点。
       - 插入后链表长度 ≥ **8** → `treeifyBin`：若 **table 长度 ≥ 64** 则转红黑树，**否则先扩容**。
4. `++size > threshold` → **resize() 扩容**。

> 为什么用 equals 还要先比 hash？hash 不等则 key 必不等，先比 hash（int 比较快）能快速跳过，只有 hash 相等才调相对昂贵的 equals。

## 4. 扩容 resize() ⭐

- 触发：`size > capacity * loadFactor`（如 16 * 0.75 = 12，第 13 个元素触发）。
- 新容量 = **旧容量 × 2**。
- **JDK 8 的精妙优化**：扩容后元素要么在**原索引**，要么在**原索引 + 旧容量**。因为容量翻倍后，`(newCap-1) & hash` 只多看 hash 的一个 bit：
  - 该 bit 为 0 → 留在原位 `i`。
  - 该 bit 为 1 → 移到 `i + oldCap`。
- 于是把旧链表**拆成 lo（低位）和 hi（高位）两条链**，分别放到 `i` 和 `i+oldCap`，**无需重新计算 hash**，且保持相对顺序。

## 5. 为什么这些"魔数"

| 参数 | 值 | 原因 |
|------|----|----|
| 默认容量 | 16 | 2 的幂，折中（太小频繁扩容，太大浪费） |
| 负载因子 | 0.75 | 时间与空间的权衡。太大冲突多查询慢，太小浪费空间且扩容频繁。0.75 下泊松分布算出桶冲突概率较优 |
| 树化阈值 | 8 | 理想 hash 下，一个桶有 8 个元素的概率极低（约千万分之六），到 8 说明 hash 异常，才值得树化 |
| 退化阈值 | 6 | 树节点 ≤ 6 退回链表。和 8 留缓冲（防 7↔8 反复转换抖动） |
| 最小树化容量 | 64 | 容量小时冲突多是因为桶太少，优先扩容而非树化 |

## 6. ⚠️ 线程安全问题

HashMap **非线程安全**，并发使用会出问题：
- **JDK 7**：并发扩容头插法导致**链表成环** → 后续 get 在环里**死循环**（CPU 100%）。
- **JDK 8**：改尾插法消除了成环，但并发 put 仍可能**丢数据**（覆盖）、`size` 不准。
- **正确做法**：并发场景用 **ConcurrentHashMap**（文档 07），别用 `Collections.synchronizedMap`（整表锁，性能差）。

---

## 7. key 的 hashCode/equals 约定 ⭐

用作 HashMap 的 key 必须正确重写 **equals + hashCode**，且满足：
- `equals` 相等 → `hashCode` 必须相等（否则放进去就找不回来了）。
- `hashCode` 相等 → `equals` 不一定相等（hash 冲突正常）。
- key 最好**不可变**（如 String、Integer、record），否则放进去后改了字段，hash 变了就再也取不出来。

```java
// 经典反例：用可变对象做 key，改了字段后 get 不到
Map<Point, String> m = new HashMap<>();
Point p = new Point(1, 2);  // 假设 Point 非不可变
m.put(p, "v");
p.setX(99);                  // hash 变了！
m.get(p);                    // 返回 null —— 在新 hash 的桶里找，但元素还在旧桶
```

## 8. 高频面试题 + 标准答案

**Q1：HashMap 底层数据结构？JDK 7 和 8 的区别？** ⭐⭐
> JDK 8 是数组+链表+红黑树。区别：① 8 引入红黑树（链长≥8 且容量≥64 时转），优化极端冲突的查询从 O(n) 到 O(log n)；② 7 头插法（并发扩容成环死循环），8 尾插法；③ 扩容时机和 rehash 方式优化（8 用高低位拆链不重算 hash）。

**Q2：HashMap 的 put 过程？** ⭐⭐
> 算扰动 hash → table 空则初始化 → `(n-1)&hash` 定桶 → 桶空直接放；冲突则比较：key 相同覆盖，是树走树插，是链表尾插（链长≥8 且容量≥64 转树，否则扩容）→ size 超阈值扩容。

**Q3：为什么容量是 2 的幂？为什么负载因子 0.75？** ⭐
> 容量是 2 的幂使 `(n-1)&hash` 等价于取模且更快，扩容时能用高低位拆链优化。0.75 是时间与空间的折中：太大冲突多查询慢，太小浪费空间且频繁扩容。

**Q4：为什么链表长度 8 才转红黑树？** ⭐
> 理想 hash 分布下，单桶达到 8 个元素的概率约千万分之六（泊松分布），正常情况几乎不会到 8。到 8 说明 hash 严重不均，此时树化收益（O(log n)）才值得其空间开销。且要求 table≥64，否则优先扩容。

**Q5：HashMap 为什么线程不安全？怎么解决？** ⭐⭐
> JDK 7 并发扩容头插成环导致死循环；JDK 8 并发 put 会丢数据、size 不准。解决：用 ConcurrentHashMap（推荐），或 Collections.synchronizedMap（整表锁，性能差）。

**Q6：HashMap 扩容时 rehash 怎么优化的？**
> JDK 8 扩容翻倍后，元素新位置要么是原索引 i，要么是 i+oldCap，取决于 hash 多出来的那一位是 0 还是 1。所以把旧桶链表拆成低位链和高位链分别放，无需重新计算 hash。

**Q7：用什么对象做 key 合适？**
> 不可变且正确实现 equals/hashCode 的对象，如 String、Integer、record。可变对象做 key，改了参与 hashCode 的字段后会 get 不到。

---

## 一句话总结

> HashMap = **数组+链表+红黑树**，扰动函数让高位参与定位、容量恒为 2 的幂以便 `(n-1)&hash` 取模；
> put 走"定桶→冲突挂链→链长≥8 且容量≥64 树化"，扩容翻倍并用**高低位拆链**免重算 hash；
> 它**线程不安全**（7 成环、8 丢数据），并发请上 **ConcurrentHashMap**（文档 07）。
