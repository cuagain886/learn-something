# 03 · 垃圾回收 GC ⭐⭐⭐

> "Java 不用手动释放内存，GC 怎么知道谁该回收？又怎么做到低延迟？"
> 核心：**可达性分析找垃圾 + 分代收集 + 现代收集器（G1/ZGC）把 STW 压到极致。**

---

## 1. 怎么判断对象"死了"——可达性分析

> ⚠️ 不是引用计数（Java 不用它，因为解决不了**循环引用**：A↔B 互相引用但都没用了，计数永远不为 0）。

**可达性分析（Reachability Analysis）**：从一组 **GC Roots** 出发，沿引用链遍历，**不可达**的对象就是垃圾。

**GC Roots 有哪些**（高频考点）：
- 虚拟机栈中**局部变量**引用的对象
- 方法区**静态变量**引用的对象
- 方法区**常量**引用的对象
- 本地方法栈 **JNI** 引用的对象
- 被同步锁 `synchronized` 持有的对象、JVM 内部引用等

**四种引用强度**：
| 引用 | 回收时机 | 用途 |
|------|---------|------|
| 强引用 `Object o = new ...` | 可达就**永不回收** | 普通引用 |
| 软引用 `SoftReference` | **内存不足**时回收 | 缓存 |
| 弱引用 `WeakReference` | **下次 GC** 就回收 | `WeakHashMap`、ThreadLocal 的 key |
| 虚引用 `PhantomReference` | 随时回收，仅用于**回收通知** | 管理堆外内存（如 DirectByteBuffer 清理） |

> 对象被判定不可达后，若重写了 `finalize()` 且未执行过，还有"一次自救"机会，但 `finalize` 已废弃，别用。

---

## 2. 垃圾收集算法（三种基础思想）

| 算法 | 做法 | 优点 | 缺点 | 用在哪 |
|------|------|------|------|--------|
| **标记-清除** Mark-Sweep | 标记垃圾，直接清除 | 简单 | 产生**内存碎片** | 老年代(CMS) |
| **标记-复制** Mark-Copy | 内存分两半，存活对象复制到另一半，清空原半 | 无碎片、快 | **浪费一半空间** | 新生代 |
| **标记-整理** Mark-Compact | 标记后把存活对象**向一端移动**，再清边界外 | 无碎片、不浪费 | 移动对象**成本高** | 老年代 |

---

## 3. 分代收集 ⭐——为什么把堆分成新生代/老年代

**分代假说**：① 绝大多数对象**朝生夕死**；② 熬过多次 GC 的对象会活很久。
于是按对象年龄分区，用不同算法：

### 3.1 新生代（Young）—— 标记复制

```
Eden : Survivor0(S0) : Survivor1(S1) = 8 : 1 : 1（默认）
```

- 新对象在 **Eden** 分配。
- Eden 满 → 触发 **Minor GC / Young GC**：把 Eden + 当前 Survivor 的存活对象**复制**到另一个 Survivor，清空 Eden。
- 对象每熬过一次 Minor GC，**年龄 +1**；年龄达阈值（默认 15，存在对象头 Mark Word 的 4 位里）→ **晋升老年代**。
- 只用一个 Survivor 工作、留一个空着做复制目标，所以"浪费"的只是 10% 而非 50%。

### 3.2 老年代（Old）—— 标记清除/整理

- 存长寿对象、大对象（`-XX:PretenureSizeThreshold` 直接进老年代）。
- 满了触发 **Major GC / Full GC**，慢得多（涉及整理移动）。

### 3.3 对象晋升老年代的几种情况
1. 年龄达到阈值（默认 15）。
2. **大对象**直接进老年代（如大数组）。
3. **动态年龄判定**：Survivor 中同年龄对象总和 > Survivor 一半，则该年龄及以上直接晋升。
4. Survivor 放不下，提前晋升。

## 4. STW 与三色标记

### 4.1 Stop-The-World（STW）
GC 某些阶段必须**暂停所有应用线程**（否则一边标记一边改引用会出错）。STW 时间长 = 用户卡顿，**降低 STW 是现代 GC 的核心目标**。

### 4.2 三色标记法（并发标记的基础）
把对象染三色：
- **白**：未访问（最终白色 = 垃圾）
- **灰**：自己被访问到，但**引用的对象还没扫完**
- **黑**：自己和引用都扫完了

并发标记（应用线程同时在跑）会出现 **漏标** 问题：黑对象新指向了一个白对象，且原引用断了 → 白对象被误回收。解决方案：
- **CMS**：增量更新（记录黑→白的新增引用，重新扫描）。
- **G1/ZGC**：原始快照 **SATB**（记录被删除的引用）+ **写屏障**。

## 5. 主流垃圾收集器演进 ⭐

| 收集器 | 区域 | 算法 | 特点 | 适用 |
|--------|------|------|------|------|
| Serial | 新+老 | 复制/整理 | 单线程、STW 全程 | 客户端/小堆 |
| Parallel Scavenge | 新+老 | 复制/整理 | 多线程、**吞吐量优先** | 批处理/后台计算 |
| CMS | 老年代 | 标记清除 | **并发**、低延迟，但有碎片、已废弃(Java 14 删除) | 老式低延迟服务 |
| **G1** | 整堆 | 复制+整理 | ⭐ **Java 9+ 默认**，分 Region，可预测停顿 | 大堆(4G+)、通用 |
| **ZGC** | 整堆 | 并发整理 | ⭐ **超低延迟(<1ms~几ms)**，TB 级堆，Java 15 转正、21 分代化 | 大堆、延迟敏感 |
| Shenandoah | 整堆 | 并发整理 | 低延迟，类似 ZGC（OpenJDK/Redhat） | 低延迟 |
| Epsilon | — | 不回收 | 只分配不 GC，测试/短任务用 | 实验 |

### G1（Garbage First）关键点
- 把堆切成约 2000 个大小相等的 **Region**，每个 Region 动态扮演 Eden/Survivor/Old/Humongous。
- 优先回收**垃圾最多**的 Region（名字由来），用 `-XX:MaxGCPauseMillis` 设**目标停顿时间**，GC 据此挑选回收多少 Region。
- 兼顾吞吐与延迟，是当前最通用的默认选择。

### ZGC 关键点
- **染色指针（Colored Pointers）+ 读屏障**实现几乎全程并发，STW 只有微秒级。
- 停顿时间**不随堆增大而增长**，支持 TB 级堆。Java 21 引入**分代 ZGC**，进一步提升吞吐。
- 延迟敏感、大堆场景的首选。

## 6. GC 触发与调优排查

**何时触发**：
- Minor GC：Eden 满。
- Full GC：老年代满 / 元空间满 / `System.gc()`（不保证立即执行）/ 晋升失败。

**常用参数**：
```bash
-Xms4g -Xmx4g            # 堆初始=最大，避免动态扩容抖动
-Xmn2g                   # 新生代大小
-XX:+UseG1GC             # 选 G1（Java 9+ 默认可不写）
-XX:+UseZGC              # 选 ZGC
-XX:MaxGCPauseMillis=200 # G1 目标停顿
-Xlog:gc*:file=gc.log    # GC 日志（Java 9+ 统一日志）
-XX:+HeapDumpOnOutOfMemoryError  # OOM 时自动 dump，事后分析
```

**排查思路**：
1. `jstat -gcutil <pid> 1000` 看各区使用率和 GC 频率/耗时。
2. **频繁 Full GC** → 老年代不断变满：可能内存泄漏（对象该死没死）或新生代太小导致过早晋升。
3. `jmap -histo <pid>` / 堆 dump + **MAT/VisualVM** 分析 → 找占用最大、数量异常的对象，定位泄漏点（典型：static 集合只增不删、ThreadLocal 没 remove、监听器没注销）。

## 7. 高频面试题 + 标准答案

**Q1：怎么判断对象可以回收？为什么不用引用计数？** ⭐
> 用可达性分析：从 GC Roots 出发遍历引用链，不可达的就是垃圾。不用引用计数是因为它解决不了循环引用（互相引用但都已无用，计数不为 0 永不回收）。

**Q2：GC Roots 有哪些？**
> 栈中局部变量、方法区静态变量、常量引用的对象、本地方法栈 JNI 引用、被 synchronized 持有的对象等。

**Q3：为什么新生代用复制、老年代用标记整理？** ⭐
> 新生代对象朝生夕死、存活率低，复制算法只需复制少量存活对象，快且无碎片，代价（浪费 Survivor 空间）小。老年代对象多、存活率高，复制成本太大，用标记整理避免碎片又不浪费一半空间。

**Q4：Minor GC 和 Full GC 区别？什么时候触发 Full GC？**
> Minor GC 只回收新生代，频繁但快；Full GC 涉及老年代（通常含整堆），慢、STW 长。触发：老年代满、元空间满、晋升失败、System.gc()。频繁 Full GC 往往是内存泄漏信号。

**Q5：G1 和 ZGC 的区别？** ⭐⭐
> G1：分 Region、优先回收垃圾多的区、可设目标停顿、兼顾吞吐与延迟，是 Java 9+ 默认，适合大堆通用场景。ZGC：染色指针+读屏障近乎全并发，停顿微秒级且不随堆增大而增长，支持 TB 级堆，Java 21 分代化，适合延迟敏感的大堆。

**Q6：对象什么时候进入老年代？**
> 年龄达阈值（默认 15）、大对象直接进、动态年龄判定（同龄对象超 Survivor 一半）、Survivor 放不下提前晋升。

**Q7：三色标记的漏标问题怎么解决？**
> 并发标记时黑对象新增了对白对象的引用且原引用断开会漏标。CMS 用增量更新（记黑→白新增引用后重扫），G1/ZGC 用 SATB 原始快照（记被删引用）配合写屏障保证不漏。

---

## 一句话总结

> **可达性分析**从 GC Roots 找活对象，剩下的回收；**分代收集**让新生代用复制、老年代用整理；
> 从 Serial→Parallel→CMS→**G1（默认）**→**ZGC（超低延迟）**，一路都在和 STW 死磕。
> 频繁 Full GC + 老年代涨不停 = 内存泄漏，用 jstat/jmap/MAT 顺藤摸瓜。
