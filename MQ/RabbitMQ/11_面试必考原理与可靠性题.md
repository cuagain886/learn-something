# 11｜RabbitMQ 面试必考：原理与可靠性题

## 1. RabbitMQ 的消息链路是什么？

Publisher 通过 Connection 上的 Channel 将消息发布到 Exchange；Exchange 根据类型、Routing Key 和 Binding 路由到一个或多个 Queue；Consumer 从 Queue 收到 Delivery 并 Ack/Nack。Exchange 通常不存消息，Queue 承载工作队列数据。

## 2. Direct、Topic、Fanout、Headers 区别？

Direct 精确 Binding Key；Topic 用点分词和 `*`/`#` 模式；Fanout 广播到所有绑定 Queue；Headers 按属性匹配。同一 Queue 多 Consumer 是竞争，不是广播；广播需要多个 Queue。

## 3. Connection 和 Channel 区别？

Connection 是昂贵 TCP/TLS/认证会话，应长期复用；Channel 是其上的轻量逻辑会话，通过协议 frame 多路复用。Channel exception 通常只关闭 Channel。Channel 不应被多线程无约束共享，Ack 还必须在原 Delivery Channel。

## 4. durable Queue 和 persistent Message 能保证不丢吗？

不能单独保证。还需 durable Exchange/Binding、正确队列类型、Publisher Confirm、mandatory/Return、复制故障域和客户端未知结果处理。Classic Queue 在 4.x 不因 Cluster 自动复制；关键数据应评估 Quorum Queue。

## 5. Publisher Confirm 与 Consumer Ack 区别？

Confirm 是 Broker→Publisher，说明发布达到对应队列类型的确认条件；Consumer Ack 是 Consumer→Broker，说明某 Delivery 已处理完成。Confirm 不证明业务消费，Ack 不证明上游可靠发布。

## 6. Confirm Ack 是否证明成功路由？

不能只靠 Confirm 判断。消息可被 Exchange 接受却没有匹配 Queue。使用 `mandatory=true` 处理 Return，或 Alternate Exchange。Confirm 与 Return 是正交信号。

## 7. mandatory 和 Alternate Exchange 区别？

mandatory 让不可路由消息返回 Publisher；Alternate Exchange 在 Broker 内把不可路由消息交给备用 Exchange 再路由。Alternate Exchange 自身也必须有有效 Binding/Queue，Publisher 仍要监控最终路径。

## 8. Consumer Ack 前后崩溃会怎样？

先 Ack 后业务：崩溃可能漏处理；先业务后 Ack：业务成功但 Ack 丢失会重投和重复。常用 At-Least-Once + eventId 唯一约束/版本状态机实现业务结果只生效一次。

## 9. Delivery Tag 能跨 Channel Ack 吗？

不能。Delivery Tag 的作用域是 Channel。跨 Channel Ack 会导致 unknown delivery tag 等协议错误并关闭 Channel。并发处理也不能直接用最大已完成 tag 做 multiple Ack，可能跳过未完成 Delivery。

## 10. Prefetch 有什么作用？

限制 Consumer 未确认 Delivery 数，形成 Credit/背压。太小降低吞吐，太大增加 Consumer/Broker 内存、降低公平性，并放大故障重投。依据目标吞吐 × 处理延迟测量，不背固定值。

## 11. RabbitMQ 如何保证顺序？

Queue 有入队/投递顺序，但多 Consumer、prefetch、处理时长、Priority、Nack/Requeue、故障重投都会改变观察到的完成顺序。严格顺序用 Single Active Consumer/单 Consumer、串行处理，并以业务 version 防御重复和乱序。

## 12. Classic、Quorum、Stream 如何选？

Classic 是单副本传统工作队列，适合临时/可重建；Quorum 是 Raft 复制工作队列，适合关键长期任务；Stream 是复制追加日志，支持保留和重复读取，适合长积压、重放与大 Fanout。

## 13. Quorum Queue 原理？

每个 Queue 是 Raft Group，一个 Leader、若干 Followers，多数派提交状态。三成员可容忍一个成员不可用；Publisher Confirm 在消息复制到 quorum 并安全后发出。失去多数派不能继续正常推进。

## 14. Cluster 是否自动复制消息？

不自动复制所有类型。Cluster 共享元数据/路由视图；Classic Queue 4.x 已无经典镜像复制；Quorum Queue 和 Stream 是复制数据结构。客户端连接任意节点不等于每节点都有一份 Queue 数据。

## 15. Khepri 是什么？

RabbitMQ 4.2 新部署默认的 Raft 元数据存储，保护 Exchange、Queue、Binding、Policy 等元数据。Khepri quorum 与各 Quorum Queue 的数据 Raft Group 是两套状态，不能混为一谈。

## 16. RabbitMQ 为什么会流控 Publisher？

节点内存/磁盘告警、内部处理/复制跟不上、Credit 和网络写压力会阻塞或限流发布，避免 OOM/磁盘耗尽。应用应监听 blocked/unblocked，并限制 Pending Confirm；不能在本地无限缓存。

## 17. Ready 和 Unacked 分别是什么？

Ready 等待投递；Unacked 已投递但未确认。Ready 高通常消费能力不足；Unacked 高通常 Consumer 已拿到但处理/Ack 慢或 prefetch 过大。Queue length 常只指 Ready，排障必须同时看两者和字节。

## 18. TTL 和 DLX 如何实现延迟重试？

失败消息发送到带固定 TTL 的 Retry Queue，过期后通过 DLX 路由回主 Exchange。TTL 不是精确定时，不同 TTL 混队列会头阻塞。必须有最大次数、总 deadline、Parking Queue 和幂等。

## 19. Requeue 有什么风险？

立即 `nack(requeue=true)` 可让毒消息在 Consumer 间高速循环，CPU/网络高、Ack 低，并破坏顺序。短暂错误应用延迟退避，不可重试错误直接 Parking/DLQ。

## 20. 自动恢复会补发断线消息吗？

不会。Java Client 自动恢复可重连、恢复 Channel、拓扑、QoS、Confirm 和 Consumer，但连接断开期间发布的消息不会自动缓存并补发。Publisher 仍要维护有界 Pending、Confirm 和业务去重。

## 21. RabbitMQ Transaction 与 Confirm 如何选？

Channel transaction 同步提交开销大；Publisher Confirm 更适合高吞吐可靠发布。两者都不能原子覆盖外部数据库，数据库→RabbitMQ 使用 Outbox/CDC。

## 22. 60 秒回答模板

> RabbitMQ 以 Exchange/Binding/Queue 分离路由和存储；Connection 上用 Channel 多路复用。可靠发布需要 durable topology、合适 Queue 类型、persistent 属性、mandatory Return 和 Publisher Confirm；可靠消费使用 manual Ack、合理 Prefetch 和业务幂等。4.x 中 Classic Queue 不再镜像，需要复制时用 Quorum Queue，重放与长积压用 Stream。Cluster 元数据由 Khepri 管理，Quorum Queue 数据由独立 Raft Group 复制。排障始终区分 Ready、Unacked、Pending Confirm 和资源告警。
