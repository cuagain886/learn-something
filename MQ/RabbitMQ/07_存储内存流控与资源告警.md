# 07｜存储、内存、流控与资源告警：为什么 Publisher 会突然变慢

> 现代 Classic Queue v2 和 Quorum Queue 都会积极将数据移到磁盘，只在内存保留工作集。RabbitMQ 的内存/磁盘告警会对发布施加背压，保护节点而不是保证业务延迟。

## 1. 消息状态与资源

- Ready：在 Queue 中等待投递，占 Queue 索引/消息存储；
- Unacked：已发给 Consumer 但未确认，Broker 仍维护状态，Consumer 也持有消息；
- Publisher unconfirmed：客户端保留在途，Broker 正处理/复制；
- Dead-letter pending：某些可靠 DLX 路径仍保留源消息等待目标确认。

积压要同时看消息数和字节。100 万条 100B 与 100 万条 1MiB 的磁盘、内存和网络风险完全不同。

## 2. 内存水位

节点内存超过高水位时会触发 memory alarm，并阻塞/限流发布连接，给磁盘分页和消费释放资源的机会。集群中某节点告警可能影响连接到该节点的 Publisher。

内存告警排查：

1. Ready/Unacked 和消息大小；
2. Connection/Channel/Consumer 数；
3. Quorum/Stream writer、DLX worker、索引与 Erlang 进程内存；
4. Consumer prefetch 是否过大；
5. OS/container memory limit 与 RabbitMQ 识别值是否一致；
6. 是否发生 paging、swap 和 GC 压力。

只提高内存水位可能把保护阈值推到 OOM。

## 3. 磁盘告警

Free disk space 低于阈值时 Broker 阻塞 Publisher，防止磁盘耗尽导致更严重损坏。要监控 `free bytes / net growth rate` 的剩余时间，而不只静态百分比。

处理优先级：限流 Publisher → 恢复 Consumer → 扩容/迁移 → 经业务确认调整 TTL/max-length。不要直接删 RabbitMQ 数据目录。

## 4. Flow Control 与 Blocked Connection

Publisher 可能因：

- memory/disk resource alarm；
- Queue/replication/磁盘处理跟不上；
- 网络写缓冲与内部 credit；
- 单 Connection 发布过多 Channel；
- Quorum majority/Leader 异常；

进入 blocked/flow 状态。应用必须监听 blocked/unblocked notification，并给 publish 在途集合设置上限；否则 Broker 背压会转成应用 OOM。

## 5. 积压的容量模型

```text
backlogGrowth = publishBytesPerSec - ackedBytesPerSec
timeToLimit = remainingCapacity / backlogGrowth  (仅 backlogGrowth > 0)
```

容量还包括 Queue 副本数、索引/元数据、segment/chunk、compaction/恢复临时空间和安全余量。Quorum 三副本的数据磁盘量会近似产生复制放大，但真实比例需用消息大小和实现测量。

## 6. 大消息问题

大消息会：

- 占用 Channel frame/客户端堆；
- 拉长单次网络和磁盘操作；
- 降低 Consumer 公平性；
- 放大重投、复制和 DLX 成本；
- 让少量消息掩盖巨量字节积压。

通常将大对象存对象存储，Queue 传 URI、digest、size 和权限信息；但必须处理对象与消息的生命周期一致性。
