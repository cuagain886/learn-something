# 09｜本地实验与故障注入：用 Delivery 状态验证语义

> 所有实验只在本地/授权环境执行。先记录预测，再注入一个变量，最后用管理 API、CLI、客户端日志和 eventId 对账。

## 1. 环境与基线

建议 3 节点环境才能验证 Quorum Queue 多数派。单节点只用于路由、Confirm/Ack 和 TTL。

基线记录：RabbitMQ/Erlang/客户端版本、Queue 类型/成员、Policy、Publisher/Consumer 配置、消息大小、Publish/Deliver/Ack rate、Ready/Unacked、Confirm p99、内存和磁盘。

常用只读探针：

```bash
rabbitmqctl cluster_status
rabbitmqctl list_queues name type state messages_ready messages_unacknowledged consumers memory
rabbitmqctl list_connections name state channels send_pend recv_oct send_oct
rabbitmqctl list_channels connection number consumer_count messages_unacknowledged confirm
rabbitmq-diagnostics status
```

## 2. 实验一：路由与 Return

1. 声明 Topic Exchange、Queue 和 `order.paid` Binding；
2. `mandatory=true` 发布 `order.paid`，预期 Confirm Ack、无 Return、Queue Ready+1；
3. 发布 `order.unknown`，预期 Return；
4. 删除目标 Queue 后重试；
5. 验证只看 Confirm 会遗漏不可路由。

证据必须关联 Publisher sequence/eventId、Return reply code/exchange/routing key 和 Queue 计数。

## 3. 实验二：Consumer 崩溃与重复

Consumer manual Ack：

1. 收到 event E；
2. 数据库/本地文件写成功；
3. Ack 前等待 10 秒；
4. 强制结束 Consumer；
5. 重启，观察 E 的 redelivered 标记和再次处理；
6. 加 `eventId` 唯一约束，验证尝试两次但结果一次。

反向实验：收到后先 Ack，再等待并处理；Ack 后终止，验证业务漏处理。

## 4. 实验三：Prefetch

固定 2 个 Consumer：快 Consumer 10ms/条，慢 Consumer 1s/条。分别设置 prefetch=1、10、100，记录：

- 每个 Consumer 收到/确认数量；
- Unacked、客户端内存；
- 总吞吐和 p99；
- 慢 Consumer 故障后的重投数量。

结论不应是“越大越快”，而是找到吞吐、缓存、公平和恢复成本平衡点。

## 5. 实验四：Quorum 多数派

三成员 Quorum Queue + Confirm Publisher：

1. 确认 Leader/成员；
2. 持续发布并记录 Confirm；
3. 停一个 Follower，观察继续可用和成员状态；
4. 再停另一个成员，观察失去多数派后的 Publish/Confirm；
5. 恢复成员，记录 Leader/数据追赶和客户端恢复；
6. 对 eventId 去重计数，查未知 Confirm 是否重发重复。

## 6. 实验五：Confirm 未知结果

通过网络代理在 publish 后延迟/丢弃 Broker→Client 流量，使消息可能已入 Queue但 Confirm 未返回。验证：

- 客户端 Pending 集合；
- Queue 是否已有 eventId；
- 重连重发是否重复；
- Consumer 幂等是否正确。

不要把关闭 Channel 前的所有 Pending 简化为“失败未写”。

## 7. 实验六：重试与毒消息

构造永远失败的 event：

1. 立即 requeue，观察 Deliver rate、CPU 和 redelivery；
2. 改为 5s/30s Retry Queue；
3. attempts=3 后进入 Parking Queue；
4. 故意删除 DLX 目标 Binding，观察死信行为；
5. 修复后人工重放，确认 eventId 不变。

## 8. 实验七：资源背压

只在受控小环境，用低阈值制造 memory/disk alarm 或停止 Consumer 形成积压。观察 blocked notification、Connection state、Confirm latency、Publisher Pending、Ready bytes。

验证 Publisher 是否有界阻塞/拒绝，而不是在 JVM 堆中无限缓存。实验后恢复阈值、排空 Queue 并确认告警解除。
