# 12｜RabbitMQ 面试必考：场景排障与系统设计题

## 1. Ready 持续上涨怎么排查？

确认 Queue/时间范围，比较 Publish、Deliver、Ack rate。查 Consumer 数、Consumer utilisation、下游 DB、Single Active Consumer、Prefetch、节点/Queue Leader 资源和 Redelivery。只有可并行且瓶颈不在下游时增加 Consumer 才有效。

追平时间 `Ready/(AckRate-PublishRate)` 仅在 AckRate 大于 PublishRate 时存在。

## 2. Ready 很低但 Unacked 很高怎么办？

消息已推给 Consumer：查线程池、数据库 p99、锁/死锁、GC、Ack 是否在错误 Channel、prefetch 是否过大。直接重启会让大量 Unacked 重投，先确认业务幂等和剩余容量。

## 3. Publisher Confirm p99 变高怎么查？

按 Queue 类型和目标拆分：Quorum 成员/Leader/磁盘、节点 alarm/flow、Fanout 最慢目标、消息大小、网络、Pending 年龄和 Nack。增大 timeout 只会扩大未知窗口和客户端内存。

## 4. Publisher 收到 Confirm Ack，但 Queue 没消息？

检查 mandatory Return、Exchange/Binding/Routing Key、Alternate Exchange、消息是否被其他 Consumer 立即取走/Ack、TTL/max-length/DLX、查看的 vhost 是否正确。Confirm 不等于必然路由到预期 Queue。

## 5. Consumer 重复扣款怎么修？

根因通常是 DB commit 后 Ack 前崩溃重投，或 Publisher 未确认重发。消息含稳定 eventId；数据库本地事务中插入 Inbox 唯一键并更新余额；成功后 Ack。重试和人工重放保持相同 eventId，并做对账。

## 6. 大量 Redelivered 且 CPU 高？

查 Consumer Nack/Requeue、异常日志、依赖故障和 Delivery Limit。很可能热循环。暂停受影响 Consumer/路由，错误分类后转延迟 Retry，设置最大次数和 Parking Queue。

## 7. 三节点 Quorum Queue 停两台会怎样？

失去多数派，不能安全选 Leader/提交新状态，发布/消费推进受阻。恢复至少一个原成员以重建多数派。不能把剩余单副本强行当正常 Leader而仍声称无数据风险。

## 8. Cluster 加了新节点，为什么负载没下降？

加入节点不自动改变所有既有 Quorum Queue members/Leaders，也不搬迁 Classic Queue 数据。需要 membership reconciliation/增长、Leader rebalance 和数据追赶；迁移本身占网络磁盘，要限速观察前台延迟。

## 9. 内存告警导致 Publisher Blocked，怎么止血？

限制上游、让 Publisher 有界等待/失败；恢复 Consumer；降低过大 Prefetch；查 Ready/Unacked、Connection/Channel 数和大消息；必要时扩容。不要简单上调水位到容器 OOM 边缘。

## 10. 磁盘将满如何处理？

按字节增长预测 time-to-full，定位大 Queue/副本；限流、恢复消费、扩盘/加节点并受控迁移；经业务确认调整 TTL/max-length。禁止手工删除数据目录文件。

## 11. 如何设计可靠重试？

错误分为可重试、永久失败、未知。可重试用 5s/1m/10m 等有界退避，最多 N 次/总 deadline；永久失败进 Parking；消息保留 eventId/attempt/错误/原路由；DLX 目标失败可观测；所有目标 Consumer 幂等。说明 Retry 会破坏顺序。

## 12. 设计订单消息系统

**需求：**30k msg/s、2KiB、节点故障不静默丢、支付落 MySQL 不重复、同订单状态有序、失败重试 5 次。

**参考方案：**

1. `order.events` Topic Exchange，Routing Key=`order.paid` 等；
2. 支付用三成员 Quorum Queue，跨节点放置；
3. DB 业务事务 + Outbox，Relay mandatory publish + 异步 Confirm + 有界 Pending；
4. Consumer manual Ack，Prefetch 由处理延迟实测；
5. Inbox `(consumer,eventId)` 唯一键 + order version 条件更新；
6. 同订单路由到稳定 shard Queue，每 shard Single Active Consumer/串行 lane；
7. 5s/1m/10m 重试，总 5 次后 Parking，顺序敏感时阻塞对应 shard；
8. 监控 Return/Confirm、Ready/Unacked、Redelivery、Queue members、alarm、DB 和对账；
9. 演练 Confirm 丢失、Consumer 崩溃、Quorum 少数节点故障、DLX 目标不可用。

## 13. 什么时候不选 RabbitMQ Queue？

若核心需求是数天保留、按 offset 任意重放、超大 Fanout、分区日志和流处理，应评估 RabbitMQ Stream/Super Stream 或 Kafka；若只是同步 RPC，优先直接 RPC 而非为所有调用强行引入队列。选择来自语义，不是技术偏好。

## 14. 排障回答模板

```text
现象口径（Ready/Unacked/Confirm/业务）
→ 异常 Queue/节点/客户端范围
→ Publish/Deliver/Ack/Redelivery 时间线
→ Connection/Channel/Queue/下游分层证据
→ 有代价说明的止血
→ 根因修复
→ eventId 对账与故障复演
```

## 15. 常见扣分答案

- “durable + persistent 就绝不丢”；
- “Confirm 成功就是业务成功”；
- “Cluster 自动复制所有 Queue”；
- “积压就加 Consumer”；
- “Prefetch 越大吞吐越高”；
- “失败一直 requeue”；
- “DLX 天然 Exactly-Once”；
- “自动恢复会补发断线消息”；
- “三副本可以同时坏两台继续写”。
