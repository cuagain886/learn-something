# 00｜RabbitMQ 深度学习计划：从路由模型到生产故障

> 建议 7 周，每周 8～10 小时。每周必须完成实验、故障时间线和口述验收。

## 1. 学习终点

完成后应具备：

1. **建模能力**：从业务路由、消费并行度、积压与可靠性选择 Exchange、Queue 类型和 Binding；
2. **正确性能力**：精确定义 Publisher Confirm、Return、Ack、Requeue 和 At-Least-Once 的边界；
3. **底层能力**：解释 Connection/Channel、Credit/Prefetch、Quorum Queue Raft、Khepri 和资源流控；
4. **生产能力**：定位 Ready/Unacked 堆积、Confirm 变慢、消费者抖动、内存/磁盘告警和节点故障；
5. **设计能力**：为订单、任务、通知、事件日志选择 Classic、Quorum 或 Stream，而不是默认全用一种队列。

## 2. 起点测验

1. Publisher Confirm 成功是否证明消息一定进入了目标 Queue？
2. `mandatory=true` 与 Confirm 分别证明什么？
3. durable Queue + persistent Message 是否绝对不丢？
4. Consumer Ack 前数据库成功，随后进程崩溃，会发生什么？
5. Prefetch=100 是每个 Connection、Channel 还是 Consumer 的限制？
6. Requeue 后消息一定回到原位置吗？多个 Consumer 时顺序如何？
7. Quorum Queue 三副本丢两台为什么不能继续可用？
8. RabbitMQ Cluster 是否自动复制所有 Classic Queue 消息？
9. Ready 很少、Unacked 很多说明什么？
10. DLX 是否天然提供可靠、无重复的队列间转移？

课程结束后重新作答，每题必须给失败窗口和可观测证据。

## 3. 七周路线

### 第 1 周：AMQP 路由模型

阅读：[01 AMQP 模型](01_AMQP模型Exchange与路由.md)、[02 Connection/Channel](02_ConnectionChannel与协议帧.md)

产出：

- 画 Publisher → Exchange → Binding → Queue → Consumer 全链路；
- 分别用 direct/topic/fanout/headers 设计一个业务场景；
- 解释默认 Exchange、vhost、Channel exception 的边界。

### 第 2 周：可靠发布

阅读：[03 Publisher Confirm](03_PublisherConfirmReturn与可靠发布.md)

实验：mandatory Return、不可路由消息、单条/批量/异步 Confirm、连接中断的未知结果。

验收：能区分“Broker 收到”“Exchange 路由成功”“目标队列安全接收”“业务消费成功”。

### 第 3 周：消费、背压与顺序

阅读：[04 Consumer Ack](04_ConsumerAckPrefetch与投递语义.md)

实验：manual ack、nack/requeue、Consumer 崩溃、不同 prefetch、单活跃消费者。

验收：画出数据库 commit 与 Ack 的两个崩溃窗口，设计业务幂等表。

### 第 4 周：队列类型与复制

阅读：[05 队列类型](05_ClassicQuorum与Stream选型.md)、[06 集群与一致性](06_集群Khepri与QuorumQueue原理.md)

产出：

- 为临时回复、关键订单、长积压审计流分别选型；
- 画 Khepri 元数据 quorum 与 Quorum Queue 数据 quorum 两套状态；
- 推演三节点少数派/多数派故障。

### 第 5 周：存储、流控与重试

阅读：[07 资源控制](07_存储内存流控与资源告警.md)、[08 TTL/DLX](08_TTLDLX重试与毒消息.md)

实验：制造 Ready 堆积、Unacked 堆积、TTL 过期、死信、毒消息循环和 Publisher Blocked。

### 第 6 周：故障实验与生产排障

阅读：[09 故障注入](09_本地实验与故障注入.md)、[10 生产设计](10_生产设计监控与排障.md)

产出：节点故障、Consumer 慢、磁盘水位和 Confirm 超时的证据链；恢复后做数量与 eventId 对账。

### 第 7 周：面试与系统设计

阅读：[11 原理面试题](11_面试必考原理与可靠性题.md)、[12 场景面试题](12_面试必考场景与系统设计题.md)

要求：每题先口述 60 秒；追问阶段必须补充版本、队列类型、故障模型、指标和代价。

### 第 8 周：BEAM 与两类 Queue 存储

阅读：[13 BEAM 消息流水线](13_BEAM进程模型与消息处理流水线.md)、[15 Classic Queue v2](15_ClassicQueueV2存储索引与恢复.md)

产出：

- 从 TCP Frame 到 `rabbit_channel`、Exchange Route、Queue Process 的完整时序；
- Ready/Unacked、Queue Process mailbox、Message Store 引用三套状态对照；
- 一次异常关机后 Classic Queue index/store 恢复路径。

### 第 9 周：Quorum Queue 与 Khepri

阅读：[14 Quorum Queue Raft](14_QuorumQueue的Raft日志与FIFO状态机.md)、[18 Khepri](18_Khepri元数据Raft与拓扑一致性.md)

产出：

- Publish Confirm、Consumer Ack 分别对应的 Raft command/commit 边界；
- Khepri quorum 与 Queue quorum 的四格故障矩阵；
- term、log index、commit index、applied index、snapshot 的手绘状态图。

### 第 10 周：Stream 与客户端源码

阅读：[16 Stream/Osiris](16_Stream与Osiris日志存储原理.md)、[17 四条反馈链](17_ConfirmReturnAck与Credit状态机.md)、[19 Java Client](19_Java客户端源码与自动恢复机制.md)

产出：

- Chunk/Segment/Index/Offset 的磁盘读取图；
- Pending 注册早于 Publish 的竞态证明；
- Java Client Connection MainLoop、Consumer Dispatcher、自动恢复断点记录。

### 第 11 周：性能与容量答辩

阅读：[20 性能模型](20_性能模型基准测试与容量规划.md)

完成同一 workload 在 Classic、Quorum、Stream 上的对照压测，必须覆盖空 Queue、稳定积压、Consumer catch-up、一个副本故障四阶段。报告必须包含 p99/p999、字节放大、Confirm Pending、Ready/Unacked、磁盘和 N-1 容量。

### 第 12 周：运行时取证与源码答辩

阅读：[21 BEAM 故障取证](21_BEAM内存调度与故障取证.md)、[22 源码阅读地图](22_官方源码模块阅读地图.md)

选择一次真实或故障注入事件，从业务指标追到 RabbitMQ per-object metrics、BEAM Process/mailbox、磁盘/网络，再映射到源码入口。答辩时必须区分业务 Queue Ready、Erlang mailbox、客户端 Pending、OS page cache 四种完全不同的“堆积”。

## 4. 固定学习闭环

```text
业务不变量 → 选择拓扑/队列类型 → 预测 Delivery 状态
     ↑                                  ↓
复盘与修正 ← 指标/管理 API/日志 ← 故障注入
```

每个结论回答：

- Publisher 看到什么结果？
- Exchange 是否成功路由？
- Queue 的 Leader/Replica 持有什么状态？
- Message 是 Ready、Unacked、Dead-lettered 还是已删除？
- Consumer/数据库崩溃后从哪里恢复？
- 哪个指标或 API 能证明？

## 5. 毕业设计

设计订单事件系统：峰值 30,000 条/秒，消息 2 KiB，关键订单事件不可静默丢失，支付 Consumer 更新 MySQL，同订单状态有序，失败最多重试 5 次并指数退避，集群允许 1 节点故障。

答案至少包括：Exchange/Binding、Queue 类型和副本、Confirm/Return、Connection/Channel 池、Ack/Prefetch、业务幂等、重试拓扑、毒消息、容量与水位、监控、滚动升级和故障演练。
