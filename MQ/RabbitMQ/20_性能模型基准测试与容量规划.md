# 20｜性能模型、基准测试与容量规划：把吞吐拆成字节、状态机与故障余量

> 不接受“RabbitMQ 每秒能处理多少消息”的无上下文答案。能力取决于 Queue 类型、消息大小、Confirm/Ack、Fanout、成员数、磁盘、Consumer latency 和积压状态。

## 1. 三个基础速率

```text
λp = Publish messages/s
λd = Deliver messages/s
λa = Ack/settle messages/s

Ready growth ≈ λp_routed - λd
Unacked growth ≈ λd - λa
```

稳定系统长期需要 Ack/retention removal 能追上 Publish。短时 `λa < λp` 可以由 Buffer 吸收，但必须有最大积压和恢复时间。

## 2. 字节放大

单条 2 KiB，Fanout=4，Quorum members=3，粗略数据写入已产生：

```text
2 KiB × 4 target queues × 3 replicas = 24 KiB
```

尚未包含 frame/header、Ra log command、index、Ack/checkout、WAL/segment、DLX、网络协议和文件系统放大。Fanout 与副本数是乘法关系。

## 3. 延迟分解

```text
Publisher E2E
= client enqueue/lock
+ socket/network
+ Broker Channel/router
+ Queue owner mailbox
+ local store/raft replication/fsync
+ Confirm return path

Consumer E2E
= ready wait
+ delivery scheduling/network
+ client executor queue
+ business processing
+ Ack return/settle
```

只看 Producer API latency 会漏掉 Confirm；只看 Deliver latency 会漏掉客户端 executor queue 和 DB。

## 4. Little's Law 与 Prefetch

若单 Consumer 目标 500 msg/s，p95 处理 40ms：

```text
平均并发需求 ≈ 500 × 0.04 = 20
```

初始 prefetch 可在 20 附近加波动余量，再用吞吐、公平、Unacked 和崩溃重投测试。若 Consumer 单线程串行，prefetch=1000 不能让它同时处理 1000，只会缓存。

## 5. Confirm Window

Publisher 吞吐近似受在途窗口与 Confirm RTT 限制：

```text
max throughput ≈ pendingWindow / confirmRTT
```

若 Confirm p99=50ms，window=1000，理论管线 20k msg/s 量级；真实还受 bytes、Channel、Broker 和 batch。Window 太小饿死管线，太大使故障时 UNKNOWN/Pending 内存爆炸。

## 6. Quorum 成员数

3 members 容忍 1 故障；5 容忍 2。更多成员增加：

- 每条日志复制网络；
- Follower fsync/写入；
- 多数派尾延迟取样；
- snapshot/catch-up；
- 运维复杂度。

同一三节点 Cluster 上把 Queue group size 设 5 没有意义；跨 7 节点所有 Queue 都七成员也通常成本过高。

## 7. 容量模型

```text
backlogBytesLogical = maxBacklogMessages × avgStoredBytes
diskPerQueue ≈ backlogBytesLogical × replicaCount × storageOverhead
nodeDisk ≈ Σ(queueReplicaBytes on node) + WAL/snapshot/temp + headroom
```

`avgStoredBytes` 必须从真实消息测：AMQP properties/headers 对小消息比例很高。容量还需考虑：

- max message p99/p999；
- TTL/ack 后物理回收滞后；
- At-Least-Once DLX 源侧保留；
- 新 member 全量同步临时 IO；
- Stream retention segment 粒度；
- 磁盘告警阈值以上必须留空闲。

## 8. 基准矩阵

至少测试：

| 变量 | 取值方向 |
|---|---|
| Queue 类型 | Classic / Quorum 3 / Stream |
| message size | 128B / 2KiB / 64KiB / p99 |
| Publish | no confirm / async confirm window N |
| Consume | auto ack / manual ack；prefetch 1/20/200 |
| Fanout | 1 / 4 / 20 Queue |
| backlog | empty / steady / 数百万积压 |
| fault | stable / one follower down / catch-up |
| disk | warmed page cache / historical read / compaction |

每组记录 p50/p95/p99/p99.9、CPU、scheduler run queue、disk latency/throughput、network、Ready/Unacked、Confirm Pending、GC/binary memory。

## 9. 为什么空队列压测会骗人

Publisher 和 Consumer 同速，消息 publish-delivered 后很快 Ack：

- 工作集完全在 cache；
- 无长期 index/segment/retention 压力；
- 无恢复扫描；
- 无大 Ready/Unacked；
- Stream 历史读取未竞争；
- Quorum snapshot/catch-up 尚不明显。

生产会允许 2 小时积压，就必须先制造同等字节积压再压测恢复。

## 10. Catch-up 与 RTO

```text
Tcatchup ≈ backlog / (sustainableAckRateDuringCatchup - livePublishRate)
```

Ack rate 必须是在数据库、磁盘、重投和实时流量同时存在时的可持续值。若差值≤0，永远追不上。

Quorum Replica catch-up 还会消耗与 Consumer catch-up 不同的复制带宽，故障恢复时两者可能竞争。

## 11. Hot Queue 与 Sharding

一个 Classic/Quorum Queue 的权威状态机不能靠多节点自动分片。单 Queue 饱和时：

- 按业务 key 建固定 shard Queues；
- Exchange routing key/hash 分配；
- Consumer 每 shard 独立；
- 监控每 shard 而非总和；
- 扩 shard 前处理 key remapping/顺序迁移。

若需求本来是分区日志，优先 Super Stream，而不是手工创建上千 Quorum Queue。

## 12. 故障余量

正常负载不应占满所有节点。三节点 Quorum Cluster 需保证任一节点故障后：

- 剩余 Leader/Replica 的 CPU、disk、network 可承载；
- Confirm p99 仍在 SLO；
- Leader rebalance/恢复不会越过水位；
- Consumer/Publisher reconnect 不形成惊群；
- 磁盘有 member catch-up 空间。

容量规划用 N-1 状态而非 N 节点正常平均。

