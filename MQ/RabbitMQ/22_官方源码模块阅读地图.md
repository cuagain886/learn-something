# 22｜RabbitMQ 官方源码模块阅读地图：按问题追踪，不按目录漫游

> 源码仓库：[rabbitmq/rabbitmq-server](https://github.com/rabbitmq/rabbitmq-server)。务必 checkout 部署版本 tag。Ra、Khepri、Osiris、Java Client 可能是独立仓库/依赖，版本要与 Server release 对齐。

## 1. 仓库层次

RabbitMQ monorepo `deps/` 包含 Core Server 和内置插件。阅读时先找 OTP application，再找入口 module：

```text
deps/rabbit/                 Core AMQP broker, queues, routing, auth, stores
deps/rabbitmq_management/    HTTP API / management UI backend
deps/rabbitmq_prometheus/    metrics exporter
deps/rabbitmq_stream/        Stream protocol plugin
deps/rabbitmq_shovel/        message moving plugin
deps/rabbitmq_federation/    federation
```

不要从文件名猜完整行为；先看 `.app.src`、supervisor、behaviour callback 和 tests。

## 2. 问题：Connection 为什么关闭

阅读链：

```text
listener/ranch accept
→ rabbit_reader connection handshake/frame loop
→ authentication mechanism / access control
→ heartbeat / frame error
→ rabbit_channel channel-level method
→ shutdown signal/log formatting
```

关键输入：Protocol method class-id/method-id、reply code、Channel vs Connection close、client properties、vhost/user。

## 3. 问题：消息为何不可路由

```text
rabbit_channel basic.publish
→ rabbit_exchange lookup/type callback
→ rabbit_router / binding lookup
→ destination queue references
→ mandatory return / alternate exchange
```

对照 tests 验证：多条 Binding 指向同一 Queue 是否重复入队、Exchange-to-Exchange、Topic wildcard、Alternate Exchange 循环保护。

## 4. 问题：Classic Queue 为何慢

```text
rabbit_amqqueue_process mailbox
→ rabbit_queue_consumers credit/delivery
→ rabbit_variable_queue
→ rabbit_classic_queue_index_v2
→ rabbit_msg_store
```

用 metrics 选择入口：mailbox/reductions 高先看 Queue Process；disk reads/writes/sync 高看 index/store；Unacked 高看 consumer/credit。

## 5. 问题：Quorum Confirm 为何慢

```text
rabbit_quorum_queue deliver
→ ra process command
→ ra server leader append
→ WAL/segment replication
→ majority commit
→ rabbit_fifo apply/effects
→ channel confirm
```

同时查 Ra metrics：term/leader changes、commit index lag、WAL/snapshot、member status。不要只在 `rabbit_channel` 找等待时间。

## 6. 问题：消息为何反复重投

```text
rabbit_channel ack/nack/reject
→ queue type settle/return
→ classic consumer state OR rabbit_fifo checkout state
→ delivery count
→ DLX handler/internal consumer
```

建立 eventId、delivery tag、redelivered、x-death/delivery count 的映射。Tag 变化不等于新业务消息。

## 7. 问题：Stream offset/retention

```text
rabbit_stream_queue / coordinator
→ Osiris writer/reader
→ chunk/segment/index
→ consumer attach offset
→ retention evaluator / segment delete
→ offset tracking / dedup
```

AMQP Stream Queue 与 Stream Protocol 路径不同，功能/性能也不同。确认测试使用哪种客户端协议。

## 8. 问题：Topology 操作为何超时

```text
AMQP declare/delete/bind
→ metadata store abstraction
→ Khepri transaction
→ Ra leader/majority commit
→ projection/cache update
→ protocol -ok response
```

对照 Khepri quorum、Cluster node connectivity 和 topology churn，而不是只检查目标 Queue 数据 Leader。

## 9. Behaviour 与状态机阅读法

Erlang module 常实现 behaviour：`gen_server`/`gen_server2`、supervisor、queue type callback、Ra machine。阅读顺序：

1. `-behaviour(...)`；
2. exported API；
3. state record/map；
4. `init`；
5. `handle_call/cast/info` 或 `apply`；
6. effects/replies；
7. terminate/recovery；
8. Common Test/PropEr property tests。

不要从一个 `handle_info` 分支推导全部状态；先画 state ownership 和消息协议。

## 10. Property Tests 为什么重要

`rabbit_fifo` 等状态机大量使用 property/model tests 验证随机命令序列下不变量：

- 已 settle 消息不会重新 Ready（除非语义允许的未知窗口）；
- credit 不为负；
- checkout 只属于有效 Consumer；
- snapshot/replay 等价；
- leader change 后状态一致；
- delivery limit/DLX effect 不重复丢状态。

读测试往往比从实现分支猜业务语义更快。

## 11. Git 与版本方法

```bash
git clone https://github.com/rabbitmq/rabbitmq-server.git
git checkout <server-release-tag>
git grep "-module(rabbit_channel)"
git grep "basic.publish"
git log -S "function_or_record" -- deps/rabbit/src
git blame <file> -L <start>,<end>
```

再从 release manifest/lock 确认 Ra/Khepri/Osiris dependency revision。Trunk 已包含下一版本行为，不能直接解释生产 4.2.x。

## 12. 调试边界

- 不在生产开启每消息 debug 日志；
- 不打印 body/敏感 headers；
- 优先用 correlation：Connection/Channel/Queue/eventId；
- 使用 tracing/firehose 会放大流量，必须小范围有时限；
- `sys:get_state`/Process inspection 可能阻塞热点 Process，生产慎用；
- 源码 instrumentation 只能在复现环境。

## 13. 一次完整阅读练习

问题：“Quorum Queue Publisher Confirm p99 从 20ms 升至 2s。”

1. Channel 已发送 publish，Pending age 上升；
2. Queue Leader node 的 mailbox/reductions 是否高；
3. Ra term 是否稳定、majority members 是否在线；
4. commit index 与 member progress；
5. WAL sync/segment IO p99；
6. `rabbit_fifo` apply/effect 是否滞后；
7. Confirm 回 Channel/Connection writer 是否堵塞；
8. 对照正常 Queue/节点；
9. 用 source path 解释最慢阶段，再做单变量实验。

这比“调大 Confirm timeout”更接近源码级排障。
