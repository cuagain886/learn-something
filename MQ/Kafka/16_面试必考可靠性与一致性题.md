# 16｜Kafka 面试必考：可靠性、消费语义与一致性陷阱

> 这一组题用于区分“背过配置”与“能推演故障窗口”。回答时优先画事件顺序，再给结论。

## 1. 如何保证 Kafka 消息不丢？

**标准回答：**

先追问“不丢”的边界：Producer 到 Kafka、Kafka 副本、Consumer 处理，还是外部数据库结果？没有单一参数能保证端到端不丢。

Producer 到 Kafka 通常需要：

- 正确等待 send Future/callback，不能忽略异步异常；
- 使用幂等安全配置和足够的 delivery deadline；
- `acks=all`；
- Topic 有合理 RF，`min.insync.replicas` 与故障目标匹配；
- 副本跨故障域，监控 ISR/URP；
- 上游面对未知结果时保留稳定 `eventId`。

Consumer 侧通常先完成可验证、可幂等的业务处理，再提交 offset；还需要 DLT、重试、对账与恢复演练。

**加分点：**“绝不丢”必须定义机架、地域、磁盘同时损坏等故障模型，以及故障期选择拒绝写还是继续不安全写。

## 2. Kafka 在哪些地方可能产生重复？

**标准回答：**

1. Broker 已写入但响应丢失，Producer 重试；
2. 上层 API 超时后重新构造业务事件发送；
3. Consumer 业务副作用成功但 offset 提交前崩溃；
4. retry topic/DLT 写入成功但原 offset 未提交；
5. Outbox relay 发布成功但标记发送成功前崩溃；
6. 人工重放或位点回退。

协议幂等只解决第 1 类的特定范围；业务系统仍需 `eventId`、唯一约束或版本状态机。

## 3. 幂等 Producer 的原理是什么？

**标准回答：**

Broker 不按消息 value 去重，而是根据 Producer ID、Producer Epoch 和每个 Partition 的 Sequence 验证 Batch。相同会话中响应丢失后的同序列重试可以识别为重复，跳序或旧 Epoch 会被拒绝/恢复。

幂等要求与 `acks=all`、重试和最大 in-flight 数兼容。现代客户端通常默认启用幂等，前提是没有冲突配置；面试时不要只背旧版本默认值，应以所用版本配置为准。

**边界：**不解决业务代码重新发送、多个 Producer 实例发送相同 `eventId`、Consumer 重复落库，也不自动提供跨 Partition 原子性。

## 4. 幂等 Producer 和事务 Producer 的区别？

**标准回答：**

幂等 Producer 保证单个 Producer 会话内、单 Partition 的协议重试不产生重复并保护顺序。事务 Producer 在幂等基础上，用 `transactional.id`、事务协调器和 marker，使多个 Kafka Partition 的记录及 Consumer offsets 原子提交或中止，并可跨实例重启 fencing 旧 Producer。

跨 Partition 原子需要事务；外部 MySQL/HTTP 不在 Kafka 事务原子边界内。

## 5. Kafka 的 Exactly-Once 到底保证什么？

**标准回答：**

必须限定为 Kafka 管理的 read-process-write 链路：事务 Producer 可原子提交输出 Topic 记录和输入 Consumer Group offsets；下游使用 `read_committed` 只看已提交事务。恢复后要么输出与新 offset 一起可见，要么都不可见并重做。

它不保证任意外部数据库或支付 API 只执行一次。端到端业务效果仍需外部幂等键、Inbox/Outbox、唯一约束或状态版本。

关联：[05 一致性边界](05_交付语义事务与一致性边界.md)、[14 事务实现](14_事务协调器与ExactlyOnce实现.md)

## 6. At-Most-Once 和 At-Least-Once 如何实现？

**标准回答：**

- 先提交 offset，再执行业务：崩溃窗口可能跳过业务处理，偏 At-Most-Once；
- 先执行业务，成功后提交 offset：崩溃窗口会重放，偏 At-Least-Once；
- At-Least-Once 加业务幂等/原子协议，可实现 Exactly-Once Effect。

面试时用事件时间线说明，不要只背中文“最多一次/至少一次”。

## 7. 自动提交 Offset 会丢消息吗？

**标准回答：**

自动提交本身不是必然丢，风险取决于提交时机是否领先于业务完成。`poll()` 返回后 Consumer position 已可能前进，若自动提交记录了这批进度，但业务线程池尚未处理完就崩溃，恢复后会跳过未完成记录。

如果处理很轻且在 poll 线程内完成，风险窗口不同；生产中必须理解客户端具体提交行为，而不是把 `enable.auto.commit=false` 当完成可靠性设计。

## 8. 为什么处理完再提交仍会重复？

**标准回答：**

数据库 commit 与 Kafka offset commit 是两个独立操作。数据库成功后、offset 提交前进程崩溃，重启会从旧 offset 重放。解决方式是让数据库副作用幂等，例如在同一个数据库事务中先插入 `(consumer, eventId)` 唯一记录，再更新业务表。

无法用调整提交顺序同时消除“重复”和“漏处理”：先提交则会产生另一侧的丢处理窗口。

## 9. 为什么批量并发消费不能提交最大已完成 Offset？

**标准回答：**

假设 100、102、103 完成，101 仍失败。若提交 104，崩溃后从 104 恢复，101 被永久跳过。可提交点只能是连续完成前缀，当前应提交 101。

需要按 Partition 跟踪完成集合与连续水位；不同 Partition 的进度独立提交。

## 10. `commitSync` 和 `commitAsync` 如何选择？

**标准回答：**

`commitSync` 等待结果，错误处理简单但阻塞；`commitAsync` 降低等待，但回调可能乱序。若 201 已成功，101 的迟到失败被无条件重试，可能让进度倒退并造成大量重复。

常见策略是正常循环异步提交并维护单调水位，revoke/关闭时同步提交最终安全前缀。具体选择要结合处理语义和延迟目标。

## 11. Consumer Rebalance 为什么会导致重复？

**标准回答：**

Partition 被 revoke 时，旧 Consumer 可能有已处理未提交或仍在途的记录。新 Consumer 从 committed offset 接管，就会重放；如果旧 Worker 未 fencing，甚至可能在 assignment 失效后产生晚到副作用。

正确处理包括停止新任务、drain/cancel 在途任务、提交连续完成前缀、释放 Partition 状态，并让 Worker 检查 assignment generation/epoch。

## 12. `session.timeout` 与 `max.poll.interval` 有什么区别？

**标准回答：**

Session timeout 关注组成员心跳活性；max poll interval 关注应用是否持续调用 poll、具备处理进展。即使后台心跳线程还活着，应用长时间不 poll 也不应永久占有 Partition。

调大 max poll interval 可以容忍慢批次，但会延长真实卡死的接管时间。更好的修复可能是减小单次拉取、优化下游、partition worker 与 pause/resume 背压。

## 13. Cooperative Rebalance 是否完全无停顿？

**标准回答：**

不是。它通过增量撤销/分配减少整体 stop-the-world 范围，但迁移的 Partition 仍需先由旧 owner revoke，再交给新 owner，可能经历多轮协议。应用仍需正确处理 revoke、在途任务和 offset。

## 14. Producer 超时是否说明消息没写入？

**标准回答：**

不能。超时只表示客户端在 deadline 内未得到确定结果。Broker 可能已写入并复制，但响应丢失或延迟。此时结果是未知，必须依赖幂等 Producer 重试与业务 `eventId` 去重，不能武断地重新生成一个“新事件”。

## 15. `retries` 越大越可靠吗？

**标准回答：**

重试只对暂时错误有效，并受总 delivery timeout 约束。永久配置错误、鉴权失败、记录过大等盲目重试没有意义。重试过久还会让上游请求早已超时但 Producer 继续占用缓冲和资源。

应以业务 deadline、delivery timeout、backoff、幂等和错误分类共同设计。现代客户端通常建议主要用总交付时间控制，而不是只盯重试次数。

## 16. Unclean Leader Election 有什么风险？

**标准回答：**

当没有合格同步副本可选时，让落后副本成为 Leader 可以恢复 Partition 可用性，但会丢失该副本未拥有的尾部，可能包括此前已被客户端确认的数据。它是明确的“可用性换数据安全”操作，不是普通容灾优化。

## 17. Log Compaction 能实现业务去重吗？

**标准回答：**

不能当作实时业务去重。Compaction 后台渐进保留每个 key 的最新值，旧记录在清理前仍可被消费；它不阻止相同业务事件先后触发两次数据库副作用。业务去重需要消费侧唯一键或状态版本。

## 18. Retry Topic 和 DLT 有什么一致性问题？

**标准回答：**

把失败记录旁路后，原 Partition 后续记录可以先完成，会破坏同 key 顺序。Retry/DLT 写成功与原 offset commit 之间也有崩溃窗口，可能重复写旁路 Topic。

必须保留原 topic/partition/offset、eventId、异常和重试次数；写入幂等；明确顺序敏感事件是原地阻塞、按 key 串行重试，还是允许旁路。

## 19. Kafka → MySQL 如何实现业务结果不重复？

**标准回答：**

采用 At-Least-Once + 数据库本地幂等事务：

```text
BEGIN
  INSERT inbox(consumer_name, event_id)  -- 唯一键
  UPDATE business_state ...
COMMIT
commit Kafka offset
```

崩溃后 Kafka 可重放，但唯一键阻止第二次业务更新。Inbox 保留期必须覆盖最长重放窗口，并配合对账。

## 20. 数据库 → Kafka 如何避免业务成功但事件没发出？

**标准回答：**

使用 Transactional Outbox：业务更新和 Outbox 事件在同一数据库本地事务提交，再由 CDC/Relay 发布 Kafka。Relay 在“发成功但标记失败”窗口仍可能重复，因此事件使用稳定 `eventId`，下游保持幂等。

## 21. 可靠性题的回答框架

遇到“如何保证不丢/不重/有序”时按下面顺序回答：

1. 定义作用域：Partition、Producer session、Consumer Group、数据库；
2. 定义故障：超时、进程崩溃、Broker/机架/地域损坏；
3. 画成功动作与进度动作的先后；
4. 找两者之间崩溃窗口；
5. 用复制、幂等、事务或补偿关闭窗口；
6. 给出指标、对账和故障演练证据。
