# 17｜Kafka 面试必考：生产排障与系统设计题

> 高级面试看的是推理过程。回答结构固定为：明确现象口径 → 分层假设 → 指标证据 → 临时止血 → 根因修复 → 防复发验证。

## 1. Consumer Lag 持续上涨，怎么排查？

**标准回答：**

先确认 lag 口径、时间范围和分布，不能只看总数：

1. 看所有 Partition 还是少数 Partition；
2. 对比输入速率 `λin`、处理速率 `λout` 和 lag 增长率；
3. 看 committed offset、fetch position 是否都不动；
4. 查 Consumer CPU、GC、poll 间隔、线程池队列、错误率与再均衡；
5. 查下游 DB/API 延迟、连接池、锁等待和限流；
6. 查 Broker Fetch 延迟、网络、磁盘、Leader 分布；
7. 检查反序列化毒丸、事务 LSO 阻塞和单 Partition 热点。

追平时间只有在 `λout > λin` 时才存在：

```text
Tcatchup ≈ Lag / (λout - λin)
```

**为什么不能直接加 Consumer？**

Consumer 已多于 Partition、热点集中一个 Partition、瓶颈在共享数据库或频繁再均衡时，加实例无效甚至更差。

**止血：**控制上游流量、扩容真正瓶颈、暂停非关键 Group、对热点 key 限流。根治要修改 Partition/key、处理逻辑或下游容量。

## 2. Producer p99 延迟突然升高，如何定位？

**标准回答：**

先把请求总时间拆开：queue、local、remote、response queue、response send。

- record queue time 高：Producer Buffer/Batch 堆积、Sender/网络慢；
- request queue time 高：Broker handler 饱和；
- local time 高：Leader 校验、追加、磁盘或格式转换慢；
- remote time 高：`acks=all` 等待 Follower/ISR；
- response send 高：网络拥塞、客户端读慢或大响应。

再按时间对齐 Leader 变更、ISR shrink、Producer retry、metadata refresh、Broker GC、磁盘 p99、网络丢包和 quota throttle。

**错误回答：**只把 `request.timeout.ms` 调大。它可能减少表面超时，却扩大业务等待与 Buffer 占用，根因仍存在。

## 3. Topic 总流量不高，但某些消息延迟很大，为什么？

**标准回答：**

高度怀疑热点 Partition 或热点 key。总流量平均掩盖 P7 的吞吐可能是其他 Partition 数倍。检查 Partition 级 records/bytes、Leader 所在 Broker、key top-N、Producer queue time 和 Consumer per-partition lag。

解决方式按业务顺序约束选择：

- 可拆分业务实体：重新设计更均匀 key；
- 超级账户不能拆：单独 Topic/Partition 隔离并限流；
- 可分片后聚合：key 加稳定 shard，第二阶段按实体聚合；
- 纯写热点：增加 Partition 仅在 key 可重新分布时有效。

随意给 key 加随机后缀会破坏同实体顺序，不能作为无条件答案。

## 4. Under Replicated Partitions 不为 0，怎么办？

**标准回答：**

URP 表示某些 Partition 的 ISR 少于 assignment 副本集合。先判断范围和持续时间：

1. 是否集中某 Broker、机架或磁盘目录；
2. Follower lag、fetch rate 和 ISR shrink 时间；
3. Broker 是否重启、GC、CPU 饱和、网络丢包；
4. 磁盘延迟/空间和 offline log directory；
5. 副本恢复流量是否挤压前台请求；
6. Leader 是否过度集中。

**风险：**容灾余量下降；若 ISR 跌破 min ISR，严格 Producer 写失败。已有 URP 时不要盲目滚动重启另一台 Broker。

**恢复：**修复故障资源，让 Follower 追平；必要时限速副本迁移、控制流入。不要通过降低 min ISR 来掩盖副本长期失同步，除非经过明确可靠性降级决策。

## 5. Broker 磁盘快满了，如何处理？

**标准回答：**

先预测剩余时间，不等到 100%：

```text
timeToFull ≈ freeBytes / netGrowthBytesPerSecond
```

排查：

- 哪些 Topic/Partition 占用最大，Leader/Follower 是否失衡；
- retention 是否未生效、active segment 尚未 roll；
- compact cleaner 是否跟不上、dirty ratio 与 cleaner IO；
- 是否有异常大消息、流量突增、重分配临时副本；
- remote/tiered storage 策略是否符合预期。

**止血优先级：**控制流入 → 扩容磁盘/Broker → 受控迁移副本 → 经业务确认缩短非关键 Topic retention。

不能直接进入日志目录删除文件。这样会破坏索引、副本、Producer/事务状态；还可能把单点容量事故升级为数据损坏。

## 6. Consumer 频繁 Rebalance，怎么排查？

**标准回答：**

按触发源分类：

- 实例频繁发布/重启、弹性扩缩；
- 心跳超时：网络、GC、CPU 饥饿；
- poll 间隔超限：批次过大、业务慢、下游卡顿；
- Topic Partition/订阅变化；
- member identity 不稳定；
- coordinator/internal offsets partition 异常。

证据包括 rebalance reason、member/generation 变化、time-between-poll、last-poll、GC pause、处理时长和部署时间线。

修复不是只增大 timeout：可减小 `max.poll.records`、分离 poll 与 partition worker、加入 pause/resume 背压、使用 cooperative assignment/稳定 member identity，并优化真实慢点。timeout 只用于覆盖合理抖动。

## 7. `acks=all` 的 Producer 突然大量报错，但 Broker 只坏了一台，为什么？

**标准回答：**

假设 RF=3、min ISR=2。理论上坏一份后仍有两份可写，但实际可能发生：

- 故障前已有另一个 Follower 落后并退出 ISR；
- Replica 没有跨故障域，单次机架故障影响多份；
- 故障 Broker 恰为 Leader，选举/metadata 刷新窗口暂时失败；
- 剩余 Follower 复制慢，ISR 很快缩到 1；
- 某些 Topic 配置不同；
- Eligible Leader Replica 等 feature 改变当前版本语义，需查实际配置。

回答时必须查看目标 Partition 的 replicas/ISR，而不是用集群 Broker 总数推导。

## 8. 消费速度正常但业务数据缺失，如何查？

**标准回答：**

“消费速度正常”可能只说明 position 前进。建立端到端坐标：`eventId → topic/partition/offset → consumer attempt → DB transaction/result`。

排查：

1. Producer callback 是否真实成功；
2. Topic 中按坐标能否读到；
3. Group committed offset 是否越过该记录；
4. 是否自动/提前提交后业务失败；
5. 反序列化、过滤、DLT 是否静默跳过；
6. DB 事务是否回滚、唯一键是否误判；
7. 状态版本是否拒绝了乱序事件；
8. 对账口径、时区与数据延迟是否一致。

修复后要从明确 offset/eventId 重放，避免全 Topic 无界重放造成重复副作用。

## 9. 如何设计 Topic 的 Partition Key？

**标准回答：**

步骤：

1. 定义顺序作用域：订单、账户、设备还是不要求顺序；
2. 选择能稳定标识该作用域的 key；
3. 分析 key 基数、倾斜、超级热点和跨语言分区算法；
4. 评估未来扩分区导致的映射变化；
5. 用真实分布做压测，不用均匀随机数据代替生产 key；
6. schema 中保留业务 ID、eventId 和版本，便于重放与纠错。

例：订单状态用 `orderId`；账户余额流用 `accountId`。若账户有超级热点，需业务分片/隔离，不能直接随机化破坏顺序。

## 10. 如何估算 Kafka 存储容量？

**标准回答：**

```text
rawPerDay = recordsPerSecond × avgRecordBytes × 86400
disk ≈ rawPerDay × retentionDays × replicationFactor
       × compressedToRawRatio × overhead × headroom
```

必须补充：峰值/平均差异、RecordBatch/索引开销、Segment 延迟删除、Compaction 临时空间、副本重建、故障后剩余节点容量、未来增长和磁盘安全水位。

**面试加分：**压缩比不能拍脑袋，用真实 schema、batch 和 key 分布测试；Broker 出流量还包括 Consumer Group 数和副本复制放大。

## 11. 如何估算 Partition 数？

**标准回答：**

```text
Pwrite = peakWriteThroughput / measuredPerPartitionWrite
Pread  = peakReadThroughput / measuredPerConsumerLane
Pparallel = maxExpectedConsumerParallelism
P = max(Pwrite, Pread, Pparallel) × safetyFactor
```

单 Partition 能力必须在真实消息大小、压缩、acks、RF、硬件和 Consumer 逻辑下测量。然后检查 Broker 上 Leader/Replica 数、文件/元数据成本和未来扩分区的 key 语义。

## 12. 设计一个订单事件平台

**题目：**峰值 80,000 条/秒，平均 1.5 KiB，保留 7 天，同账户内有序，允许一台 Broker 故障，Consumer 更新 MySQL 余额且不能重复扣款。

**参考回答骨架：**

1. **Schema**：`eventId/accountId/orderId/type/amount/version/occurredAt/schemaVersion`；
2. **Key**：`accountId`，保证账户内 Partition 顺序；评估超级账户；
3. **Partition**：用真实 workload 测单 Partition 吞吐，再按第 11 题公式计算并留余量；
4. **复制**：RF=3、跨 rack，min ISR=2，Producer `acks=all`；
5. **Producer**：幂等、稳定 eventId、处理 Future；业务 deadline 与 delivery timeout 协调；
6. **Consumer**：按 Partition 串行或账户 lane；数据库 Inbox 唯一键 + 余额版本更新同事务；成功后提交连续 offset；
7. **容量**：原始约 10 TiB/天量级，再乘 7 天、RF、实测压缩和安全余量；
8. **恢复**：验证 Consumer 可持续速率大于峰值输入，计算积压追平；
9. **监控**：ISR/URP、Produce p99、Partition 热点、lag、poll、DB 延迟、去重命中、业务对账；
10. **演练**：Broker/机架故障、响应丢失、Consumer 崩溃、DB 超时和重放。

**追问：为什么不使用 Kafka 事务直接保证 MySQL？**

Kafka 事务不能原子提交任意 MySQL 更新。使用数据库本地 Inbox/业务事务实现 Exactly-Once Effect，Kafka 侧接受 At-Least-Once 重放。

## 13. Topic 扩分区有哪些风险？

**标准回答：**

- 默认 key → Partition 映射可能变化，同 key 历史与新记录分开；
- Consumer Group 触发重新分配；
- Partition/Leader/Replica 增多，元数据和资源成本上升；
- 上下游缓存或硬编码 Partition 逻辑可能失效；
- 短期并不自动均衡已有历史数据和热点 key。

变更前要做 key 映射影响分析、客户端兼容检查、负载/Leader 分布计划、灰度和回滚设计。若严格顺序无法跨扩容保持，考虑新 Topic + 双写/迁移协议。

## 14. Broker 扩容后为什么负载没有自动下降？

**标准回答：**

新 Broker 加入只增加可用节点，不会自动把所有既有 Replica 立即迁移过去，也不会改变 Topic Partition 数或热点 key。需要制定 Partition reassignment/Leader balance，并控制迁移带宽，观察前台延迟。

即使 Replica 均衡，单热点 Partition 仍只能由一个 Leader 承载；此时要解决 key/Partition 设计，而不是继续加 Broker。

## 15. 如何回答“Kafka 集群挂了怎么办”？

**标准回答：**

先拒绝模糊前提，拆成：

- 单 Broker 宕机：Leader 选举、客户端 metadata refresh、ISR 变化；
- Controller 少数节点故障：多数派仍在时控制面继续；
- Controller 丢多数派：元数据变更/选主受阻，已有数据面行为视状态而定；
- 整机架/地域故障：取决于 Replica/Controller 是否跨故障域；
- 全集群不可用：Producer 本地 Buffer 有期限，不应无限堆；上游限流/降级，恢复后按 eventId 重试和对账；
- 数据损坏：从其他副本、跨集群镜像或备份恢复，并评估 RPO/RTO。

优秀回答必须包含事前设计、故障期选择、恢复步骤和数据对账，而不是“Kafka 会自动选主”。

## 16. 排障题通用模板

```text
1. 现象：哪个 SLI、哪些 partition/client、从何时开始？
2. 变化：发布、扩容、流量、配置、故障、GC、磁盘？
3. 分层：客户端 → 网络 → Broker 请求 → 日志/副本 → 下游。
4. 对照：正常 partition/broker/group 与异常对象差异。
5. 时间线：原因指标应先于结果指标变化。
6. 止血：限流、隔离、扩容真正瓶颈，写明可靠性代价。
7. 根治：机制层修复，不用 timeout 掩盖。
8. 验证：故障注入、容量余量、告警和对账闭环。
```

## 17. 面试官常见扣分点

- 不问版本、规模、消息大小、Partition 和故障模型就给参数；
- 把 `acks=all` 说成所有副本物理刷盘；
- 把 RF=3 说成无条件可坏 2 台；
- Lag 一高就加 Consumer；
- 磁盘满就手工删日志；
- 用 Kafka Transaction 保证外部数据库；
- 只说“零拷贝所以快”；
- 只给最终方案，不描述证据和失败窗口。
