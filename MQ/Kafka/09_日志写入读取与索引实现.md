# 09｜日志写入、读取与索引实现：从 RecordBatch 到磁盘字节

> 本章把“顺序写所以快”拆成实际路径。顺序追加只是基础，性能还依赖 batch、校验位置、稀疏索引、页缓存、文件传输路径以及清理任务与前台 IO 的隔离。

## 1. 典型写入调用链

不同小版本的方法名会调整，阅读主线通常是：

```text
KafkaApis
  → ReplicaManager.appendRecords
    → Partition.appendRecordsToLeader
      → UnifiedLog.appendAsLeader
        → LogValidator / ProducerStateManager
        → LocalLog / active LogSegment.append
        → offset index / time index / txn index
```

四层职责不要混淆：

- `ReplicaManager`：跨 partition 请求、leader 身份与 delayed produce；
- `Partition`：单 partition 的 leader/follower 状态、ISR/HW；
- `UnifiedLog`：日志语义、offset、producer/transaction state；
- `LogSegment`：具体文件和索引。

## 2. RecordBatch 是存储与传输单元

现代消息格式以 batch 组织，多条 record 共享 batch header。概念字段包括：

```text
baseOffset, batchLength, leaderEpoch, magic, CRC,
attributes(compression/transaction/control),
lastOffsetDelta, timestamps,
producerId, producerEpoch, baseSequence,
records...
```

好处：

- CRC、协议头与系统调用成本被摊薄；
- 压缩在一批记录上获得更好重复模式；
- PID/epoch/sequence 能描述一段幂等序列；
- follower 与 consumer 可传递批而非逐条重编码。

压缩通常作用于 batch 的 records 部分。broker 若不需要格式转换，可保存/转发压缩 batch，避免先解压再逐条重压；但它仍需做必要校验，旧消息格式转换会显著增加 CPU 和临时内存。

## 3. leader append 的关键校验

追加不是简单 `write(bytes)`：

1. 验证当前 broker/partition 是否为预期 leader，检查 leader epoch；
2. 验证 batch 大小、CRC、时间戳与压缩记录合法性；
3. 对 leader 写入分配最终 offset；
4. 校验幂等 Producer 的 PID/epoch/sequence；
5. 更新事务中 producer 状态；
6. 追加 active segment；
7. 更新 offset/time/transaction index；
8. 更新 LEO，并触发 HW、fetch/produce 等待条件检查。

校验失败必须在写入前或以可恢复方式处理，否则部分 batch 落盘会破坏日志可解析性。

## 4. segment roll 的原子切换

active segment 因大小、时间或索引容量等条件滚动。滚动过程需要：

- 用新 base offset 创建文件组；
- 将旧 active segment 变为不可追加；
- 刷新/整理旧索引；
- 更新内存 segment map；
- 与清理、保留删除和读取并发协调。

为什么不能只保留一个巨大文件？因为删除旧数据、恢复扫描、索引管理和 compaction 都需要可管理粒度。为什么又不能 segment 极小？文件句柄、索引、roll 和后台任务开销会激增。

## 5. 稀疏 offset index 如何定位

索引保存的是相对 offset 到物理 position 的映射：

```text
relativeOffset = targetOffset - segment.baseOffset
index.lookup(relativeOffset) → floor(relativeOffset) 的 position
log.scan(position) → 找到包含 targetOffset 的 batch
```

索引通常使用固定宽度条目并可内存映射。固定宽度使二分和位置计算简单；相对 offset 让条目更紧凑。稀疏意味着 lookup 只给附近起点，最终仍需顺序扫描。

TimeIndex 类似地把时间映射到近似 offset，再经 OffsetIndex 和日志扫描得到结果。按时间查 offset 不是数据库式精确时间索引，多个事件相同/乱序时间戳时尤其要理解口径。

## 6. 恢复：为什么需要扫描尾部

非正常关闭后，broker 不能假设所有内存状态和索引都可信。恢复通常需要根据 checkpoint/恢复点选择扫描范围，验证日志 batch，重建或修复索引及 producer state。

恢复成本受这些因素影响：

- 未干净关闭的日志目录数量；
- active segment 大小；
- producer/transaction state snapshot 可用性；
- 磁盘顺序读能力；
- 每 data dir 的 recovery threads；
- 同时恢复的 partition 数。

因此“大 segment 降低文件数”与“故障后尾部恢复成本”存在权衡。

## 7. Fetch 读取与零拷贝边界

读取主线：根据 partition/offset/隔离级别确定最大可见位置 → 找 segment → 索引定位 → 构造文件记录范围 → 网络层发送。

在适用路径中，文件支持通过 `transferTo`/sendfile 风格把页缓存中的数据送到 socket，减少用户态复制与上下文切换。不要把它绝对化：

- TLS 加密可能改变传输路径，需要用户态/引擎处理；
- 消息格式转换需要读入并重写；
- 事务隔离需要依据 aborted transaction 信息过滤可见性元数据；
- 远程分层存储不等同于本地文件传输；
- 小响应、缓存未命中时收益模型不同。

“Kafka 使用零拷贝”应表述为特定文件记录发送路径可利用零拷贝能力，而非所有请求都零复制。

## 8. ProducerStateManager 与快照

为了验证幂等序列和事务状态，broker 需要按 producer 维护最近 epoch、sequence、offset、事务起点等状态。若每次启动都从 offset 0 重放，成本不可接受，所以会周期性形成 producer snapshot，并在恢复时从较近快照加载后扫描尾部。

读 `ProducerStateManager` 时关注三个问题：

1. 新 batch 如何验证 sequence 连续与 epoch 合法；
2. 过期 producer state 如何清理；
3. 日志截断后内存状态与 snapshot 如何回退到一致边界。

## 9. Log Cleaner 的两遍思路

compaction 不能简单用 HashMap 装下整个日志。典型思路：

1. 扫描待清理范围的较新部分，构建 key → latest offset 的 offset map；
2. 重写较旧 dirty segment，仅保留仍是最新的记录、必要 tombstone/control batch；
3. 生成 cleaned 文件与索引；
4. 以受控重命名/替换完成 segment swap；
5. 延迟删除旧文件，保护并发 reader。

offset map 内存有限时一次只能覆盖部分范围，因此清理是渐进的。cleaner 还要保留 offset 单调语义和事务控制记录边界，绝不是对 value 做普通去重。

## 10. 源码实验

选择一个测试 partition：

1. 发送不同 batch size/压缩类型的数据；
2. 用官方 dump log 工具查看 batch header，而不是手工修改文件；
3. 记录 `.log/.index/.timeindex` 大小；
4. 触发 segment roll，验证 base offset 命名；
5. 正常关闭与强制终止分别启动，比较恢复日志与耗时；
6. compact topic 更新同 key，观察旧值何时被后台清理。

## 11. 检查题

1. 稀疏索引为何不会让每次查找都退化为扫描整个 segment？
2. broker 为什么仍需校验已由 Producer 计算 CRC 的 batch？
3. TLS 开启后为什么不能简单宣称消费路径仍完全零拷贝？
4. producer snapshot 损坏时如何从日志恢复状态？代价是什么？
5. compaction 重写 segment 时如何避免正在读取旧文件的请求失败？
