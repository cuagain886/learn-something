# 06｜本地实验与故障注入：用证据校准心智模型

> 实验目标不是“命令跑通”，而是先预测状态，再注入单一故障，最后用 topic 描述、consumer group 位点、客户端日志和业务结果验证。

## 1. 环境原则

- 当前官方 Kafka Quickstart 提供本地脚本与官方 Docker 镜像两种方式；命令与镜像 tag 随版本变化，执行前查对应版本帮助。
- 单节点用于 API 入门；副本、ISR 和选主实验至少需要 3 个 broker。
- 本地数据可删除，但不要把生产配置从实验环境直接复制。
- 每次实验记录 Kafka/Java 版本、配置、topic partition/RF 和时间线。

### 最小命令探针

以下使用发行包脚本名；Windows 可在 WSL/Git Bash/Docker 环境运行：

```bash
bin/kafka-topics.sh --bootstrap-server localhost:9092 --list
bin/kafka-topics.sh --bootstrap-server localhost:9092 \
  --describe --topic payment-events
bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
  --describe --group payment-risk
bin/kafka-configs.sh --bootstrap-server localhost:9092 \
  --entity-type topics --entity-name payment-events --describe
```

## 2. 实验零：建立可追踪事件

创建实验 topic 时明确参数，不依赖默认值：

```bash
bin/kafka-topics.sh --bootstrap-server localhost:9092 \
  --create --topic payment-events \
  --partitions 6 --replication-factor 3 \
  --config min.insync.replicas=2
```

测试记录应包含：

```json
{"eventId":"e-000001","accountId":"a-42","seq":1,"amount":100}
```

Producer 输出或业务日志至少记录 `eventId/topic/partition/offset/timestamp`；Consumer 再记录 `group/member/attempt`。没有这些坐标，重复和乱序无法精确复盘。

## 3. 实验一：key、partition 与局部有序

### 预测

相同 key 在 partition 数不变、分区算法一致时进入同一 partition；不同 key 不承诺相对顺序。

### 步骤

1. 交替发送 `a-42 seq=1..20`、`a-99 seq=1..20`；
2. 打印每条 send result 的 partition/offset；
3. Consumer 按收到顺序打印；
4. 将 topic 扩到更多 partition 后再次发送；
5. 比较扩容前后 key 映射。

### 证据与结论

- 同 key 的 offset 应在单 partition 内递增；
- 扩分区后映射可能变化，历史记录不会自动搬迁；
- 若 consumer 用线程池随机执行，完成日志可能乱序，证明 broker 顺序不等于业务完成顺序。

## 4. 实验二：ISR 收缩与写入可用性

### 预测

RF=3、min ISR=2、Producer `acks=all`。停一个 follower 后 ISR 可能从 3 变 2，写入仍可成功；再停一个同步副本后，写入无法满足最小同步副本条件。

### 步骤

1. describe topic，记下目标 partition 的 leader/replicas/ISR；
2. 持续低速发送带序号记录；
3. 停一个 follower broker，重复 describe；
4. 观察 Producer 延迟和错误；
5. 再停一台属于该 partition ISR 的 broker；
6. 恢复 broker，观察 ISR 追平和 Producer 恢复。

### 不要误判

- 停错 broker 可能不影响目标 partition；
- ISR 变化有检测窗口，不一定瞬时；
- 客户端可能先经历 timeout/metadata refresh；
- 恢复 broker 进程不等于副本瞬间追平。

## 5. 实验三：响应丢失与幂等重试

精确丢弃响应需要网络代理或容器网络规则。若环境不便，可用代理注入 broker 响应延迟，使其超过客户端 request timeout，同时 broker 仍有机会完成写入。

对照两组：

- A：使用现代客户端的幂等安全配置；
- B：显式关闭幂等，仅用于实验。

发送唯一 `eventId`，最终全量消费并按 `eventId` 统计。关注：

- callback 报 timeout 时日志中是否已有记录；
- B 是否可能出现重复；
- A 是否避免协议重试重复；
- 若应用捕获 timeout 后重新创建 Producer/记录再发，A 是否仍能按业务 ID 去重。

## 6. 实验四：提交窗口导致重复

Consumer 流程设置为：写入本地数据库/文件 → 等待 10 秒 → commit。处理完成后等待期间强制结束进程。

预测与验证：

1. 外部结果已存在；
2. committed offset 仍指向旧位置；
3. 重启后同一 event 重放；
4. 无幂等时副作用重复；
5. 加 `eventId` 唯一约束后，处理尝试重复但结果只生效一次。

再做反向实验：commit → 等待 → 业务处理，在等待期间结束进程，验证业务漏处理。

## 7. 实验五：慢处理与再均衡

1. 启动两个同组 consumer；
2. 将单批处理时间故意拉长，超过允许的 poll 间隔；
3. 观察 group 状态、成员变化、assignment 与客户端日志；
4. 记录有效处理时间和再均衡停顿；
5. 减小单次拉取/采用 partition worker + pause/resume，再对比。

验证目标不是“把 timeout 调大就好了”，而是判断慢在哪里，以及改造后是否同时改善心跳稳定、内存队列和处理延迟。

## 8. 实验六：积压恢复曲线

1. 暂停 consumer，固定速率生产 10 分钟，形成已知积压 L；
2. 恢复不同数量 consumer；
3. 每 10 秒记录各 partition lag、输入速率和处理速率；
4. 用 `L/(λout-λin)` 预测追平时间；
5. 比较预测与实际，解释再均衡、冷缓存、热点和下游限流造成的差异。

若增加 consumer 后吞吐不升，检查 partition 上限和数据库连接/锁瓶颈。

## 9. 故障实验报告模板

```markdown
## 假设
在 RF=3、min ISR=2、acks=all 时停两个同步副本，写入应失败而非降级成功。

## 基线
版本、broker/partition/RF、客户端配置、正常吞吐和延迟。

## 时间线
12:00:00 开始发送；12:02:00 停 B2；12:04:00 停 B3……

## 证据
topic describe、group describe、客户端错误、broker 日志、指标截图。

## 观察
只写事实，不先写解释。

## 结论
是否支持假设；不一致如何修正模型。

## 清理与恢复
恢复所有 broker，确认 ISR、lag 和测试进程状态。
```

## 10. 实验安全清单

- 故障注入只能针对本地/明确授权环境；
- 一次只改变一个主要变量；
- 注入前保存基线，注入后确认完全恢复；
- 不只看应用“没报错”，同时核对记录数量、eventId 和位点；
- 使用超时与资源上限，避免无限重试占满磁盘/内存；
- 把预期与实际都写下来，禁止事后改写预测。
