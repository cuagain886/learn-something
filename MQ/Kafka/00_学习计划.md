# 00｜Kafka 深度学习计划：从提交日志到生产故障

> 周期建议：6 周，每周 8～10 小时。若时间紧，减少扩展阅读，不要跳过实验与复盘。

## 1. 学习终点

完成后不以“会使用 Producer/Consumer API”为终点，而应具备四层能力：

1. **模型层**：用追加日志、分区、副本、位点解释 Kafka，而不是把它类比成普通队列。
2. **正确性层**：能为“有序、可靠、幂等、事务、Exactly-Once”写出严格的作用域与失败条件。
3. **工程层**：能从吞吐、延迟、保留期、峰值与容灾目标推导分区数、存储量和关键配置。
4. **诊断层**：面对积压、频繁再均衡、Under Replicated Partitions、请求超时时，能构造证据链而不是盲目调参。

### 毕业验收

独立完成下面的系统设计并接受反例追问：

> 设计一个订单事件平台：峰值 80,000 条/秒，平均记录 1.5 KiB，保留 7 天，同订单严格有序，跨机架容忍 1 台 broker 故障；下游写 MySQL，要求重复事件不得重复更新余额。

答案至少覆盖：key 与分区策略、分区吞吐测量、复制因子、`min.insync.replicas`、Producer 确认与幂等、Consumer 提交时机、MySQL 幂等、积压恢复时间、容量冗余、监控与演练。

## 2. 前置知识与起点测验

### 前置知识

- TCP 请求/响应、超时与重试；
- 文件、页缓存、顺序 IO、`fsync` 的基本差异；
- 哈希、队列、并发与故障恢复；
- 至少一种语言的客户端开发经验，推荐 Java；
- Docker 或本地 JVM 环境。

### 起点测验

先写答案，课程结束后再答一次：

1. Topic 有 12 个 partition，组内有 20 个 consumer，最大并行度是多少？为什么？
2. `acks=all` 是否等于数据已经落入所有副本磁盘？
3. Consumer 处理完业务再提交 offset，进程在二者之间崩溃会怎样？
4. 同一 key 是否永远落到同一 partition？扩容 partition 后呢？
5. ISR 里的 follower 是否要求与 leader 每个 offset 都完全一致？
6. 开启幂等 Producer 后，数据库一定不会重复扣款吗？
7. lag 很大一定说明 consumer 算力不足吗？

判断答案是否合格的标准不是“选对”，而是能给出事件顺序、状态变化和边界条件。

## 3. 六周路线

### 第 1 周：建立正确心智模型

阅读：[01 核心模型与 KRaft 架构](01_核心模型与KRaft架构.md)

重点：event/topic/partition/offset/broker/controller；数据面与控制面；元数据；KRaft quorum。

产出：

- 手画一条记录从 `send()` 到消费的时序图；
- 写出“Kafka 是分布式提交日志”比“Kafka 是消息队列”更准确的三个理由；
- 解释为什么 offset 只在 partition 内有意义。

验收：随机给出 broker、controller、producer、consumer 任一故障，能说清元数据、数据和客户端分别发生什么。

### 第 2 周：存储与复制

阅读：[02 分区日志、索引与副本机制](02_分区日志索引与副本机制.md)

重点：segment、稀疏索引、页缓存、保留与压缩、leader/follower、ISR、LEO、HW、leader epoch。

产出：

- 用 LEO/HW 画出 follower 落后与追平过程；
- 对比 delete retention 与 log compaction；
- 解释“副本数 3”为什么不自动等于“任意时刻可安全坏 2 台”。

实验：观察 segment 文件和 topic describe；停掉 follower，观察 ISR 变化。

### 第 3 周：写入链路

阅读：[03 Producer 发送链路与可靠性](03_Producer发送链路与可靠性.md)

重点：序列化、分区器、RecordAccumulator、batch、压缩、`linger.ms`、`batch.size`、`acks`、重试、超时、幂等序列号。

产出：

- 画出业务线程与 Sender 线程分工；
- 给低延迟与高吞吐两类 workload 各设计一次基准测试；
- 构造“broker 已写入但响应丢失”场景，解释重复从何而来。

### 第 4 周：消费、位点与再均衡

阅读：[04 Consumer Group、位点与再均衡](04_ConsumerGroup位点与再均衡.md)

重点：poll loop、fetch position、committed offset、group coordinator、assignment、heartbeat、再均衡、静态成员。

产出：

- 分别画出先提交后处理、先处理后提交的失败窗口；
- 对比自动提交、同步提交、异步提交与“每 partition 保存处理进度”；
- 解释慢处理为什么可能触发再均衡风暴。

### 第 5 周：端到端语义与业务一致性

阅读：[05 交付语义、事务与一致性边界](05_交付语义事务与一致性边界.md)

重点：at-most-once、at-least-once、Kafka transaction、read-process-write、`read_committed`、事务 fencing、outbox/inbox。

产出：

- 为 Kafka→Kafka、Kafka→MySQL 两条链路分别定义 exactly-once；
- 证明“幂等 Producer ≠ 端到端 exactly-once”；
- 设计 payment-events 的业务幂等表与失败恢复流程。

### 第 6 周：生产化、容量与故障演练

阅读：[06 本地实验与故障注入](06_本地实验与故障注入.md)、[07 生产设计、容量规划与排障](07_生产设计容量规划与排障.md)

重点：SLO、容量模型、分区规划、热点、监控、积压、限流、滚动维护、灾难演练。

毕业产出：

- 完成第 1 节系统设计；
- 留下一份故障时间线：现象、假设、证据、结论、修复、预防；
- 做一次 broker 故障、consumer 卡顿和数据库写入超时注入。

## 4. 第 7～10 周：底层实现与源码

前六周通过后再进入源码阶段，避免把类名当原理：

| 周次 | 阅读 | 必须产出 |
|---|---|---|
| 第 7 周 | [08 Broker 网络层](08_Broker网络层与请求处理流水线.md)、[09 日志实现](09_日志写入读取与索引实现.md) | Produce 请求火焰图假设；从 frame 到 segment 的完整调用图 |
| 第 8 周 | [10 副本复制](10_副本复制HW与Leader切换.md)、[11 KRaft 控制器](11_KRaft元数据日志与控制器.md) | 数据 HW 与元数据 HW 对照；leader 故障双时间线 |
| 第 9 周 | [12 Producer 源码](12_Producer客户端源码主线.md)、[13 Consumer/Group 源码](13_Consumer与GroupCoordinator源码主线.md) | 两个客户端状态机；一次 retry 和一次 rebalance 的断点记录 |
| 第 10 周 | [14 事务实现](14_事务协调器与ExactlyOnce实现.md) | commit/abort marker 实验；HW/LSO/open transaction 可见性图 |

源码阶段的验收不是“读完多少类”，而是可以从异常或指标反向定位到状态所有者。例如：`RemoteTimeMs` 高应先进入副本确认路径，`RequestQueueTimeMs` 高应先检查 handler 饱和，`read_committed` 停滞则比较 HW、LSO 与 open transaction。

## 5. 每章固定学习闭环

```text
提出问题 → 写出预测 → 阅读机制 → 运行实验 → 收集指标/日志
    ↑                                             ↓
    └──────── 用反例修正模型 ← 写故障时间线 ←──────┘
```

每个结论都要过四道检查：

- **作用域**：topic、partition、producer session、consumer group 还是外部系统？
- **时间范围**：一次请求、一次会话、一次事务还是跨重启？
- **失败模型**：进程崩溃、网络超时、磁盘损坏、机架故障分别如何？
- **观测证据**：哪个 CLI、指标、日志或业务表能证实？

## 6. 学习记录模板

```markdown
### 问题

### 我的预测

### 不变量

### 实验

### 证据
日志、指标、topic/partition/offset、时间戳。

### 结论与边界
结论成立的配置、版本和失败假设。

### 反例
什么条件一变，结论就不成立？
```

## 7. 暂时不要做的事

- 不背“Kafka 为什么快”的固定话术；先用批处理、顺序 IO、页缓存、零拷贝/传输路径分别解释。
- 不复制生产参数模板；配置必须服务于明确 SLO。
- 不一开始阅读全部源码；先形成协议与状态机模型，再沿关键路径读源码。
- 不用单节点实验推导高可用结论；单节点只能验证 API 和日志模型。
- 不把消费成功等同于业务成功；外部副作用必须单独建模。
