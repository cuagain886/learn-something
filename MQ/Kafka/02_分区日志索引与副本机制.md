# 02｜分区日志、索引与副本机制：数据何时算可见、何时算安全

> 核心结论：partition 在磁盘上是一组 segment；leader 负责定义日志顺序，follower 通过 fetch 复制。LEO 描述副本末尾，HW 划出普通消费者可见的已提交前缀，ISR 是动态同步集合，不是静态副本清单。

## 1. 从 partition 到 segment

一个 partition 是逻辑上的连续日志，但不会永远写在单个大文件中。broker 将其滚动为多个 segment：

```text
payment-events-3/
├── 00000000000000000000.log
├── 00000000000000000000.index
├── 00000000000000000000.timeindex
├── 00000000000001234567.log      <- active segment
├── 00000000000001234567.index
└── 00000000000001234567.timeindex
```

文件名通常以该 segment 的 base offset 命名。`.log` 保存 record batch；`.index` 将相对 offset 稀疏映射到物理位置；`.timeindex` 支持时间戳到 offset 的近似定位。

### 为什么是稀疏索引

索引不需要为每条记录存一个条目。查 offset 时：

1. 先根据 base offset 选择 segment；
2. 在稀疏 offset index 中二分找到不大于目标 offset 的最近位置；
3. 从该物理位置顺序扫描少量 batch。

这在索引体积、内存映射开销和扫描成本之间折中。Kafka 的高吞吐不是“只因为顺序写”，还来自 batch、压缩、页缓存和避免逐消息开销。

## 2. 页缓存与持久性不要混为一谈

broker 追加日志通常先进入操作系统页缓存，再由操作系统刷盘。三种状态要区分：

1. leader 进程已接收；
2. 数据已进入 leader 的本地页缓存/日志；
3. 多个副本已复制，甚至各自稳定落盘。

Kafka 的可靠性主要通过副本协议而不是“每条消息同步 fsync 所有磁盘”获得。`acks=all` 表达满足 ISR/min ISR 的复制确认条件，不应简化为“所有 replica 已物理落盘”。若同一故障同时摧毁多个副本或其缓存，仍可能丢数据，因此机架分散与故障域设计同样重要。

## 3. LEO、HW 与已提交前缀

- **LEO（Log End Offset）**：某副本下一条将写入的位置，可理解为该副本日志末端。
- **HW（High Watermark）**：已安全复制到合格副本集合、可向普通消费者暴露的日志边界。
- **LSO（Last Stable Offset）**：涉及事务读取时，`read_committed` 可见范围还受未完成事务限制。

示例：

```text
offset:  0 1 2 3 4 5 6 7
Leader:  ● ● ● ● ● ● ● ●   LEO=8
F1:      ● ● ● ● ● ●       LEO=6
F2:      ● ● ● ● ● ● ●     LEO=7
                     ^ HW=6（示意）
```

leader 尾部可能已有尚未进入已提交前缀的记录。消费者默认不能把这部分当作稳定数据，否则 leader 切换后尾部被截断，消费者就会看见“读过的记录消失”。HW 用可见性换取一致的前缀。

## 4. ISR 是动态集合

replica assignment 说明 partition 应在哪些 broker 上有副本；ISR（in-sync replicas）说明当前哪些副本满足同步条件。follower 长时间无法及时 fetch 或落后超出允许条件，会被移出 ISR；追平后可重新加入。

因此：

```text
replicas = [B1, B2, B3]
ISR      = [B1, B2]
```

并不代表 B3 副本被删除，只表示它当前不能作为“同步副本”参与安全确认/选主判断。

### `acks=all` 与 `min.insync.replicas`

假设 replication factor=3，`min.insync.replicas=2`：

- ISR 有 3 个：写入可在满足协议条件后成功；
- ISR 缩到 2 个：通常仍可写，但已没有继续损失同步副本的余量；
- ISR 缩到 1 个：要求 all 的 Producer 会收到无法满足副本条件的错误，系统选择停止成功写入来保护可靠性。

这就是一致性/可用性取舍。把 `min.insync.replicas` 降到 1 会提高故障期可写性，却扩大仅存一份有效数据时继续接受写入的风险。

## 5. leader 切换与日志截断

leader epoch 用于区分不同任期的 leader 历史，帮助副本/客户端识别过期 leader 与确定一致日志边界。故障恢复时，新 follower 不能简单地把本地更长的尾部当成正确；它必须与当前 leader 的历史对齐，必要时截断未提交分叉，再继续复制。

要记住：

- “本地日志更长”不等于“更正确”；
- 已提交前缀的安全依赖选主限制和同步副本；
- 允许不在 ISR 的副本成为 leader（不安全选主）可能恢复可用性，但可能丢失已确认记录，生产环境必须清楚这一代价。

## 6. 保留删除与日志压缩

### delete policy

按时间或大小删除旧 segment，适合事件历史：

```text
retention.ms / retention.bytes
```

删除以 segment 为粒度且由后台周期任务执行，因此不是到期瞬间逐条删除。容量规划不能把 retention 当成精确截止线。

### compact policy

log compaction 目标是最终保留每个 key 的最新值，而非保留最近 N 天：

```text
k1:v1, k2:a, k1:v2, k3:x, k2:b
压缩后的逻辑结果约为：k1:v2, k3:x, k2:b
```

边界：

- 压缩是后台渐进过程，旧值不会写入后立即消失；
- 无 key 的记录无法按 key 压缩；
- key 对应 null value 常作为 tombstone，表示删除语义，tombstone 也有保留窗口；
- compact 保证“至少保留最新值”的语义，不提供数据库式即时唯一行视图；
- 一个 topic 可组合 `compact,delete`，但必须分别理解两种清理条件。

## 7. segment 与配置之间的因果关系

| 配置方向 | 过小的代价 | 过大的代价 |
|---|---|---|
| segment roll | 文件、索引和后台操作增多 | 过期数据等待 active segment 滚动，删除粒度粗 |
| retention check interval | 后台检查更频繁 | 过期回收延迟更明显 |
| index interval | 索引更大 | 定位后顺序扫描更多 |
| replica fetch/batch | 请求开销增加 | 单次内存与延迟可能增加 |

不要孤立调一个值。比如缩小 segment 可更快回收过期数据，但会增加文件句柄、索引和 segment 管理成本。

## 8. 一次确认丢失的推演

1. Producer 向 leader 发送 batch X；
2. leader 追加 X，followers 复制，X 达到可确认条件；
3. leader 的成功响应在网络中丢失；
4. Producer 超时，不知道 X 是否成功；
5. Producer 重试 X。

没有幂等协议时，X 可能被追加两次；有幂等 Producer 时，broker 可利用 producer identity、partition sequence 等状态识别同一会话内的重试。注意，业务代码自己重新构造并发送“相同业务事件”，未必拥有相同协议序列，不能指望 broker 自动按业务字段去重。
