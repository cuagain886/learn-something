# 05｜交付语义、事务与一致性边界：Exactly-Once 不是一句配置

> 核心结论：交付语义必须针对“哪一段链路、哪个可观察副作用”定义。幂等 Producer 处理协议重试重复；Kafka transaction 原子提交 Kafka 记录与消费位点；Kafka 无法单独让任意外部数据库、HTTP 服务与 Kafka 形成原子提交。

## 1. 先定义“处理一次”

对事件 E，至少有四个不同事实：

1. E 被 Producer 发送一次；
2. E 在 Kafka partition 日志中出现一次；
3. Consumer 的处理函数执行一次；
4. 数据库余额等业务结果生效一次。

它们不等价。处理函数可能执行两次但幂等结果只生效一次；Kafka 日志只有一条记录，但 HTTP 下游在响应丢失后执行两次。

因此一个合格定义应类似：

> 对每个唯一 `eventId`，无论 Consumer 在任意指令边界崩溃多少次，`account_balance` 的版本最多推进一次；恢复后最终至少推进一次。Kafka 内允许重复投递，数据库唯一约束保证唯一生效。

## 2. 三类语义的失败窗口

| 语义 | 典型实现 | 故障结果 |
|---|---|---|
| at-most-once | 先提交位点，再处理 | 不重复，但可能跳过业务处理 |
| at-least-once | 先处理，成功后提交 | 不轻易跳过，但可能重复处理 |
| exactly-once effect | at-least-once + 幂等/原子协议 | 可重试执行，结果只生效一次 |

“Exactly-once delivery”容易误导，因为网络不确定结果迫使重试。工程上更实用的是 exactly-once effect：执行尝试可以多次，但可观察状态转移一次。

## 3. 幂等 Producer 解决哪一段

它解决同一 Producer 协议会话中，因 broker 响应丢失等导致的 Produce 重试重复与序列问题。它不解决：

- 用户重复点击产生两个独立业务命令；
- 两个 Producer 实例都发送同一 `eventId`；
- Consumer 重放后重复写数据库；
- Kafka 成功而调用方本地状态未更新；
- 任意外部 API 的重复副作用。

所以消息 schema 中保留稳定 `eventId` 仍是关键设计，而不是让 consumer 用整段 JSON 做模糊去重。

## 4. Kafka transaction 的原子边界

事务 Producer 可将多个 partition 的输出记录和 consumer group offsets 原子地提交到 Kafka。典型 read-process-write：

```text
consume input offsets
beginTransaction
produce output records (可跨多个 partition)
sendOffsetsToTransaction(processed offsets, group metadata)
commitTransaction
```

成功后，读取 committed 数据的下游同时看到输出与进度；失败/abort 后，二者都不作为已提交结果生效。

### `read_committed`

普通读取可能接触事务期间写入但最终 abort 的记录；需要端到端事务语义的 consumer 使用只读已提交隔离。它的可见上界还会受尚未完成事务影响，因此长事务会增加读取延迟和积压表象。

### fencing

`transactional.id` 标识逻辑事务 Producer。新实例以同一身份初始化后，应使旧实例失去继续提交的资格，防止脑裂的两个实例同时代表同一处理分片写入。遇到 fencing 不是普通网络抖动，旧实例必须停止并释放所有权。

### 事务不等于无限大批次

事务有超时和协调状态成本。长事务会：

- 延迟 `read_committed` 可见性；
- 增大中止/恢复成本；
- 更易因处理超时失败；
- 占用更多在途状态。

事务边界应匹配可控的处理批次，而非把整天的数据放进一个事务。

## 5. Kafka → MySQL：双写困境

目标：消费 Kafka 事件并更新 MySQL，再提交 Kafka offset。

```text
方案 A: DB commit → offset commit
DB 成功后崩溃 => 重放并再次写 DB

方案 B: offset commit → DB commit
offset 成功后崩溃 => DB 永远漏写
```

没有共同事务协调器时，两步之间必有窗口。通常选择 at-least-once 加数据库幂等，而不是做脆弱的“尽量同时”。

### inbox/去重表示例

```sql
CREATE TABLE consumed_event (
    consumer_name VARCHAR(100) NOT NULL,
    event_id      VARCHAR(100) NOT NULL,
    processed_at  TIMESTAMP NOT NULL,
    PRIMARY KEY (consumer_name, event_id)
);
```

在同一个 MySQL 本地事务中：

1. 插入 `(consumer_name, event_id)`；
2. 若唯一键冲突，说明已处理，直接视为成功；
3. 若插入成功，执行业务状态更新；
4. 提交数据库事务；
5. 再提交 Kafka offset。

步骤 4 与 5 之间崩溃会重放，但步骤 1 使数据库副作用不会重复。注意去重表的生命周期必须覆盖 Kafka 可能重放的最长窗口，否则清理太早会让旧事件重新生效。

### 状态版本法

若事件带聚合版本 `aggregateVersion`，可用条件更新：

```sql
UPDATE account
SET balance = ?, version = :newVersion
WHERE account_id = :id AND version = :newVersion - 1;
```

影响行数为 0 时要区分：事件已处理、事件乱序、数据缺失。它不仅去重，还能发现顺序缺口，但需要定义迟到和补偿策略。

## 6. 数据库 → Kafka：Transactional Outbox

业务事务同时修改订单表与 outbox 表：

```text
BEGIN
  UPDATE orders ...
  INSERT outbox(event_id, aggregate_id, payload, status) ...
COMMIT
```

后台 relay/CDC 将 outbox 发布到 Kafka。发布成功后更新状态也可能失败，所以 relay 仍可能重复发送；下游用稳定 `event_id` 幂等。outbox 解决的是“业务数据已提交但事件没发出”的原子性缺口，不自动保证 Kafka 中绝无重复。

## 7. 重试 Topic 与 DLT 的语义代价

失败记录转入 retry topic/DLT 可以解除原 partition 阻塞，但会改变顺序：offset 101 失败旁路后，102 可能先完成。若订单状态必须有序，不能无条件旁路。

设计时明确：

- 重试是原地阻塞、延迟 topic 还是外部调度？
- 最大次数和总时间预算是多少？
- DLT 记录是否包含原 topic/partition/offset、异常类型、重试次数、schema 版本？
- DLT 写成功与原 offset 提交如何避免重复？
- 修复重放如何保持原 `eventId` 并审计？

## 8. 一致性设计检查表

1. 业务事件的唯一标识由谁生成，跨重试是否稳定？
2. 顺序作用域是账户、订单还是全局？
3. Kafka 内部需要跨 partition 原子性吗？
4. 外部副作用的幂等落点在哪里：唯一键、版本号、状态机还是收件箱？
5. 去重数据保留多久，最长重放窗口多长？
6. 毒丸消息会阻塞、旁路还是人工介入？顺序如何变化？
7. 超时结果未知时，上游能否安全重试？
8. 对账如何发现漏处理、重复业务结果与非法状态跳转？

## 9. 深度检查题

1. Kafka Streams 的 exactly-once 是否能自动让第三方支付 HTTP API 只扣一次？
2. transaction 已 commit，但应用在收到成功响应前崩溃，恢复时如何避免旧实例继续写？
3. inbox 表保留 7 天，而 Kafka 可回放 30 天，会出现什么反例？
4. 为什么“处理函数执行两次、数据库只变化一次”仍可满足 exactly-once effect？
5. retry topic 为什么可能破坏同 key 顺序？给出一种保持顺序的替代设计。
