# 15｜Kafka 面试必考：基础、架构与底层原理题

> 使用方式：先用 30～60 秒给出结论，再根据追问下钻机制。标准回答必须包含作用域和边界，避免“Kafka 高吞吐、不会丢、全局有序”这类无条件结论。

## 1. Kafka 是什么？为什么不只说它是消息队列？

**标准回答：**

Kafka 是分布式事件流平台，核心数据抽象是分区追加日志。Producer 向 topic partition 追加 record，Consumer 用 offset 控制读取位置。数据生命周期由保留策略决定，不因某个 Consumer 消费完成就立即删除，所以同一数据可被多个 Consumer Group 独立读取和重放。

说它是消息队列没有错，但不完整。传统工作队列强调消息交给某个消费者后确认删除；Kafka 还强调持久日志、重放、多订阅组、流处理和状态重建。

**常见追问：Kafka 与 RabbitMQ 如何选择？**

不做“谁绝对更快”的比较。若核心需求是大规模事件流、长时间保留、重放、分区并行和流处理，Kafka 更匹配；若强调复杂路由、逐消息确认、低规模任务分发等，可评估传统 Broker。最终要用吞吐、延迟、顺序、路由、积压和运维模型决策。

关联：[01 核心模型](01_核心模型与KRaft架构.md)

## 2. Topic、Partition、Replica、Segment 分别是什么？

**标准回答：**

- Topic 是逻辑数据集；
- Partition 是有序追加日志，也是并行和复制的基本单元；
- Replica 是某个 Partition 在不同 Broker 上的数据副本，其中一个是 Leader；
- Segment 是 Partition 日志在磁盘上的滚动文件单元，通常配套 offset/time/transaction 等索引。

Partition 是逻辑连续的，Segment 是物理分段；Replica 复制的是 Partition，不是整个 Topic 一次性复制。

**错误回答：**“一个 Topic 就是一个队列文件”“一个 Broker 对应一个 Partition”。Topic 可以有多个 Partition，一个 Broker 可承载许多不同 Partition 的 Leader/Follower。

## 3. Offset 是全局唯一 ID 吗？

**标准回答：**

不是。Offset 只在一个 TopicPartition 内定位记录。完整坐标是 `(topic, partition, offset)`。不同 Partition 都可以存在 offset 100。Offset 表示日志位置，不等于业务主键，也不等于严格事件时间。

Consumer Group 提交的通常是“下一条要消费的 offset”。处理完 offset 100 后提交 101。

## 4. Kafka 能保证消息顺序吗？

**标准回答：**

Kafka 只保证单 Partition 内的日志顺序，不提供跨 Partition 全局顺序。同一业务实体要有序，通常把稳定实体 ID 作为 key，使其映射到同一 Partition。

还要补三个边界：

1. 扩分区后 key 的映射可能变化，历史和新数据可能分居不同 Partition；
2. 多个 Producer 实例的业务发生顺序不由 Kafka 自动定义；
3. Consumer 拉取有序，但记录级线程池可能让业务完成乱序。

**追问：如何保证订单状态顺序？**

使用 `orderId` 作为 key；Consumer 对同一 Partition 或同一 key 串行处理；事件携带状态版本，数据库用版本条件更新拒绝倒序状态。

## 5. Partition 数越多越好吗？

**标准回答：**

不是。更多 Partition 提高潜在写入并行度和 Consumer Group 并行上限，但也增加元数据、文件句柄、索引、Leader 选举、客户端内存、再均衡和副本恢复成本。

分区数应由实测单 Partition 吞吐、目标 Consumer 并行度、峰值流量和增长余量共同推导。扩分区还是语义变化，因为默认 key 映射可能改变。

**追问：为什么通常不能随便减少 Partition？**

减少会涉及 offset 空间、key 顺序、Consumer 位点和数据合并，无法通过简单元数据修改安全完成。常用方式是新建目标 Topic，再迁移/重放数据并切换上下游。

## 6. Consumer 数量超过 Partition 数会怎样？

**标准回答：**

同一个 Consumer Group 的稳定 assignment 中，一个 Partition 只分给一个 Consumer member。若 12 个 Partition、20 个 Consumer，最多 12 个 Consumer 有 Partition，其余空闲。增加 Broker 不会直接提高该 Group 的并行上限；增加 Partition 才可能提高，但要评估语义和成本。

不同 Group 之间不共享这个限制：每个 Group 都可以完整消费同一 Topic。

## 7. Kafka 4.x 为什么强调 KRaft？Controller 做什么？

**标准回答：**

KRaft 用 Kafka 自身的 Raft 元数据日志管理集群元数据。Controller quorum 负责 Broker 注册、Topic/Partition 元数据、Replica assignment、Leader/ISR 变化、配置和其他控制面状态。

Controller 决定“谁是 Leader、有哪些副本”，业务 Partition Leader 负责实际 Produce/Fetch。Controller 不转发所有数据请求，也不保存业务 Topic 的内容。

**追问：3 个 Controller 和 replication factor=3 是一回事吗？**

不是。前者保护元数据 quorum，后者保护业务 Partition 日志。Controller 多数派健康不代表业务副本健康。

关联：[11 KRaft 原理](11_KRaft元数据日志与控制器.md)

## 8. Leader、Follower、AR、ISR 分别是什么？

**标准回答：**

- Leader：处理当前 Partition 的主要读写并定义日志顺序；
- Follower：主动 Fetch Leader 日志并追加本地副本；
- AR/replica assignment：配置上应存在的全部副本集合；
- ISR：当前满足同步条件的动态副本集合。

Follower 进程上线不等于立刻进入 ISR，必须追平到要求边界。ISR 收缩意味着容灾余量下降，也可能让 `acks=all` 写入因 `min.insync.replicas` 不满足而失败。

## 9. LEO、HW、LSO 有什么区别？

**标准回答：**

- LEO：某副本日志末尾的下一位置；
- HW：已进入复制确认前缀、普通 Consumer 可见的边界；
- LSO：Last Stable Offset，事务隔离下 `read_committed` 可见性的进一步边界。

Leader LEO 可以高于 HW，表示尾部尚未达到安全提交条件；HW 可以高于 LSO，表示前面存在尚未完成的事务。长事务可能让 `read_committed` Consumer 看起来停滞，即使 HW 已继续推进。

## 10. `acks=0/1/all` 分别代表什么？

**标准回答：**

- `acks=0`：客户端不等待 Broker 确认，无法可靠感知写入失败；
- `acks=1`：Leader 本地接受后响应，不等待 Follower 达到确认条件；
- `acks=all`：Leader 等待当前同步副本条件满足后响应，是最强的可配置确认级别。

`acks=all` 必须结合 `min.insync.replicas`。它不等于 assignment 中所有副本都落盘，更不等于任意数量节点损坏都不丢。

## 11. `min.insync.replicas` 有什么作用？

**标准回答：**

它限制 `acks=all` 成功写入时所需的最小同步副本数量。RF=3、min ISR=2 时，ISR 有 2 或 3 个通常可继续满足写入；ISR 只剩 1 个时，严格写入会失败，选择牺牲故障期写可用性来保护复制安全。

**陷阱：**RF=3、min ISR=2 不等于可以同时随意坏 2 台还继续写。坏 2 台后只剩一份，无法满足 min ISR=2。

## 12. Kafka 为什么吞吐高？

**标准回答：**

不能只回答“顺序写 + 零拷贝”。完整原因包括：

1. Partition 日志顺序追加，减少随机写；
2. Producer、网络请求、磁盘和复制均以 RecordBatch 为单位摊薄固定成本；
3. batch 压缩降低网络与磁盘字节；
4. 大量利用操作系统页缓存；
5. Fetch 文件记录的适用路径可使用 `transferTo`/sendfile 风格减少复制；
6. Partition 提供跨 Broker 和 Consumer 的水平并行；
7. 长轮询与 delayed operation 避免空转和线程阻塞。

同时要说边界：TLS、格式转换、远程存储等路径不一定能完整使用零拷贝；磁盘、网络、CPU、热点 Partition 都可能成为瓶颈。

## 13. Kafka 的网络线程模型是什么？

**标准回答：**

典型模型是 Acceptor 接受连接，多个 Processor/Selector 负责非阻塞网络读写，请求进入 RequestChannel，再由 KafkaRequestHandler 线程执行业务逻辑，KafkaApis 按 ApiKey 分派。

等待 Follower、Fetch 长轮询或配额时，使用 DelayedOperation/Purgatory 注册条件，而不是占住 handler 线程睡眠。响应完成后进入响应队列，由 Processor 写回客户端。

关联：[08 Broker 网络层](08_Broker网络层与请求处理流水线.md)

## 14. Segment 和稀疏索引如何工作？

**标准回答：**

Partition 按大小、时间或索引容量等条件滚动为 Segment。每个 Segment 以 base offset 命名，`.log` 存 RecordBatch，offset index 保存相对 offset 到物理位置的稀疏映射，time index 保存时间到近似 offset 的映射。

查 offset 时先选 Segment，再在稀疏索引二分找到不大于目标的最近位置，最后顺序扫描少量 Batch。稀疏索引降低索引大小，扫描距离由索引间隔约束。

## 15. 页缓存和刷盘如何理解？

**标准回答：**

Kafka 日志写入通常先进入操作系统页缓存，后台按系统策略刷盘。Kafka 的持久性主要依靠多副本复制协议，而非每条消息对所有磁盘同步 `fsync`。

所以要区分 Leader 已接收、进入本地日志/页缓存、多副本已确认、物理介质稳定写入。`acks=all` 表达复制确认语义，不能直接翻译成“所有磁盘已刷盘”。

## 16. Log Retention 和 Log Compaction 有什么区别？

**标准回答：**

Retention delete 按时间或大小以 Segment 为粒度清理旧日志，关注“保留多久/多大”；Compaction 按 key 最终保留最新值，关注“每个 key 的最新状态”。

Compaction 是后台渐进过程，不保证旧值立即消失。null value 常作为 tombstone 表示删除，tombstone 也有保留窗口。Compacted Topic 不是数据库唯一索引或实时 KV 查询系统。

## 17. Kafka 的零拷贝是什么？

**标准回答：**

在适用的文件记录 Fetch 路径中，Broker 可利用文件通道 `transferTo`/sendfile，让页缓存数据更直接地进入 Socket，减少用户态复制和上下文切换。

不要回答“Kafka 全链路零拷贝”。Producer 写入、协议解析、压缩校验、TLS 加密、格式转换和远程存储可能仍需进入用户态或发生复制。

## 18. Follower 为什么采用拉取而不是 Leader 推送？

**标准回答：**

Follower 主动 Fetch 可以复用读取协议，自主控制复制批量和节奏，Leader 不必为每个 Follower 维护复杂推送流控。Follower 在请求中携带自身 offset/epoch，Leader 返回后续 Batch 和水位信息。

代价是 Leader 对 Follower 已追加进度的认识存在交互时延，需要从后续 Fetch 等信息推进副本状态和 HW。

## 19. Leader Epoch 解决什么问题？

**标准回答：**

只比较 offset 不能区分不同 Leader 任期产生的分叉日志。Leader Epoch 记录各任期与日志边界，旧 Leader 恢复后通过 epoch 找共同前缀，必要时截断未提交尾部，再复制当前 Leader。

“本地日志更长”不代表“更正确”。正确性由任期和已提交前缀共同决定。

## 20. 为什么不能手工删除损坏副本的某个 `.log` 文件？

**标准回答：**

日志与 offset/time/transaction index、Leader Epoch cache、ProducerStateManager、producer snapshot、HW/LSO 等状态相关。只删某个文件可能导致索引悬空、幂等序列错误或事务可见性破坏。

应让 Kafka 的副本恢复、日志目录故障处理和受控迁移机制完成修复，先保存证据并确认故障范围。

## 21. 60 秒总结模板

> Kafka 的核心是分区追加日志。Topic 通过 Partition 扩展并行度，Partition 内有序；每个 Partition 由 Leader/Follower 副本保护，ISR、HW、Leader Epoch 决定安全前缀与故障恢复。Producer 通过 Batch、压缩、异步 Sender 提高吞吐，可靠性由 acks、min ISR、重试和幂等共同决定；Consumer Group 以 Partition 为分配单元，offset 独立于数据保留。现代集群使用 KRaft 元数据日志管理控制面。任何“有序、不丢、Exactly-Once”都必须说明 Partition、会话、事务和外部系统边界。
