# Redis Stream 深度学习计划

## 学习目标

完成后应能独立回答并验证以下问题：

- 为什么 Stream 既不像 List，也不像 Pub/Sub？
- 一条记录从 `XADD` 到 listpack 的字节布局经历什么？
- `XREADGROUP >` 为什么会写数据，重复投递怎样产生？
- 消费者宕机后，谁拥有消息、怎样安全接管、如何避免双重副作用？
- 裁剪后 PEL 为什么可能仍存在，为什么读取 pending 可能得到空 payload？
- AOF、RDB、异步复制、Sentinel/Cluster failover 分别留下什么数据窗口？
- 如何由平均消息大小、保留时间、峰值速率、PEL 和 fork 内存计算容量？
- 哪些需求应切换到 Kafka 或 RabbitMQ，而不是继续堆 Redis 补丁？

## 四周路径

### 第一周：建立正确模型

阅读 01—05，完成：

1. 手工生成 `*`、`ms-*`、显式 ID，验证单 key ID 必须递增。
2. 比较 `XRANGE`、`XREAD`、`XREADGROUP` 的返回与状态变化。
3. 用 `XINFO STREAM FULL` 画出 stream、group、consumer、PEL 的关系。
4. 对照源码识别 rax 节点、listpack 宏节点和组状态不是同一个树。

验收标准：不看资料解释 `0`、`$`、`>` 的上下文差异；说明为什么业务时间不能直接当可靠排序依据。

### 第二周：消费可靠性

阅读 06—08、13，完成：

1. 制造“业务成功但未 ACK”和“ACK 后业务提交失败”两个窗口。
2. 用 `XPENDING` 观察 idle、delivery count、owner。
3. 用 `XAUTOCLAIM` 分页扫描长时间 idle 项并设计停止条件。
4. 裁剪仍处于 PEL 的条目，观察 pending 引用与消息体的差异。
5. 设计幂等表、重试计划流和死信流，证明不会无限热重试。

验收标准：能写出至少一次消费循环，并指出它仍无法保证跨 Redis 与数据库的 exactly-once。

### 第三周：持久化、高可用和 Cluster

阅读 09—12，完成：

1. 对比 `appendfsync always/everysec/no` 的故障丢失窗口和成本。
2. 让副本产生延迟，在主节点写入后强制切换，记录消息与组状态的变化。
3. 对 `XADD` 使用 `WAIT`，区分“副本已确认收到”与“故障切换一定选择该副本”。
4. 将不同 stream key 放入不同 slot，验证多 key 命令限制。
5. 按峰值流量做容量模型，并把 fork 时 Copy-on-Write 峰值纳入预算。

验收标准：能明确写出 RPO/RTO，而不是只说“Redis 有持久化和主从所以可靠”。

### 第四周：源码、压测与选型

阅读 14—18，完成：

1. 从命令表定位 `xaddCommand`、`xreadCommand`，追踪到 stream 操作函数。
2. 给阻塞消费和普通命令使用不同连接，验证连接池耗尽现象。
3. 做生产速率大于消费速率的阶梯压测，测量 lag、PEL、内存斜率。
4. 注入消费者停顿、慢数据库、网络闪断、主从切换和大批量 claim。
5. 对同一业务分别给出 Redis Stream、RabbitMQ、Kafka 的选型论证。

验收标准：能在白板上画完整的数据面、控制状态、持久化和故障恢复路径。

## 每章学习模板

不要只记结论。每个机制按六问学习：

1. **状态在哪里**：stream 主体、group、consumer、PEL、客户端还是外部数据库？
2. **谁修改状态**：命令是否只读，是否会传播到 AOF/副本？
3. **关键不变量**：ID 单调、owner 唯一、ACK 删除何种引用？
4. **复杂度与放大**：时间复杂度、内存放大、网络返回量、fork 影响？
5. **故障点**：命令前、执行中、响应丢失、业务提交前后、failover 后？
6. **如何证伪**：用什么命令、指标、源码或故障实验验证？

## 统一项目作业

实现订单事件处理器：

```text
producer -> orders:{tenant} -> payment-workers -> payment DB
                                  | failure
                                  v
                            retry schedule stream
                                  | exceeded
                                  v
                               DLQ stream
```

要求：

- `event_id` 全局业务唯一；Stream ID 只做日志位置。
- 数据库中以 `event_id` 建唯一约束并在同一事务记录处理结果。
- 正常消费者只读新消息；恢复器专门扫描 idle PEL。
- 重试有指数退避、上限、抖动和死信原因。
- 生产者记录写入不确定状态，不能因超时盲目生成新事件 ID。
- 监控入口速率、完成速率、oldest pending idle、lag、内存和 failover。

## 学习误区

- “单线程”等于端到端顺序：多消费者和外部副作用会打破完成顺序。
- `XACK` 等于消息删除：ACK 只处理待确认状态。
- `MAXLEN ~ N` 等于严格 N 条：近似裁剪允许短暂超过阈值。
- `NOACK` 更快且一样可靠：它直接放弃服务端未确认跟踪。
- `WAIT 1` 等于零丢失：异步复制和故障选主仍有边界。
- lag 为 0 等于系统健康：PEL 可能很大，消费者可能拿到但未完成。
