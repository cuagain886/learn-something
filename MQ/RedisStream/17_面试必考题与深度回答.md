# Redis Stream 面试必考题与深度回答

## 1. Stream 与 Pub/Sub 最大区别？

Pub/Sub 只向在线订阅者推送，不保留历史、无确认和组消费恢复；Stream 保存按 ID 有序条目，可范围回放，并用 Consumer Group/PEL 跟踪待确认。深层差别是 Stream 有可持久化数据面和消费状态，代价是内存、保留、PEL 与故障治理。

## 2. Stream 底层为什么用 rax + listpack？

rax 按宏节点首 ID 做有序定位和前缀压缩，listpack 将一批相邻条目连续紧凑编码，并可复用 master entry 的 ID/字段信息。它在范围定位、缓存局部性和元数据开销间折中。不能误答“一条消息一个 rax 节点”。

## 3. ID 能保证全局顺序吗？

只能保证单 Stream key 内按 ID 有序。多 key/Cluster 分片无全局 ID；消费者并发也会让完成顺序变化。业务因果应使用 aggregate version，按实体分片或条件更新。

## 4. `XREADGROUP` 为什么是写命令？

读取 `>` 会推进 group last-delivered-id，并为消息创建 PEL、记录 owner/time/count；这些状态需复制和持久化。因此不能路由只读副本。

## 5. `>`、`$`、`0` 有何区别？

`>` 是组语境的“尚未交付给本组的新消息”；`$` 常表示调用/建组时流尾；非组 XREAD 的 ID 是严格大于该位置；XREADGROUP 的 `0` 等显式范围用于读取当前消费者 pending 历史。必须结合命令解释。

## 6. XACK 会删除消息吗？

不会。它删除该 group 的 PEL 引用，消息主体仍供 XRANGE、其他组和普通读者读取，直到 XDEL/XTRIM。较新版本有 ACK+删除/引用策略能力，但要检查版本。

## 7. PEL 如何实现故障恢复？

正常投递进入 PEL；XPENDING 观察 owner/idle/count；消费者恢复可读自己历史，永久离线实例的消息由 XCLAIM/XAUTOCLAIM 转移；完成后 XACK。claim 只转移服务端 owner，不能取消旧进程外部副作用，所以仍须幂等。

## 8. lag 为 0 为什么还可能严重积压？

lag 表示尚未交付的新条目，已经交付但未完成的消息在 PEL。last-delivered 到尾时 lag 可为 0，而 PEL 可能百万。需结合 PEL size、oldest idle、完成/ACK rate。

## 9. 如何实现 exactly-once？

Redis Stream 与外部 DB 没有共同原子事务。采用业务提交后 ACK会重复，反序会丢失。工程上用至少一次 + 稳定 event_id + DB 唯一键/同事务幂等记录 + 状态机版本，实现业务效果一次；外部 HTTP还需对方 idempotency key。

## 10. 为什么裁剪后 pending 可能还在？

payload 主体和各组 PEL 是独立索引。经典删除为避免扫描所有组，不必同步清 PEL，于是可能只剩 ID 引用，pending 读取 payload 为空。保留窗口需覆盖最慢组，恢复器要处理 payload missing，并检查新版本引用策略。

## 11. `MAXLEN ~` 为什么快？

近似裁剪可以优先删除完整 listpack 宏节点，避免为精确边界频繁重写节点，所以允许长度暂时超过阈值。它不是后台异步裁剪。

## 12. XDEL 后内存为什么没明显下降？

中间条目可能逻辑删除，待比例达到阈值才压缩；宏节点未整体释放；allocator 碎片和 RSS 不归还也会影响。应同时看 XLEN、MEMORY USAGE、used_memory/RSS，并比较头部裁剪。

## 13. WAIT 能保证消息不丢吗？

不能。WAIT 等副本确认复制到某偏移，缩小异步复制窗口；不保证 fsync，也不保证 failover 一定选择该副本，更不是多数派共识提交。`min-replicas-to-write` 同样是风险/可用性约束而非零丢失证明。

## 14. Redis Cluster 会自动分区一个 Stream 吗？

不会。一个 key 落一个 slot/主节点，需应用拆多个 Stream key。这样只保留分片内顺序，组和运维对象也随分片增长。hash tag 可共址但可能制造热点。

## 15. 为什么阻塞读取不阻塞 Redis 主线程？

无数据时 Redis 登记客户端及等待 key，暂停该客户端并返回事件循环；XADD 标记 key ready 后再唤醒检查。阻塞的是连接语义，但大量 blocked clients 仍消耗资源和唤醒成本。

## 16. 如何设计重试？

不要长期让失败消息停在 PEL等 claim。按错误分类；可重试写显式调度状态，用 ZSET/重试流表达 next-attempt，指数退避+jitter；永久错误或耗尽进入带上下文的 DLQ；先成功落重试/DLQ再 ACK 原消息，双写靠幂等/同槽脚本处理。

## 17. 如何做容量规划？

用峰值速率×保留窗口×真实每条内存成本，并加 PEL/组、碎片、复制/AOF缓冲、RDB/AOF fork COW和故障承载。还要计算 Rp>Rc 时积压斜率。若长保留海量数据导致数百 GiB 内存，应重新评估 Kafka。

## 18. 什么情况不应使用 Stream？

长期海量廉价磁盘保留、多分区高吞吐回放、强生态流处理通常选 Kafka；复杂路由、成熟延迟/TTL/DLX、队列隔离和 broker 投递功能常选 RabbitMQ；要求共识级已确认不丢也不应仅靠异步复制 Redis。Stream 适合已有 Redis 能力、低延迟、中等规模、内存可承受且愿意自己治理重试/幂等的场景。
