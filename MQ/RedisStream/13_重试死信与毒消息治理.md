# 重试、死信与毒消息治理

## 不要把 pending 当延迟队列

失败后一直不 ACK，等待 claim，会让 PEL 充当重试调度器：无法精确表达下次执行时间，反复扫描成本高，毒消息永久占 PEL，并与真正宕机恢复混淆。PEL 应表示“正在处理或异常中断”，计划重试应有显式状态。

## 推荐三流模型

```text
main stream --failure--> retry stream/sorted-set scheduler
     ^                         |
     | due and republish ------+
     +-- exhausted --> DLQ stream
```

Redis Stream 自身不按未来时间自动可见。延迟调度常用 ZSET：score=next_attempt_at，调度器原子领取到期项并 XADD 回重试/主流。也可使用时间桶 Stream，但要处理空桶、迟到和迁移。

## 失败分类

- 可重试：网络超时、限流、暂时不可用；指数退避 + jitter。
- 不可重试：schema 不支持、必填字段缺失、非法状态；直接 DLQ。
- 不确定：远端超时但可能成功；先用同一幂等键查询/重试，不能当普通失败。
- 系统性：数据库整体故障；启动全局熔断，避免每条消息制造重试风暴。

```text
delay = min(base × 2^attempt, maxDelay) × random(0.5, 1.5)
```

## 转移的双写窗口

“XADD retry/DLQ，然后 XACK 原消息”如果跨 slot/跨系统，不是原子操作：

- 新消息已写、ACK 失败：重复转移；靠 event_id + attempt 幂等。
- ACK 成功、新消息未写：丢失；所以绝不能先 ACK。

同 slot 可用 Lua/Function 原子 XADD+XACK，但脚本大小和跨槽限制需控制；外部调度仍要幂等。

## DLQ 不是垃圾桶

死信字段至少包括：原 stream/id、event_id、group、失败分类、异常摘要、attempt、首次/最近失败时间、payload/schema version、代码版本、trace ID。敏感数据需脱敏/加密。必须有告警、负责人、重放工具和保留策略。

重放不能简单把旧 payload 盲写回主流：先修复根因，验证 schema 兼容，以新 Stream ID 发布但保留 event_id/原始引用；消费幂等表需决定是跳过、补偿还是允许新的处理版本。

## 防止热循环

- claim min-idle 大于正常 P999。
- 单事件最大 attempt 和总重试时间上限。
- 指数退避和随机抖动。
- 按下游设置并发、令牌桶和 circuit breaker。
- 恢复器每轮 COUNT/CPU/时间预算。
- 高 delivery count、重复 event_id、DLQ rate 单独告警。

## Poison message 与 consumer crash

反序列化异常若发生在 ACK 前且每次都让进程退出，会形成 crash loop。读取后先做有界校验，捕获单消息异常并写 DLQ；OutOfMemory 等进程级问题仍会留下 PEL，由恢复器处理。最大 payload 要在 producer 和 consumer 双侧限制。
