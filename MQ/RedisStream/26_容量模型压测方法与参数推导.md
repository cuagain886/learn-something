# 容量模型、压测方法与参数推导

## 1. 目标不是得到一个 TPS 数字

完整容量结论至少包含：

```text
安全生产速率
安全完成速率
最大可恢复积压时间
主体内存与 PEL 内存
fork/rewrite 峰值
复制与 AOF 字节速率
主线程 P99/P999
故障切换后的降级容量
```

只测空 Stream 上 XADD QPS，会系统性高估生产能力。

## 2. 到达率与服务率

定义：

```text
λ = producer arrival rate
μ = consumer completion rate
ρ = λ / μ
```

当 `ρ < 1`，系统理论上可清空，但接近 1 时排队延迟对波动极敏感。

当 `ρ > 1`：

```text
backlog(t) = backlog(0) + (λ - μ) × t
```

示例：

```text
λ = 30,000/s
μ = 24,000/s
净积压 = 6,000/s
10 分钟新增 = 3,600,000 条
```

若每条真实内存 600B，仅主体就新增约 2.0GiB，尚未含 PEL。

## 3. 服务率必须用“完成”而非“领取”

XREADGROUP delivery rate 很高不代表 μ 很高。

正确 μ 是：

```text
成功业务提交 + 永久失败完成治理 + 可确认重试转移
```

若 worker 每秒领取 50k 但数据库只提交 10k，lag 会下降，PEL 以 40k/s 增长。

监控只看 lag 会得到相反结论。

## 4. 实测每条主体字节

准备真实 schema，先记录空流：

```redis
XADD bench * event_id warmup type test payload x
XDEL bench <id>
MEMORY USAGE bench SAMPLES 0
```

分阶段写 N 条，记录斜率：

```text
B_stream = (usage_N - usage_0) / N
```

至少测：

- 固定字段顺序。
- 字段顺序随机。
- 小/中/P99 payload。
- 不同 `stream-node-max-bytes/entries`。
- 有无随机 XDEL 墓碑。

不要用单个样本，因为 allocator 和宏节点创建是阶梯函数。

## 5. 实测每条 PEL 字节

同一 Stream 创建 group：

1. 记录没有 pending 的 MEMORY USAGE/used_memory。
2. XREADGROUP 领取 N 条不 ACK。
3. 记录增量。
4. 再增加第二个 group 重复。

```text
B_pel ≈ (memory_after_pending - memory_before) / N
```

单 key MEMORY USAGE 是否完整计入 group/PEL 依实现与命令统计，应同时看全实例 used_memory 差值，并保证无其他流量。

Redis 8.2 引用跟踪会改变成本，结果必须绑定版本。

## 6. 稳态内存公式

```text
M_stream = retention_entries × B_stream
M_pel    = inflight_entries × B_pel × group_factor
M_keys   = stream_count × per_key_overhead
M_base   = Redis process + modules + connections
M_steady = M_stream + M_pel + M_keys + M_base
```

再乘 allocator/碎片安全系数：

```text
M_rss_steady = M_steady × F_fragmentation
```

不要固定使用 1.2；从同类实例的 P95/P99 碎片实测。

## 7. 故障积压内存

下游完全停止 `T_outage`：

若消费者停止领取，增加主体 backlog。

若消费者仍领取但不能完成，同时增加 PEL。

最危险是无界预取：主体因裁剪保持近似恒定，PEL 元数据持续增长，且旧 payload 可能被裁剪。

```text
M_outage ≈ λ × T_outage × (B_stream + optional B_pel)
```

应在下游熔断时停止领取，控制 PEL 上限。

## 8. fork 峰值

定义 fork 持续 `T_fork`，期间脏页速率 `W_dirty bytes/s`：

```text
M_COW <= min(dataset_pages_touched, W_dirty × T_fork adjusted by page amplification)
```

小字段修改也会复制整页，故 page amplification 不能从业务 payload 直接计算。

压测时读取 `rdb_last_cow_size`、AOF rewrite COW 指标和 RSS 峰值。

机器安全内存需要：

```text
RAM > M_rss_steady + M_COW_p99 + replication_buffers + client_buffers + OS_reserve
```

## 9. AOF 磁盘模型

AOF 字节率不等于 payload 字节率。

包含命令名、key、字段名、RESP 长度和 group 状态传播。

实测：

```text
AOF_growth_rate = Δaof_current_size / Δtime
```

磁盘需同时承受：

- 正常 AOF append/fsync。
- rewrite 顺序写。
- RDB 写。
- 全量复制读取/写入。
- 备份上传。

压测要模拟并发而不是分别测峰值。

## 10. 网络模型

每条消息可能经历：

```text
producer -> primary
primary -> replicas × R
primary -> consumer groups × G
consumer ACK/claim/control
AOF/backup 不计网络或另计
```

粗略出口：

```text
Net_out ≈ λ × encoded_bytes × (replicas + active_groups)
```

多个独立 XREAD fan-out 会比组内竞争产生更多 payload 出口。

还需加入协议、TLS 和重传开销。

## 11. 批次大小推导

定义：

```text
L_net = 单次往返延迟
T_item = 单条业务平均处理时间
B = batch count
W = worker 数
```

批量读取摊薄 RTT，但实际完成能力受 worker 与下游限制。

约束：

```text
B <= worker_queue_free_capacity
B × payload_p99 <= response_byte_limit
batch_processing_p99 << claim_min_idle
```

从 16/32/64/128 做阶梯测试，而不是直接 COUNT 1000。

## 12. claim min-idle 推导

采集正常处理端到端分布：

```text
T_process = receive -> DB commit -> ACK attempt
```

建议起点：

```text
min_idle >= T_process_p999 + max_GC_pause + network_jitter + safety_margin
```

阈值太小：活消费者任务被误 claim，双执行增加。

阈值太大：真实宕机恢复慢。

长任务应续租/拆分或使用外部 fencing，不应把统一阈值无限放大。

## 13. retention 推导

按时间恢复目标：

```text
T_retention >= detection_time
             + operator_response
             + downstream_repair
             + backlog_replay
             + safety_margin
```

转换 MAXLEN：

```text
N = λ_peak × T_retention × burst_factor
```

还要加入近似裁剪宏节点误差，但那通常是小项；真正的大项是峰值持续时间和最慢 group。

## 14. replay 时间

故障积压 `Q`，恢复后总完成能力 `μ_recovery`，生产仍以 λ 到达：

```text
T_replay = Q / (μ_recovery - λ)
```

只有 `μ_recovery > λ` 才能追平。

例如 Q=10M，恢复能力 40k/s，正常到达 30k/s：

```text
净清理 10k/s
需要 1000s ≈ 16.7min
```

若容量规划只让 μ=λ，故障后永远无法清 backlog。

## 15. Cluster 分片数

单分片安全吞吐以最坏组合压测得 `C_shard`。

```text
shards >= ceil(λ_peak / (C_shard × target_utilization))
```

target utilization 不应为 100%，需留 failover 和 replay 余量。

N 个主平均分布，单主故障后副本晋升不会自动让其他主分担该 slot；但节点资源和故障域仍要能承接晋升负载。

## 16. 压测阶段

1. 单命令微基准：了解编码和节点参数。
2. 完整链路稳态：producer + groups + DB stub。
3. 真实下游：测 completion rate。
4. 阶梯升压：找到延迟拐点而非直到宕机。
5. 下游降速：验证 lag/PEL 和背压。
6. fork/rewrite：验证 COW、磁盘和 P99。
7. 副本全量同步：验证网络/CPU。
8. failover：验证重连、重复和降级容量。
9. 长稳压：观察碎片、AOF增长和泄漏。

## 17. 延迟拐点判定

当负载增加 10%，P99 增加数倍而吞吐几乎不再增加，系统进入饱和排队区。

瓶颈可能是：

- Redis 单主 CPU。
- 网络带宽。
- AOF fsync。
- consumer worker。
- 数据库连接池。
- client output buffer。

必须用资源指标相关性定位，不能把所有超时归因 Redis。

## 18. 告警阈值从耗尽时间反推

剩余内存 `M_free`，积压内存增长率 `g bytes/s`：

```text
time_to_exhaust = M_free / g
```

告警应基于耗尽时间：

- 60 分钟：warning，自动降速。
- 30 分钟：critical，停止非关键生产/领取。
- 15 分钟：执行预案。

固定“内存 80%”无法区分缓慢稳定与每分钟增长 5%。

## 19. 测试报告最小字段

```text
Redis/客户端/OS版本
CPU、内存、磁盘、网络
持久化与复制配置
stream node 配置
消息大小分布与字段 schema
组数、consumer 数、inflight
生产/领取/完成/ACK rate
lag、PEL、oldest idle
P50/P95/P99/P999
RSS、COW、AOF、复制字节
错误、超时、重连、重复数
```

缺少配置与数据分布的 TPS 不能复用到生产。

## 20. 最终容量结论模板

> 在 Redis X、固定字段 schema、payload P99 Y、AOF everysec、一个副本和 G 个消费组下，单分片在 CPU 不超过 60%、P99 不超过 Z ms 时安全完成速率为 C。保留 T 小时与最大 PEL P 条占用 M GiB；rewrite COW P99 为 K GiB；预留故障恢复后 30% 追赶能力。超过该边界进行分片或迁移专用日志系统。
