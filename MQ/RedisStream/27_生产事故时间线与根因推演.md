# 生产事故时间线与根因推演

## 1. 事故背景

订单事件使用：

```text
stream = orders:{00..15}
group = payment-workers
MAXLEN ~ 1,800,000
正常生产 = 15,000/s
消费者领取 = 18,000/s
数据库完成 = 16,000/s
claim min-idle = 60s
AOF everysec + 1 replica
```

团队认为 180 万条可以保留“两分钟”。

这个假设只在 15k/s 且没有突发时成立。

## 2. T-30 分钟：被忽略的前兆

数据库 P99 从 40ms 升到 800ms。

worker 仍继续 XREADGROUP，大批消息进入本地队列。

指标：

```text
group lag: 下降
PEL: 快速上升
oldest pending idle: 上升
DB pool wait: 上升
Redis memory: 缓慢上升
```

监控只告警 lag，因此显示“消费追平”。

第一层根因：把 delivery 当 completion。

## 3. T-10 分钟：误 claim 开始

单批消息在本地队列等待超过 60 秒。

恢复器认为 consumer 死亡，XAUTOCLAIM 给其他实例。

旧实例并未宕机，只是排队。

同一 event_id 被两个 worker 并发调用支付接口。

部分第三方接口支持幂等，部分旧接口不支持。

第二层根因：prefetch 无界且 min-idle 小于排队+处理 P999。

## 4. T0：数据库短暂不可用

数据库完全拒绝连接 6 分钟。

消费者异常处理采用：

```text
catch -> 不 ACK -> 立即下一轮读取
```

结果：

- 新消息继续进入 PEL。
- 恢复器继续 claim。
- delivery count 快速增长。
- Redis CPU 被读取、claim 和异常日志占用。
- 没有熔断停止领取。

第三层根因：把 PEL 当重试调度器。

## 5. T+2 分钟：Stream 开始裁掉 pending payload

生产突增到 25k/s。

180 万 MAXLEN 实际只覆盖约 72 秒。

默认 KEEPREF 近似裁剪删除旧宏节点，但保留各组 PEL。

于是：

```text
XPENDING: ID 仍存在
XRANGE ID ID: 无 payload
XAUTOCLAIM: 返回 dangling/deleted ID（依版本）
```

第四层根因：保留按正常平均速率设计，没有覆盖故障发现+修复+回放。

## 6. T+4 分钟：错误的扩容

值班人员把 consumer 从 20 扩到 100。

数据库仍不可用。

更多实例意味着：

- 更多阻塞连接。
- 更多领取和 PEL。
- 更多 claim 竞争。
- 更多 DB 重连风暴。
- 更多日志和 CPU。

吞吐没有增加，恢复反而更慢。

扩 consumer 只有在下游有余量且瓶颈在 consumer CPU 时有效。

## 7. T+6 分钟：主节点延迟尖刺

此时触发 AOF rewrite。

高写入、PEL 修改和 listpack裁剪导致 COW 增长。

磁盘同时承担：

- AOF append/fsync。
- rewrite 顺序写。
- 副本同步。

Redis P99 从 2ms 升到 300ms。

producer 超时但 XADD 部分已执行。

producer 每次重试生成新 event_id。

第五层根因：生产重试不保持业务幂等键。

## 8. T+7 分钟：触发主从切换

健康检查因延迟判定主不可用，Sentinel 晋升副本。

副本落后一小段复制流。

可能出现：

- 少量最近 XADD 消失。
- 某些 XACK 回退，已完成消息重新 pending。
- 某些 claim 回退，owner 回旧 consumer。
- 阻塞连接全部重建。

新实例启动只读取 `>`，没有先恢复 pending。

第六层根因：把 failover 当纯连接切换，没有处理消费状态回退。

## 9. T+10 分钟：数据库恢复

100 个 consumer 同时重连数据库并开始处理。

形成恢复洪峰：

```text
正常新流量 25k/s
历史 PEL 重做
producer 重复事件
claim 双执行
数据库缓存冷启动
```

数据库再次被打满。

这叫 recovery storm。

需要限速恢复，使：

```text
normal traffic + replay traffic < downstream safe capacity
```

## 10. 用户表象

- 部分订单重复扣款。
- 部分订单事件缺失。
- 一批订单长时间卡处理中。
- DLQ 没有记录 payload missing。
- Redis XLEN 看起来稳定。
- group lag 一度为 0。

稳定 XLEN 是 MAXLEN 在持续裁剪，不代表没有积压。

lag 为 0 是消息都被领取，不代表完成。

## 11. 证据收集

需要冻结而不是立即 destroy group：

```text
XINFO STREAM FULL
XINFO GROUPS
XINFO CONSUMERS
XPENDING 摘要及分页样本
Stream first/last entry
Redis INFO memory/persistence/replication/clients
SLOWLOG/LATENCY
Sentinel 切换时间线
AOF rewrite 与 COW 指标
producer timeout/retry event_id
DB 幂等表和第三方请求日志
```

销毁 group 会删除关键 PEL 证据。

## 12. 区分三类重复

### Producer 重复

同一业务事实拥有不同 event_id/Stream ID。

原因：超时重试生成新 event_id。

### Delivery 重复

同一 event_id、同一或重新发布的 Stream ID 被多次投递。

原因：ACK 丢失、claim、failover 状态回退。

### Business duplicate

外部系统发生两次不可逆副作用。

原因：没有以 event_id 使用幂等键或状态机条件。

三类重复的修复层不同。

## 13. 区分三类缺失

### Stream payload 缺失

PEL ID 仍有，但 entry 被裁剪。

### Redis failover 缺失

旧主确认的 XADD 未复制到新主。

### 业务处理缺失

错误地先 XACK 后 DB commit，或异常被吞并 ACK。

必须用 outbox、Stream、PEL、幂等表四方 event_id 对账。

## 14. 立即止血顺序

1. 停止继续无界领取，保留证据。
2. producer 对非关键流量限速；关键事件写 outbox。
3. 关闭激进恢复器，避免反复 claim。
4. 对数据库连接做全局限流与熔断。
5. 将已确认 payload missing 写审计清单。
6. 以固定速率恢复可读 PEL，业务幂等后 ACK。
7. 从 outbox/数据库重建丢失 payload。
8. 单独处理不支持幂等的第三方重复副作用。

不要先扩大 MAXLEN：内存已接近上限时会加速 OOM。

## 15. 正确恢复器

恢复器分三类队列：

```text
已在幂等表完成 -> 只补 ACK
payload 可用未完成 -> 限速处理，提交后 ACK
payload 缺失 -> 从事实库重建或进入人工审计
```

delivery count 高不直接 ACK。

必须先有可审计的最终去向。

## 16. 架构整改

### Producer

- 业务事务写 outbox。
- event_id 首次生成后永久复用。
- relay 重试不创造新事件。
- Redis 写结果不确定时对账。

### Consumer

- DB 唯一键幂等。
- 有界 worker queue 和 prefetch。
- DB 熔断时停止领取。
- 正常消费与 PEL recovery 分离。
- min-idle 基于 P999 推导。

### Retention

- 按峰值和恢复窗口计算。
- 监控 oldest readable age。
- 多组分别定义 SLA。
- 使用目标版本引用策略并实验。

### High Availability

- 明确异步复制 RPO。
- 关键写可选 WAIT，但不宣传零丢失。
- failover 后执行 group/PEL 审计。
- 定期故障演练。

## 17. 监控整改

必须同时展示：

```text
producer rate
delivery rate
business completion rate
ACK rate
group lag
PEL size
oldest pending idle
oldest readable age
claim rate
payload-missing count
duplicate-event count
DB pool wait/P99
Redis COW/AOF/replication lag
```

建立速率关系告警：

```text
delivery - completion 持续为正 -> PEL增长
producer - completion 持续为正 -> 总未完成增长
retention age < estimated recovery time -> 数据风险
```

## 18. 容量整改

正常峰值 25k/s，目标覆盖：

```text
故障发现 2min
修复 10min
回放 15min
安全余量 10min
总计 37min
```

仅条目数：

```text
25,000 × 2,220s = 55,500,000 条
```

若每条 600B，主体约 31GiB，单副本翻倍且未含 PEL/COW。

这个结果可能直接证明应迁 Kafka，而不是把 MAXLEN 调到 5550 万。

容量计算也是选型工具。

## 19. 为什么单元测试没发现

单元测试通常：

- 单 consumer。
- 无真实 DB 延迟。
- 无 fork/rewrite。
- 无复制延迟与切换。
- 消息少于 MAXLEN。
- 没有响应丢失。

需要组合故障测试：

```text
下游变慢 + 无界预取
裁剪 + pending
rewrite + 高写入
producer timeout + 重试
claim + 长 GC
DB commit + ACK丢失
failover + PEL恢复
```

可靠性问题通常出现在机制交叉处。

## 20. 复盘结论模板

不要写“Redis 性能不足”。

应写：

> 数据库降速后消费者仍以高于完成能力的速率领取，导致 PEL 增长；60 秒 claim 阈值低于本地排队时间，引发双执行；MAXLEN 仅覆盖 72 秒峰值，KEEPREF 裁剪形成悬空 PEL；rewrite COW/磁盘竞争放大延迟，producer 超时重试又更换 event_id；随后异步复制切换回退 ACK/claim 状态。缺少 DB 幂等的旧接口最终产生重复副作用。

这个结论指出每个因果环节和相应整改，不把所有现象归因于单一组件。
