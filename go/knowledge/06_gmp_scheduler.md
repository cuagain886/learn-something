# 06 · GMP 调度模型 ⭐⭐⭐

> 这是大厂面试**区分度最高**的题目。"goroutine 那么轻量，几百万个怎么调度的？"——答案就是 GMP。能把 G/M/P 三者关系、调度流程、work-stealing、抢占讲清楚，深度就出来了。

---

## 1. 为什么需要 GMP？

**goroutine vs 线程**：
| | OS 线程 | goroutine |
|---|---------|-----------|
| 栈大小 | 固定，约 1-8MB | 初始 **2KB**，按需增长/收缩 |
| 创建/切换 | 内核态，开销大（μs 级） | 用户态，开销极小（ns 级） |
| 调度者 | 操作系统内核 | Go 运行时（用户态调度器） |
| 数量级 | 几千个就吃力 | 轻松上百万 |

**核心思想**：把 M 个 goroutine 映射到 N 个 OS 线程上（**M:N 调度**），在用户态自己调度，避免频繁陷入内核。GMP 就是实现这个映射的模型。

---

## 2. G、M、P 三者是什么 ⭐

```
G (Goroutine)  ── 你 go 出来的那个任务，含栈、程序计数器、状态
M (Machine)    ── OS 线程，真正执行代码的实体
P (Processor)  ── 逻辑处理器/调度上下文，是 G 和 M 之间的"中介"
                  数量 = GOMAXPROCS（默认 = CPU 核数）
```

- **G**：一个 goroutine。结构体 `g`，保存执行栈、状态（运行/就绪/阻塞）、现场。
- **M**：内核线程，是干活的"工人"。M 必须**绑定一个 P** 才能执行 G。
- **P**：**调度的关键**。P 持有一个**本地可运行 G 队列**（runnext + 长度 256 的环形队列）。P 的数量限制了**同时并行**执行 Go 代码的 goroutine 数量。

```
        ┌─────────────────────────────────────────┐
        │  全局队列 GRQ（所有 P 共享，需加锁）       │
        │  [G][G][G]...                            │
        └─────────────────────────────────────────┘
              ▲ 偷                   ▲ 偷
   ┌──────────┴──────┐   ┌──────────┴──────┐
   │ P0              │   │ P1              │
   │ 本地队列LRQ:     │   │ 本地队列LRQ:     │
   │ [G][G][G]       │   │ [G][G]          │
   └────────┬────────┘   └────────┬────────┘
            │ 绑定               │ 绑定
        ┌───▼───┐           ┌────▼──┐
        │  M0   │           │  M1   │  ← OS 线程，在 CPU 上跑
        └───────┘           └───────┘
```

**为什么要 P 这一层？**（早期 Go 只有 G-M，没有 P）
- 没有 P 时，所有 M 共享一个全局队列，每次取 G 都要抢全局锁——锁竞争严重。
- 引入 P 后，每个 P 有**本地队列**，M 优先从绑定的 P 的本地队列取 G，**无锁**，大幅降低竞争。
- P 还实现了 work-stealing 的负载均衡。

---

## 3. 调度流程：一个 G 是怎么被执行的 ⭐

**`go func()` 发生了什么**：
1. 创建一个 G，优先放入当前 P 的本地队列（`runnext` 槽优先，实现"刚创建的优先执行"的局部性）。
2. 本地队列满了（256 个），就把一半 G 移到全局队列。

**M 找 G 执行的顺序**（`schedule()` 函数）：
```
1. 偶尔（1/61 概率）先看全局队列   ← 防止全局队列饥饿
2. 从绑定 P 的本地队列取 G         ← 主路径，无锁
3. 本地空了 → 从全局队列取一批
4. 还没有 → work-stealing：随机选一个其他 P，偷走它一半的 G ★
5. 实在没有 → M 解绑 P，进入休眠（park），等待新任务唤醒
```

### work-stealing（工作窃取）⭐

当一个 P 的本地队列空了，它不会闲着，而是**随机挑一个其他 P，偷走对方本地队列里一半的 G** 来执行。这保证了负载均衡——忙的 P 的任务会被闲的 P 分担。

## 4. 阻塞处理：hand-off 机制 ⭐（高频考点）

**关键问题**：一个 G 阻塞了，会不会把整个 M（线程）和 P 都堵死，导致其他 G 没法跑？

分两种阻塞：

### ① 系统调用阻塞（如文件 IO、CGO）

```
G 执行 syscall 陷入内核 → M 被内核阻塞
   ↓ runtime 检测到（sysmon 监控线程）
P 与该 M 解绑（hand-off），P 带着剩下的 G 去找/创建另一个 M 继续跑
   ↓ syscall 返回
原 M 尝试重新获取一个 P 继续执行；抢不到 P 就把 G 放回队列，M 休眠
```

**这就是 hand-off**：P 不会被阻塞的 M 拖累，及时转移到其他 M 上，保证 P 的本地队列继续被消费。这也解释了为什么**阻塞的系统调用会导致 M（线程）数量增加**。

### ② channel/mutex/网络 IO 阻塞

- **channel/mutex**：G 被挂起（gopark），M **不阻塞**，立即去执行 P 队列里的下一个 G。等条件满足，G 被重新放回就绪队列。这是纯用户态切换，极快。
- **网络 IO**：Go 用 **netpoller**（基于 epoll/kqueue/IOCP）。G 发起网络读写若未就绪，被挂起，M 继续跑别的 G；数据就绪时 netpoller 唤醒对应 G。**所以 Go 里写"同步阻塞"风格的网络代码，底层其实是高效的异步 IO**——这是 Go 高并发网络服务的基石。

## 5. 抢占式调度 ⭐（版本演进重点）

**问题**：一个 G 如果是死循环不让出 CPU，会不会饿死同 P 的其他 G？

| 版本 | 抢占方式 | 局限 |
|------|---------|------|
| ≤1.13 | **协作式抢占**：只在函数调用时检查抢占标志 | ⚠️ 死循环里没有函数调用 → 无法被抢占，卡死调度器 |
| **1.14+** | **基于信号的异步抢占** | 解决了死循环问题 |

**1.14 的异步抢占**：监控线程 `sysmon` 发现某个 G 运行超过 **10ms**，给它所在的 M 发送 `SIGURG` 信号，M 收到信号中断当前 G，保存现场并让出，G 被放回队列。这样即使纯计算死循环也能被打断。

```go
// Go 1.13 及之前，这段代码会卡死整个程序（如果 GOMAXPROCS=1）
// Go 1.14+ 能正常被抢占
func main() {
    runtime.GOMAXPROCS(1)
    go func() { for {} }() // 死循环
    time.Sleep(time.Millisecond)
    fmt.Println("1.14+ 能打印出来，1.13 会卡死")
}
```

**sysmon（监控线程）** 还负责：定时触发 GC、抢占长时间运行的 G、回收长时间休眠的 M、netpoll 检查。它是个不绑定 P 的特殊 M，独立循环运行。

## 6. GOMAXPROCS ⭐

```go
runtime.GOMAXPROCS(0)   // 返回当前值（不修改）
n := runtime.NumCPU()   // CPU 核数
```

- 决定 **P 的数量** = 同时并行执行 Go 代码的最大线程数。
- 默认 = CPU 核数（Go 1.5 起）。
- **CPU 密集型**：设为核数最优（默认即可）。
- **IO 密集型**：goroutine 多在等 IO，P 数影响不大。
- ⚠️ **容器环境的坑**：容器限制了 CPU（如 limit 2 核），但 `runtime.NumCPU()` 可能读到宿主机的核数（如 64），导致 P 过多、调度开销大、GC 频繁。
  - **解决**：用 `uber-go/automaxprocs` 库自动读取 cgroup 限制设置 GOMAXPROCS。**Go 1.25 起运行时已原生感知 cgroup CPU 配额**，缓解了这个问题。这是个很好的实战加分点。

## 7. G 的状态流转（了解即可）

```
_Gidle → _Grunnable（在队列等待） → _Grunning（执行中）
              ▲                          │
              │                          ▼
         _Gwaiting（阻塞，如等 channel）←┘
              │
              ▼
         _Gdead（执行完，可复用）
```

G 执行完不会立即销毁，会被放进 P 的 `gFree` 列表**复用**，减少创建开销。

## 8. 面试速答清单

| 问题 | 一句话答案 |
|------|-----------|
| GMP 各是什么？ | G=goroutine任务，M=OS线程，P=调度上下文(持本地队列)，数量=GOMAXPROCS |
| 为什么要 P？ | 给每个 M 提供本地无锁队列，降低全局锁竞争 + 实现 work-stealing |
| G 怎么被调度？ | M 优先取 P 本地队列(无锁) → 全局队列 → 偷其他 P 一半 → 休眠 |
| 系统调用阻塞？ | hand-off：P 与阻塞 M 解绑，转移到新 M 继续跑，所以线程数会涨 |
| channel 阻塞？ | G 挂起，M 不阻塞继续跑别的 G（纯用户态切换） |
| 网络 IO？ | netpoller(epoll)，同步代码异步执行，G 挂起 M 不堵 |
| 死循环会卡死吗？ | 1.14+ 基于信号异步抢占(>10ms)，不会；1.13 协作式会卡死 |
| GOMAXPROCS 容器坑？ | NumCPU 读宿主机核数→P 过多；用 automaxprocs 或 Go1.25+ 原生感知 cgroup |
