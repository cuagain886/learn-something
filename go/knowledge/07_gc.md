# 07 · GC 垃圾回收 ⭐⭐⭐

> "Go 的 GC 怎么做到低延迟的？"是大厂高频题。核心三件套：**三色标记法 + 混合写屏障 + 并发标记**。讲清这三个，再补 STW 时机和调优，就很完整了。

---

## 1. Go GC 的演进与定位

Go 的 GC 是 **并发的、非分代的、非压缩的、基于三色标记的标记-清除（mark-sweep）** 收集器。

**核心目标：低延迟（低 STW）**，而非最高吞吐。演进史：

| 版本 | 里程碑 | STW 时间 |
|------|--------|---------|
| 1.3 | 标记-清除，全程 STW | 百 ms 级 |
| 1.5 | 并发标记清除，三色标记 | 降到 ~10ms |
| 1.8 | **混合写屏障**，几乎消除 STW | **< 1ms** ⭐ |
| 1.12+ | 持续优化 | 通常几十~几百 μs |

> 现在 Go 的 STW 通常在**亚毫秒级**，这是 Go 适合做延迟敏感服务的关键。

---

## 2. 三色标记法 ⭐（核心算法）

把所有对象分成三种颜色：

```
⚪ 白色：未被标记 = 垃圾候选。GC 结束时还是白的 → 回收
🔘 灰色：已标记，但它引用的对象还没扫描完 = 待处理队列
⚫ 黑色：已标记，且引用的对象也都扫描过了 = 存活，安全
```

**标记流程**：
```
1. 初始：所有对象白色
2. 把 GC Root（全局变量、各 goroutine 栈上的变量）标记为灰色，入队
3. 循环：从灰色队列取一个对象 →
     - 把它引用的所有白色对象标灰、入队
     - 把它自己标黑
4. 灰色队列空了 → 标记结束
5. 清除：所有还是白色的对象 = 不可达 = 回收
```

```
Root ─▶ A ─▶ B ─▶ C        D（孤立，无人引用）
扫描后：A⚫ B⚫ C⚫           D⚪ → 被回收
```

**为什么用灰色这个中间态？** 为了支持**并发标记**——GC 和用户程序同时跑，灰色队列让标记过程可以**暂停和恢复**，不必一次性扫完。

---

## 3. 并发标记的难题与写屏障 ⭐⭐（最难也最区分度的点）

### 问题：并发标记时对象引用在变

GC 标记的同时，用户程序（mutator）还在改对象引用。可能发生**对象丢失**：一个存活对象被错误回收。

**触发条件（Wilson 条件，两个同时满足才会漏标）**：
1. 一个**黑色**对象引用了一个**白色**对象。
2. 那个白色对象与**灰色**对象之间的引用被删除了。

```
扫描前：灰B ─▶ 白C        黑A
用户操作：黑A ─▶ 白C（黑引用白）   且   灰B 删除 ─▶ 白C 的引用
结果：C 没有任何灰色对象引用它了，而黑色 A 已扫描完不会再看它
     → C 被当垃圾回收，但 A 还在用它！❌ 悬空指针
```

### 解决：写屏障（Write Barrier）

写屏障是编译器插入的一小段代码，在**指针赋值时**触发，维护标记的正确性。Go 1.8 用的是**混合写屏障（Hybrid Write Barrier）= Dijkstra 插入屏障 + Yuasa 删除屏障**：

**规则（简化记忆）**：
1. 把**被删除**的旧引用对象标灰（删除屏障，Yuasa）。
2. 把**新写入**的引用对象标灰（插入屏障，Dijkstra）。
3. 栈上对象在标记开始时一次性扫描，标记期间**栈不加屏障**（性能关键）。

**效果**：保证不会漏标存活对象（宁可多标——"浮动垃圾"留到下轮回收，也不能漏标）。这就是所谓 **强/弱三色不变性** 的维护。

> 面试能说出"混合写屏障 = 插入屏障 + 删除屏障，避免了重新扫描栈，把 STW 降到亚毫秒"，就是高水平回答。

## 4. GC 完整流程与 STW 时机 ⭐

Go GC 一轮的阶段，现在**只有两次极短的 STW**：

```
1. Sweep Termination（清扫终止）   ── STW① 极短：完成上轮清扫
2. Mark（并发标记）               ── 与用户程序并发！开启写屏障
       ↑ 占绝大部分时间，但不停顿用户程序
3. Mark Termination（标记终止）    ── STW② 极短：关闭写屏障，统计
4. Sweep（并发清扫）              ── 与用户程序并发，按需回收白色对象
```

**两次 STW 都极短（μs~亚 ms 级）**，最耗时的标记和清扫都和用户程序并发执行。这是 Go 低延迟的核心。

**辅助标记（Mark Assist）**：如果用户程序分配内存太快、标记跟不上，分配内存的那个 goroutine 会被"拉壮丁"帮忙做一部分标记工作（按分配量比例），防止 GC 落后。这保证了 GC 不会无限拖延。

## 5. GC 触发时机 ⭐

三种触发方式：

1. **内存增长触发（主要）**：由 `GOGC` 控制。默认 `GOGC=100`，表示**当堆内存增长到上次 GC 后存活对象的 2 倍时**触发。
   ```
   下次触发堆大小 = 上次存活 × (1 + GOGC/100)
   GOGC=100 → 2 倍；GOGC=200 → 3 倍（GC 更少，内存更高）
   ```
2. **定时触发**：`forcegcperiod`，超过 **2 分钟**没 GC 强制触发一次。
3. **手动触发**：`runtime.GC()`（一般不用，测试/特殊场景才用）。

## 6. GC 调优 ⭐（实战加分）

### GOGC：吞吐 vs 内存的权衡

```bash
GOGC=100  # 默认，平衡
GOGC=200  # 内存翻倍，GC 频率减半 → 省 CPU，费内存（吞吐优先）
GOGC=50   # GC 更勤，内存占用低 → 省内存，费 CPU
GOGC=off  # 关闭 GC（危险，仅特殊批处理场景）
```

### GOMEMLIMIT（Go 1.19+）⭐ 重要新特性

设置**软内存上限**，接近上限时 GC 更激进，防止 OOM：
```bash
GOMEMLIMIT=4GiB   # 软上限 4GB
```
- 解决了 GOGC 在内存尖峰时不够灵敏导致 OOM 的问题。
- **最佳实践**：容器里设 `GOMEMLIMIT` ≈ 容器内存 limit 的 90%，配合 `GOGC` 使用。这是当前生产环境 Go 内存调优的标准做法。

### 观察 GC 行为

```bash
GODEBUG=gctrace=1 go run main.go
# 输出每次 GC：
# gc 1 @0.012s 2%: 0.018+1.3+0.005 ms clock, ... 4->4->1 MB, 5 MB goal
#                  ↑两次STW+并发标记耗时    ↑堆大小变化  ↑下次目标
```

### 减少 GC 压力的代码技巧

1. **减少堆分配**（见 [08 逃逸分析](08_memory_alloc_escape.md)）：能栈分配就别逃逸。
2. **复用对象**：`sync.Pool` 缓存临时对象（见 [09](09_sync_primitives.md)）。
3. **预分配**：`make([]T, 0, n)` 一次到位，避免多次扩容产生垃圾。
4. **减少指针**：`[]int` 比 `[]*int` 对 GC 友好——GC 不用扫描无指针对象。值类型数组扫描更快。

## 7. 为什么 Go 不用分代 GC？

面试有时会问。Go 选择**非分代**的原因：
- 分代 GC 基于"大部分对象朝生夕死"的假设，需要维护代际、记忆集（remembered set），复杂。
- Go 的**逃逸分析**已经把大量短命对象留在了**栈上**（栈对象不归 GC 管，函数返回即释放）——相当于在编译期就做掉了"年轻代"的活。
- 所以堆上剩下的对象生命周期相对均匀，分代收益不大。这是 Go "编译期逃逸分析 + 运行期并发 GC" 的组合拳。

## 8. 面试速答清单

| 问题 | 一句话答案 |
|------|-----------|
| Go GC 算法？ | 并发三色标记-清除，非分代非压缩 |
| 三色含义？ | 白=垃圾候选，灰=待扫描，黑=已扫描存活 |
| 并发标记为何要写屏障？ | 防止"黑引用白+灰删白"导致存活对象被误回收 |
| 写屏障类型？ | 1.8 混合写屏障=插入屏障+删除屏障，避免重扫栈，STW<1ms |
| 几次 STW？ | 两次极短：清扫终止 + 标记终止；标记/清扫都并发 |
| GC 触发？ | GOGC 控制堆增长到存活2倍(默认)，或2分钟定时，或手动 |
| 调优手段？ | GOGC 调频率，GOMEMLIMIT(1.19+)设软上限防 OOM，sync.Pool/减少逃逸 |
| 为什么非分代？ | 逃逸分析已让短命对象留栈，相当于编译期做了年轻代 |
