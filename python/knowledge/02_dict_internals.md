# 02 · dict 底层原理 ⭐⭐⭐

> dict 是 Python 中使用频率最高的数据结构——**类的属性存储、模块的全局变量、关键字参数** 底层都是 dict。理解 dict 的实现，就理解了 Python 的半壁江山。

---

## 1. 底层结构：紧凑哈希表（Python 3.6+）

Python 3.6 之前的 dict 是传统的开放寻址哈希表，浪费大量空间。3.6+ 采用了 Raymond Hettinger 提出的紧凑（compact）实现：

```
旧版（3.5-）：稀疏数组，每个槽位存 hash+key+value，2/3 空间浪费
新版（3.6+）：分离索引和条目

indices（稀疏数组，只存索引）：
┌────┬────┬────┬────┬────┬────┬────┬────┐
│ -1 │  1 │ -1 │  0 │ -1 │  2 │ -1 │ -1 │
└────┴────┴────┴────┴────┴────┴────┴────┘
  -1 表示空槽位，数字指向 entries 的索引

entries（紧凑数组，按插入顺序存储）：
┌───┬──────────────┬────────┬────────┐
│ # │ hash         │ key    │ value  │
├───┼──────────────┼────────┼────────┤
│ 0 │ hash("name") │ "name" │ "Alice"│
│ 1 │ hash("age")  │ "age"  │ 30     │
│ 2 │ hash("city") │ "city" │ "北京" │
└───┴──────────────┴────────┴────────┘
```

### 优势

1. **内存更省**：indices 数组的元素只占 1-8 字节（根据条目数量选择 int8/16/32/64），entries 是紧凑存储
2. **保序**：entries 按插入顺序存储 → **Python 3.7+ dict 保证插入顺序**（3.6 是 CPython 实现细节，3.7 是语言规范）
3. **缓存友好**：遍历时按 entries 顺序扫描，内存连续

## 2. 哈希与冲突解决

### 哈希计算

```python
hash("hello")    # 调用对象的 __hash__() 方法
hash(42)         # 对小整数，hash(n) == n
hash((1, 2, 3))  # 元组可哈希（元素都可哈希时）
hash([1, 2, 3])  # ⚠️ TypeError! 可变对象不可哈希
```

⚠️ **自定义类实现 `__eq__` 后必须实现 `__hash__`**，否则变成不可哈希（无法做 dict key 或 set 元素）。

### 冲突解决：开放寻址法

Python dict 不用链表法，而是**开放寻址**（open addressing）：冲突时探测下一个空槽位。

```python
# 简化的探测序列（CPython 实际使用的扰动函数）
perturb = hash_value
index = hash_value % table_size
while table[index] is not EMPTY:
    perturb >>= 5
    index = (5 * index + perturb + 1) % table_size
```

这个探测函数比简单的线性探测更均匀，减少了聚集（clustering）。

## 3. 扩容与缩容

### 扩容时机

当已用条目数达到哈希表大小的 **2/3** 时触发扩容。

### 扩容策略

- 条目数 < 50000：扩容为当前大小的 **4 倍**
- 条目数 >= 50000：扩容为当前大小的 **2 倍**

```python
# 观察扩容
import sys
d = {}
for i in range(20):
    d[i] = i
    print(f"len={len(d):2d}  size={sys.getsizeof(d)} bytes")
```

### 缩容

删除大量 key 后 dict 不会自动缩小。只有重建（如 `d = {k: v for k, v in d.items()}`）才会释放空间。

## 4. 为什么 dict 的 key 必须可哈希？

可哈希的要求：
1. 对象的 `__hash__()` 在其生命周期内返回相同值
2. 如果 `a == b`，则 `hash(a) == hash(b)`

可变对象（list、dict、set）不可哈希，因为修改内容会改变哈希值，导致已存入的 key 再也找不到。

## 5. dict 的性能特征

| 操作 | 平均时间复杂度 | 最坏时间复杂度 |
|------|--------------|---------------|
| 查找 `d[key]` | O(1) | O(n) |
| 插入 `d[key] = val` | O(1) | O(n) |
| 删除 `del d[key]` | O(1) | O(n) |
| 遍历 | O(n) | O(n) |
| `key in d` | O(1) | O(n) |

最坏情况（所有 key 哈希冲突）在实际中几乎不会发生。

## 6. 与 Go map 的对比

| 特性 | Python dict | Go map |
|------|-------------|--------|
| 底层 | 紧凑哈希表 + 开放寻址 | 哈希表 + 链表（bucket） |
| 保序 | ✓（3.7+ 保证插入顺序） | ✗（遍历顺序随机） |
| 并发安全 | ✗（但有 GIL 保护单条操作） | ✗（并发读写 panic） |
| 线程安全替代 | `threading.Lock` | `sync.Map` |
| 扩容 | 2/3 负载因子触发 | 6.5 负载因子触发 |
| key 要求 | 可哈希（`__hash__` + `__eq__`） | 可比较（`comparable`） |

## 高频面试题

**Q1：Python 的 dict 为什么是有序的？**
A：Python 3.6+ 使用紧凑哈希表（分离 indices 和 entries），entries 按插入顺序存储。3.7 起这一行为成为语言规范。

**Q2：dict 的查找时间复杂度是什么？为什么？**
A：平均 O(1)，底层是哈希表。哈希计算 O(1)，索引定位 O(1)，冲突解决平均 O(1)。

**Q3：什么对象可以做 dict 的 key？**
A：可哈希的对象——实现了 `__hash__` 且哈希值在生命周期内不变，同时 `__eq__` 和 `__hash__` 一致（相等的对象哈希值必须相同）。内置不可变类型（int、str、tuple）都可以。

**Q4：两个相等的对象哈希值不同会怎样？**
A：违反哈希约定。可以存入 dict 但无法正确查找——存入时用一个哈希值定位，查找时用另一个哈希值定位到不同位置，找不到。

---

## 一句话总结

Python 3.7+ 的 dict 是紧凑有序哈希表（开放寻址），O(1) 平均查改删，2/3 负载因子扩容；key 必须可哈希且哈希值稳定。
