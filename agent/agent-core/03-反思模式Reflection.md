# 03 · 反思模式（Reflection）

> 目标：理解让 Agent "自我评估、自我纠错"的反思模式。读完知道反思怎么实现、为什么有效、什么时候值得加，以及它的成本边界。

---

## 1. 反思解决什么问题

[文档 01](01-Agent循环与ReAct.md) 提到 ReAct 的失败模式之一是"**过早停止 / 答得不对不全**"——模型一次性产出结果，没有"检查一下"的环节，错了也不知道。

**反思模式（Reflection）就是给 Agent 加一个"自我审查"的环节**：

> **生成 → 评估自己的输出 → 接受或修订**。让 Agent 在把结果交给用户之前，先自己批判一遍、改一遍。

这模仿了人类"写完初稿再回头检查修改"的过程。它针对的核心失败模式是 **正确性（correctness）不足**。

---

## 2. 最简反思循环

反思是最简单的"自我改进"循环：

```
draft = LLM 生成初稿(任务)
for i in range(MAX_REVISIONS):
    critique = LLM 评估(draft, 评判标准)     # "这个输出哪里不好？"
    if critique 判定"足够好":
        break
    draft = LLM 根据 critique 修订(draft)     # 改进
return draft
```

关键在第二步的"评估"：让模型对照**明确的标准**审视自己的输出——有没有事实错误？有没有遗漏？逻辑通不通？格式对不对？满足需求了吗？

### 单模型 vs 双角色
- **同一个模型自评**：让模型切换到"批判者"角色审自己的初稿。简单常用。
- **生成者 + 评估者分离（Evaluator-Optimizer）**⭐：一个 LLM 调用负责生成，另一个负责评估和给反馈，循环往复。**当评判标准明确时特别有效**（这是 Anthropic 五种工作流模式之一）。分离角色能减少"自己看不出自己错"的盲区。

---

## 3. Reflexion：从失败中学习 ⭐

**Reflexion** 是反思的强化版，把它嵌进 ReAct 的行动循环：

> 在 Agent 产出结果后，评估器给它打分；如果失败，Agent **反思"为什么失败、下次该怎么改"，并把这个教训记进（短期）记忆**，在下一次尝试时带着教训重做。

```
尝试任务 → 评估器打分 → 失败？
   → 反思："我失败是因为没考虑 X，下次应该先 Y"
   → 把教训加入记忆
   → 带着教训重新尝试 → 再评估 → ...
```

**它和普通反思的区别**：Reflexion 强调"**在一次会话内从失败中积累经验**"，反思的产物（教训）会指导后续尝试，而不只是改一版当前输出。这能系统性缓解 [文档 01](01-Agent循环与ReAct.md) 的多种失败（上下文漂移、错误累积、低效工具使用）。

### 实证效果（为什么值得学）
反思类循环在有客观反馈信号的任务上效果显著。一个经典案例：**AlphaCodium** 用"反思重的循环"（起草 → 跑测试 → 反思失败 → 重写）把 GPT-4 在 CodeContests 上的成绩**从 19% 提升到 44%**。

> 关键前提：**有"客观的反馈信号"时，反思最有效**——比如代码能跑单元测试、数学有标准答案、检索能验证事实。反馈越客观，反思越有力。

---

## 4. 反思有效的条件（什么时候该用）

反思**不是免费的**——每轮评估和修订都是额外的 LLM 调用，增加延迟和成本。**只在收益明确时用：**

| 适合反思 ✅ | 不适合 ❌ |
|------------|----------|
| 有明确评判标准（代码过测试、格式校验、规则检查） | 标准模糊、纯主观（评估器也判断不准） |
| 任务复杂、一次难做对（复杂代码、长文写作、多约束） | 简单任务（一次就对，反思纯属浪费） |
| 有客观反馈信号（能跑、能验证） | 没有外部信号，全靠模型自评（可能"自我感觉良好"） |
| 正确性比延迟/成本更重要 | 延迟敏感、对成本极敏感的高频场景 |

> **反思的天花板由"评估的质量"决定**。如果评估器判断不准，反思可能越改越糟，或在"自我感觉良好"里打转。**有客观信号（测试、校验、检索验证）时优先把它接进评估**，比让模型空想"我觉得这答案不错"可靠得多。

---

## 5. 工程要点

- **评估标准要具体**：给评估器一个明确的检查清单（"检查：①是否回答了全部子问题 ②有无事实依据 ③格式是否合规"），而非"看看好不好"。
- **接入客观信号**：能跑测试就跑测试，能用 RAG 验证事实就验证（把"验证"做成评估器的工具）。
- **限制修订轮数**：设 `MAX_REVISIONS`（常 1~3 轮），并加"足够好就停"的判定，防止无限打磨、边际收益递减。
- **防震荡**：避免在两个版本间来回改。可保留"当前最佳"，只在确有改进时替换。
- **成本意识**：反思至少让调用次数翻倍。用 [INDEX 阶段 6](../INDEX.md) 的评估确认它真的提升了质量再保留。

---

## 6. 与其他模式的关系

- **反思 ⊥ ReAct**：可以在 ReAct 循环里周期性插入反思（"我目前收集的信息够回答吗？"），也可以在最终输出前加一轮反思。
- **反思 vs 规划**：规划是"做之前先想清楚步骤"，反思是"做之后检查并改"。两者互补——复杂任务常"先规划、执行、再反思"。见 [文档 04](04-规划模式Planning.md) 和 [文档 06](06-模式选择与组合.md)。
- **反思在多智能体里**：可以把"评估者"做成一个独立的 critic Agent。见 [文档 05](05-多智能体协作模式.md)。

---

## 7. 常见坑

- **没有客观评判标准就上反思** → 评估器瞎判，越改越乱。
- **不限轮数** → 无限打磨、成本爆炸、边际收益趋零。
- **评估标准太笼统** → 反思流于形式，挑不出真问题。
- **反思导致震荡** → A 版改成 B、B 又改回 A。要保留最佳版、确有改进才替换。
- **对简单任务也反思** → 纯浪费成本和延迟。
- **不评估反思的收益** → 以为加了就好，实际可能没提升还更贵。

---

## 8. 本章小结

- 反思 = "**生成 → 自我评估 → 修订**"，针对**正确性不足**的失败模式。
- **Evaluator-Optimizer**（生成者+评估者分离）在评判标准明确时特别有效。
- **Reflexion** 把反思嵌入行动循环，**在一次会话内从失败中积累教训**再重试；AlphaCodium 用反思循环把 GPT-4 从 19%→44%。
- **反思的有效性取决于评估质量**：有客观反馈信号（测试/校验/检索验证）时最强，纯主观自评易失效。
- 反思**不免费**（调用翻倍）：只在"标准明确 + 任务难 + 正确性优先"时用，限轮数、防震荡、用评估验证收益。
