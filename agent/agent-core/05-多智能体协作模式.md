# 05 · 多智能体协作模式（Multi-Agent）

> 目标：理解多个 Agent 协作的模式——**何时真的需要它**、有哪些拓扑结构、怎么交接、代价多大。核心结论先行：**多智能体是最后才考虑的选项，不是默认。**

---

## 1. 什么是多智能体，以及最重要的一句忠告

> **多智能体系统（Multi-Agent System）**：多个各有专职/角色的 Agent 协作完成一个任务，它们之间传递消息、交接工作、汇总结果。

最重要的忠告（贯穿 [文档 00](00-Agent核心学习总览.md) 的纪律）：

> ⚠️ 只有当任务存在可测的**并行宽度、上下文隔离、权限隔离或独立 specialist ownership**，并且单 Agent 基线不能满足 SLO 时，才考虑多智能体。不能用无任务边界的“大多数任务”比例代替实验。

为什么如此谨慎？因为多智能体把"一个循环的失败模式"乘以 N，还**新增**了智能体间通信、状态同步、错误传播、协调开销等一堆新问题。很多团队上了多智能体后发现还不如一个调好的单 Agent。

---

## 2. 什么时候多智能体才真的值得

| 真的需要 ✅ | 其实不需要 ❌（单 Agent 更好） |
|------------|-------------------------------|
| 需要不同证据域/工具/权限，且隔离后能减少上下文污染 | 只是给同一模型换“法律/财务”角色名 |
| 子任务**天然并行**且彼此独立，多 Agent 并行能显著加速 | 子任务串行依赖——单 Agent 顺序做就行 |
| 需要**隔离上下文**避免互相干扰（每个 Agent 只看自己那摊） | 任务共享大量上下文——拆开反而要反复同步 |
| 需要**不同工具集/权限边界**分离 | 工具不多——一个 Agent 全拿着即可 |

> 升级条件应写成可证伪假设，例如：“把三个独立检索分片并行后，在成本不超过 1.8 倍的条件下，p95 延迟下降至少 35%，最终 claim recall 不下降。”没有这样的门槛，多 Agent 只是架构偏好。

---

## 3. 常见拓扑结构

### 3.1 Orchestrator-Workers（编排者-工人）⭐ 最常用
一个**编排者** Agent 负责拆解任务、分派给多个**工人** Agent，收集并整合结果。

```
                 ┌──→ Worker A（研究员）──┐
用户任务 → Orchestrator ─→ Worker B（分析师）─┼──→ Orchestrator 汇总 → 输出
                 └──→ Worker C（写作）────┘
```
- 适合"主任务可拆成若干专门子任务"。编排者是大脑，工人是专才。
- 与 [文档 04](04-规划模式Planning.md) 的 Orchestrator-Workers 是同一模式——它既是规划也是多智能体。

### 3.2 Sequential / Pipeline（流水线）
Agent 串成流水线，前一个的输出是后一个的输入。
```
研究 Agent → 写作 Agent → 审校 Agent → 输出
```
- 适合有清晰阶段的任务。本质接近 Anthropic 的 **Prompt Chaining** 工作流，只是每个环节是一个 Agent。

### 3.3 Hierarchical（分层）
编排者下还有子编排者，多层级。复杂大型任务用，但协调成本最高，慎用。

### 3.4 Collaborative / Debate（协作/辩论）
多个 Agent 就同一问题给出观点、互相批判、达成共识。可提升某些推理任务的质量，但成本高。一个常见特例是 **Generator + Critic**（生成者 + 批判者），其实就是 [文档 03](03-反思模式Reflection.md) 的 Evaluator-Optimizer 用两个 Agent 实现。

## 4. 智能体之间怎么协作

- **交接（Handoff）**：控制权和用户回复 ownership 转给另一个 Agent；要传 task contract、必要状态、权限上下文和回收条件，而不是整段聊天转发。
- **共享状态 / 黑板（Blackboard）**：Agent 们读写一块共享状态区，松耦合协作。
- **Agent as Tool（Agent 即工具）**⭐：manager 保留用户回复 ownership，把 specialist 当作有输入/输出契约的工具调用。

### 4.1 Agent-as-Tool 与 Handoff 的关键差别

| 问题 | Agent-as-Tool | Handoff |
|------|---------------|---------|
| 谁向用户给最终答复 | manager | 被交接的 specialist |
| specialist 返回什么 | 结构化结果/产物 | 接管后的连续对话 |
| 上下文边界 | manager 选择传入 | 需要迁移会话/状态策略 |
| 适合 | 中央编排、可组合子能力 | 路由到长期 owner，如客服专线 |

OpenAI Agents SDK 官方文档也用“谁拥有最终回复”来区分 manager-style agents-as-tools 与 decentralized handoffs。

### 4.2 MCP 不是 Agent-to-Agent 任务协议

- **MCP**：host/client/server，面向工具、资源、prompt 等能力供给。
- **A2A**：独立 Agent 间发现、任务、消息、artifact、状态与版本协商。
- **进程内 agent-as-tool/handoff**：框架内部的控制权组合，未必需要网络协议。

可以把远端 Agent 包装成 MCP tool，但这会把长任务状态、artifact、身份和取消语义压扁成一次工具调用。需要跨组织长任务互操作时，A2A 更贴近问题层。完整分层见 [协议与互操作边界](../systems-engineering/05-Agent协议与互操作边界.md)。

## 5. 框架与编排

多智能体的工程编排通常借助框架：

- **LangGraph**：图状态/持久化/interrupt 路线。
- **CrewAI**：以"角色 + 任务 + 协作"为抽象，上手快。
- **AutoGen**：微软的多 Agent 对话框架。
- **LlamaIndex Workflows**：事件驱动的工作流编排。

> 不按“主流排名”选框架。先比较 checkpoint replay 语义、状态所有权、取消传播、人工暂停、工具 effect、遥测导出和版本迁移，再在自己的 eval 上测。

---

## 6. 代价（为什么要克制）

- **成本**：N 个 Agent ≈ N 倍甚至更多的 LLM 调用。编排、通信、汇总都要额外调用。
- **延迟**：除非真并行，否则多 Agent 往往更慢（串行交接 + 协调开销）。
- **不确定性/调试难**：失败可能发生在任一 Agent 或它们的交接处，trace 更复杂（[INDEX 阶段 6](../INDEX.md) 的可观测性更重要）。
- **错误传播**：上游 Agent 的小错会被下游放大。
- **上下文同步**：共享信息时容易出现不一致、重复传递。

### 6.1 并行收益受 Amdahl 定律与协调开销约束

若任务可并行比例为 \(p\)，使用 \(N\) 个 worker 的理想加速上限：

\[
S(N)=\frac{1}{(1-p)+p/N}
\]

Agent 系统还要扣除拆分、上下文复制、排队、汇总、冲突和验证成本 \(C_{coord}\)。例如只有 60% 工作可并行，4 个 worker 的理想上限仅约 1.82 倍；加入相当于原任务 20% 的协调开销后约 1.33 倍。不能按 Agent 数量线性估算。

### 6.2 多 Agent 的核心是所有权，不是“大家共享记忆”

每个 work item 应有：

- 唯一 `task_id`、owner、lease 和 deadline。
- 明确输入 artifact/version，不复制模糊聊天历史。
- 可验证 success predicate。
- 写集合或资源分区，避免两个 worker 同时改同一对象。
- 幂等提交、冲突处理和取消传播。

共享自然语言黑板适合灵感交流，不适合作为并发真相源。生产一致性详见 [多 Agent 并发与一致性](../systems-engineering/06-多Agent并发与一致性.md)。

### 6.3 错误不是只会“向下传播”

多 Agent 故障至少分三类：

1. **规格/设计失败**：任务切分错误、角色重叠、依赖遗漏。
2. **Agent 间失配**：术语、证据、版本、优先级和消息语义不一致。
3. **验证/终止失败**：编排者无法判断结果是否完成，错误汇总或无限委派。

MAST 研究把多 Agent 失败归纳为 14 种模式并落在上述三类。工程上应分别给 task-contract validator、message schema、artifact lineage、global budget 和 final verifier，而不是只“加强 supervisor prompt”。

## 7. 常见坑

- **过早上多智能体** → 本可用单 Agent 解决，徒增复杂度和成本。**头号坑。**
- **角色划分不清** → Agent 职责重叠、互相打架或都不管。
- **交接时上下文丢失或冗余** → 下游 Agent 缺信息或被淹没。
- **没有全局 trace** → 多 Agent 出问题无从排查。
- **无收敛/终止机制**（尤其辩论类）→ Agent 们没完没了。
- **把"步骤多"误判成"需要多智能体"** → 其实加 [Planning](04-规划模式Planning.md) 就够。
- **所有 worker 共写一个 scratchpad** → 状态覆盖和陈旧读；用单写者、分区所有权、CAS 或确定性 reducer。
- **角色名不同但模型/证据完全相同** → 只增加相关样本与成本，不产生独立信息。
- **没有取消传播/背压** → 上游已失败，worker 仍继续烧 token 和写外部系统。

---

## 8. 本章小结

- 多智能体 = 多个专职 Agent 协作；**但它是最后的选项，不是默认**——先穷尽单 Agent。
- **值得用的信号**：需要截然不同的专长/上下文隔离/工具权限分离、或子任务天然并行可加速。
- 常见拓扑：**Orchestrator-Workers（最常用）**、Pipeline、Hierarchical、Collaborative/Debate。
- 协作方式要按 ownership 区分 agent-as-tool 与 handoff；跨独立 Agent 的任务互操作更接近 A2A，MCP 主要是能力供给。
- 框架只是实现手段，选型要看恢复、状态、取消、审批和遥测语义。
- **代价显著**：成本/延迟/不确定性/调试难/错误传播——所以要克制。
- "步骤多"≠"需要多智能体"，那多半是 [Planning](04-规划模式Planning.md) 的活。
