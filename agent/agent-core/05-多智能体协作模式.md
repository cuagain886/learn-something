# 05 · 多智能体协作模式（Multi-Agent）

> 目标：理解多个 Agent 协作的模式——**何时真的需要它**、有哪些拓扑结构、怎么交接、代价多大。核心结论先行：**多智能体是最后才考虑的选项，不是默认。**

---

## 1. 什么是多智能体，以及最重要的一句忠告

> **多智能体系统（Multi-Agent System）**：多个各有专职/角色的 Agent 协作完成一个任务，它们之间传递消息、交接工作、汇总结果。

最重要的忠告（贯穿 [文档 00](00-Agent核心学习总览.md) 的纪律）：

> ⚠️ **只有当任务"确实需要超出单个 Agent 上下文/能力的专门角色"时，才考虑多智能体。**
> **单 Agent + ReAct + 好工具能解决现实中大多数任务。** 多智能体引入巨大的协调成本、延迟、成本和不确定性。**先穷尽单 Agent 的可能，再上多智能体。**

为什么如此谨慎？因为多智能体把"一个循环的失败模式"乘以 N，还**新增**了智能体间通信、状态同步、错误传播、协调开销等一堆新问题。很多团队上了多智能体后发现还不如一个调好的单 Agent。

---

## 2. 什么时候多智能体才真的值得

| 真的需要 ✅ | 其实不需要 ❌（单 Agent 更好） |
|------------|-------------------------------|
| 需要**截然不同的专长/角色**，且单个上下文塞不下（如"法律审查 + 财务分析 + 技术评估"并行） | 只是步骤多——用 [Planning](04-规划模式Planning.md) 即可 |
| 子任务**天然并行**且彼此独立，多 Agent 并行能显著加速 | 子任务串行依赖——单 Agent 顺序做就行 |
| 需要**隔离上下文**避免互相干扰（每个 Agent 只看自己那摊） | 任务共享大量上下文——拆开反而要反复同步 |
| 需要**不同工具集/权限边界**分离 | 工具不多——一个 Agent 全拿着即可 |

> 经验法则：**先问"换个更好的单 Agent 设计（更好的工具、加规划/反思）能不能解决？"** 如果能，就别上多智能体。

---

## 3. 常见拓扑结构

### 3.1 Orchestrator-Workers（编排者-工人）⭐ 最常用
一个**编排者** Agent 负责拆解任务、分派给多个**工人** Agent，收集并整合结果。

```
                 ┌──→ Worker A（研究员）──┐
用户任务 → Orchestrator ─→ Worker B（分析师）─┼──→ Orchestrator 汇总 → 输出
                 └──→ Worker C（写作）────┘
```
- 适合"主任务可拆成若干专门子任务"。编排者是大脑，工人是专才。
- 与 [文档 04](04-规划模式Planning.md) 的 Orchestrator-Workers 是同一模式——它既是规划也是多智能体。

### 3.2 Sequential / Pipeline（流水线）
Agent 串成流水线，前一个的输出是后一个的输入。
```
研究 Agent → 写作 Agent → 审校 Agent → 输出
```
- 适合有清晰阶段的任务。本质接近 Anthropic 的 **Prompt Chaining** 工作流，只是每个环节是一个 Agent。

### 3.3 Hierarchical（分层）
编排者下还有子编排者，多层级。复杂大型任务用，但协调成本最高，慎用。

### 3.4 Collaborative / Debate（协作/辩论）
多个 Agent 就同一问题给出观点、互相批判、达成共识。可提升某些推理任务的质量，但成本高。一个常见特例是 **Generator + Critic**（生成者 + 批判者），其实就是 [文档 03](03-反思模式Reflection.md) 的 Evaluator-Optimizer 用两个 Agent 实现。

## 4. 智能体之间怎么协作

- **交接（Handoff）**：一个 Agent 把控制权和必要上下文传给另一个（如"客服 Agent 判断是技术问题，交接给技术 Agent"）。要传递**足够但不冗余**的上下文。
- **共享状态 / 黑板（Blackboard）**：Agent 们读写一块共享状态区，松耦合协作。
- **Agent as Tool（Agent 即工具）**⭐：把一个子 Agent 直接**封装成上一层 Agent 的一个工具**（[文档 02](02-工具使用ToolUse.md)）。这是最干净的组合方式——上层"调用子 Agent"就像调用一个工具。配合 **MCP**（[INDEX 阶段 4](../INDEX.md)），Agent 之间还能互相暴露能力、标准化协作。

## 5. 框架与编排

多智能体的工程编排通常借助框架：

- **LangGraph**⭐：在 LangChain 上加"基于图的状态机"，用显式的节点/边管理多 Agent 的状态流转、人类介入检查点、复杂多步流程。**2026 多智能体的主流选择**，且 MCP 兼容。
- **CrewAI**：以"角色 + 任务 + 协作"为抽象，上手快。
- **AutoGen**：微软的多 Agent 对话框架。
- **LlamaIndex Workflows**：事件驱动的工作流编排。

> 框架深入属于 [INDEX 阶段 5](../INDEX.md) 的内容。本专题先理解**模式与权衡**，框架是实现手段。

---

## 6. 代价（为什么要克制）

- **成本**：N 个 Agent ≈ N 倍甚至更多的 LLM 调用。编排、通信、汇总都要额外调用。
- **延迟**：除非真并行，否则多 Agent 往往更慢（串行交接 + 协调开销）。
- **不确定性/调试难**：失败可能发生在任一 Agent 或它们的交接处，trace 更复杂（[INDEX 阶段 6](../INDEX.md) 的可观测性更重要）。
- **错误传播**：上游 Agent 的小错会被下游放大。
- **上下文同步**：共享信息时容易出现不一致、重复传递。

---

## 7. 常见坑

- **过早上多智能体** → 本可用单 Agent 解决，徒增复杂度和成本。**头号坑。**
- **角色划分不清** → Agent 职责重叠、互相打架或都不管。
- **交接时上下文丢失或冗余** → 下游 Agent 缺信息或被淹没。
- **没有全局 trace** → 多 Agent 出问题无从排查。
- **无收敛/终止机制**（尤其辩论类）→ Agent 们没完没了。
- **把"步骤多"误判成"需要多智能体"** → 其实加 [Planning](04-规划模式Planning.md) 就够。

---

## 8. 本章小结

- 多智能体 = 多个专职 Agent 协作；**但它是最后的选项，不是默认**——先穷尽单 Agent。
- **值得用的信号**：需要截然不同的专长/上下文隔离/工具权限分离、或子任务天然并行可加速。
- 常见拓扑：**Orchestrator-Workers（最常用）**、Pipeline、Hierarchical、Collaborative/Debate。
- 协作方式：交接、共享状态、**Agent-as-Tool（最干净）**；配合 MCP 标准化互联。
- 编排框架以 **LangGraph** 为主流（图状态机 + HITL + MCP 兼容）。
- **代价显著**：成本/延迟/不确定性/调试难/错误传播——所以要克制。
- "步骤多"≠"需要多智能体"，那多半是 [Planning](04-规划模式Planning.md) 的活。
