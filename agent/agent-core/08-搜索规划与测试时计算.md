# 08 · 搜索、规划与测试时计算

> 目标：理解“让模型多想一会儿”背后的算法，而不是把 Planning 简化成先输出一张待办清单。读完应能比较 greedy ReAct、Best-of-N、Self-Consistency、Tree of Thoughts、beam search 与 MCTS/LATS，并说明验证器为什么既是能力放大器也是新故障源。

---

## 1. 规划的本质：在候选轨迹空间里搜索

把一条 Agent 轨迹写成：

\[
\tau=(b_0,a_0,o_1,b_1,a_1,o_2,\ldots,a_T)
\]

规划要寻找期望效用更高的轨迹：

\[
\tau^*=\arg\max_\tau E[U(\tau)]
\]

现实里不能枚举所有轨迹，因为分支因子为 \(B\)、深度为 \(D\) 时，朴素搜索规模是：

\[
O(B^D)
\]

所以所有“高级规划”都在回答三个问题：

1. **生成哪些候选？** exploration。
2. **如何估计候选价值？** verifier/value function。
3. **有限预算给哪些分支？** search/allocation policy。

---

## 2. 从单轨迹到树搜索

| 方法 | 搜索结构 | 选择机制 | 适合 | 关键限制 |
|------|----------|----------|------|----------|
| Greedy / ReAct | 单条轨迹 | 每步选当前一个动作 | 开放探索、反馈频繁 | 早期错误难回退 |
| Best-of-N | N 个完整候选 | outcome verifier 选最好 | 可独立生成完整答案 | 成本线性，候选高度相关 |
| Self-Consistency | N 条推理路径 | 对最终答案投票/边缘化 | 有相对唯一答案的推理 | 开放任务无法简单投票 |
| Beam Search | 每层保留 K 个分支 | 局部累积分数 | 深度可控、可逐步评分 | verifier 短视会过早剪掉好路径 |
| Tree of Thoughts | thought 级树 | BFS/DFS + LM 评估 | 需要回溯和 lookahead | 分支爆炸、LM 自评偏差 |
| MCTS / LATS | 非均匀搜索树 | UCB/价值 + 模拟 + 回传 | 环境反馈、预算较大 | 实现复杂，value 噪声会误导搜索 |

这些方法不是“模型架构”，而是 harness 如何分配推理和工具预算。

---

## 3. Best-of-N 与 Self-Consistency 不是一回事

### 3.1 Best-of-N

生成 \(N\) 个候选，用 verifier 选择：

\[
y^*=\arg\max_{y_i} V(x,y_i)
\]

关键问题不在生成，而在 \(V\)：

- 如果 verifier 只能检查格式，选不出事实更正确的答案。
- 如果 generator 与 judge 同源，错误可能高度相关。
- 如果目标可被投机，候选会逐渐学会“讨好评分器”。

### 3.2 Self-Consistency

Self-Consistency 采样多条推理路径，按最终答案的一致性聚合：

\[
\hat y=\arg\max_y\sum_{i=1}^N \mathbf{1}[answer(\tau_i)=y]
\]

它依赖“不同正确路径汇聚到同一答案”的假设。对数学短答案较自然；对调研报告、代码补丁、UI 操作轨迹，没有一个可直接多数投票的离散答案。

### 3.3 为什么重复采样不等于独立证据

多个候选来自相同模型、prompt 和上下文时，错误相关性很高。`N=10` 不能按十个独立专家计算置信度。要增加真实多样性，可以改变：

- 检索证据或数据切片。
- 分解方法与搜索策略。
- verifier 类型。
- 模型/提示，但要防止比较预算不公平。

最终仍应以外部 oracle 或环境状态验证，而不是用“十个样本都这么说”替代事实。

## 4. Tree of Thoughts：把 thought 当搜索节点

Tree of Thoughts（ToT）把一个完整回答拆成可评估的中间 thought：

```text
初始问题
├─ thought A ─ A1 ─ A11
│            └ A2
├─ thought B ─ B1
└─ thought C ─ C1 ─ C11
```

一个通用 ToT 过程：

```python
frontier = [initial_state]
for depth in range(MAX_DEPTH):
    candidates = []
    for state in frontier:
        thoughts = propose(state, branching=B)
        for thought in thoughts:
            next_state = transition(state, thought)
            score = evaluate(next_state)
            candidates.append((score, next_state))
    frontier = select(candidates, beam_width=K)
    if any(is_terminal(s) and verify(s) for _, s in frontier):
        return best_verified(frontier)
return fail_or_best_partial(frontier)
```

面试时要指出：ToT 的提升不是“树”这个名词自动带来的，而取决于：

- thought 的粒度是否可评价。
- proposal 是否有足够分支多样性。
- evaluator 能否在未完成状态上估值。
- 剪枝是否保留了未来有潜力的路径。
- 对照基线是否使用了相同 token/调用预算。

## 5. Beam Search：局部高分不等于最终最好

Beam search 每一层只保留得分最高的 K 个状态：

\[
F_{t+1}=TopK\{V(s')\mid s'\in Expand(F_t)\}
\]

它比全搜索便宜，但有典型失败：

- **评价短视**：暂时得分低、最终更好的路径被过早剪掉。
- **beam collapse**：K 个候选只是同一路径的轻微改写。
- **长度偏好**：累计分数偏爱短路径或长路径。
- **不可比较分数**：不同深度状态的 judge 分数没有校准。

缓解手段包括多样性惩罚、深度归一化、保留探索槽位、外部约束检查和最终 outcome verifier。

## 6. MCTS / LATS：把预算投给更有希望的分支

Monte Carlo Tree Search 常分四步：

1. **Selection**：沿树选择要继续探索的节点。
2. **Expansion**：生成新动作/新 thought。
3. **Simulation/Evaluation**：估计该节点未来价值。
4. **Backpropagation**：把结果回传到祖先节点。

经典 UCB1 选择项：

\[
UCB_i=\bar X_i+c\sqrt{\frac{\ln N}{n_i}}
\]

- \(\bar X_i\)：节点当前平均价值，代表 exploitation。
- \(N\)：父节点访问数。
- \(n_i\)：子节点访问数。
- \(c\)：探索强度。

LATS 把 LM 生成动作、环境反馈、LM value/self-reflection 与 MCTS 结合。关键价值是**非均匀分配预算**：不是每条路线都展开同样深，而是把更多调用给当前看起来更有希望或不确定的分支。

### 6.1 LLM value function 的危险

传统棋类 MCTS 有明确规则和终局输赢；开放式 Agent 的 value 往往由 LLM 猜测：

- 中间状态信息不足，价值难估。
- value model 与 policy model 共享盲点。
- 文风、长度或自信程度可能被误当作质量。
- 被 prompt injection 污染的观察会同时误导生成器和评分器。

因此环境可执行反馈、代码测试、数据库后置条件、引用验证应优先于纯 LM value。

## 7. Verifier 的四级证据

| 级别 | verifier | 例子 | 可靠性边界 |
|------|----------|------|------------|
| 1 | 结构/约束 | JSON Schema、类型、正则、lint | 只能证明格式/局部约束 |
| 2 | 可执行环境 | 单测、编译、SQL dry-run、模拟器 | 测试覆盖之外仍可能错 |
| 3 | 世界状态 | 数据库后置条件、支付对账、引用可达 | 需要处理新鲜度与权限 |
| 4 | 人类/专家 | 高风险审批、开放质量判断 | 昂贵、有分歧和审批疲劳 |

LLM judge 可用于补充开放式质量，但不能把“judge 说通过”提升为比世界状态更强的证据。

### 7.1 Goodhart 与 verifier hacking

当一个指标成为搜索目标，它可能不再是好指标。常见表现：

- 生成器堆关键词讨好 rubric。
- 为通过单测硬编码测试输入。
- judge 偏爱更长、更自信或和自己相似的答案。
- 反思循环反复改文风，却没有改善任务状态。

控制方法：

- 把硬约束、世界状态、开放质量分开评分。
- 保留未暴露给生成器的 holdout tests。
- 定期用人工锚点集测 judge 混淆矩阵。
- 搜索用 surrogate verifier，发布门禁用独立 oracle。

## 8. 计划表示决定能否执行与恢复

### 8.1 线性列表

```yaml
steps: [search, fetch, summarize]
```

简单，但无法表达并行、条件和补偿。

### 8.2 DAG

```yaml
tasks:
  market: {depends_on: []}
  competitors: {depends_on: []}
  synthesis: {depends_on: [market, competitors]}
```

适合依赖调度；需要处理 join 是 `all`、`any` 还是 quorum。

### 8.3 HTN（Hierarchical Task Network）

把高层任务按方法展开为更细任务。优势是能注入领域知识和可控模板；代价是要维护任务/方法库。

### 8.4 Contingent Plan

显式表达观察分支：

```yaml
- action: check_inventory
  on:
    in_stock: reserve
    out_of_stock: propose_alternative
    timeout: reconcile_inventory_read
```

它比“失败后再让模型想”更适合高风险、已知异常路径。

一个可执行计划项至少应包含：

- `id`、目标与 owner。
- preconditions、inputs、expected effect。
- success predicate 与 verifier。
- dependency、deadline、budget。
- retry policy、compensation 与 replan signal。

## 9. Replan 不是“每 K 步重新问一次”

固定 K 是兜底，不是语义条件。真正应该触发 replan 的信号包括：

- 前置条件失效或资源版本变化。
- 观察落在计划未覆盖的分支。
- success predicate 连续失败。
- 成本/延迟预测超过剩余预算。
- 新证据推翻关键假设。
- 任务被取消、权限收回或人工修改目标。

重规划时不能把已产生的真实副作用当成“计划草稿”覆盖掉。输入应包含：

```text
原始目标 + 不可变约束 + 已提交副作用 + 当前 world snapshot
+ 已验证产物 + 未完成工作 + 剩余预算 + replan 原因
```

输出计划必须验证：没有重复已完成副作用，依赖无环，所有工具存在且权限可达。

## 10. 测试时计算怎样分配

给定总预算 \(B\)，不是所有题都值得同样搜索。可把分配写成：

\[
\max_{b_1+\cdots+b_n\le B}\sum_i E[\Delta Q_i(b_i)]
\]

实际策略：

- 简单/高置信任务走 greedy。
- 有唯一答案且可聚合时用 self-consistency。
- 可生成完整候选且有强 outcome verifier 时用 Best-of-N。
- 需要回溯、早期选择影响巨大时用 ToT/beam。
- 有环境反馈、分支价值差异大且预算充足时考虑 MCTS/LATS。

测试时计算论文也表明，收益强依赖题目难度、policy model 和 verifier；不能把某个 benchmark 的倍数当通用规律。

---

## 11. 搜索与真实工具副作用必须隔离

搜索树可以自由生成“候选动作”，但不能在每个分支都真实付款或发邮件。应区分：

- `simulate/propose`：纯读、dry-run 或沙箱，不改变生产世界。
- `commit`：选定一条轨迹后，通过策略、审批、幂等和后置验证执行。

若工具没有模拟模式：

- 搜索阶段只规划调用，不执行。
- 或在隔离环境/事务中执行并可回滚。
- 不可逆动作只允许 winning plan 进入 commit gate。

否则“多分支探索”会变成“把所有候选副作用都执行一次”。

## 12. 如何公平评测规划/搜索方法

至少控制：

- 相同 base model 和模型版本。
- 相同工具、环境快照和权限。
- 相同最大 token/tool/墙钟/费用预算。
- 相同最终 world-state oracle。
- 每个任务多次运行，报告置信区间。

必要消融：

1. greedy baseline。
2. 只增加采样、不加 verifier。
3. 固定候选数，比较 verifier。
4. 固定 verifier，比较搜索策略。
5. 去掉反思或环境反馈。
6. 分难度、任务类型、轨迹长度报告。

结果至少报告质量、`pass^k`、成本/成功、p95 延迟、工具调用数和风险事件。只报“成功率提升”无法判断搜索是否值得。

## 13. 面试追问树

### Q1：Planning 和 ReAct 的本质区别？

ReAct 近似单轨迹在线策略，每次观察后贪心选择下一动作；Planning 显式构造未来状态/任务结构，可能探索多个候选并用价值函数选择。两者可组合：高层 DAG + 每个节点内部 ReAct。

### Q2：Tree of Thoughts 为什么可能比 Chain of Thought 好？

它允许分支、评估、回溯，能修复早期选择；代价是 \(O(B^D)\) 搜索和 evaluator 偏差。收益只在任务真的需要 lookahead、且中间状态可评价时成立。

### Q3：MCTS 用在 LLM Agent 最大的难点？

开放任务没有可靠 world model 和 value function；LM 自评噪声/偏差会被树搜索放大，真实工具又可能有不可逆副作用。因此要优先用环境反馈、沙箱和确定性 verifier。

### Q4：为什么 Best-of-N 不一定随 N 单调变好？

候选相关、生成分布尾部质量差、verifier 选择错误、成本预算挤压最终验证；N 增加只扩大“候选池”，不保证 oracle 选择正确。

### Q5：什么时候不该用高级搜索？

固定工作流已有可靠解；没有可区分候选的 verifier；动作不可安全模拟；延迟预算很紧；或简单 baseline 已满足 SLO。此时增加分支只会放大成本与攻击面。
