# 06 · 模式选择与组合

> 目标：把前面所有模式收口成一套**可操作的决策框架**。读完能拿到任意需求，判断"该用什么、怎么组合、什么时候别用 Agent"，并避开过度工程的反模式。

---

## 1. 第一性原则：从简单开始，失败驱动地加复杂度 ⭐⭐

这是整个 Agent 工程最重要的一条，2026 业界（尤其 Anthropic）反复强调：

> **每个模式都是为某个具体的失败模式存在的。如果你还没遇到那个失败，就别加那个模式。**

```
                 成本太高、调用太多  →  ReWOO / 减少 LLM 往返
                 任务复杂、老跑偏    →  Planning（+ re-plan gate）
ReAct（起点） ──→  正确性不够        →  Reflection / Reflexion
                 需要不同专长/隔离   →  Multi-Agent
                 （没遇到失败）      →  就用 ReAct，别动
```

每个模式都要付出代价（成本、延迟、复杂度、不确定性）。**加之前先问：它解决的是我已经观察到的失败，还是我臆想的需求？**

---

## 2. 一张总决策树

```
你的任务……

① 步骤完全固定、可预测吗？
   是 → 别用 Agent！用写死的工作流 / 单次 LLM 调用 + RAG（最稳最省）
   否 → ②

② 先用 [单 Agent + ReAct + 好工具]（文档01/02）做一版
   能解决吗？ 是 → ✅ 收工。别过度设计。
   不行 → 看是哪种失败：③

③ 诊断失败类型：
   ├─ 老跑偏、忘了目标、步骤太多        → 加 [Planning + re-plan gate]（文档04）
   ├─ 答得不对/不全，但有客观评判标准    → 加 [Reflection / Reflexion]（文档03）
   ├─ 调用太多太贵                      → [ReWOO] 或精简工具/上下文
   ├─ 需要截然不同的专长 / 上下文隔离    → [Multi-Agent]（文档05），且先确认单Agent真不行
   └─ 检索不到知识                      → 强化 [RAG]（rag/），或做成 Agentic RAG

④ 仍不行？ → 回到 ② 的工具和 Prompt 质量上找问题（多半是工具设计/上下文，不是模式不够）
```

> 关键提醒：**大多数"Agent 不好用"的根因是工具设计差、上下文管理烂、Prompt 不清晰，而不是"模式不够高级"。** 加模式之前先回头审视地基（文档 01/02）。

## 3. 模式速查表

| 模式 | 解决的失败 | 代价 | 何时上 | 文档 |
|------|-----------|------|--------|------|
| **ReAct** | —（默认起点） | 低 | 总是先用它 | [01](01-Agent循环与ReAct.md) |
| **Tool Use** | 模型只能"说"不能"做" | 低 | 几乎必备 | [02](02-工具使用ToolUse.md) |
| **Reflection** | 正确性不足 | 中（调用翻倍） | 有客观评判标准、任务难、重正确性 | [03](03-反思模式Reflection.md) |
| **Reflexion** | 反复犯同类错 | 中 | 有反馈信号、需会话内学习 | [03](03-反思模式Reflection.md) |
| **Planning** | 复杂任务跑偏 | 中 | 步骤多、结构清晰、需全局视角 | [04](04-规划模式Planning.md) |
| **ReWOO** | 调用太多太贵 | 低（省） | 成本敏感、步骤较确定 | [04](04-规划模式Planning.md) |
| **Multi-Agent** | 单 Agent 专长/上下文不够 | 高 | 需不同专长/隔离/并行，且单Agent确实不行 | [05](05-多智能体协作模式.md) |

## 4. 模式是可以组合的 ⭐

真实的生产 Agent 往往是多个模式的组合。理解每个模式后，组合是自然的：

```
典型的"复杂任务"组合：
   Planning（先拆解出计划）
      └─ 每个子任务用 ReAct + Tool Use 执行
            └─ 关键产出用 Reflection 自检
                  └─ 若子任务需专长，派给专门的 Multi-Agent worker
   全程：循环控制（步数上限）+ 上下文工程 + trace 可观测
```

例子——一个"深度调研报告" Agent：
1. **Planning**：把"调研 X 行业"拆成"找市场规模 / 找主要玩家 / 找趋势 / 写结论"。
2. 每步用 **ReAct + Tool Use**（搜索、抓网页、RAG 检索）执行；遇意外触发 **re-plan**。
3. 写完结论用 **Reflection** 自评"是否覆盖全部子问题、有无事实依据"。
4. 若某块需要深度专业分析，**Orchestrator-Workers** 派给专门 worker。

> 但还是那句：**从最简组合开始，每加一层都因为你观察到了对应的失败。**

---

## 5. 横切关注点（无论用什么模式都要做）

这些不是"模式"，但任何能上线的 Agent 都必须有（详见后续 INDEX 阶段）：

- **循环控制**（[文档 01](01-Agent循环与ReAct.md)）：步数/预算上限、防重复、失败喂回、超限兜底。**没有步数上限的 Agent 不能上线。**
- **上下文工程**（[INDEX 阶段 4](../INDEX.md)）：滑动窗口、摘要、记忆卸载——防上下文漂移（65% 的 Agent 失败源于此）。
- **评估与可观测**（[INDEX 阶段 6](../INDEX.md)）：全链路 trace + 任务成功率/轨迹质量评估。**每加一个模式都要用评估验证它真的提升了**，否则就是徒增成本。
- **安全护栏**（[INDEX 阶段 7](../INDEX.md)）：最小权限、高风险动作人工确认、防 prompt 注入。模式越复杂、自主性越强，安全越关键。

---

## 6. 反模式（明确要避免的）

| 反模式 | 为什么错 | 正解 |
|--------|----------|------|
| **一上来就多智能体** | 巨大复杂度，单 Agent 多半够 | 先 ReAct，失败再升级 |
| **能用工作流却硬上 Agent** | 步骤固定就别要自主性，又贵又不稳 | 固定流程用写死的工作流 |
| **堆砌所有模式** | 规划+反思+多智能体全上，调试地狱 | 失败驱动，只加需要的 |
| **没评估就加模式** | 不知道有没有用，凭感觉 | 先建评估，用数据决定 |
| **没有步数上限** | 跑飞时无限烧钱 | 必设上限和兜底 |
| **忽视工具/上下文质量，只追模式** | 根因没解决，加再多模式也白搭 | 先打磨工具设计和上下文 |
| **自主性与权限不匹配** | 高自主 Agent 拿着危险权限 | 自主越高，护栏越严，最小权限 |

---

## 7. 一句话决策口诀

> **能不用 Agent 就不用（固定流程用工作流）；要用就从 ReAct + 好工具起步；只在观察到具体失败时，才加对应的那一个模式；每加一层都用评估和 trace 验证；越自主，护栏越严。**

---

## 8. 本章小结

- **第一性原则**：从简单（ReAct）开始，**失败驱动**地加复杂度——没遇到对应失败就别加对应模式。
- 用**总决策树**判断：先问"要不要 Agent"，再"ReAct 够不够"，不够则按失败类型加 Planning / Reflection / ReWOO / Multi-Agent。
- **多数"Agent 不好用"是工具/上下文/Prompt 的锅，不是模式不够高级**——先审地基。
- 模式**可组合**（Planning 套 ReAct 套 Reflection……），但从最简组合起步。
- 无论什么模式，都要做**循环控制 + 上下文工程 + 评估可观测 + 安全护栏**这些横切项。
- 牢记反模式：过早多智能体、能用工作流硬上 Agent、堆砌模式、没评估就加、没步数上限。
