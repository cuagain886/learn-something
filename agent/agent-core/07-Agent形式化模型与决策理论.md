# 07 · Agent 形式化模型与决策理论

> 目标：把“LLM + 工具 + 循环”提升为可推导、可评测的决策系统。面试中如果被问“Agent 和普通工作流的本质区别是什么”“为什么需要记忆”“什么时候应该停止”，可以从本章的模型出发，而不是继续背框架名词。
>
> 形式化是设计语言，不代表必须训练强化学习模型。它的价值是逼迫我们说清：真实状态是什么、Agent 看到了什么、能做什么、优化什么、为错误付出什么代价。

---

## 1. 为什么“LLM + 工具 + 循环”还不够

这个定义能描述外形，却回答不了以下问题：

- 工具返回的信息不完整或过时时，Agent 根据什么决策？
- 对话历史、数据库状态和任务 checkpoint，哪个才是真实状态？
- “再搜索一次”与“直接回答”之间如何权衡？
- 一个成功率更高但可能误转账的 Agent，是否真的更好？
- Workflow 与 Agent 是二元分类，还是自主控制程度不同？

要回答这些问题，需要把 Agent 看成一个在**部分可观测环境**中连续决策的系统。

---

## 2. 用 POMDP 描述交互式 Agent

许多交互式 Agent 任务可抽象为部分可观测马尔可夫决策过程：

\[
\mathcal{M}=\langle S,A,O,T,Z,R,\gamma \rangle
\]

| 符号 | 含义 | Agent 工程里的例子 |
|------|------|--------------------|
| \(S\) | 环境真实状态 | 数据库记录、网页真实内容、文件系统、用户真实意图 |
| \(A\) | 可执行动作 | 搜索、读文件、调用 API、请求审批、结束任务 |
| \(O\) | Agent 可得到的观察 | 工具返回、截图、错误、用户回复、检索片段 |
| \(T(s'\mid s,a)\) | 动作后的状态转移 | 更新订单后数据库从 `pending` 变成 `refunded` |
| \(Z(o\mid s,a)\) | 在某状态下看到某观察的概率 | API 可能返回截断、陈旧或带噪结果 |
| \(R(s,a,s')\) | 即时收益/代价 | 任务质量、token 成本、延迟、误操作风险 |
| \(\gamma\) | 对远期收益的折扣 | 长任务是否值得继续投入更多步骤 |

为什么是“部分可观测”？因为模型通常看不到 \(s_t\)，只能看到观察历史：

\[
h_t=(o_1,a_1,o_2,a_2,\ldots,o_t)
\]

网页摘要不等于网页，数据库查询结果不等于数据库全貌，UI 截图也不等于应用内部状态。**Observation 是关于世界的证据，不是世界本身。**

OSWorld 等计算机操作基准也使用 POMDP 描述数字 Agent：屏幕和可访问树是观察，鼠标/键盘是动作，应用内部状态并不完全可见。

## 3. Belief State：Agent 真正需要维护的“认知状态”

理论上的 belief state 是对真实状态的后验分布：

\[
b_t(s)=P(s_t=s\mid h_t)
\]

得到新观察后，理想的贝叶斯更新为：

\[
b_{t+1}(s') \propto Z(o_{t+1}\mid s',a_t)
\sum_s T(s'\mid s,a_t)b_t(s)
\]

LLM Agent 通常不知道精确的 \(T\) 和 \(Z\)，也不会真的维护完整概率分布。但工程上仍应维护一个**结构化 belief approximation**：

```yaml
belief_state:
  confirmed_facts:
    - claim: "订单 O-123 已退款"
      evidence: "operation/op-889/result.json"
      observed_at: "2026-07-19T10:32:11+08:00"
      version: 42
  hypotheses:
    - claim: "用户可能重复提交了退款请求"
      confidence_band: medium
      supporting_evidence: ["ticket/771", "ticket/772"]
      contradicting_evidence: []
  unknowns:
    - "支付渠道是否已完成到账"
  stale_after:
    order_status: "5m"
```

这里刻意使用 `confidence_band`，而不是让模型随口生成 `0.83`。没有校准集时，小数点概率只是伪精确。

### 3.1 对话记录不是 belief state

聊天记录只是未经整理的 observation log，存在四个问题：

1. **不可区分事实与推测**：模型说“可能已退款”会和工具确认结果混在一起。
2. **没有新鲜度**：两小时前的库存状态可能已经失效。
3. **没有冲突规则**：两个工具返回不同结果时，不知道谁覆盖谁。
4. **无法并发更新**：多个 worker 在自然语言 scratchpad 中写状态，没有 CAS/version。

因此至少要区分：

- `event_log`：发生过什么，追加写、不可变。
- `world_snapshot`：某资源在某版本的已确认状态。
- `belief_state`：根据现有证据形成的事实、假设与未知项。
- `working_context`：本轮送给模型的有限投影。

上下文压缩只能改变最后一项，不能替代前三项。

## 4. LLM Agent 的策略不只来自模型

策略表示根据历史或 belief 选择动作：

\[
\pi(a_t\mid h_t) \quad \text{或} \quad \pi(a_t\mid b_t)
\]

在工程系统里，最终策略不是“底座模型”单独决定的，而是复合策略：

\[
\pi_{system}=\text{PolicyGate}\circ\text{ToolBroker}\circ
\pi_{LLM}(prompt,tools,memory,state)
\]

影响动作分布的因素包括：

- 模型与解码设置。
- system/developer 指令和示例。
- 当前可见的工具集合、描述和 schema。
- context assembler 选择的证据。
- 规划器、路由器和 verifier。
- 权限策略、审批与预算控制。

这解释了为什么只比较模型榜单不能预测 Agent 产品表现：同一个模型放进不同 harness，实际可达动作和失败恢复完全不同。

## 5. Workflow 与 Agent 是控制权连续谱

“固定路径是 workflow，动态路径是 Agent”是有用入门，但真实系统常位于中间。

可以从三个维度描述自主性：

| 维度 | 低自主 | 高自主 |
|------|--------|--------|
| **动作集合** | 代码固定调用一个工具 | 模型从大量工具中选择或发现工具 |
| **控制流** | 节点/边完全写死 | 模型决定分支、循环、委派与终止 |
| **目标解释** | 明确输入输出契约 | 模型要澄清、分解甚至修订子目标 |

还可以用策略熵做概念化描述：

\[
H(\pi(\cdot\mid b_t))=-\sum_a \pi(a\mid b_t)\log \pi(a\mid b_t)
\]

- 只有一个合法下一步时，策略熵接近 0，更像 workflow。
- 多个动作均可能且由模型动态选择时，策略熵更高，更像 Agent。

这不是要求线上计算熵，而是提醒架构师：**自主性来自运行时允许的选择空间，不来自把组件命名为 Agent。** 一个叫 `ResearchAgent`、但始终固定执行三步的对象仍是工作流节点。

## 6. Reward 不是一句“请做好任务”

Agent 产品通常同时优化质量、成本、延迟与风险：

\[
U=Q-\lambda_c C-\lambda_l L-\lambda_r Risk
\]

- \(Q\)：最终世界状态或产物质量。
- \(C\)：模型、工具、人工和基础设施成本。
- \(L\)：端到端延迟，尤其尾延迟。
- \(Risk\)：错误动作的概率与影响。

有些风险不应被“更高平均质量”抵消，应写成硬约束：

\[
\max_\pi E[Q-\lambda_cC-\lambda_lL]
\quad s.t.\quad P(unsafe\ action)\le \epsilon
\]

例如“退款回答更流畅”不能抵消“偶尔给错账户退款”。安全动作应由权限、schema、审批和数据库约束保证，而不是仅靠 reward 提示模型权衡。

### 6.1 区分训练 reward 与运行时业务效用

- **训练 reward**：用于 RL/偏好优化，可能改变模型参数。
- **运行时 evaluator score**：对候选答案或轨迹打分，不会自动改变参数。
- **业务 KPI/SLO**：最终任务成功、损失、延迟、投诉率等。

把 LLM judge 的 0.9 分叫“reward”并不意味着系统在做强化学习，更不意味着它和业务价值对齐。

## 7. 停止是一个决策问题

“没有工具调用就结束”只是 API 现象，不是可靠停止条件。Agent 在每一步要比较继续行动的期望信息价值与代价：

\[
VOI(a)=E[U\mid \text{执行 }a]-U(\text{现在停止})
\]

当所有可用动作的预期增益都不超过成本与风险时，应该停止：

\[
\max_a VOI(a) \le C(a)+Risk(a)
\]

生产系统无法精确求解，但可以用可测代理：

- 必要证据覆盖率是否达到门槛。
- 新搜索结果的独立 claim 增量是否趋近 0。
- 未解决高风险 unknown 是否仍存在。
- 下一动作是否超过 deadline/token/tool/人工预算。
- verifier 是否确认所有硬约束满足。

硬上限仍然必须存在，因为模型估计的 VOI 可能错误。软停止用于效率，硬停止用于资源和安全边界。

## 8. 部分可观测导致的典型故障

| 故障 | 机制 | 不能只靠 Prompt 修的原因 |
|------|------|--------------------------|
| **Observation aliasing** | 两个不同世界状态看起来相同 | 需要主动探测动作或更多传感器/工具 |
| **陈旧观察** | 读取后世界已变化 | 需要版本、TTL、CAS 和提交前重读 |
| **选择性观察** | 检索只返回支持当前假设的内容 | 需要反证查询、来源多样性和召回评测 |
| **对抗观察** | 网页/邮件把恶意指令伪装成数据 | 需要 provenance、权限和数据/指令隔离 |
| **不可观测副作用** | 请求超时，不知远端是否执行 | 需要幂等键、operation log 和对账 |
| **状态折叠错误** | 摘要删除了关键否定词/约束 | 需要结构化事实、摘要保真测试和原文引用 |

这也是为什么 Agent 的核心问题不能只讨论“模型推理能力”。观察通道和状态估计错误，足以让一个强模型稳定做错。

## 9. 主动感知：有些工具调用不是为了完成动作

动作可以分为：

- **Epistemic action（认知动作）**：为了减少不确定性，如查询、搜索、向用户澄清。
- **World-changing action（改变世界的动作）**：更新数据库、付款、发邮件。

认知动作通常可重试、风险较低；改变世界的动作必须有更强的授权和幂等语义。一个可靠策略往往先用认知动作降低 belief uncertainty，再提交写动作。

例如退款 Agent 不应在只看到“用户说没收到货”时直接退款，而应先读取订单、物流、历史退款和策略版本。这个过程不是“多想几步”，而是**选择能最大幅度降低决策不确定性的观察动作**。

---

## 10. 三种“学习”不要混淆

| 机制 | 改变了什么 | 生命周期 | 主要风险 |
|------|------------|----------|----------|
| **参数学习** | 模型权重 | 跨请求、跨用户 | 数据污染、灾难性遗忘、发布风险 |
| **上下文内适应** | 当前 prompt/history | 当前运行或会话 | 窗口截断、指令污染、不可持久 |
| **外部记忆更新** | 数据库/向量库/知识图 | 跨会话 | 错误固化、冲突、隐私删除、陈旧事实 |

Reflexion 把语言反馈写入 episodic memory，通常属于后两类，不是更新模型参数的强化学习。面试中说“Agent 会自己学习”时，必须说明到底改变了哪个状态、由谁审核、何时失效以及如何回滚。

## 11. 完整案例：把退款 Agent 写成决策问题

### 11.1 状态与观察

- 真实状态 \(S\)：订单、支付、物流、用户身份、政策版本、历史退款。
- 观察 \(O\)：各系统查询结果、用户陈述、错误和审批反馈。
- belief：已确认事实、冲突信息、未知项、新鲜度。

### 11.2 动作

- 读动作：查订单、支付、物流、策略。
- 交互动作：向用户补充提问、请求人工审批。
- 写动作：创建退款、更新工单、通知用户。
- 终止动作：批准、拒绝、转人工、等待外部事件。

### 11.3 效用与约束

- 正确解决请求提高 \(Q\)。
- 重复工具调用增加 \(C\) 和 \(L\)。
- 错误退款的损失进入 `Risk`，且高金额退款必须满足审批硬约束。
- `create_refund` 必须携带订单版本和 idempotency key；超时后进入 `OUTCOME_UNKNOWN`，先对账再重试。

### 11.4 如何证明设计更好

对比三个版本：

1. 直接根据用户文本决定。
2. 固定工作流读取四个系统后决定。
3. Agent 根据 belief 选择认知动作，但写操作受相同确定性控制面约束。

在同一任务集上测最终账务状态、错误退款、人工率、工具数、p95 延迟和成本。只有第三版在某些分群上形成 Pareto 改善，动态 Agent 才有存在价值。

## 12. 面试追问树

### Q1：为什么 LLM Agent 可以看成 POMDP？

答题骨架：真实世界状态不可完全见；模型只通过工具/界面得到观察；动作会改变状态；下一步依赖历史形成的 belief；目标是带成本和风险的长期效用。再补一句：实际系统通常不求解精确 POMDP，而是用结构化任务状态近似。

### Q2：上下文窗口是不是 Agent 的状态？

不是。它是当前策略调用的输入投影。真实世界状态在外部系统，任务状态在持久化存储，belief 是证据化估计，聊天历史只是 observation log。把它们都塞进 messages 会导致新鲜度、冲突和恢复问题。

### Q3：Workflow 和 Agent 的本质区别？

不要只答“是否用 LLM”。看运行时把多少控制权交给策略：动作集合、控制流、目标分解和终止是否动态决定。它是连续谱；生产系统通常是确定性 workflow 外壳包住局部 agentic 节点。

### Q4：什么时候 Agent 应该停止？

当成功条件满足、关键未知项消除，且继续动作的边际信息价值不抵成本/风险时软停止；同时受步数、成本、deadline 和权限硬上限约束。不能仅相信模型说“完成了”。

### Q5：Reflection 算不算强化学习？

通常不算参数层 RL。Reflexion 使用反馈生成语言记忆，在后续 trial 中通过上下文影响策略；模型权重不更新。要明确 feedback、memory 和 policy update 分别发生在哪里。

## 13. 检验清单

- [ ] 能写出 POMDP 七元组，并把一个业务 Agent 映射到每个元素。
- [ ] 能解释 observation、event log、belief、working context 和 world state 的区别。
- [ ] 能说明最终 Agent 策略为什么是模型与 harness 的复合物。
- [ ] 能从控制权和策略选择空间解释 workflow/Agent 连续谱。
- [ ] 能写出质量、成本、延迟、风险的多目标效用，并指出哪些风险必须做硬约束。
- [ ] 能用信息价值解释停止和主动查询，而不只说“设 max steps”。
- [ ] 能区分参数学习、上下文适应与外部记忆更新。

## 14. 一手资料

- [OSWorld](https://arxiv.org/abs/2404.07972)：将通用计算机 Agent 任务形式化为 POMDP，并公开环境与评测。
- [ReAct](https://arxiv.org/abs/2210.03629)：交错生成推理轨迹与环境动作的原始工作。
- [Reflexion](https://arxiv.org/abs/2303.11366)：语言反馈、episodic memory 与后续 trial 改进；不更新模型权重。
- [OpenAI Agents SDK](https://developers.openai.com/api/docs/guides/agents)：区分由应用拥有循环的 Responses API 与由 SDK 管理 loop/state/handoff 的 Agent run。
