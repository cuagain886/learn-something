## 1. 一个贯穿全程的心智模型

### 1.1 Agent 的本质：循环 + 自主决策

> 普通 LLM 调用是"一问一答"；**Agent 是把 LLM 放进一个循环里，让它反复"思考下一步→采取行动→观察结果"，由它自己决定何时停止。**

```
普通调用：   输入 ──→ LLM ──→ 输出（结束）

Agent：      目标 ──→ ┌─────────────────────────────┐
                      │  LLM 思考"下一步做什么"       │
                      │      ↓                        │
                      │  采取行动（调用工具）          │ ←─ 循环
                      │      ↓                        │
                      │  观察结果，喂回 LLM            │
                      └──────────┬──────────────────┘
                                 ↓ （LLM 判断"完成了"）
                              最终答案
```

这个循环就是 Agent 的"引擎"。[文档 01](01-Agent循环与ReAct.md) 会把它拆到最细。

### 1.2 设计模式是"循环的不同玩法"

本专题的几个模式，本质都是在改造这个基础循环：

| 模式 | 对循环做了什么 |
|------|----------------|
| **ReAct** | 最基础的循环：思考与行动交替 |
| **Tool Use** | 循环里"行动"的具体实现——调用外部工具 |
| **Reflection** | 在循环里加一步"自我评估→修订" |
| **Planning** | 循环开始前/中途先产出一个"计划"，按计划走 |
| **Multi-Agent** | 把循环拆给多个专职 Agent，各跑各的再协作 |

### 1.3 最重要的一条纪律：从简单开始 ⭐

这是贯穿整个专题、也是 2026 业界（尤其 Anthropic）反复强调的：

> **先建立最简单、可评测的 ReAct + 好工具基线。** 是否足够必须由你的任务分布、成本和风险 SLO 证明，不能引用跨任务通用比例。
> 其它模式（规划、反思、多智能体）都是为**特定失败模式**准备的：
> - 成本太高 → ReWOO / 减少 LLM 调用
> - 计划太复杂、步骤多 → Plan-and-Execute
> - 正确性不够 → Reflection / Reflexion
> - 单 Agent 上下文/角色不够 → Multi-Agent
>
> **如果你还没遇到这些失败，就别加对应的复杂度。让失败来告诉你何时"毕业"到更复杂的模式。**

[文档 06](06-模式选择与组合.md) 会把这条纪律变成可操作的决策树。

```
01 Agent循环与ReAct  ← 必读，地基。先彻底搞懂基础循环
        ↓

        ↓

        ↓
07 形式化模型 → 08 搜索规划  ← 面试深挖：机制、假设、算法与验证
```

- **前两篇（01、02）是地基，必须动手实现。** 一个能调用工具的 ReAct 循环，就是你的第一个真正的 Agent。
- **中间三篇（03、04、05）按需深入**，理解它们各自针对的失败模式即可，不必全部立刻上手。
- **06 是工程决策收口，07/08 是面试深挖**：前者告诉你怎么选，后两篇解释为什么这些模式在部分可观测环境和有限计算预算下成立或失效。

## 4. 动手项目（边学边做）

学完本专题，目标是搭出这样一个 Agent：

```
一个"研究助手" Agent：
  - 工具：网络搜索、网页抓取、（可选）RAG 检索本地知识库、计算器
  - 循环：ReAct —— 思考要查什么 → 搜索 → 读结果 → 判断够不够 → 不够再搜 → 汇总
  - 进阶：给最终报告加一轮 Reflection（自我评估是否完整、有无遗漏）
  - 控制：设最大步数上限、处理工具失败、防止重复搜同样的东西
```

这个项目能串联 01-04，但是否真正掌握要靠隐藏任务集、工具故障注入、世界状态 oracle 和同预算基线，而不是 demo 能跑通。

## 5. 本专题的核心结论（剧透）

- “模型 + 工具 + 循环”只是最小外形；更准确的 Agent 是**在部分可观测环境中由策略选择动作、由确定性控制面约束执行的闭环系统**。
- **ReAct 是候选基线**；它是否满足任务要用最终状态、成本、延迟和风险评测证明。
- Agent 可形式化为部分可观测决策系统；messages 只是 observation history，不是完整状态。
- Planning 的本质是在候选轨迹中分配测试时计算；verifier 决定搜索上限，也会引入 Goodhart 风险。
- 工具是能力与风险边界：描述/schema 只解决发现和结构；effect/error/权限/幂等/结果验证决定动作能否可靠落地。模型、上下文、环境和 verifier 同样可能成为系统瓶颈。
- **进阶模式是"失败驱动"的**：先遇到失败，再上对应模式，别提前过度工程。
- **循环控制（停止条件、步数上限、防循环）是工程重点**，否则 Agent 会无限循环、烧钱、跑飞。

## 6. 面试追问树

| 层次 | 追问 | 合格回答必须覆盖 |
|---|---|---|
| 定义 | Agent 和 workflow/单次 LLM 的边界是什么？ | 动态决策权、环境交互、状态、终止，而非“会调用工具” |
| 机制 | ReAct/Planning/Search 如何分配 test-time compute？ | belief/observation、候选动作、verifier、budget、stopping |
| 反例 | 为什么多思考、多反思或多 Agent 可能更差？ | 相关错误、judge 偏差、Goodhart、成本、误差与协调放大 |
| 落地 | 工具调用如何安全、幂等、可恢复？ | typed schema、effect/error contract、receipt、result unknown、权限 |
| 评测 | 如何证明 planning/reflection/multi-Agent 有效？ | 单 Agent/同预算 Best-of-N 基线、paired ablation、world-state、cost/success |
| 边界 | 为什么不能把隐藏 CoT 当审计证据？ | 可见动作/状态/引用是证据；自然语言理由可能不忠实 |
