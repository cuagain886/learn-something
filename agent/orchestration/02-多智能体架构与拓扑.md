# 02 · 多智能体架构与拓扑

> 目标：掌握动态多 Agent 的拓扑、任务所有权、上下文隔离、故障域与负载控制。Supervisor/去中心 handoff 只是控制权分布的两端，不存在脱离任务与实现的固定“更准/更快”排名。

---

## 1. 前提：你确实需要多智能体了吗

再次重申 [agent-core/05](../agent-core/05-多智能体协作模式.md) 的纪律（本专题不再展开，但默认你已接受）：

> 先建立**单 Agent 基线**。只有在上下文隔离、权限隔离、动态任务分解、并行关键路径或组织边界带来可测收益时才上多 Agent。Agent 数量本身既不代表能力，也不必然把成功概率简单“乘以 N”；系统结果取决于失败相关性、依赖结构、验证器和协调协议。

如果你已确认需要，本章讲怎么组织这些 Agent。

---

## 2. 单 Agent vs 多 Agent 的本质权衡

| | 单 Agent（多工具） | 多 Agent |
|---|---|---|
| 上下文 | 全在一个窗口（易膨胀/串味） | 每个 Agent 上下文**隔离、聚焦** |
| 专长 | 一个"通才" | 多个"专才" |
| 控制 | 简单、可预测 | 复杂、需协调 |
| 成本/延迟 | 低 | 高（多次调用+协调） |
| 调试 | 容易 | 难（失败可能在任一 Agent 或交接处） |

多 Agent 常见收益不是“角色扮演更聪明”，而是形成可强制的边界：

- **上下文边界**：每个 worker 只接收当前 work item 的证据和工具。
- **权限边界**：研究 Agent 只能读，发布 Agent 才可能写，审批不能被普通 worker 绕过。
- **资源边界**：不同模型、sandbox、地域或数据域分开运行。
- **并行边界**：独立 work item 能以受控 fan-out 缩短关键路径。

如果所谓“专长”只是给同一模型换了角色名、却共享同一上下文和工具，收益需要特别谨慎验证。

## 3. 四种核心拓扑

### 3.1 Supervisor（监督者 / 中央编排）⭐

一个**中央 Supervisor** 接收所有输入、判断意图、路由给合适的专门 Agent；专门 Agent 完成后**控制权交回 Supervisor**，由它决定继续路由还是结束。

```
            ┌─────────────────────────────┐
用户 ──→ [Supervisor] ←──────────────────┐ │
            │ 分类意图、决定派给谁          │ │ 控制权返回
       ┌────┼─────────┬──────────┐       │ │
       ▼    ▼         ▼          ▼       │ │
   Agent A  Agent B  Agent C  Agent D ───┘─┘
   (研究)   (写作)   (代码)   (检索)
```

- **优点**：路由、预算、最终汇总与 guardrail 可以集中；控制流更容易审计。是否“更准”取决于 router eval，不能由拓扑推出。
- **缺点**：每次都要过 Supervisor（多一跳，**更慢、更多 token**）；Supervisor 是单点。
- **适用**：需要单一答案 owner、集中策略和全局资源调度的场景。
- 这是 [文档 01](01-工作流编排五种模式.md) "编排者-工人"的多智能体版。

### 3.2 Swarm（蜂群 / 去中心化交接）⭐

**没有 Supervisor**。Agent 之间**直接互相交接（handoff）**——一个 Agent 判断该轮到谁，就把控制权直接交给那个 Agent。

```
用户 ──→ Agent A ──handoff──→ Agent B ──handoff──→ Agent C ──→ 输出
        (自己判断该交给谁，直接转交，无中介)
```

- **优点**：在接收方明确且不需要集中汇总时，可以少一次中央模型路由；实际端到端时延仍取决于 handoff 数、上下文重建、网络和重试。
- **缺点**：路由策略分散，容易出现交接环、责任漂移和权限扩散；必须把 active owner、handoff history、预算和状态版本持久化。checkpoint 只是载体，真正要求是 durable ownership state。
- **适用**：交接逻辑相对明确、追求低延迟的场景。
- **实现**（以 LangGraph 为例）：交接通过 `create_handoff_tool` 生成的工具完成，Agent 调用它时返回一个 `Command(goto=目标, graph=PARENT)`，更新父图状态并把执行重定向到目标 Agent。

> **Supervisor vs 去中心 handoff 的本质是决策权与答案所有权放在哪里。** 前者集中，后者随 handoff 转移。比较时应测路由错误、handoff 次数、context token、p95、级联失败和审计复杂度，而不是背“准 vs 快”。

### 3.3 Hierarchical（分层）

Supervisor 之下还有子 Supervisor，形成多层团队（"团队的团队"）。

- **适用**：超大型、可层层分解的任务（一个总编排者管几个领域编排者，每个领域编排者管自己的专才）。
- **代价**：协调开销和延迟最高，调试最难。**慎用**，只在任务规模真的需要时。

### 3.4 Network（网络 / 自由协作）

Agent 之间多对多自由通信，无固定层级。最灵活也最难控制和预测，**生产中少见**，多用于研究性的协作/辩论场景（[agent-core/05](../agent-core/05-多智能体协作模式.md) 的 Debate）。

### 3.5 拓扑图不等于执行语义

同一个 Supervisor 图可以有完全不同的可靠性。拓扑至少还需标注：

```yaml
edge_contract:
  from: planner
  to: researcher
  transfer: delegation       # delegation | handoff | event
  answer_owner_after: planner
  payload_schema: WorkItemV2
  allowed_state_projection: [goal, evidence_refs]
  timeout_ms: 45000
  retry_policy: transient_only
  cancel_propagation: true
  max_traversals_per_task: 2
```

- **delegation/agent-as-tool**：调用者仍是 owner，子 Agent 返回结果。
- **handoff**：接收者成为当前回复/决策 owner。
- **event**：生产者不等待特定接收者；需要消息去重、顺序与消费确认。

这三种边画成同一条箭头会掩盖完全不同的失败和恢复语义。

## 4. 上下文隔离 vs 共享（编排的关键设计）⭐

多 Agent 一定要回答："各 Agent 之间，信息怎么传、共享多少？"——这直接关系效果和成本。

- **完全隔离**：每个 Agent 只看自己的输入和工具。上下文最干净，但交接时要显式传递必要信息，否则下游"缺信息"。
- **共享状态（黑板）**：所有 Agent 读写一块共享状态。协作方便，但容易互相干扰、上下文膨胀、串味。
- **交接时传上下文**：Agent 交接时携带"足够但不冗余"的上下文（OpenAI Agents SDK 的 handoff 就是"转移控制并携带对话上下文"）。

> 设计要点（呼应 [context-engineering/](../context-engineering/00-MCP与上下文工程学习总览.md)）：
> - **传太少** → 下游 Agent 缺上下文，重复劳动或答错。
> - **传太多** → 上下文膨胀、信噪比下降、成本上升、迷失在中间。
> - **找平衡**：交接时只传"下游完成任务所必需"的摘要/关键信息，而非整个历史。

记忆维度还要考虑：**各 Agent 共享长期记忆还是各自独立？** 多租户下记忆要按用户隔离（[context-engineering/03](../context-engineering/03-Agent记忆系统.md)）。共享 storage 不等于共享全部可见性；每个 Agent 仍通过 capability、scope 和 context assembler 获取最小投影。

### 4.1 Handoff payload 是状态投影，不是一段随意摘要

```yaml
handoff:
  handoff_id: ho_88
  task_id: task_7
  from_owner: triage
  to_owner: refund
  reason: duplicate_charge
  objective: "验证重复扣款并提出退款"
  invariants: ["不得直接 commit", "金额上限 500"]
  artifact_refs: [artifact://ledger/tx-9]
  unresolved: ["客户时区未知"]
  committed_effects: []
  state_version: 14
  capability_grant: [ledger.read, refund.propose]
  deadline: 2026-07-19T12:00:00+08:00
```

接收方以 `state_version` 接管；旧 owner 的迟到写入必须被 CAS 拒绝。摘要只表达语义，不能代替已提交副作用、审批和 artifact hash。

## 5. 所有权、一致性与故障隔离

### 5.1 一个 work item 同时只能有一个提交 owner

并行读取可以多 owner，但改变同一业务对象的写入需要串行化、分区或冲突协议：

```text
READY → LEASED(owner, lease_until, version)
       → COMMITTING(idempotency_key)
       → SUCCEEDED(receipt) | RETRYABLE | FAILED | OUTCOME_UNKNOWN
```

- lease 过期允许重新认领，但旧 worker 可能仍在运行，因此写入还需 fencing token/version。
- `OUTCOME_UNKNOWN` 先对账，不可直接重试非幂等动作。
- handoff 应原子地更新 owner 与 state version，避免两个 Agent 都认为自己有权回复/提交。

更完整的一致性模型见 [多 Agent 并发与一致性](../systems-engineering/06-多Agent并发与一致性.md)。

### 5.2 故障域和 bulkhead

每个 Agent/tenant/tool pool 应有独立并发、队列和预算。一个慢的浏览器 Agent 不应耗尽退款系统线程；一个递归 planner 不应生成无限任务。至少设置：

- 每任务/租户/Agent 的最大并发、fan-out、队列长度、token 与 wall-clock。
- per-edge timeout、circuit breaker、retry budget 和降级路径。
- 父子 cancellation token；对子任务已经提交的 effect 做 reconciliation/compensation。
- required/optional work item，允许明确的 partial result，而不是 silent partial success。

### 5.3 背压是正确性问题

队列满时继续接单会让证据过期、lease 超时并触发重试风暴。背压策略可以是拒绝并返回 retry-after、降低并行度、切换低成本路径、延迟非关键任务或要求用户缩小范围。不能仅靠“自动扩容”，因为下游 API 配额和人工审批能力可能不可扩。

## 6. 选择拓扑的决策

```
需要一个组件拥有最终答案/全局预算？     → manager + agents-as-tools
希望专员直接接管用户回复？             → handoff，并持久化 owner/version
子任务可形成稳定组织/权限边界？         → hierarchical，但限制深度/fan-out
跨系统异步长任务？                     → task protocol/event，不要伪装成本地函数
多对多协作确有基准收益？               → network，并加 ownership/bulkhead

横切：无论哪种，都要先想清楚"上下文隔离 vs 共享"的策略
```

先实现单 Agent 和 code-routed 基线。若需要多 Agent，通常从“manager 调 bounded specialist”开始，因为答案 owner 明确；但用户对话需专员持续接管时，handoff 更自然。最终按 eval 选择，不能把任一拓扑写成默认真理。

## 7. 常见坑

- **拓扑选太复杂**（一上来分层/网络）→ 协调成本超过专业化收益；先做单 Agent/code route 基线。
- **只开 checkpoint 就认为 handoff 可靠** → 还缺 owner、version、lease、fencing 与迟到写拒绝。
- **交接传上下文传太多/太少** → 膨胀 或 缺信息。要传"必需的摘要"。
- **没想清隔离 vs 共享** → 要么 Agent 互相串味，要么缺信息。设计期就定。
- **Supervisor 成性能瓶颈/单点** → 高频场景注意它的开销和可用性。
- **共享黑板任意写** → 最后写入覆盖、来源不明、恶意 Agent 污染全局；声明 read/write set 与 reducer/CAS。
- **没有 bulkhead/backpressure** → 一个慢 Agent 或重试风暴拖垮全局。
- **父任务结束而子任务继续** → 成本泄漏或迟到副作用；传播取消并核对 effect。
- **把"步骤多"当成"要多 Agent"** → 多半是 [文档 01](01-工作流编排五种模式.md) 的工作流或 [agent-core/04](../agent-core/04-规划模式Planning.md) 的规划该做的事。

## 8. 本章小结

- 多 Agent 的实在价值 = **上下文隔离 + 专长分工**，代价是协调开销、成本、调试难。
- 四种拓扑只是控制权结构；真正语义由 delegation/handoff/event、答案 owner、state version、失败与取消契约决定。
- manager-style 保留答案所有权；handoff 转移当前回复所有权。不能把差异简化为“准 vs 快”。
- **上下文隔离 vs 共享**要落实为带 artifact、invariant、capability 和版本的状态投影，而不只是“传一段摘要”。
- 可靠多 Agent 需要单 writer/lease/fencing、bulkhead、backpressure、取消传播和 outcome reconciliation。
- 拓扑从简单起步，按真实瓶颈升级。
