# 02 · 多智能体架构与拓扑

> 目标：掌握动态多 Agent 系统的几种拓扑结构，尤其 **Supervisor vs Swarm** 这对核心取舍，以及上下文隔离与交接。这是 [agent-core/05](../agent-core/05-多智能体协作模式.md) 的工程化深入。

---

## 1. 前提：你确实需要多智能体了吗

再次重申 [agent-core/05](../agent-core/05-多智能体协作模式.md) 的纪律（本专题不再展开，但默认你已接受）：

> **单 Agent + ReAct + 好工具能解决大多数任务。** 只有当任务**确实需要超出单个上下文的不同专长、需要上下文隔离、或子任务天然并行可加速**时，才上多智能体。它把不确定性乘以 N，还新增协调开销。

如果你已确认需要，本章讲怎么组织这些 Agent。

---

## 2. 单 Agent vs 多 Agent 的本质权衡

| | 单 Agent（多工具） | 多 Agent |
|---|---|---|
| 上下文 | 全在一个窗口（易膨胀/串味） | 每个 Agent 上下文**隔离、聚焦** |
| 专长 | 一个"通才" | 多个"专才" |
| 控制 | 简单、可预测 | 复杂、需协调 |
| 成本/延迟 | 低 | 高（多次调用+协调） |
| 调试 | 容易 | 难（失败可能在任一 Agent 或交接处） |

> **多 Agent 最实在的价值是"上下文隔离 + 专长分工"**：每个 Agent 只看自己那摊、只带自己需要的工具，上下文更干净（呼应 [context-engineering/02](../context-engineering/02-上下文工程基础.md) 的高信噪比）。代价是协调。

---

## 3. 四种核心拓扑

### 3.1 Supervisor（监督者 / 中央编排）⭐

一个**中央 Supervisor** 接收所有输入、判断意图、路由给合适的专门 Agent；专门 Agent 完成后**控制权交回 Supervisor**，由它决定继续路由还是结束。

```
            ┌─────────────────────────────┐
用户 ──→ [Supervisor] ←──────────────────┐ │
            │ 分类意图、决定派给谁          │ │ 控制权返回
       ┌────┼─────────┬──────────┐       │ │
       ▼    ▼         ▼          ▼       │ │
   Agent A  Agent B  Agent C  Agent D ───┘─┘
   (研究)   (写作)   (代码)   (检索)
```

- **优点**：**Supervisor 路由更准**——因为路由是它唯一的工作（专注的 prompt、专门的 LLM 调用）。控制流清晰、可追踪、易加护栏。
- **缺点**：每次都要过 Supervisor（多一跳，**更慢、更多 token**）；Supervisor 是单点。
- **适用**：需要可控、可审计、对路由准确性要求高的场景。**多数生产系统的默认选择。**
- 这是 [文档 01](01-工作流编排五种模式.md) "编排者-工人"的多智能体版。

### 3.2 Swarm（蜂群 / 去中心化交接）⭐

**没有 Supervisor**。Agent 之间**直接互相交接（handoff）**——一个 Agent 判断该轮到谁，就把控制权直接交给那个 Agent。

```
用户 ──→ Agent A ──handoff──→ Agent B ──handoff──→ Agent C ──→ 输出
        (自己判断该交给谁，直接转交，无中介)
```

- **优点**：**更快**——跳过了 Supervisor 这个中介。
- **缺点**：每个 Agent 都要"知道能交给谁、何时交"，逻辑分散；控制流不如 Supervisor 清晰；**必须配 checkpoint 记住"当前激活的是哪个 Agent"**，否则多轮对话会"忘了"上次轮到谁、丢失历史（见 [文档 03](03-状态管理与控制流.md)）。
- **适用**：交接逻辑相对明确、追求低延迟的场景。
- **实现**（以 LangGraph 为例）：交接通过 `create_handoff_tool` 生成的工具完成，Agent 调用它时返回一个 `Command(goto=目标, graph=PARENT)`，更新父图状态并把执行重定向到目标 Agent。

> **Supervisor vs Swarm 是本章最核心的一对取舍：Supervisor 更准、更可控（路由是专职）；Swarm 更快（省去中介）。** 不确定就先用 Supervisor。

### 3.3 Hierarchical（分层）

Supervisor 之下还有子 Supervisor，形成多层团队（"团队的团队"）。

- **适用**：超大型、可层层分解的任务（一个总编排者管几个领域编排者，每个领域编排者管自己的专才）。
- **代价**：协调开销和延迟最高，调试最难。**慎用**，只在任务规模真的需要时。

### 3.4 Network（网络 / 自由协作）

Agent 之间多对多自由通信，无固定层级。最灵活也最难控制和预测，**生产中少见**，多用于研究性的协作/辩论场景（[agent-core/05](../agent-core/05-多智能体协作模式.md) 的 Debate）。

## 4. 上下文隔离 vs 共享（编排的关键设计）⭐

多 Agent 一定要回答："各 Agent 之间，信息怎么传、共享多少？"——这直接关系效果和成本。

- **完全隔离**：每个 Agent 只看自己的输入和工具。上下文最干净，但交接时要显式传递必要信息，否则下游"缺信息"。
- **共享状态（黑板）**：所有 Agent 读写一块共享状态。协作方便，但容易互相干扰、上下文膨胀、串味。
- **交接时传上下文**：Agent 交接时携带"足够但不冗余"的上下文（OpenAI Agents SDK 的 handoff 就是"转移控制并携带对话上下文"）。

> 设计要点（呼应 [context-engineering/](../context-engineering/00-MCP与上下文工程学习总览.md)）：
> - **传太少** → 下游 Agent 缺上下文，重复劳动或答错。
> - **传太多** → 上下文膨胀、信噪比下降、成本上升、迷失在中间。
> - **找平衡**：交接时只传"下游完成任务所必需"的摘要/关键信息，而非整个历史。

记忆维度还要考虑：**各 Agent 共享长期记忆还是各自独立？** 多租户下记忆要按用户隔离（[context-engineering/03](../context-engineering/03-Agent记忆系统.md)）。

## 5. 选择拓扑的决策

```
需要可控、可审计、路由要准？        → Supervisor（默认）
交接逻辑明确、追求低延迟？          → Swarm（记得配 checkpoint）
任务超大、可层层分解？             → Hierarchical（慎用）
研究性协作/辩论？                  → Network（生产少用）

横切：无论哪种，都要先想清楚"上下文隔离 vs 共享"的策略
```

> 务实建议：**从 Supervisor 起步。** 它控制流清晰、最好加护栏和观测，是多数团队的稳妥选择。确有延迟瓶颈、且交接逻辑清楚，再考虑 Swarm。

---

## 6. 常见坑

- **拓扑选太复杂**（一上来分层/网络）→ 协调地狱。从 Supervisor 起。
- **Swarm 不配 checkpoint** → 多轮对话"忘了"当前激活 Agent、丢历史。
- **交接传上下文传太多/太少** → 膨胀 或 缺信息。要传"必需的摘要"。
- **没想清隔离 vs 共享** → 要么 Agent 互相串味，要么缺信息。设计期就定。
- **Supervisor 成性能瓶颈/单点** → 高频场景注意它的开销和可用性。
- **把"步骤多"当成"要多 Agent"** → 多半是 [文档 01](01-工作流编排五种模式.md) 的工作流或 [agent-core/04](../agent-core/04-规划模式Planning.md) 的规划该做的事。

---

## 7. 本章小结

- 多 Agent 的实在价值 = **上下文隔离 + 专长分工**，代价是协调开销、成本、调试难。
- 四种拓扑：**Supervisor（中央协调，准、可控，默认）、Swarm（去中心交接，快，需 checkpoint）、Hierarchical（分层，超大任务，慎用）、Network（自由协作，生产少用）**。
- **Supervisor vs Swarm 是核心取舍**：准/可控 vs 快。不确定先用 Supervisor。
- **上下文隔离 vs 共享**是编排的关键设计：交接传"必需的摘要"，平衡"缺信息"与"膨胀"。
- 拓扑从简单起步，按真实瓶颈升级。
