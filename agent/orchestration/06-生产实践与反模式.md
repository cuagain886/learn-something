# 06 · 多智能体生产实践：SLO、故障域与因果评测

> 目标：把多 Agent 从“能演示”推进到可运行服务：定义 SLO/错误预算、隔离级联故障、观测跨 Agent 因果链、控制关键路径与成本，并证明增加 Agent 确实带来净收益。

---

## 1. 不要说“可靠性乘以 N”，先画依赖图

若一个任务必须顺序通过 (n) 个独立组件，且每个成功率为 (p_i)，理想化全链路成功率是：

\[
P(success)=\prod_{i=1}^{n}p_i
\]

但真实 Agent 失败并不独立：相同模型、prompt、数据源或工具会产生**相关错误**；并行 quorum、fallback 和 verifier 又可能提高结果。因此“多 Agent 必然把不确定性乘 N”只是警示，不是可直接套用的数学结论。应从任务 DAG 推导：

- 哪些节点是 required、optional、fallback 或 speculative。
- 哪些错误共享 common cause（模型、provider、index、policy）。
- 哪些分支结果由确定性 verifier 验证。
- 哪些 effect 已不可撤销，取消只停止后续工作。

## 2. 先定义 SLO 与风险预算

### 2.1 不同任务等级使用不同 SLO

| 等级 | 示例 | 关键 SLO/控制 |
|------|------|---------------|
| R0 只读低风险 | 内部资料摘要 | 成功率、groundedness、p95、成本 |
| R1 可恢复写 | 创建草稿/工单 | 幂等、可撤销、审计、失败恢复 |
| R2 对外/财务写 | 发邮件、退款提案 | proposal approval、权限、receipt、至多一次业务 effect |
| R3 高影响 | 大额支付、删除核心数据 | 双人/外部审批、强规则、极低自动化或禁止 |

一个退款 Agent 的 SLO 示例：

```yaml
slo:
  valid_refund_decision_rate: ">= 99.5%"
  unauthorized_commit_rate: "0"
  duplicate_refund_rate: "0"
  evidence_freshness_violation: "< 0.1%"
  p95_proposal_latency: "< 12s"
  p95_approval_resume_latency: "< 5s"
  mean_cost_per_completed_case: "< $0.08"
```

百分比必须绑定任务定义、风险样本、时间窗口和置信区间；这里是设计示例，不是行业基准。

### 2.2 预算是分层的

```yaml
run_budget:
  wall_clock_ms: 90000
  model_calls: 24
  input_tokens: 220000
  output_tokens: 18000
  tool_calls: 30
  remote_tasks: 6
  handoffs: 4
  fanout: 5
  retries: 5
```

worker 只能消费父任务授予的子预算；递归委派不能重新生成完整预算。预算耗尽是显式终态/升级理由，不应由模型自行忽略。

## 3. 统一错误代数与传播策略

跨 Agent 只传 `"failed"` 不够。至少区分：

```text
INVALID_INPUT       不重试，澄清/拒绝
UNAUTHORIZED        不重试，重新授权或升级
POLICY_DENIED       不重试，记录规则
NOT_FOUND           可能换来源
STALE_VERSION       重读 + replan
CONFLICT            对账/CAS/人工
RATE_LIMIT          带 retry-after 退避
TRANSIENT           有界重试
PERMANENT           fallback/失败
TIMEOUT_BEFORE_SEND 可安全按策略重试
OUTCOME_UNKNOWN     先查 receipt/task，不直接重试非幂等 effect
CANCELED            停止新工作，对已提交 effect 对账
```

### 3.1 错误传播矩阵

| 子任务类型 | 子任务失败 | 父任务行为 |
|------------|------------|------------|
| required | 无替代证据 | fail/clarify/escalate，不得伪装成功 |
| optional | 可缺失 | 输出 partial 并声明 coverage |
| redundant | quorum 仍满足 | 取消剩余/继续聚合 |
| speculative | 未获 verifier 通过 | 丢弃候选，不污染 best-so-far |
| side-effecting | outcome unknown | 进入 reconciliation，阻塞重复提交 |

重试要有全局 retry budget，防止每层各重试 3 次造成指数放大。circuit breaker 针对故障下游停止新请求；bulkhead 防止该下游的队列/线程耗尽其他 Agent。

## 4. 负载控制：fan-out、背压与取消传播

### 4.1 并行不是越多越快

端到端延迟由关键路径决定：

\[
T_{run}\approx\sum_{v\in critical\ path}T_v + T_{queue}+T_{join}+T_{replan}
\]

并行分支延迟近似取最大值，成本近似求和。增加 worker 可能受到下游 QPS、排队、rate limit 和串行汇总限制。应观察 concurrency—throughput—p95 曲线，而不是只比较单次 demo。

### 4.2 分层限流与公平性

- global / tenant / user / agent / tool 五层 concurrency 与 token bucket。
- queue length、oldest age、deadline slack 和 rejection rate。
- weighted fair queue，防止一个长研究任务饿死短交互任务。
- downstream rate-limit feedback 调整 fan-out，而不是所有 worker 同时重试。

### 4.3 取消是一种协作协议

父 run 取消后：

1. 停止生成新 work item。
2. 向本地 worker 和远程 A2A Task 发送 cancel。
3. 标记无法取消/已提交的 activity，等待最终 receipt。
4. 关闭 stream/subscription，回收 lease 与 sandbox。
5. 聚合 `canceled / cancel_requested / completed_after_cancel / outcome_unknown`。

不能因 UI 已显示“已取消”就假定外部邮件、支付或删除已经撤销。

## 5. 跨 Agent 可观测：记录可见证据和动作，不依赖隐藏推理

一个 run 需要统一 trace tree：

```text
run/task span
 ├─ context_assembly span
 ├─ model_call span
 ├─ route/handoff span
 │   └─ child_agent span
 │       ├─ retrieval span
 │       └─ tool_attempt span
 ├─ approval_wait span（可跨数天，或以 link 关联）
 └─ reconciliation span
```

### 5.1 每类 span 的最低字段

| Span | 必需字段 |
|------|----------|
| Run | task/run ID、tenant、risk class、graph/policy/model version、budget |
| Agent | agent/role/version、owner、input/output schema、token/cost |
| Handoff | from/to、reason、state version、context/artifact IDs、capability grant |
| Tool | tool/schema version、args hash、effect type、idempotency key、outcome/receipt |
| State | expected/new version、changed field IDs、reducer/transition |
| Eval | case/grader version、score、failure taxonomy |

敏感 prompt/输出按 retention 与 DLP 策略保存；必要时保存 hash、受控 artifact ref 和脱敏摘要。记录模型可见输入、结构化业务理由、证据与动作，不把隐藏 chain-of-thought 当审计日志。

### 5.2 必须能回答的诊断问题

1. 首次偏离正确轨迹在哪个 step/span？
2. 正确证据在候选池、装配上下文还是都不在？
3. 谁在什么 state version 下拥有 work item？
4. handoff 是错路由、payload 丢失还是接收方执行错？
5. effect 是否提交，receipt 和 idempotency key 在哪？
6. 新版本相对旧版本首先在哪个决策产生差异？

## 6. 多 Agent 评测必须做因果拆解

“换成多 Agent 后成功率提高”可能同时改变模型调用次数、上下文、工具目录、test-time compute 和 verifier，不能归因于拓扑。

### 6.1 基线与消融

```text
E0 单模型/无工具
E1 单 Agent + 相同工具
E2 E1 + 相同总调用预算的 Best-of-N
E3 manager + specialist（相同模型/总预算）
E4 handoff topology
E5 E4 + durable/HITL/security controls
```

paired cases 固定模型 snapshot、工具/世界快照、预算和 grader。逐次只改变一个因素；对二元 paired outcome 使用 McNemar/paired bootstrap，报告置信区间和风险分层结果。

### 6.2 分层指标

| 层 | 指标 |
|----|------|
| Router | confusion matrix、cost-sensitive error、abstention |
| Handoff | destination accuracy、payload completeness、loop rate、ownership violation |
| Worker | task-specific success、evidence/citation、schema、cost/p95 |
| Join | coverage、conflict resolution、partial-result correctness |
| Coordination | duplicate work、idle/queue time、cancel lag、retry amplification |
| End-to-end | task success、risk-weighted error、human rate、cost、p95/p99 |

再做 MAST 类失败标注：任务分解、角色选择、信息共享、冲突解决、停止/验证等。最终平均成功率可能不变，但 failure taxonomy 会揭示不同架构的事故形态。

### 6.3 线上实验

- shadow：新编排只提出动作，不产生副作用。
- canary：按低风险任务/租户逐步放量。
- champion/challenger：同输入离线或只读并跑，比较轨迹和成本。
- 回滚：保留 graph/policy/model/tool version，暂停中的旧任务按兼容策略处理。

高风险 effect 不适合直接随机 A/B；先用 recorded/sandbox world 或 proposal-level evaluation。

## 7. 安全：Agent 间通信是 trust transition

每次 handoff、shared memory 写入、A2A Message/Artifact 和 tool result 都跨信任边界：

- **身份**：区分用户、调用 Agent、服务 Agent 和工具服务主体；不能共享一把全局 token。
- **授权**：capability 按 work item 下发并有 scope/TTL；接收 Agent 不继承发送者全部权限。
- **信息流**：外部/低信任数据携带 taint，不能被下游提升为 system instruction。
- **共享状态**：单 writer、CAS/reducer、lineage；任意 Agent 不能直接改全局 policy/程序性记忆。
- **artifact**：hash、media type、大小、ACL、恶意内容/SSRF 扫描。
- **动作**：参数校验、额度、审批、sandbox、DLP、幂等与审计在确定性 control plane。

### 7.1 最小 blast radius

按 Agent 职责拆 credential、network egress、data scope 和 sandbox。研究 Agent 被网页注入时，最多能读取允许资料和生成 artifact，不能直接发邮件或退款；发布 Agent 只接受通过 verifier/approval 的结构化 proposal。

## 8. 运行手册与事故演练

上线前至少演练：

1. 模型 provider 故障/高延迟。
2. MCP/A2A server schema/version 改变。
3. checkpoint store 部分不可用。
4. 子 Agent 卡死、泄漏 lease、取消不响应。
5. 大规模 rate limit 导致重试风暴。
6. 错误记忆或恶意 artifact 已传播多个 Agent。
7. effect outcome unknown 与重复消息。
8. graph 升级时有大量暂停审批。

Runbook 要包含检测信号、自动降级、人工 owner、停止副作用的 kill switch、对账查询、污染 lineage 删除、用户通知和复盘数据。kill switch 应在模型外实现。

## 9. 反模式

| 反模式 | 为什么错 | 机制性修复 |
|--------|----------|------------|
| 用 Agent 数量解释能力 | 忽略相关错误和调用预算 | 单 Agent/Best-of-N/多 Agent 等预算消融 |
| 每层独立重试 | 3×3×3 放大、压垮下游 | 全局 retry budget + error algebra + breaker |
| “能并行就并行” | 写冲突、QPS、p95 和成本失控 | DAG/read-write set、join、limit、backpressure |
| UI 显示取消即认为完成 | 远程任务/effect 可能继续 | cancel propagation + final reconciliation |
| trace 只存最终回答 | 无法定位候选/路由/handoff/effect | 跨 Agent span + state/context/artifact IDs |
| 记录隐藏推理做审计 | 不稳定、不可验证、可能不可用 | 记录可见证据、业务理由、状态与动作 |
| 每个 Agent 共用高权限 token | 注入一处即可横向移动 | per-agent/work-item capability 与独立身份 |
| 共享黑板任意写 | 竞态、污染、来源丢失 | owner/CAS/reducer/lineage/write gate |
| 只看平均成功率 | 掩盖高风险和长尾 | risk stratification、p95/p99、failure taxonomy |
| 新拓扑直接承接真实写流量 | 难以安全归因/回滚 | shadow → canary → staged rollout |

## 10. 端到端验收清单

- [ ] 已定义任务等级、质量/风险/延迟/成本 SLO 与统计口径。
- [ ] 父子预算、fan-out、handoff、retry、deadline 有硬上限。
- [ ] 错误区分 outcome unknown、stale version、policy denied、cancel 等语义。
- [ ] 有 per-tenant/agent/tool bulkhead、backpressure 与公平队列。
- [ ] 取消会传播，已提交 effect 会最终对账。
- [ ] trace 贯通 context/model/handoff/worker/tool/approval/reconciliation。
- [ ] 单 Agent、等预算 Best-of-N 与多 Agent 做 paired ablation。
- [ ] router/handoff/worker/join/coordination/end-to-end 分层评测。
- [ ] 身份、capability、taint、shared state 和 artifact 安全边界明确。
- [ ] provider、协议、checkpoint、重试风暴、污染和 graph migration 已演练。
