# 06 · 生产实践与反模式

> 目标：让多智能体/编排系统真正扛得住生产——可靠性、错误传播、可观测、成本/延迟、评估，以及系统化避坑。这是本专题的收口。

---

## 1. 多智能体的"放大效应"：为什么生产更难

单 Agent 的所有挑战（[agent-core/](../agent-core/00-Agent核心学习总览.md)），到多智能体都被**放大**：

```
单 Agent 的问题  ──×N个Agent──→  放大
                 ──+协调──────→  新增：交接错误、状态不一致、错误传播
```

- 失败可能发生在**任一 Agent 内部**，也可能发生在**它们之间的交接处**。
- 一个上游 Agent 的小错，会被下游**放大累积**（错误传播）。
- 成本和延迟随 Agent 数和交接轮数**成倍增长**。

> 所以生产多智能体的核心命题是：**用结构化编排（[文档 03](03-状态管理与控制流.md) 的图/状态/checkpoint）+ 强可观测，把放大的不确定性重新关进笼子。**

---

## 2. 可靠性

### 2.1 错误传播与隔离
- **错误隔离**：一个 Agent 失败，不应让整个系统崩。用 [文档 03](03-状态管理与控制流.md) 的条件边导向"兜底/重试/降级节点"。
- **错误当信号喂回**（[agent-core/02](../agent-core/02-工具使用ToolUse.md) 的原则在多 Agent 同样适用）：子 Agent/工具失败，把错误信息回传给编排者，让它决定重试、换路或上报。
- **防错误累积**：在关键交接点加**验证 gate**（[文档 01](01-工作流编排五种模式.md) 的提示链 gate 思想）——下游接手前先校验上游产物质量。

### 2.2 终止与边界
- **全局步数/预算上限**：不仅单 Agent 要有（[agent-core/01](../agent-core/01-Agent循环与ReAct.md)），**整个多 Agent 系统也要有全局上限**，防止 Agent 之间互相交接成无限循环。
- **防交接环路**：A 交给 B、B 又交回 A 反复横跳。检测交接环、设交接次数上限。
- **超时**：每个 Agent/每次交接设超时，避免某环卡死拖垮全局。

### 2.3 确定性 vs 自主
- 能用确定性（写死的工作流 [文档 01](01-工作流编排五种模式.md)）的地方就别用自主决策。**自主性是为灵活付的"不确定性税"，按需购买。**

---

## 3. 可观测性（多智能体的命脉）⭐

单 Agent 就强调 trace（[INDEX 阶段6](../INDEX.md)），多智能体**更离不开**——否则出问题完全无从下手。

要记录的"决策轨迹"：
- **每个 Agent**：收到什么输入/上下文、思考了什么、调了什么工具、产出什么。
- **每次交接**：谁交给谁、为什么交、带了什么上下文。
- **状态变化**：每步 state 怎么变的（[文档 03](03-状态管理与控制流.md)）。
- **全局**：总步数、各 Agent 调用次数、各段延迟、总成本、token 分布。

> **关键**：要能回答"这个错误发生在**哪个 Agent**、还是**哪次交接**？"——这只有完整的跨 Agent trace 能回答。工具：LangSmith、Langfuse、Arize Phoenix（[INDEX 阶段6](../INDEX.md)）。

---

## 4. 成本与延迟

多智能体是**烧钱烧时间**的大户：

- **成本**：N 个 Agent + 编排者 + 多轮交接 = 调用次数倍增。优化：
  - 简单子任务用**小模型**（路由/分类/汇总不必用最强模型）。
  - **Prompt Caching**（[context-engineering/04](../context-engineering/04-上下文管理技巧.md)）缓存各 Agent 重复的系统提示/工具定义。
  - 交接**只传必需上下文**（[文档 04](04-智能体通信与协议.md)），少传 = 少 token。
  - 能用工作流/单 Agent 解决就别用多 Agent。
- **延迟**：
  - **能并行就并行**（[文档 01](01-工作流编排五种模式.md) 的并行化、Swarm 比 Supervisor 少一跳）。
  - **流式输出**降低体感首字延迟。
  - 减少不必要的交接轮次。

---

## 5. 评估（多智能体评估更难）

呼应 [rag/07](../rag/07-RAG评估与可观测性.md) 和 [INDEX 阶段6](../INDEX.md)，多智能体评估要分层：

- **端到端**：整个系统的任务成功率、质量、成本、延迟。
- **单 Agent 级**：每个专门 Agent 在它那一摊上做得好不好（可单独评，像单元测试）。
- **交接级**：路由/交接决策对不对（该交给 A 却交给了 B？）。
- **轨迹质量**：整条执行路径是否高效（有没有绕路、重复、无效交接）。

> 多智能体一旦改动（加 Agent、改拓扑、改交接逻辑），**务必用评估集回归**——改动的连锁反应比单 Agent 大得多，凭感觉调必翻车。

---

## 6. 安全（攻击面更大，详见 INDEX 阶段7）

- **每个 Agent 最小权限**：按职责给最小工具/数据权限（[context-engineering/01](../context-engineering/01-MCP模型上下文协议.md) 的 MCP 最小权限）。一个 Agent 被攻破，不应殃及全局。
- **交接/通信的边界与鉴权**：跨 Agent（尤其 A2A 跨系统）通信要鉴权、审计，防恶意/被注入的 Agent 影响他人。
- **间接 prompt 注入会在 Agent 间传播**：被注入的内容可能随交接的上下文扩散给下游 Agent。交接的上下文也要审视。
- **高风险动作加 HITL**（[文档 03](03-状态管理与控制流.md)）：多 Agent 自主性高，关键动作更要留人类闸门。

## 7. 反模式（明确避免）

| 反模式 | 为什么错 | 正解 |
|--------|----------|------|
| **过早/无必要上多智能体** | 放大不确定性、成本、调试难 | 先穷尽工作流和单 Agent（[文档01](01-工作流编排五种模式.md)/[agent-core/05](../agent-core/05-多智能体协作模式.md)） |
| **没有全局步数/预算上限** | Agent 互相交接成无限循环烧钱 | 全局上限 + 防交接环 |
| **无跨 Agent trace** | 出问题不知道在哪个 Agent/交接 | 完整决策轨迹（§3） |
| **交接传整段历史** | 上下文膨胀、成本飙升 | 只传必需摘要（[文档04](04-智能体通信与协议.md)） |
| **所有 Agent 都用最强模型** | 成本爆炸 | 简单子任务用小模型 |
| **拓扑过度复杂**（一上来分层/网络） | 协调地狱 | 从 Supervisor 起（[文档02](02-多智能体架构与拓扑.md)） |
| **改了就上、不评估** | 连锁反应大、必翻车 | 评估集回归（§5） |
| **每个 Agent 满权限** | 一处被攻破殃及全局 | 每 Agent 最小权限（§6） |
| **能确定性却用自主** | 白付不确定性税 | 能写死就写死（[文档01](01-工作流编排五种模式.md)） |

---

## 8. 本章小结

- 多智能体把单 Agent 的问题**×N 并新增交接错误/状态不一致/错误传播**，生产更难——靠**结构化编排 + 强可观测**重新关进笼子。
- **可靠性**：错误隔离、错误喂回、交接 gate 校验、**全局步数/预算上限 + 防交接环 + 超时**；能确定性就别自主。
- **可观测是命脉**：完整跨 Agent trace，要能定位"错误在哪个 Agent 或哪次交接"。
- **成本/延迟**：小模型干简单活、Prompt Caching、交接只传必需、能并行就并行、流式输出。
- **评估分层**：端到端 / 单 Agent / 交接 / 轨迹质量；改动必回归。
- **安全**：每 Agent 最小权限、交接鉴权审计、防注入跨 Agent 传播、高风险加 HITL。
