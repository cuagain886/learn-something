# 01 · 工作流编排五种模式

> 目标：掌握 Anthropic 总结的五种工作流编排模式。它们是**经过验证、可控、可靠的工程模板**——很多任务用工作流就够，比多智能体稳得多。先穷尽这些，再考虑动态多 Agent。

---

## 1. 先复述：工作流 vs 智能体

> - **工作流（Workflow）**：LLM 和工具被**预先写死的代码路径**编排。流程由你设计，**可预测、可控、可靠、易调试、成本可估**。
> - **智能体（Agent）**：LLM 自己动态决定流程。灵活但不确定。

> Anthropic 的核心建议：**对很多应用，"优化单次 LLM 调用 + 检索 + 示例"就够了；再进一步，优先用结构化的工作流；只有当任务步数无法预测、确需模型自主时，才上 Agent。**

本章的五种模式都属于**工作流**（可控编排）。它们能覆盖大量真实场景，且远比多智能体稳。**把它们当成你的默认工具箱。**

---

## 2. 模式一：提示链（Prompt Chaining）

把一个任务拆成**清晰的顺序步骤**，每步一次 LLM 调用，前一步的输出是后一步的输入。

```
输入 → [LLM调用1] → 中间结果 → [LLM调用2] → … → [LLM调用N] → 输出
                         ↑可加程序化检查(gate)：不合格就中止/重试
```

- **适用**：任务能**明确分解为固定的串行步骤**。如"先提取要点 → 再翻译 → 再润色格式"。
- **优点**：每步专注一件事，质量更高、更可控；可在步骤间插入**程序化检查（gate）**验证中间结果。
- **代价**：串行 → 延迟累加。
- **vs Agent**：步骤固定就用链式，别让 Agent 临场决定（又贵又不稳）。

---

## 3. 模式二：路由（Routing）

先**分类**输入，再根据类别**分发**到不同的专门处理路径。

```
                 ┌─ 类别A → 处理路径A（专门prompt/工具/模型）
输入 → [分类器] ──┼─ 类别B → 处理路径B
                 └─ 类别C → 处理路径C
```

- **适用**：**不同类型的输入需要不同处理**。如客服：技术问题、账单问题、退款问题各走专门流程。
- **优点**：每条路径可针对性优化（专门 prompt、专门工具、甚至不同模型——简单问题用小模型省钱）。分类与处理**关注点分离**，各自更准。
- **实现**：分类器可以是 LLM、嵌入相似度（语义路由）、或规则/小分类器（参见 [rag/05](../rag/05-查询理解-改写路由与转换.md) 的路由）。
- **代价**：多一次分类调用；分类错了下游全错（要处理"兜底/默认路径"）。

---

## 4. 模式三：并行化（Parallelization）

把任务**拆成可并行的子任务同时跑**，再聚合结果。两种子型：

- **分段（Sectioning）**：把任务切成**独立的部分**并行处理。如"同时审查一段代码的安全性、性能、风格"，最后汇总。
- **投票（Voting）**：**同一任务跑多次**，对结果投票/取共识，提升可靠性。如"让 3 次独立判断这段内容是否违规，多数说违规才判违规"。

```
            ┌─ 子任务A ─┐
输入 ──分发──┼─ 子任务B ─┼──→ 聚合/投票 → 输出
            └─ 子任务C ─┘   （并行执行）
```

- **适用**：子任务相互独立、可并行（降延迟）；或需要多次采样提升可靠性（投票）。
- **优点**：**降延迟**（并行）、**提可靠性**（投票）、每个子任务上下文更聚焦（[context-engineering/02](../context-engineering/02-上下文工程基础.md) 的高信噪比）。
- **代价**：调用次数增加（成本上升），需要设计聚合逻辑。

---

## 5. 模式四：编排者-工人（Orchestrator-Workers）⭐

一个**编排者（Orchestrator）LLM 动态拆解任务**，分派给若干**工人（Workers）**执行，再综合结果。

```
              ┌──→ Worker（动态生成的子任务1）──┐
输入 → [Orchestrator] ─→ Worker（子任务2）──────┼──→ Orchestrator 综合 → 输出
   (动态拆解，子任务数不固定) └──→ Worker（子任务3）──┘
```

- **与"并行化"的关键区别**：并行化的子任务是**你预先定好的**；编排者-工人的子任务是**编排者在运行时根据输入动态决定的**——**子任务的数量和内容事先不可知**。
- **适用**：**任务复杂到无法预先确定要哪些步骤**。如"修改一个涉及多个文件的代码需求"——改哪些文件、改几处，要看具体需求才知道。
- **这是"工作流"和"Agent"的交界**：编排者有了自主决策（动态拆解），已带 Agent 性质。它也是多智能体 **Supervisor 拓扑**的雏形（[文档 02](02-多智能体架构与拓扑.md)）。
- **代价**：动态性带来不确定性和成本；编排者拆解错了会拖累全局。

---

## 6. 模式五：评估者-优化者（Evaluator-Optimizer）⭐

一个 LLM **生成**，另一个 LLM **评估并给反馈**，循环改进直到满意。

```
        ┌─────────────────────────────────┐
输入 → [生成者] → 草稿 → [评估者] → 反馈 ──┘ (不合格则带反馈重新生成)
                            ↓ 合格
                          输出
```

- **适用**：**有明确评判标准**、且迭代能提升质量的任务。如代码（能跑测试）、翻译（有质量标准）、文案（有 checklist）。
- **本质**：这就是 [agent-core/03 反思模式](../agent-core/03-反思模式Reflection.md) 用**两个角色分离**实现的版本。生成者和评估者分离，减少"自己看不出自己错"的盲区。
- **关键前提**：评估标准要明确、最好有客观信号（测试/校验）。标准模糊时评估者也判不准（[agent-core/03](../agent-core/03-反思模式Reflection.md) 的告诫）。
- **代价**：每轮翻倍调用；要限制迭代轮数防止无限打磨。

---

## 7. 五模式速查与选择

| 模式 | 一句话 | 何时用 | 主要代价 |
|------|--------|--------|----------|
| **提示链** | 固定串行步骤 | 任务可明确分解为顺序步骤 | 延迟累加 |
| **路由** | 先分类再分流 | 不同输入需不同处理 | 多一次分类、分类错则下游错 |
| **并行化** | 拆开并行 / 多次投票 | 子任务独立可并行，或要多采样提可靠性 | 调用增多、需聚合 |
| **编排者-工人** | 动态拆解分派 | 子任务事先不可知的复杂任务 | 不确定、成本高 |
| **评估者-优化者** | 生成+评估循环 | 有明确评判标准、迭代提质 | 调用翻倍、需限轮 |

### 选择顺序
```
能一次 LLM 调用解决？        → 就别编排（最省最稳）
能拆成固定串行步骤？        → 提示链
不同输入要不同处理？        → 路由
子任务独立可并行 / 要投票？ → 并行化
有明确标准、要迭代提质？    → 评估者-优化者
子任务事先不可知、要动态拆？→ 编排者-工人（已近 Agent）
以上都不够、需高度自主？    → 才考虑动态多 Agent（文档02起）
```

> **这五种可以组合嵌套**：如"路由到某条路径后，该路径内部是一个提示链 + 末尾加评估者-优化者"。真实系统常是它们的拼装。

---

## 8. 常见坑

- **能用工作流却硬上 Agent** → 牺牲可控性、稳定性、成本可预估性。头号坑。
- **提示链不加 gate** → 中间步骤出错一路带到底。串行步骤间应加程序化检查。
- **路由没有兜底路径** → 遇到分类不了的输入就崩。
- **并行化忘了聚合逻辑** → 拿到一堆子结果不知道怎么合。
- **评估者-优化者标准模糊/不限轮** → 评估失效或无限打磨（[agent-core/03](../agent-core/03-反思模式Reflection.md)）。
- **编排者-工人当成"必用的高级模式"** → 它带 Agent 的不确定性，没必要时用简单模式。

---

## 9. 本章小结

- 五种工作流模式都是**可控、可靠的编排模板**，是多智能体之前的默认工具箱。
- **提示链**（固定串行+gate）、**路由**（分类分流）、**并行化**（分段并行/投票）、**编排者-工人**（动态拆解，近 Agent）、**评估者-优化者**（生成+评估循环，即双角色反思）。
- 关键区分：**并行化的子任务预先定好，编排者-工人的子任务运行时动态决定**。
- 选择遵循"**能简单就简单**"：从单次调用 → 工作流模式 → 动态多 Agent，逐级升级，按需组合嵌套。
