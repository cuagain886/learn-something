# 01 · 工作流编排五种模式

> 目标：掌握 Anthropic 总结的五种常用工作流模式，并能为每种模式定义输入/输出契约、失败传播、重试、join 与停止语义。它们是设计模板，不是脱离任务分布就天然“更可靠”的保证；是否优于单次调用或动态 Agent，必须用同预算对照实验验证。

---

## 1. 先复述：工作流 vs 智能体

> - **工作流（Workflow）**：LLM 和工具被**预先写死的代码路径**编排。流程由你设计，**可预测、可控、可靠、易调试、成本可估**。
> - **智能体（Agent）**：LLM 自己动态决定流程。灵活但不确定。

> Anthropic 的核心建议：**对很多应用，"优化单次 LLM 调用 + 检索 + 示例"就够了；再进一步，优先用结构化的工作流；只有当任务步数无法预测、确需模型自主时，才上 Agent。**

本章的五种模式主要是**工作流结构**，但编排者-工人已经把任务分解交给模型，带有较高策略自由度。与其二分“workflow/agent”，不如看控制权落在哪里：

| 决策 | 代码控制 | 模型控制 |
|------|----------|----------|
| 下一步走哪个节点 | 固定边/规则路由 | 模型规划/动态 handoff |
| 可调用能力 | capability allowlist | 模型从允许集合中选择 |
| 完成判定 | schema/test/business predicate | 模型自评 |
| 重试与停止 | 预算、错误类型、状态机 | “再试一次”的自然语言判断 |

模型控制越多，越需要在外层用预算、权限、完成谓词和 durable state 约束。五种模式是可组合的控制结构，不是成熟度等级。

### 1.1 每个节点都要有执行契约

```yaml
node_contract:
  input_schema: ResearchRequestV2
  output_schema: EvidenceBundleV1
  reads: [task.goal, artifact.web]
  writes: [task.evidence]
  effect: READ
  timeout_ms: 30000
  retry_on: [RATE_LIMIT, TRANSIENT]
  max_attempts: 3
  success_predicate: "all claims have source_ref"
  on_failure: fallback_search
```

没有契约的“节点 A 调节点 B”只是 prompt 拼接，无法回答超时后是否可重试、部分结果能否提交和恢复后会不会重复副作用。

## 2. 模式一：提示链（Prompt Chaining）

把一个任务拆成**清晰的顺序步骤**，每步一次 LLM 调用，前一步的输出是后一步的输入。

```
输入 → [LLM调用1] → 中间结果 → [LLM调用2] → … → [LLM调用N] → 输出
                         ↑可加程序化检查(gate)：不合格就中止/重试
```

- **适用**：任务能**明确分解为固定的串行步骤**。如"先提取要点 → 再翻译 → 再润色格式"。
- **优点**：每步专注一件事，质量更高、更可控；可在步骤间插入**程序化检查（gate）**验证中间结果。
- **代价**：串行 → 延迟累加。
- **vs Agent**：步骤固定就用链式，别让 Agent 临场决定（又贵又不稳）。

链式失败有三种语义：`fail-fast`（任一步失败即停止）、`fallback`（转替代节点）、`compensate`（前面已有副作用时执行补偿）。不能把所有失败都当作“把错误文本交给下一步”。gate 也应优先使用 schema、测试、业务规则等确定性验证；LLM judge 只是不能程序化部分的补充。

---

## 3. 模式二：路由（Routing）

先**分类**输入，再根据类别**分发**到不同的专门处理路径。

```
                 ┌─ 类别A → 处理路径A（专门prompt/工具/模型）
输入 → [分类器] ──┼─ 类别B → 处理路径B
                 └─ 类别C → 处理路径C
```

- **适用**：**不同类型的输入需要不同处理**。如客服：技术问题、账单问题、退款问题各走专门流程。
- **优点**：每条路径可针对性优化（专门 prompt、专门工具、甚至不同模型——简单问题用小模型省钱）。分类与处理**关注点分离**，各自更准。
- **实现**：分类器可以是 LLM、嵌入相似度（语义路由）、或规则/小分类器（参见 [rag/05](../rag/05-查询理解-改写路由与转换.md) 的路由）。
- **代价**：多一次分类调用；分类错了下游全错（要处理"兜底/默认路径"）。

路由器输出不应只有 label，还应包含 `confidence`、`evidence`、`router_version` 与可执行的目标 capability。低置信度策略可以是多路执行、澄清或人工分流；“默认路径”若权限最大，反而会成为安全漏洞。评测需看 confusion matrix 和**错路由代价矩阵**，因为把退款误分到 FAQ 与把 FAQ 误分到退款的风险不同。

---

## 4. 模式三：并行化（Parallelization）

把任务**拆成可并行的子任务同时跑**，再聚合结果。两种子型：

- **分段（Sectioning）**：把任务切成**独立的部分**并行处理。如"同时审查一段代码的安全性、性能、风格"，最后汇总。
- **投票（Voting）**：**同一任务跑多次**，对结果投票/取共识，提升可靠性。如"让 3 次独立判断这段内容是否违规，多数说违规才判违规"。

```
            ┌─ 子任务A ─┐
输入 ──分发──┼─ 子任务B ─┼──→ 聚合/投票 → 输出
            └─ 子任务C ─┘   （并行执行）
```

- **适用**：子任务相互独立、可并行（降延迟）；或需要多次采样提升可靠性（投票）。
- **优点**：**降延迟**（并行）、**提可靠性**（投票）、每个子任务上下文更聚焦（[context-engineering/02](../context-engineering/02-上下文工程基础.md) 的高信噪比）。
- **代价**：调用次数增加（成本上升），需要设计聚合逻辑。

### 4.1 并行的核心不是 `gather`，而是 join 语义

| Join | 何时结束 | 适用 | 风险 |
|------|----------|------|------|
| ALL | 所有必需分支完成 | 报告各章节都不可缺 | 一个慢分支拖累 p95 |
| ANY/FIRST_VALID | 首个满足 verifier 的结果 | 多供应商/多搜索路径竞速 | 必须取消其余分支 |
| QUORUM (q/n) | 达到法定数量 | 多样本判定 | 样本相关时多数票不增信 |
| BEST_OF_N | 全部或预算截止后由 verifier 选 | 可验证候选搜索 | 成本约随 N 增长 |
| DEADLINE_PARTIAL | 截止时聚合已有结果 | 实时摘要 | 输出必须声明缺失分支 |

并行执行必须定义：

- **依赖**：只有无读写冲突或有明确版本协议的分支才能并行。
- **背压**：限制全局/租户/工具并发，队列满时拒绝、降级或延后。
- **取消传播**：父任务取消或已有答案时，向未完成子任务传播 cancellation token；外部副作用不一定能撤销。
- **确定性聚合**：按稳定 key 合并；reducer 应满足所需的结合/交换/幂等性质，不能依赖完成先后。
- **部分失败**：明确 required/optional 分支、deadline 和是否允许 partial result。

并行时延近似 `max(branch latency) + join/merge`，成本近似各分支之和。若分解和汇总占比为串行部分 (s)，即使无限 worker，Amdahl 上限仍为 (1/s)。

## 5. 模式四：编排者-工人（Orchestrator-Workers）⭐

一个**编排者（Orchestrator）LLM 动态拆解任务**，分派给若干**工人（Workers）**执行，再综合结果。

```
              ┌──→ Worker（动态生成的子任务1）──┐
输入 → [Orchestrator] ─→ Worker（子任务2）──────┼──→ Orchestrator 综合 → 输出
   (动态拆解，子任务数不固定) └──→ Worker（子任务3）──┘
```

- **与"并行化"的关键区别**：并行化的子任务是**你预先定好的**；编排者-工人的子任务是**编排者在运行时根据输入动态决定的**——**子任务的数量和内容事先不可知**。
- **适用**：**任务复杂到无法预先确定要哪些步骤**。如"修改一个涉及多个文件的代码需求"——改哪些文件、改几处，要看具体需求才知道。
- **这是"工作流"和"Agent"的交界**：编排者有了自主决策（动态拆解），已带 Agent 性质。它也是多智能体 **Supervisor 拓扑**的雏形（[文档 02](02-多智能体架构与拓扑.md)）。
- **代价**：动态性带来不确定性和成本；编排者拆解错了会拖累全局。

### 5.1 Worker 收到的是 work item，不是随手转发的聊天记录

```yaml
work_item:
  id: wi_42
  parent_task_id: task_7
  objective: "核对 2025 年财务数字"
  input_artifacts: [artifact://filing/2025]
  expected_output: EvidenceTableV1
  allowed_capabilities: [pdf.read, table.extract]
  read_set: [filing_2025]
  write_set: [evidence_finance]
  deadline: 2026-07-19T12:00:00+08:00
  budget: {calls: 8, input_tokens: 60000}
  owner: worker_3
  lease_until: 2026-07-19T11:55:00+08:00
```

编排者需要验证分解：子任务覆盖总体目标吗、是否重叠、依赖 DAG 是否有环、写集是否冲突、预算总和是否超限。worker 只能提交结构化 artifact 与证据，不能无条件改写共享全局状态。还要限制递归深度、fan-out、总 work items 和总 token，防止“Agent 继续生成 Agent”的指数爆炸。

## 6. 模式五：评估者-优化者（Evaluator-Optimizer）⭐

一个 LLM **生成**，另一个 LLM **评估并给反馈**，循环改进直到满意。

```
        ┌─────────────────────────────────┐
输入 → [生成者] → 草稿 → [评估者] → 反馈 ──┘ (不合格则带反馈重新生成)
                            ↓ 合格
                          输出
```

- **适用**：**有明确评判标准**、且迭代能提升质量的任务。如代码（能跑测试）、翻译（有质量标准）、文案（有 checklist）。
- **本质**：这就是 [agent-core/03 反思模式](../agent-core/03-反思模式Reflection.md) 用**两个角色分离**实现的版本。生成者和评估者分离，减少"自己看不出自己错"的盲区。
- **关键前提**：评估标准要明确、最好有客观信号（测试/校验）。标准模糊时评估者也判不准（[agent-core/03](../agent-core/03-反思模式Reflection.md) 的告诫）。
- **代价**：每轮翻倍调用；要限制迭代轮数防止无限打磨。

生成—评估循环至少保存 `best_so_far`，只有当 verifier 分数显著提高且硬约束仍满足时才接受新版本。停止条件可以组合：通过硬 gate、边际收益低于阈值、连续无改进、达到调用/时间/成本预算。若生成者与评估者使用同一模型和相似 prompt，错误高度相关；换“角色名”不等于独立验证，优先引入测试、执行器、第二数据源或规则检查。

## 7. 五模式速查与选择

| 模式 | 一句话 | 何时用 | 主要代价 |
|------|--------|--------|----------|
| **提示链** | 固定串行步骤 | 任务可明确分解为顺序步骤 | 延迟累加 |
| **路由** | 先分类再分流 | 不同输入需不同处理 | 多一次分类、分类错则下游错 |
| **并行化** | 拆开并行 / 多次投票 | 子任务独立可并行，或要多采样提可靠性 | 调用增多、需聚合 |
| **编排者-工人** | 动态拆解分派 | 子任务事先不可知的复杂任务 | 不确定、成本高 |
| **评估者-优化者** | 生成+评估循环 | 有可区分候选的独立/可执行反馈 | 每轮增加评估与修订成本，错误可能相关，需限轮并保留 best-so-far |

### 选择顺序
```
能一次 LLM 调用解决？        → 就别编排（最省最稳）
能拆成固定串行步骤？        → 提示链
不同输入要不同处理？        → 路由
子任务独立可并行 / 要投票？ → 并行化
有明确标准、要迭代提质？    → 评估者-优化者
子任务事先不可知、要动态拆？→ 编排者-工人（已近 Agent）
以上都不够、需高度自主？    → 才考虑动态多 Agent（文档02起）
```

> **这五种可以组合嵌套**：如"路由到某条路径后，该路径内部是一个提示链 + 末尾加评估者-优化者"。真实系统常是它们的拼装。

### 7.1 用 Pareto 前沿选模式，而不是凭架构审美

在同一任务集、模型快照和工具快照上建立基线：

```text
E0 单次调用
E1 + 提示链
E2 + 路由
E3 + 并行/Best-of-N
E4 + 动态编排者
E5 + evaluator loop
```

逐层只改变一个因素，报告成功率、风险加权错误、p50/p95、token/美元、步骤数和人工介入率。复杂模式只有在 Pareto 前沿上才有理由保留。工作流可能降低路径方差，却也会引入路由误差、串行延迟和更多失败点，因此不能先验宣称“必然更稳”。

## 8. 常见坑

- **能用工作流却硬上 Agent** → 牺牲可控性、稳定性、成本可预估性。头号坑。
- **提示链不加 gate** → 中间步骤出错一路带到底。串行步骤间应加程序化检查。
- **路由没有兜底路径** → 遇到分类不了的输入就崩。
- **并行化忘了聚合逻辑** → 拿到一堆子结果不知道怎么合。
- **把异步当并行正确性** → `gather` 只负责调度，不定义 ALL/ANY/quorum、取消、部分失败和稳定 merge。
- **并行分支共享可变状态** → 完成顺序改变结果；用写集隔离、版本/CAS 或可证明的 reducer。
- **orchestrator 只输出自然语言任务** → worker 无法校验范围、权限、预算和完成条件；使用 work item schema。
- **父任务取消但子任务继续跑** → 浪费成本，甚至继续产生副作用；传播取消并对不可取消 effect 做对账。
- **评估者-优化者标准模糊/不限轮** → 评估失效或无限打磨（[agent-core/03](../agent-core/03-反思模式Reflection.md)）。
- **编排者-工人当成"必用的高级模式"** → 它带 Agent 的不确定性，没必要时用简单模式。

## 9. 本章小结

- 五种工作流模式都是**可控、可靠的编排模板**，是多智能体之前的默认工具箱。
- **提示链**（固定串行+gate）、**路由**（分类分流）、**并行化**（分段并行/投票）、**编排者-工人**（动态拆解，近 Agent）、**评估者-优化者**（生成+评估循环，即双角色反思）。
- 关键区分：**并行化的子任务预先定好，编排者-工人的子任务运行时动态决定**。
- 选择遵循"**能简单就简单**"：从单次调用 → 工作流模式 → 动态多 Agent，逐级升级，按需组合嵌套。
