# 03 · 状态管理与控制流

> 目标：掌握控制流、状态、checkpoint、replay 和人类介入的运行时语义。图只是表达方式；真正的生产难点是重放时如何处理非确定性与副作用、并行写如何合并、暂停中的任务如何跨版本恢复。

---

## 1. 编排的两件核心事：控制流 + 状态

[文档 00](00-多智能体与编排学习总览.md) 提过：编排本质是解决两件事。

- **控制流（Control Flow）**：下一步交给谁？何时结束？怎么分支、循环、回退？
- **状态（State）**：信息在各节点/Agent 间怎么传递、共享、持久化？

自己写 if/else 并不天然错误；小型有限状态机往往足够。复杂度来自持久化、并发、重放、HITL、版本迁移和观测。图框架能提供这些机制，但不会自动保证业务幂等、状态 schema 正确或恢复安全。

---

## 2. 图模型（Graph）：现代编排的核心抽象 ⭐

以 **LangGraph** 为代表，把编排建模成一张**有向图（状态机）**：

```
        ┌──────────────────────────────────────┐
        │            共享状态 State              │  ← 所有节点读写的"中央数据"
        └──────────────────────────────────────┘
              ▲          ▲           ▲
        ┌─────┴───┐  ┌───┴────┐  ┌───┴────┐
        │ 节点Node │→ │ 节点Node│→ │ 节点Node│   ← 节点=步骤/Agent/工具
        └─────────┘  └────┬───┘  └────────┘
                          │ 条件边（根据状态决定走向）
                    ┌─────┴─────┐
                    ▼           ▼
                 节点X         节点Y
```

三个核心概念：

- **节点（Node）**：一个执行单元——可以是一次 LLM 调用、一个工具、一个完整的子 Agent。节点读取状态、做事、更新状态。
- **边（Edge）**：控制流。
  - **普通边**：A 做完固定走 B。
  - **条件边（Conditional Edge）**⭐：根据**当前状态**决定下一步走哪个节点——这就是路由、分支的实现。
  - **循环边**：边可以指回之前的节点，形成**循环**（这正是 [agent-core/01](../agent-core/01-Agent循环与ReAct.md) Agent 循环的图表达）。
- **状态（State）**：一个贯穿全图的共享数据结构（消息历史、中间结果、当前激活 Agent 等）。节点通过"更新状态"来传递信息，不用手动传参。

图的价值是显式表达可达状态和转移，但图画出来不等于系统可控。每个节点仍需输入/输出、effect、timeout、retry 和 completion contract；每条边仍需所有权、版本和失败传播语义。

## 3. 状态管理细节

### 3.1 状态里放什么
- 对话/消息历史、各步中间结果、任务进度、**当前激活的 Agent**（多 Agent 必备）、计数器（用于步数上限）等。
- 状态设计要呼应 [context-engineering/](../context-engineering/00-MCP与上下文工程学习总览.md)：不是什么都往状态里堆，注意上下文预算。

需要进一步区分：

| 概念 | 用途 | 例子 |
|------|------|------|
| Durable state | 恢复和并发控制的业务事实 | node、owner、version、receipt、未决审批 |
| Event log | 发生过什么的不可变记录 | tool_requested、effect_committed |
| Artifact | 大对象或阶段成果 | 报告、网页快照、代码 diff |
| Working context | 本轮给模型看的状态投影 | 目标、相关证据、最近事务 |
| Long-term memory | 跨任务选择性复用 | 用户偏好、经验证经验 |

把完整 artifact/聊天都复制进每个 checkpoint 会造成存储膨胀；把 checkpoint 压成自然语言又会丢失事务语义。应保存结构化引用与版本，由 context assembler 决定本轮可见内容。

### 3.2 状态更新（Reducer）
多个节点（尤其并行节点）可能同时更新状态，框架用 **reducer** 定义"怎么合并更新"（如消息列表是**追加**，某个标志是**覆盖**）。理解这点能避免并行时状态相互覆盖。

并行 reducer 若希望完成顺序不影响结果，通常需要满足：

- 结合律：((a\oplus b)\oplus c=a\oplus(b\oplus c))
- 交换律：(a\oplus b=b\oplus a)（若运行时不保证写入顺序）
- 幂等性：(a\oplus a=a)（若可能重复投递）

列表 append 通常不满足交换/幂等；必须给 item 稳定 ID、定义排序和去重。余额、审批状态等不能靠通用 reducer 合并，应由单 writer、事务或 CAS 管理。

### 3.3 状态 schema 也要版本化

```yaml
checkpoint_header:
  graph_version: refund_graph_v7
  state_schema_version: 4
  policy_version: refund_2026_07
  tool_catalog_hash: sha256:...
  model_snapshot: pinned-id
```

部署前要回答：旧任务暂停在已删除节点怎么办、字段 rename/default 如何迁移、conditional edge 的旧结果能否继续、旧审批能否授权新参数。不能假设“发布新代码后所有 checkpoint 自动兼容”。

## 4. Checkpoint（检查点 / 持久化）⭐ 生产必备

Checkpointer 在运行时定义的边界保存状态快照/写入，使线程能够恢复或分叉。它带来以下能力，但**不自动提供 exactly-once 外部副作用**：

| 能力 | 说明 |
|------|------|
| **线程连续性** | 保持 thread-scoped graph state；它可承载短期状态，但不等于当前 working context，也不等于跨 thread 长期记忆。 |
| **暂停与恢复** | 可在任意节点暂停、之后从快照恢复执行——人类介入、长任务跨时段都靠它。 |
| **容错** | 某步崩溃后，可从最近 checkpoint 恢复，不必从头重跑（省钱省时）。 |
| **时间旅行（Time Travel）** | 回退到历史状态、修改后重跑——强大的调试手段。 |

### 4.1 Replay 不是从暂停代码行继续

以 LangGraph interrupt 为例，resume 时节点会从头执行，`interrupt()` 之前的代码会再次运行。time travel 从旧 checkpoint 重放时，之后的 LLM、API 和 interrupt 也可能重新执行。因此：

```text
确定性 workflow/control logic
        ├─ 读取已记录的 task result
        └─ 调用 activity/task（非确定性、I/O、副作用）
                         └─ idempotency key + receipt + retry policy
```

- 当前时间、随机数、UUID、LLM 调用和 API 调用不应裸放在需要确定重放的控制逻辑里。
- effect 放在可单独 checkpoint/重试的 activity/task 中，并设计幂等键或对账。
- 连接在提交后断开时标成 `OUTCOME_UNKNOWN`，查询下游 receipt，不能当失败直接重试。
- checkpoint 成功但外部 effect 未提交，以及 effect 已提交但 checkpoint 未写，是两个都要测试的 crash window。

详见 [持久化执行与故障恢复](../systems-engineering/03-持久化执行与故障恢复.md)。

### 4.2 “时间旅行”要隔离副作用

历史分叉适合调试模型/上下文，但不能默认在生产系统重新发送邮件或退款。重放模式应将写工具替换为 recorded response、sandbox 或 propose-only；每个分叉使用新的 run/attempt ID，保留与原运行的 lineage。

## 5. 人类介入（Human-in-the-Loop, HITL）⭐

很多场景不能让 Agent 全自动跑到底，需要在关键点**暂停、等人确认/修改、再继续**。

```
…执行 → 到达高风险节点 → 中断(interrupt)、保存checkpoint → 等人审批
                                                          │
                              人批准/修改 ──→ 从checkpoint恢复继续
```

- **典型场景**：高风险动作前确认（转账、删数据、对外发送——[INDEX 阶段7](../INDEX.md)）、低置信时让人决策、人工修正中间结果。
- **实现**：靠 checkpoint 支持"中断（interrupt）→ 持久化 → 恢复（resume）"。LangGraph 等开箱支持。
- **价值**：HITL 是把高自主 Agent 安全地用于生产的关键护栏之一——**自主性越高，越需要在关键节点留人类闸门**。

### 5.1 审批批准的是一个不可变 action proposal

```yaml
approval:
  approval_id: ap_19
  action_type: refund.commit
  canonical_args_hash: sha256:...
  evidence_snapshot: snapshot://refund/42
  policy_version: refund_2026_07
  requested_by: task_7
  approver_scope: finance_refund_l2
  expires_at: 2026-07-19T18:00:00+08:00
  decision: approved
```

恢复前重新校验：proposal hash 未改变、审批人有权限、审批未过期、policy 和关键世界状态仍适用、动作尚未提交。若模型在审批后修改金额，旧审批无效。审批记录也不能只是 `approved=true`。

LangGraph 的 interrupt 有具体重放规则：不要用裸 `try/except` 吞掉 interrupt；同一节点内 interrupt 顺序需稳定；payload 可序列化；interrupt 前的非幂等副作用会在 resume 时重复。不同运行时细节不同，必须按所用框架验证。

## 6. 控制流模式：循环、分支、并行、中止

图模型让这些都可显式表达：

- **循环（Loop）**：边指回前节点，配合**状态里的计数器/条件**实现"重试""迭代直到满意"。**务必有退出条件 + 步数上限**（[agent-core/01](../agent-core/01-Agent循环与ReAct.md) 的"没有步数上限的 Agent 不能上线"在图里同样适用——用条件边检查计数器强制退出）。
- **分支（Branch）**：条件边根据状态走不同路径（路由的实现）。
- **并行（Parallel / Fan-out）**：从一个节点分出多条边并行执行，再汇聚（fan-in），配 reducer 合并结果（[文档 01](01-工作流编排五种模式.md) 的并行化）。
- **中止/回退**：条件边检测到失败或超限，导向"终止节点"或"兜底节点"。

循环要区分“同一动作重试”“带新证据重新规划”“优化候选”和“等待外部条件”。只有瞬时失败适合退避重试；无新信息地重复模型调用只是消耗预算。并行必须显式选择 ALL/ANY/quorum/deadline join，并定义父取消如何传播。

---

## 7. 工程要点

- **状态结构先设计好**：它是整个编排的"数据契约"，中途改很痛。明确每个字段、谁写谁读、怎么合并。
- **按恢复目标设计 checkpoint**：记录边界、retention、加密、迁移与 crash matrix；“开一个开关”不等于 durable execution。
- **循环必设退出条件 + 计数上限**：图里用条件边强制，防跑飞。
- **高风险节点插 HITL**：用 interrupt/resume。
- **可观测**：记录每个节点的输入/输出/状态变化（trace）——多 Agent 调试全靠它（[文档 06](06-生产实践与反模式.md)、[INDEX 阶段6](../INDEX.md)）。
- **部署前做 replay/migration 测试**：旧 checkpoint 在新 graph/schema 上继续、回滚和结束的行为都应明确。

## 8. 常见坑

- **把框架当正确性证明** → 框架能持久化，不会替业务生成幂等键、对账或状态不变量。
- **不开 durable checkpoint 却声称可恢复** → 进程崩溃后只能从头；内存 saver 也不跨重启。
- **循环没有退出条件/计数上限** → 无限循环烧钱。
- **状态结构没设计好/中途乱改** → 节点间数据契约崩坏。
- **并行更新不懂 reducer** → 状态互相覆盖、结果丢失。
- **reducer 依赖完成顺序** → replay/调度变化后得到不同状态；验证代数性质并稳定排序/去重。
- **高风险全自动、不留 HITL** → 不可逆事故。
- **interrupt 前执行非幂等 effect** → resume 从节点开头重跑，导致重复发送/写入。
- **审批只存布尔值** → 参数或策略变化后仍沿用旧批准；绑定 proposal hash/version/expiry。
- **新版本删除暂停节点** → 老 checkpoint 无法恢复；做 graph/state migration 和兼容窗口。
- **状态里堆太多** → 上下文膨胀（违反 [context-engineering/02](../context-engineering/02-上下文工程基础.md)）。

## 9. 本章小结

- 编排的核心 = **控制流 + 状态**；现代框架（LangGraph）用**图模型**统一表达：**节点（执行单元）+ 边（含条件边/循环边）+ 共享状态**。
- 图模型把循环、分支、并行、多 Agent 交接装进**可控结构**，用工程结构换可靠性。
- Checkpoint 支持线程连续性、暂停恢复、容错和分叉，但不自动保证外部副作用 exactly-once；恢复正确性依赖 replay 边界、幂等和对账。
- **HITL（人类介入）** 靠 checkpoint 的中断/恢复实现，是高自主 Agent 的关键安全闸门。
- 循环必须有**退出条件 + 步数上限**（图里用条件边强制）；并行更新要懂 reducer。
- 状态结构是"数据契约"，要先设计好、别乱堆。
