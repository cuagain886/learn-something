# 04 · 智能体通信：委派、Handoff 与 A2A 1.0

> 目标：按**答案所有权、任务生命周期、消息可靠性、artifact、身份和版本**理解 Agent 通信。快照日期：2026-07-19；A2A 官方 `latest` 页面当前标记 v1.0，生产实现应固定版本并运行互操作测试。

---

## 1. 先按语义分层，不要把所有箭头都叫“Agent 通信”

| 机制 | 调用边界 | 调用后谁拥有最终答案 | 是否有远程任务生命周期 |
|------|----------|----------------------|------------------------|
| Agent-as-Tool | 通常同应用/SDK 的函数式委派 | 调用方 manager | 通常没有，除非应用自己实现 |
| Handoff | 同一运行时/编排内转移活跃 Agent | 接收方成为当前回复 owner | 通常沿用同一 run/session |
| A2A | 跨进程/团队/厂商的远程 Agent | 由应用任务契约决定 | 有 Task/Message/Artifact、查询、取消、订阅等 |
| MCP | host/client/server 能力协议 | 不规定 Agent 回复 owner | 2025-11-25 的 Tasks 仍是 experimental |

不要用“由浅入深”理解它们：A2A 不是更高级的 handoff，MCP 也不是低级 A2A。它们解决的生命周期和互操作边界不同。

---

## 2. Agent-as-Tool：委派任务，manager 保留控制权

```text
用户 → Manager ── call specialist(request) ──→ Specialist
             ←── structured result/artifact ──
     Manager 汇总、应用统一 guardrail、回复用户
```

适用于 bounded subtask，例如“从财报提取指标”。调用契约应像工具一样明确：

```yaml
specialist_call:
  objective: "提取 2025 年营收与来源页码"
  input_artifacts: [artifact://annual-report-2025]
  output_schema: FinancialEvidenceV2
  allowed_capabilities: [pdf.read, table.extract]
  deadline_ms: 45000
  budget: {calls: 6, tokens: 50000}
```

关键性质：

- manager 是最终答案 owner，适合统一汇总、多专家并行和共享 guardrail。
- 子 Agent 可能有独立模型上下文，但应用依赖、凭据和 durable state 不应塞进模型 prompt；由 runtime context 注入。
- 返回应是结构化 artifact/evidence，不是让 manager 猜一段自然语言“是否完成”。
- 子 Agent 内部仍可能产生副作用；“作为 tool”不会自动使其幂等或安全。

OpenAI Agents SDK 将此模式称为 agents as tools；与 handoff 明确并列，而不是同义词。

## 3. Handoff：转移当前回复/决策所有权

```text
Agent A（triage） ── transfer_to_refund_agent(...) ──→ Agent B（refund）
                                                     B 直接继续本轮并回复
```

在 OpenAI Agents SDK 中，handoff 以工具形式暴露给模型，但语义是接收 Agent 接管后续运行。可以定义：

- `input_type`：handoff 当时由模型生成的小型结构化元数据，例如 reason/priority。
- `on_handoff`：交接发生时执行的应用回调。
- `input_filter`：改变接收 Agent 可见的历史。
- `is_enabled`：按运行时策略动态开放/关闭目标。

容易被追问的细节：`input_type` 只描述 handoff tool 参数，不替代接收 Agent 的主输入，也不应该承载已有应用依赖。默认接收方可能看到完整历史；是否支持 input filter 还与 session/server-managed conversation 模式有关，必须按 SDK 当前文档验证。

### 3.1 可靠 handoff 需要原子所有权转移

```yaml
handoff_envelope:
  handoff_id: ho_991
  run_id: run_18
  from_agent: triage_v4
  to_agent: refund_v7
  reason: duplicate_charge
  objective: "核验并提出 300 元退款"
  invariants: ["不得直接 commit", "必须读取 ledger"]
  artifact_refs: [artifact://complaint/8]
  unresolved: ["客户时区"]
  committed_effects: []
  expected_state_version: 14
  capability_grant: [ledger.read, refund.propose]
  deadline: 2026-07-19T12:00:00+08:00
```

应用应以 CAS/事务更新 `active_owner` 和 `state_version`。旧 Agent 的迟到输出不能覆盖新 owner；发生循环 handoff 时由 `max_handoffs`、访问过的 agent/edge 和预算终止。传递的是可验证状态投影与 artifact 引用，不是一段丢失版本和副作用的“简短摘要”。

## 4. A2A 1.0：远程 Agent 互操作的任务协议

A2A 将远程 Agent 视为内部实现不透明的服务。客户端通过 Agent Card 发现能力，用 Message 发起或继续交互；服务端可以直接返回 Message，也可以创建可跟踪的 Task 并逐步产出 Artifact。

```text
discover Agent Card / negotiate version & binding / authenticate
                         ↓
Client ── SendMessage(messageId, parts, contextId?) ─→ A2A Server
       ←─ Message（简单、无需任务跟踪）───────────────
       或
       ←─ Task(id, status=SUBMITTED/WORKING, ...) ───
             ├─ stream / subscribe / push updates
             ├─ GetTask / ListTasks
             ├─ client supplies more input
             └─ Artifact(s) + terminal status
```

### 4.1 核心对象不能混

| 对象 | 语义 | 关键字段/性质 |
|------|------|---------------|
| Agent Card | 发现远程 Agent 的能力、skills、接口和认证要求 | well-known discovery、接口/binding、capability、security scheme，可签名 |
| Message | 一次通信输入、澄清或状态说明 | `messageId`、role、Parts、contextId/taskId |
| Task | 有状态工作单元 | server 生成 id、status、artifacts、可选 history |
| Part | Message/Artifact 的最小内容单元 | 文本、文件引用、结构化数据等 |
| Artifact | Task 的可交付结果 | artifactId、name、Parts，可增量更新 |
| Context | 逻辑关联多个 Task/Message | `contextId` 不是模型上下文窗口本身 |

规范特别区分 Message 与 Artifact：Message 用于通信，Task 输出应作为 Artifact。流断开时客户端可能错过瞬时 status message，因此关键业务结果不能只存在消息流里；应能通过 `GetTask` 和 artifact 重新取得。

### 4.2 Task 状态机

```text
SUBMITTED → WORKING ─────────→ COMPLETED
                  ├──────────→ FAILED
                  ├──────────→ CANCELED
                  ├──────────→ REJECTED
                  ├──────────→ INPUT_REQUIRED ──(补充消息)──→ WORKING
                  └──────────→ AUTH_REQUIRED ───(带外认证)──→ WORKING
```

`COMPLETED/FAILED/CANCELED/REJECTED` 是 terminal state；terminal Task 不能继续接收消息。`INPUT_REQUIRED/AUTH_REQUIRED` 是 interrupted state，不应当作失败重试。Cancel 是请求，不代表所有下游副作用一定回滚；客户端仍要读取最终状态和 receipt。

### 4.3 操作与交付方式

A2A 1.0 的抽象操作包括：

- Send Message / Send Streaming Message。
- Get Task、List Tasks、Cancel Task、Subscribe to Task。
- Push notification config 的创建、查询、列表与删除。
- Get Extended Agent Card（若 capability 声明支持）。

绑定层可映射到 JSON-RPC、gRPC、HTTP+JSON/REST 等；客户端按 Agent Card 声明选择接口，不能把 A2A 简化成“一个 JSON-RPC endpoint”。实时前台适合 stream；断连/长任务适合 Task 查询、订阅或经过安全校验的 push webhook。

### 4.4 幂等与重复投递

规范中 Get 类操作天然幂等，Cancel 设计为幂等；Send Message **可以**借助 `messageId` 去重，但不能假设所有 server 都自动提供 exactly-once。生产 envelope 还应携带业务 `idempotency_key`、client request ID、deadline 和 trace context：

```yaml
remote_request:
  message_id: msg_77
  business_idempotency_key: refund-case-42-v1
  a2a_version: "1.0"
  extensions: ["https://example.org/citation/v1"]
  traceparent: "00-..."
  deadline: 2026-07-19T12:00:00+08:00
```

客户端超时后先按 Task/message/key 查询，避免重复创建远程任务或重复 effect。stream/push 都可能重复、乱序或丢失连接，consumer 按 task/artifact/update identity 去重并以 GetTask 对账。

## 5. Agent Card、版本与互操作并不是“支持 A2A=true”

生产连接至少固定：

- A2A major/minor version；HTTP 绑定使用 `A2A-Version`，不支持应返回 version error。
- 选中的 AgentInterface/binding、endpoint 和 tenant routing 参数。
- capabilities：streaming、push、extended card 等，只调用声明支持的能力。
- skills、输入/输出 media type 和自定义 extension URI/version。
- security scheme、服务端身份、Agent Card hash/signature 与缓存 TTL。

公开 Agent Card 不应放凭据或内部敏感实现；需要认证后才披露的能力可用 Extended Agent Card。客户端在信任 discovery 信息前验证 HTTPS/域名，存在签名时验证 JWS，并处理 card 更新和撤销。

互操作测试应覆盖：版本不匹配、binding fallback、未知 extension、unsupported capability、Task 中断/终态、stream 断线重连、push 重放、重复 messageId、artifact 增量合并和大文件交换。

## 6. A2A 与 MCP：边界有重叠，生命周期不同

| 维度 | MCP 2025-11-25 | A2A 1.0 |
|------|----------------|---------|
| 主要抽象 | Tools/Resources/Prompts；Roots/Sampling/Elicitation | Agent Card、Message、Task、Artifact、Context |
| 典型关系 | AI host 连接能力 server | client 与不透明 remote agent 协作 |
| 长任务 | Tasks 仍 experimental | Task 生命周期是核心抽象 |
| 发现/协商 | initialize + capability negotiation | Agent Card + version/interface/capability |
| 结果 | tool/resource/prompt 协议结果 | Message 或可查询 Task/Artifact |

“MCP 连工具、A2A 连 Agent”是入门记忆法，但不要把它当严格类型系统：一个远程服务是否被视作 tool 或 agent，取决于调用者需要的是短调用能力，还是独立任务生命周期、状态、artifact 与异步协作。一个 A2A Agent 内部完全可以用 MCP 接工具。

## 7. 身份、授权与跨边界安全

Agent Card 声明认证方案，但凭据通常在 HTTP headers 等协议外层传输。服务端仍需按每个 operation/task/artifact 做授权，不能因客户端通过认证就允许所有 skill。

重点威胁：

- **伪造 Agent Card/endpoint**：HTTPS、域名/证书校验、签名、可信 registry 与缓存失效。
- **confused deputy**：客户端用户身份与远程 Agent 服务身份分离；授权要绑定 subject/audience/scope/task。
- **恶意 Part/file URL**：防 SSRF、路径穿越、超大文件、media type 欺骗；优先受控 artifact store/预签名短期 URL。
- **push webhook 攻击**：callback allowlist/ownership proof、签名、nonce/timestamp、重放保护、出站网络策略。
- **跨 Agent prompt 注入**：远程 Message/Artifact 是不可信数据，不能获得 system instruction authority。
- **能力放大**：接收 Agent 只能得到 work item 所需 capability，不能继承发送方全部权限。
- **数据驻留与删除**：明确远端保留 Task history/artifact 的期限、地域、删除与审计协议。

`AUTH_REQUIRED` 表示任务需要认证交互，不应让 Agent 在对话内容中索取密码/token；通过受控的带外流程获取凭据后再继续 Task。

## 8. 如何选择

```text
bounded specialist 帮忙，调用方要汇总/回复      → agent-as-tool
专员应直接接管本轮或后续用户对话               → handoff
跨系统但只是短、无状态、能力式调用              → HTTP/function/MCP 皆可按生态选
跨组织且需发现、长任务、异步状态、artifact       → A2A
```

选择依据是生命周期和 ownership，不是项目人数。即使同公司，只要跨网络的任务需要异步跟踪和独立 artifact，A2A 也可能合适；即使大企业，单进程 bounded specialist 也不需要为“标准化”强行上 A2A。

## 9. 常见坑

- **把 agent-as-tool 与 handoff 混为一谈** → 前者 manager 保留答案 owner，后者接收方接管。
- **handoff 只转一段摘要** → owner/version、未决项、已提交 effect 和 capability 丢失。
- **认为 stream 是可靠日志** → 断线会错过瞬时消息；关键结果写 Task/Artifact 并可 GetTask 对账。
- **把 `contextId` 当完整对话或模型窗口** → 它只是逻辑关联标识，server 如何管理内部模型上下文是实现细节。
- **收到超时就重新 SendMessage** → 可能重复任务/effect；按 task/message/idempotency key 查询。
- **发现 Agent Card 后永久缓存** → endpoint、skill、版本和安全配置可能变化；验证 TTL/hash/signature。
- **声明支持 A2A 就假设互操作** → 还要匹配版本、binding、capability、media type、extension 和 auth。
- **把 A2A Message 当可信指令** → 远端内容保留 taint，动作仍过本地权限与审批。
- **push URL 不校验** → SSRF/数据外传/重放攻击。

## 10. 面试检验清单

- [ ] 能用最终答案 owner 区分 agent-as-tool 与 handoff。
- [ ] 能设计含 state version、invariant、artifact、effect 与 capability 的 handoff envelope。
- [ ] 能区分 A2A Agent Card、Message、Task、Part、Artifact 和 Context。
- [ ] 能画出 WORKING 到 INPUT_REQUIRED/AUTH_REQUIRED/terminal states 的状态机。
- [ ] 能说明 Message 为什么不是关键结果的可靠存储，以及断线后如何 GetTask 对账。
