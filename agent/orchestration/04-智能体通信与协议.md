# 04 · 智能体通信与协议

> 目标：搞懂 Agent 之间**怎么交接控制权、怎么传上下文**，以及跨框架/跨厂商互通的 **A2A 协议**和 Agent-as-Tool、MCP 等机制。

---

## 1. 三种 Agent 协作的连接方式（先理清层次）

多 Agent 协作有三种由浅入深的连接方式，别混：

| 方式 | 是什么 | 用在哪 |
|------|--------|--------|
| **Agent-as-Tool（Agent 即工具）** | 把子 Agent 封装成上层 Agent 的一个"工具"来调用 | 同一进程/框架内，最简单干净 |
| **Handoff（交接）** | Agent 之间转移控制权 + 携带上下文 | 同一编排图内的多 Agent（Supervisor/Swarm） |
| **A2A 协议（Agent-to-Agent）** | 跨框架/跨厂商/跨网络的标准化 Agent 通信 | 不同团队/厂商的 Agent 互相协作 |

下面逐个展开。

---

## 2. Agent-as-Tool（最简单的组合）

把一个子 Agent **当成普通工具**暴露给上层 Agent（[agent-core/02](../agent-core/02-工具使用ToolUse.md) 的工具机制 + [agent-core/05](../agent-core/05-多智能体协作模式.md) 提过）。

```
上层 Agent 的工具列表：[search, calculator, research_subagent(...)]
上层 Agent 像调工具一样"调用" research_subagent，拿到它的输出当作工具结果
```

- **优点**：复用工具调用机制，**最干净**；上层不用关心子 Agent 内部怎么实现。子 Agent 的上下文天然隔离。
- **Claude Agent SDK** 就支持这种：主 Agent 推理时可**派生隔离的子 Agent 并行干活**（subagent），再收集结果——本质就是 Agent-as-Tool + 并行。
- **适用**：层级清晰的"主-从"关系，子任务可委派。

---

## 3. Handoff（交接机制）⭐

同一个编排图内，Agent 之间**转移控制权**。和 Agent-as-Tool 的区别：handoff 是"**把方向盘交出去**"（控制权真的转移给对方，对方接着开），而 Agent-as-Tool 是"**叫人帮个忙再把结果拿回来**"（控制权始终在调用方）。

```
Agent-as-Tool：  主 Agent ──调用──→ 子 Agent ──结果──→ 主 Agent（控制权没走）
Handoff：        Agent A ──交接──→ Agent B（控制权转移，B 接着主导）
```

### 交接的两个要素
1. **控制权转移**：决定"接下来由谁主导"。
   - Supervisor 拓扑：交回给 Supervisor，由它再分派。
   - Swarm 拓扑：直接交给目标 Agent。
2. **上下文携带**：交接时带上"下游完成任务所必需"的上下文。

### 实现机制（举例）
- **LangGraph**：用 `create_handoff_tool` 生成交接工具，Agent 调用它时返回 `Command(goto=目标, graph=PARENT)`——更新父图状态、把执行重定向到目标节点（[文档 03](03-状态管理与控制流.md) 的图模型）。
- **OpenAI Agents SDK**：核心抽象就是 **handoff**——Agent 显式把控制权交给另一个，并**携带对话上下文**穿过这次转移。

### 上下文携带的权衡（关键）⭐
呼应 [文档 02](02-多智能体架构与拓扑.md) 和 [context-engineering/](../context-engineering/00-MCP与上下文工程学习总览.md)：
- **传太少** → 下游 Agent 缺信息，重复劳动或答错。
- **传太多** → 上下文膨胀、信噪比降、成本升。
- **正解**：交接时只传"下游必需的摘要 + 关键事实"，而非整段历史。

---

## 4. A2A 协议（Agent-to-Agent）⭐ 跨系统互通的 2026 标准

前面两种都在"同一个系统内"。当**不同团队、不同框架、不同厂商**的 Agent 要协作时，需要一个标准协议。

> **A2A（Agent-to-Agent）协议**：一个标准化的 Agent 间通信框架，让自治 Agent 能交换信息、协调动作、协作完成复杂任务，**无需彼此了解对方的内部实现**。2026 已成标准，且 **ACP 已并入 A2A，归 Linux Foundation 治理**。

### 它解决什么
没有 A2A 时，要让"A 公司基于 LangGraph 的 Agent"和"B 公司基于 CrewAI 的 Agent"协作，得写定制对接——又是 N×M 胶水（和 [context-engineering/01](../context-engineering/01-MCP模型上下文协议.md) 里 MCP 解决工具接入是同构的问题，只不过 A2A 解决的是 **Agent 之间**的互通）。

### 它带来什么
> 跨厂商互操作：一个 Salesforce Agentforce 的 Agent 可以把任务交给跑在 Google Vertex AI 上的 Agent，后者再去查 ServiceNow 的 Agent 要 IT 资产数据——**三个系统都不需要理解彼此的内部架构**，全靠 A2A。LangGraph、CrewAI、自研 Python Agent 也能在同一个网络里通过 A2A 协作。

### A2A vs MCP（别混）⭐
两个都是"标准化连接协议"，但层次不同：

| | 连接谁 | 类比 |
|---|--------|------|
| **MCP** | Agent ↔ **工具/数据源** | 给 Agent 接"能力" |
| **A2A** | Agent ↔ **Agent** | 让 Agent 之间"对话协作" |

> 一句话：**MCP 让 Agent 用上工具，A2A 让 Agent 找到并使唤别的 Agent。** 两者互补，常一起出现（一个 Agent 用 MCP 接工具、用 A2A 和别的 Agent 协作）。

---

## 5. 怎么选连接方式

```
同一进程、主从委派、子任务隔离        → Agent-as-Tool（最简单）
同一编排图内的多 Agent、要转移主导权   → Handoff（Supervisor/Swarm）
跨框架/跨厂商/跨网络的 Agent 协作      → A2A 协议
Agent 要接外部工具/数据               → MCP（context-engineering/01）
```

> 多数学习者和中小项目：**用 Agent-as-Tool 和框架内 Handoff 就够了。** A2A 是企业级、跨组织协作才需要的。但理解 A2A 的存在和定位很重要（2026 的大趋势是 Agent 互联网）。

---

## 6. 常见坑

- **混淆 Agent-as-Tool 和 Handoff** → 一个控制权不转移、一个转移。委派用前者，转移主导用后者。
- **混淆 A2A 和 MCP** → A2A 连 Agent，MCP 连工具。
- **交接时上下文传太多/太少** → 膨胀或缺信息。传"必需摘要"。
- **过早上 A2A** → 单系统内根本不需要跨协议，徒增复杂度。
- **跨 Agent 通信无审计/无边界** → 安全黑洞（恶意/被注入的 Agent 可影响他人）。跨系统协作要做好鉴权、边界、审计（[INDEX 阶段7](../INDEX.md)）。

---

## 7. 本章小结

- 三种连接由浅入深：**Agent-as-Tool（委派，控制权不转移）→ Handoff（同图内转移控制权+带上下文）→ A2A（跨框架/厂商的 Agent 互通标准）**。
- **Agent-as-Tool 最干净**，子 Agent 上下文隔离；Claude Agent SDK 可派生并行子 Agent。
- **Handoff** 转移主导权，关键在"带多少上下文"——传必需摘要，别传整段历史。
- **A2A 协议**是 2026 跨系统 Agent 协作标准（已入 Linux Foundation），让异构 Agent 无需了解彼此内部即可协作。
- **A2A 连 Agent、MCP 连工具**，两者互补。
- 中小项目用 Agent-as-Tool + 框架内 Handoff 即可，A2A 面向企业级跨组织协作。
