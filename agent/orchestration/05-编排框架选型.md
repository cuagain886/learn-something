# 05 · 编排框架选型

> 目标：了解 2026 主流的 Agent 编排/多智能体框架，能根据需求选型。框架是落地手段，不是目的——理解了前几章的原理，框架只是不同的封装。

---

## 1. 选型前的心态

> **框架是实现"控制流 + 状态 + 通信"的封装，不是魔法。** [文档 01-04](01-工作流编排五种模式.md) 的原理（工作流模式、拓扑、图模型、交接）才是核心。理解了原理，换框架只是换 API。

延续 [rag/](../rag/00-RAG学习计划总览.md) 和 [context-engineering/](../context-engineering/00-MCP与上下文工程学习总览.md) 的一贯建议：
- **学习/原型**：用框架快速跑通，建立全局认知。
- **生产关键路径**：倾向掌控关键环节，避免被框架黑盒卡住调试。
- **趋势**：2026 主流框架基本都**默认支持 MCP**（接工具）、**逐步支持 A2A**（Agent 互通）。选型时这几乎是标配，不再是差异点。

---

## 2. 主流框架一览（2026）

| 框架 | 出品方 | 核心抽象 | 定位/特点 |
|------|--------|----------|-----------|
| **LangGraph** | LangChain | **图（节点/边/状态）** | 最可控、生产级；显式状态机、checkpoint、HITL、流式；Supervisor/Swarm 现成库。多步/多 Agent 主流选择 |
| **CrewAI** | CrewAI | **角色 + 任务 + 协作（Crew）** | 上手最快；用自然语言描述"团队角色"，一下午就能跑起原型；2026 加了 A2A 任务委派 |
| **AutoGen** | Microsoft | **可对话的 Agent（会话编排）** | 研究/实验强，多 Agent 对话范式；适合探索性多 Agent |
| **OpenAI Agents SDK** | OpenAI | **Handoff（控制权交接）** | 2025.3 取代实验性的 Swarm，生产级；轻量、以交接为核心抽象 |
| **Claude Agent SDK** | Anthropic | **Agent + 派生子 Agent** | 原生 MCP、扩展思考；可派生隔离子 Agent 并行工作；即本环境（Claude Code）所基于的 SDK |
| **Google ADK** | Google | Agent + 原生 A2A | 原生 A2A，稳定 v1.0（Python/Go/Java/TS）；Google 生态 |
| **LlamaIndex Workflows** | LlamaIndex | **事件驱动的工作流** | 事件驱动编排；与 LlamaIndex 的 RAG 能力结合好 |

---

## 3. 怎么选（决策指南）

```
要最大可控性、复杂状态/循环/HITL、生产级       → LangGraph
要最快出原型、角色化团队、上手简单            → CrewAI
以"交接"为核心、想要轻量生产级 SDK            → OpenAI Agents SDK
重度用 Claude、要原生 MCP + 子 Agent 并行      → Claude Agent SDK
在 Google 生态、要原生 A2A 跨系统协作          → Google ADK
RAG 是核心、想要事件驱动工作流                 → LlamaIndex Workflows
研究性多 Agent 对话实验                       → AutoGen
```

### 几个实用维度
- **可控性 vs 易用性**：LangGraph 控制力最强但学习曲线较陡；CrewAI 最易上手但抽象较高、定制时可能受限。
- **生产成熟度**：LangGraph、OpenAI Agents SDK、Google ADK 偏生产级；AutoGen 偏研究。
- **状态/持久化/HITL**：要复杂状态机、checkpoint、人类介入 → LangGraph 最完备。
- **生态绑定**：和你已有栈匹配（已用 LangChain → LangGraph；已用 LlamaIndex 做 RAG → Workflows；Claude 重度用户 → Claude Agent SDK；Google Cloud → ADK）。
- **互操作**：要跨框架/厂商协作 → 看 A2A 支持（Google ADK 原生、CrewAI 已加）。

## 4. 框架 vs 自研薄封装

| | 用框架 | 自研薄封装 |
|---|--------|-----------|
| 优点 | 起步快、现成的状态/checkpoint/HITL/多 Agent 模板 | 完全可控、易调试、无黑盒、依赖少 |
| 缺点 | 抽象层厚、出问题难定位、版本变动快 | 要自己实现循环控制、状态、持久化 |
| 适合 | 学习、原型、标准场景、复杂编排（状态机/HITL 自己写很累） | 简单 Agent、对可控性/性能要求极高的关键路径 |

> 务实建议：**复杂编排（多 Agent + 状态机 + checkpoint + HITL）用 LangGraph 这类成熟框架**——这些东西自己写又难又容易出错。**简单的单 Agent 循环**可以自研薄封装（[agent-core/01](../agent-core/01-Agent循环与ReAct.md) 的循环骨架就几十行）。关键是**先懂原理，再决定哪里用框架**。

## 5. 常见坑

- **为了用框架而用** → 简单任务被框架的抽象拖累。先看任务是否真需要。
- **把框架当原理** → 只会调 API，不懂底层，出问题抓瞎。原理（前几章）才是根本。
- **盲目追新框架** → 频繁迁移成本高。选成熟、社区活跃、和自己栈匹配的。
- **忽视版本变化** → Agent 框架迭代极快，锁版本、读 changelog。
- **被框架黑盒卡住** → 生产关键路径要能看穿、能介入。
- **选型只看 star 数/热度** → 要看可控性、生产成熟度、和需求的匹配，并在自己场景小规模验证。

---

## 6. 本章小结

- 框架是"控制流+状态+通信"的封装，**原理才是核心**，换框架只是换 API。
- 主流选型：**LangGraph（最可控/生产级/图模型/HITL）、CrewAI（最快原型/角色化）、OpenAI Agents SDK（以交接为核心）、Claude Agent SDK（原生 MCP+子 Agent）、Google ADK（原生 A2A）、LlamaIndex Workflows（事件驱动+RAG）、AutoGen（研究性对话）**。
- 选型看：可控性 vs 易用、生产成熟度、状态/HITL 需求、生态绑定、A2A 互操作。
- **复杂编排用成熟框架，简单循环可自研**；2026 框架基本默认支持 MCP，渐支持 A2A。
