# 05 · 编排框架选型：能力矩阵、故障注入与退出成本

> 目标：不背“最佳框架排行榜”，而是把业务不变量转成可执行的选型 spike。快照日期：2026-07-19；框架版本和产品状态变化很快，表中信息必须配合锁定版本与官方 changelog 使用。

---

## 1. 选型对象其实有三层

很多比较把 SDK、runtime 和 managed platform 混在一张表里：

| 层 | 负责什么 | 例子 |
|----|----------|------|
| Agent SDK | loop、tool、handoff、session API | OpenAI Agents SDK、AutoGen AgentChat |
| Workflow/runtime | 图/事件调度、checkpoint、interrupt、replay | LangGraph、ADK graph/workflows、CrewAI Flows、LlamaIndex Workflows |
| Managed platform | 托管、扩缩容、身份、网络、观测、registry | 云端 Agent Runtime/Service |

可以用 SDK 写 Agent，再把它放进独立 durable workflow；也可以用 managed platform 托管自研容器。先确定要买哪一层，否则会拿“SDK 代码简洁”去比较“平台有 RBAC”，结论没有意义。

---

## 2. 先写需求矩阵，再看框架名字

```yaml
selection_requirements:
  control_flow: [branch, loop, dynamic_fanout, quorum_join]
  durability:
    max_pause: 7d
    crash_recovery: true
    replay_semantics: required
    state_migration: required
  effects:
    idempotency_key: required
    outcome_reconciliation: required
  hitl:
    approval_binding: proposal_hash
    resumable: true
  concurrency:
    per_tenant_limit: true
    cancellation_propagation: true
  interoperability: [MCP_2025_11_25, A2A_1_0]
  security: [scoped_credentials, sandbox, audit, retention]
  observability: [OTel_trace, token_cost, state_diff]
  languages: [python, typescript]
  deployment: self_hosted
```

把 `required` 和 `nice-to-have` 分开。任何 required 能力都要用可运行 spike 证明，而不是从首页“production-ready”推断。

## 3. 2026-07 的代表性路线：比较抽象，不做静态排名

| 路线 | 当前核心抽象 | 值得验证的场景 | 必须亲测的边界 |
|------|--------------|----------------|----------------|
| LangGraph | graph/functional API、state/reducer、checkpointer/store、interrupt | 显式状态机、thread checkpoint、HITL/分叉 | 节点重放、effect 幂等、reducer 代数、暂停任务版本迁移 |
| OpenAI Agents SDK | Agent/Runner、agents-as-tools、handoff、sessions、RunState/HITL、tracing | manager 与 handoff、OpenAI Responses 生态、轻量应用编排 | SDK state 与业务 durable state 边界、handoff history/filter、长审批恢复 |
| Google ADK 2.0 | agents、graph workflows、collaborative/template workflows、sessions/events/artifacts | 多语言团队、Google/Vertex 部署、MCP/A2A 集成 | 各语言版本 feature parity、session migration、非 Google 模型/部署路径 |
| Microsoft Agent Framework | Agents、Harness、graph Workflows、session/context providers/middleware | Microsoft 生态、从 AutoGen/Semantic Kernel 迁移、长任务 harness | 各语言/preview 状态、迁移兼容、durable extension 和 provider 差异 |
| CrewAI | Crews（角色/任务）+ Flows（事件/状态/持久化） | 快速表达角色协作并用 Flow 包住控制路径 | replay/effect 语义、状态迁移、并发与锁、自治 Crew 的可观测/停止 |
| LlamaIndex Workflows | event-driven Workflow、Event/Context/handler | RAG/数据应用中的事件编排 | durability、外部 effect、复杂 HITL、与现有 LlamaIndex 版本兼容 |
| AutoGen | AgentChat + event-driven Core/runtime | 会话型团队、事件/分布式 Agent 研究与已有系统维护 | Agent 实例并发安全、state save/load、termination、与 successor 迁移路线 |

### 3.1 当前必须校正的知识点

- Google 官方文档当前首页已进入 **ADK 2.0** 路线，包含 graph workflows、协作/模板工作流、resume/cancel、MCP/A2A、sessions/memory 和 eval；不能继续写成“只有 v1.0 的层级 Agent”。不同语言实现仍需逐项验证。
- Microsoft 官方当前把 **Microsoft Agent Framework** 描述为 AutoGen 与 Semantic Kernel 的直接 successor，包含 Agents、Harness、Workflows；同时部分语言/能力仍可能是 preview。新项目不能只因为旧榜单热度默认选择 AutoGen，但已有 AutoGen 系统也不应无评测重写。
- OpenAI Agents SDK 官方明确区分 manager-style agents-as-tools 与 handoff；前者 manager 保持答案 owner，后者专员接管。
- LangGraph 官方说明 interrupt/resume 会从节点开头重跑，checkpoint 不替业务提供 exactly-once effect。
- 2026-07-26 官方仓库版本复核：Google ADK（python）最新 release 为 v2.5.0（仍属 2.x 代际）；Microsoft Agent Framework 已有 python 1.12.x / dotnet 1.15.x 稳定发布线，并出现 `hosting-a2a` alpha 包（A2A 跨厂商互操作落地的一个信号，注意仍是 alpha）；OpenAI Agents SDK（python）处于 0.18.x。版本号在这里只说明演进速度，选型结论仍以故障 spike 为准。

这些都是版本快照，不是永久结论。锁定依赖时保存 `package version + docs commit/release + runtime config`。

## 4. 选型 spike：用同一个退款流程把框架“压到故障里”

不要只做 happy-path hello world。所有候选框架实现同一最小流程：

```text
读取账本 → 发现重复扣款 → 生成 action proposal → 等审批
       → commit refund（幂等键）→ 连接在提交后断开 → 对账 → 回复
```

### 4.1 十一个验收实验

1. **状态契约**：Typed schema、owner/version、artifact ref 能否在节点间保持。
2. **进程崩溃**：每个节点前后 kill process，恢复是否重复 LLM/API/effect。
3. **结果未知**：commit 成功但响应丢失，能否存 `OUTCOME_UNKNOWN` 并对账。
4. **HITL 七天**：序列化、重启、跨版本部署后恢复；审批绑定原 proposal。
5. **并行 join**：ALL/ANY/deadline partial、慢分支和一个失败分支。
6. **取消传播**：父任务取消后子 Agent、工具、远程 A2A Task 的状态。
7. **状态迁移**：rename node、添加必需字段、回滚旧版本。
8. **多租户压力**：并发/队列/backpressure，验证一个租户不能耗尽全局。
9. **观测**：跨 LLM/tool/subagent/A2A 的 trace、state diff、token/cost 是否可关联。
10. **安全**：每 Agent capability、secret 注入、sandbox、审批、审计、prompt injection sentinel。
11. **可迁移性**：导出业务 state/event/artifact，替换模型 provider 或编排层需要改多少代码。

### 4.2 评分不要只看 feature checkbox

```text
weighted score = Σ(weight_i × verified_score_i) - migration_risk - lock_in_cost
```

`verified_score` 必须来自 spike：

- 0：没有能力。
- 1：需大量自研且没有稳定扩展点。
- 2：可实现，但语义/文档/版本仍有明显风险。
- 3：官方支持且故障实验通过。

安全、幂等、删除、审计等 required 项可设为 gate，而不是用 UI 易用性分数抵消。

## 5. 框架封装与业务 control plane 的边界

无论选哪个框架，以下状态建议由应用自己拥有：

- 业务 task/work item 的 ID、owner、lease、version、deadline。
- tool effect、idempotency key、receipt 与 reconciliation status。
- approval proposal/decision、权限和策略版本。
- artifact URI/hash/ACL/lineage。
- memory 的 source/valid time/supersedes/deletion。

框架 checkpoint 可以存运行时游标和 node state，但不要让业务真相只能通过某个私有 pickle/opaque thread 读取。使用 anti-corruption layer：

```python
class OrchestratorPort:
    def start(work_item: WorkItem) -> RunId: ...
    def resume(run_id: RunId, event: ExternalEvent) -> RunStatus: ...
    def cancel(run_id: RunId, reason: str) -> None: ...
    def inspect(run_id: RunId) -> PortableRunSnapshot: ...
```

这样模型、SDK 或 workflow engine 可以替换，外部 API 和业务数据契约保持稳定。

## 6. 自研薄运行时何时合理

自研不是“完全不依赖库”，而是用数据库、队列、scheduler、OpenTelemetry 等成熟组件，自己掌握少量业务编排语义。

适合：

- 有限节点、固定状态机、少量工具，不需要复杂 graph editor。
- 团队已经有成熟 job/workflow 平台。
- required 语义（特殊事务、地域、合规）与框架抽象冲突。
- 希望最小依赖并能完整理解每个 crash window。

不适合：

- 没有能力长期维护 checkpoint schema、调度、HITL、迁移和观测。
- 只是因为框架 API 看起来复杂，却低估 durable execution。

合理组合常是“薄 Agent harness + 成熟 durable workflow/runtime + 自有业务 control plane”。

## 7. 升级、迁移与供应链

框架更新快，生产必须：

1. 锁包版本、模型 snapshot、tool schema 和 protocol version。
2. 阅读 changelog，并用历史 checkpoint/replay corpus 做兼容测试。
3. canary 新版本；保留旧 worker 处理旧 graph version，或做显式 migration。
4. 对 SDK/MCP server/plugin 做 SBOM、依赖扫描和来源校验。
5. 记录数据是否发送到第三方模型/托管 runtime、区域与 retention。
6. 提前演练导出 task/event/artifact/memory 和切换 provider。

一次 SDK minor upgrade 也可能改变默认 history、并行 tool call、retry 或 serialization；“代码能启动”不足以证明暂停中的任务安全。

## 8. 常见坑

- **排行榜驱动** → “最可控/最快/最生产级”没有统一 benchmark；用需求矩阵和 spike。
- **比较不同层级产品** → SDK 与 managed platform 的能力不能直接打分。
- **首页写 persistence 就假设 durable effect** → 检查 replay、activity 边界、幂等和 crash matrix。
- **MCP/A2A 打勾即互操作** → 固定版本，测试 capability、auth、binding、取消和大 artifact。
- **旧知识不校准** → ADK、Microsoft Agent Framework 等在 2026 已有显著变化。
- **业务状态全塞私有 checkpoint** → 难审计、难迁移、难删除；保留 portable control-plane schema。
- **只做 happy path demo** → 真正差异只会在断线、重放、并发、审批和升级中出现。
- **为了避免 lock-in 全部自研** → 重新实现调度/持久化同样是长期锁定；比较总拥有成本。

## 9. 面试检验清单

- [ ] 能区分 Agent SDK、workflow/runtime 和 managed platform。
- [ ] 能把需求写成 durability/effect/HITL/concurrency/security/interop 矩阵。
- [ ] 能说明代表性框架的核心抽象，而不做无证据排名。
- [ ] 知道 ADK 2.0 与 Microsoft Agent Framework successor 是 2026-07 的当前变化，并说明版本快照边界。
- [ ] 能设计包含 crash、outcome unknown、七天审批、取消和迁移的选型 spike。
- [ ] 能说明哪些业务状态不应只留在框架私有 checkpoint。
- [ ] 能设计 anti-corruption port 以降低模型/框架/平台迁移成本。
- [ ] 能解释什么时候“薄 Agent harness + durable workflow”优于一体化框架。
