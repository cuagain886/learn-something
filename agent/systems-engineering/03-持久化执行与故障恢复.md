# 03 · 持久化执行与故障恢复

> 目标：理解 Agent 为什么天然需要 durable execution。重点不是“保存一下 state”，而是定义重放、重复投递、外部副作用、等待、取消和代码升级时的正确语义。

---

## 1. 为什么普通 retry 对 Agent 不够

考虑下单工具的时间线：

~~~text
T1  worker 向供应商发送 create_order
T2  供应商成功创建订单
T3  网络在响应返回前断开
T4  worker 超时
T5  系统重试 create_order
~~~

如果没有幂等键，产生两个订单；如果系统把超时直接当失败，则状态与现实世界不一致。

Agent 还会叠加更多故障点：

- LLM 已决定动作，但意图尚未保存。
- 工具已执行，结果尚未 checkpoint。
- 模型已看到 observation，进程在保存下一状态前崩溃。
- 人工审批等待数天，期间代码和工具 schema 升级。
- 多个 worker 因 lease 过期同时恢复同一个 run。
- graph replay 从节点开头执行，interrupt 前的代码再次运行。

所以必须把“每个窗口崩溃后会发生什么”写进设计，而不是笼统地说“失败就重试”。

---

## 2. Durable execution 的核心机制

一种常见实现是历史驱动重放：

1. 工作流把调度决定和外部结果写入持久化历史。
2. worker 崩溃后，从历史重建内存状态。
3. 已完成的非确定性 activity 读取历史结果，不重新调用。
4. 未确认完成的 activity 按策略重新调度。

另一种是显式 checkpoint 图：

1. 在节点/超步边界保存 state snapshot。
2. 恢复时从最近 checkpoint 继续。
3. checkpoint 后的节点可能重新执行。

两者都要求：

> **所有可能重复运行的副作用都必须幂等，所有非确定性值都必须记录或隔离。**

LangGraph 文档明确说明，replay 会重新执行 checkpoint 之后的 LLM 调用、API 请求和 interrupt；恢复 interrupt 时节点从头运行，所以 interrupt 之前的副作用必须幂等。Temporal 类工作流则要求工作流代码保持确定性，把 LLM、工具和外部 I/O 放入 Activities。

---

## 3. 三种投递语义

| 语义 | 含义 | 代价/风险 |
|------|------|-----------|
| **at-most-once** | 最多执行一次，失败可能丢 | 不重复，但可能没做 |
| **at-least-once** | 最终至少执行一次，可能重复 | 常见且可用，要求幂等 |
| **exactly-once effect** | 业务世界只产生一次效果 | 需事务、幂等、去重与对账共同实现 |

不要轻易声称端到端 exactly-once。跨越模型 API、队列、MCP server、SaaS 和数据库时，通常只能获得至少一次调用，再通过业务键让最终效果等价于一次。

例如邮件服务若不支持幂等键，系统最多能：

- 自己记录 send intent。
- 发送时携带唯一 Message-ID。
- 查询 sent mailbox 或供应商状态做对账。
- 接受极端故障窗口仍可能重复，并用产品设计降低影响。

这叫明确风险边界，比虚构 exactly-once 更可靠。

## 4. 工具操作日志是恢复核心

建议 tool_operations 表包含：

~~~text
operation_id
run_id
logical_action_id
action_revision
idempotency_key
tool_name
tool_version
normalized_arguments_hash
effect_class
status
attempt
external_reference
result_artifact_id
error_code
created_at / started_at / finished_at
~~~

状态机：

~~~text
INTENT_RECORDED
  → DISPATCHED
  → SUCCEEDED
  → VERIFIED

DISPATCHED
  → TRANSIENT_FAILED → DISPATCHED
  → OUTCOME_UNKNOWN → RECONCILING
  → PERMANENT_FAILED

RECONCILING
  → SUCCEEDED | NOT_APPLIED | MANUAL_REVIEW
~~~

worker 执行前先原子地 claim operation。若相同 idempotency_key 已 VERIFIED，直接返回已保存结果；若 OUTCOME_UNKNOWN，禁止创建新 action revision，先走对账。

## 5. 幂等键的正确作用域

### 5.1 同一意图的 retry 必须复用 key

~~~text
K = H(
  tenant_id,
  run_id,
  logical_action_id,
  action_revision
)
~~~

- 网络 retry、worker 重启、队列重复：复用相同 K。
- 用户修改金额或收件人：action_revision + 1，生成新 K，并使旧审批失效。
- 两个独立业务任务恰巧参数相同：run_id 不同，不能错误去重。

### 5.2 服务端必须原子去重

仅在客户端查“是否做过”会有竞态：

~~~text
worker A: 查不到
worker B: 查不到
worker A: 执行
worker B: 执行
~~~

目标系统应对 idempotency_key 建唯一约束，并在同一事务内写结果。无法改目标系统时，至少在本地 operation 表做唯一 claim，但仍需处理“本地未记成功、远端已成功”的不确定窗口。

## 6. Transactional Outbox：状态与消息一致

经典故障：

1. 数据库写 run 状态成功。
2. 发送队列消息前进程崩溃。
3. run 永远没有被调度。

反过来先发消息再写状态，则 worker 可能读取不到相应状态。

Outbox 做法：

~~~text
同一数据库事务：
  UPDATE runs ...
  INSERT run_events ...
  INSERT outbox(event_id, topic, payload)

独立 relay：
  读取未发布 outbox
  → 至少一次发到队列
  → 标记 published
~~~

消费者按 event_id 去重。这样数据库状态和“应发送的消息”原子一致，允许队列重复但不允许静默丢调度意图。

DBOS 的 outbox 示例也强调：事务内数据库步骤可与 checkpoint 原子结合；外部发送仍可能至少一次，因此仍需幂等。

## 7. Saga 与补偿：处理跨系统部分成功

采购流程：

~~~text
1. 创建供应商订单      成功
2. 扣减采购预算        成功
3. 写入资产系统        失败
~~~

无法用一个 ACID 事务覆盖三个系统。需要定义 Saga：

| 正向动作 | 补偿 |
|----------|------|
| create_order | cancel_order（若未发货） |
| reserve_budget | release_budget |
| create_asset_records | delete_draft_asset_records |

补偿不是数据库 rollback：

- 可能失败，需要自己的幂等键和重试。
- 可能只能部分抵消，如邮件无法“撤回所有收件人”。
- 可能超过可补偿窗口。
- 必须记录业务原因和人工处置。

因此每个动作要声明 reversibility、compensation_tool、compensation_deadline。不可补偿动作应尽量后置，并置于人工确认之后。

## 8. 非确定性必须隔离

会导致重放不一致的内容包括：

- LLM 输出。
- 当前时间、随机数、UUID。
- HTTP/数据库读取结果。
- 工具列表动态变化。
- feature flag 和策略结果。

工作流层有两种策略：

1. **记录结果**：首次执行后写历史，replay 读取旧值。
2. **放入 activity**：工作流只调度 activity，activity 可重试且结果持久化。

不要在可 replay 的 reducer/workflow 函数里直接调用 LLM。相同 prompt 的第二次输出不是第一次的重建，可能改变控制流。

## 9. Checkpoint 粒度的权衡

| 粒度 | 优点 | 缺点 |
|------|------|------|
| 每个模型/工具动作 | 恢复损失小、审计细 | 写放大、延迟高 |
| 每个图节点 | 简单、常用 | 节点内副作用需幂等 |
| 每个阶段 | 成本低 | 崩溃后重做多、重复风险大 |

选择依据：

- 动作是否昂贵或不可逆。
- 节点是否包含外部 I/O。
- 允许重做的时间/成本。
- 状态大小与存储吞吐。

一个实用原则：**在不可逆动作前后都形成持久化边界**。前边界保存已授权的规范化意图，后边界保存外部 reference 和验证结果。

## 10. 人工等待、定时器与外部事件

长等待需要持久化：

~~~json
{
  "status": "WAITING_APPROVAL",
  "wake_condition": {
    "type": "EVENT",
    "event_type": "approval.decided",
    "correlation_id": "apr_123"
  },
  "expires_at": "2026-07-20T12:00:00Z",
  "resume_token_hash": "...",
  "agent_version": "procurement-agent@17"
}
~~~

要求：

- 等待时不占 worker 线程。
- event 处理幂等，重复审批事件不重复推进。
- 过期有明确转换，如 EXPIRED 或重新预览。
- 恢复前重新校验资源版本、金额和权限。
- 审批者身份、理由和决策时间进入不可篡改审计。

MCP 2025-11-25 Tasks 也定义 working、input_required、completed、failed、cancelled 等状态，以及轮询/结果/取消，但其 Tasks 截至快照日仍标为 experimental。业务工作流不能把自己的全部恢复语义外包给实验协议。

## 11. 取消不是设置一个布尔值

取消要逐层传播：

~~~text
用户取消
  → run 标记 CANCELLING
  → 停止调度新步骤
  → 取消未开始工具调用
  → 对在途调用发 best-effort cancel
  → 对已完成副作用执行补偿或人工处置
  → 等待子任务收敛
  → CANCELLED / CANCELLED_WITH_SIDE_EFFECTS
~~~

必须区分：

- **停止未来工作**。
- **中止当前计算**。
- **撤销已经发生的现实动作**。

它们不是一回事。对外部系统取消失败时，状态不能谎称“完全取消”。

## 12. 版本升级与等待中的旧任务

持久化 run 至少 pin：

- workflow/agent version。
- prompt version。
- tool name + schema version。
- policy version。
- model snapshot 或兼容策略。
- state schema version。

升级有三种方式：

| 策略 | 做法 | 适合 |
|------|------|------|
| **旧代码续跑** | 保留旧 worker 直到旧 run 清空 | 高风险、数量可控 |
| **显式迁移** | state v3 → v4，带迁移测试 | 结构变化明确 |
| **重新规划** | 保存世界事实，放弃旧内部计划 | 计划不可兼容但副作用可对账 |

绝不能让新代码静默反序列化旧状态后“尽量猜”。审批等待尤其要保存版本标记；OpenAI Agents SDK 的 HITL 文档也建议对长期挂起的 state 记录 Agent 定义或 SDK 版本。

## 13. 故障注入测试

至少在这些位置强制 kill worker：

1. 模型返回前/后。
2. 写工具请求发出前。
3. 远端成功、本地收到响应前。
4. 本地收到响应、保存 operation 前。
5. checkpoint 前/后。
6. 发出 outbox 事件前/后。
7. interrupt 前副作用之后。
8. 审批事件接收后、状态推进前。

验证：

- 世界状态无重复副作用。
- run 最终可恢复或明确进入 MANUAL_REVIEW。
- 预算不会因 replay 重复计费或漏计。
- trace 能关联每次 attempt 与同一 logical_action。
- 取消和补偿不会生成新的无限重试。

---

## 14. 本章小结

- Durable execution 的核心是**可重放的确定性控制流 + 被隔离并记录的非确定性 I/O**。
- checkpoint 只能恢复状态，不能自动保证外部副作用恰好一次。
- 实际系统通常接受至少一次投递，再靠幂等键、唯一约束、operation log、对账和补偿实现一次业务效果。
- 超时必须区分“明确失败”和“结果未知”；后者先对账，不能盲重试。
- Outbox 解决数据库状态与消息发布的一致，Saga 解决跨系统部分成功。
- 等待、取消和版本升级都是状态机的一部分，不能留给临时代码。
