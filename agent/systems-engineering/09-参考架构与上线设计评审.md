# 09 · Agent 参考架构与上线设计评审

> 目标：把前八章收敛成一套可落地参考架构。示例不是要求照搬某个框架，而是给出组件职责、数据契约、端到端顺序、SLO 和上线评审问题。

## 2. 组件职责与不能承担的职责

| 组件 | 必须负责 | 不应负责 |
|------|----------|----------|
| Run API | 身份解析、创建 run、幂等请求、查询/取消 | 长时间持有执行线程 |
| Scheduler | ready/waiting、lease、优先级、并发 | 猜模型下一步 |
| Orchestrator | 持久状态机、重试、等待、补偿 | 直接在可 replay 代码里调 LLM |
| Context Assembler | 预算、来源、信任标签、按需加载 | 把全部历史无脑拼接 |
| Model Adapter | 供应商 API 与内部 Decision 转换 | 执行业务副作用 |
| Tool Broker | 校验、鉴权、审批、幂等、执行、验证 | 相信模型自报权限 |
| State/Event DB | 当前状态、历史、版本、operation log | 存大型二进制产物 |
| Artifact Store | 不可变大对象、hash、lineage | 作为实时锁/状态机 |
| Verifier | 业务后置条件、测试、rubric | 默认相信生成 Agent |
| Telemetry | trace/metrics/关联与采样 | 永久明文保存所有敏感输入 |

## 4. 采购案例端到端链路

### 4.1 创建与计划

1. API 验证用户身份，创建 run_9。
2. 记录 agent/prompt/tool/policy 版本与预算。
3. Agent 生成结构化 work items。
4. Deterministic validator 检查依赖图无环、预算和成功条件。
5. 保存 checkpoint 并投递 outbox。

### 4.2 只读研究

1. Context Assembler 只加载 procurement namespace。
2. Agent 查询供应商和报价。
3. Tool Broker 以用户委托身份执行只读 MCP tools。
4. 大结果进入 Artifact Store；模型得到摘要、ID、cursor、provenance。
5. Verifier 检查报价时效和字段完整性。

### 4.3 提交前预览

1. Agent 选择 quote_id，不直接自由填写供应商名称。
2. preview_order 规范化税费、地址和总额。
3. Broker 计算 preview_hash 和风险。
4. PDP 返回 REQUIRE_APPROVAL。
5. run 进入 WAITING_APPROVAL，worker 释放。

### 4.4 审批与恢复

1. 审批者看到结构化差异和不可逆影响。
2. approval 绑定 preview_hash、金额、quote version 和过期时间。
3. 事件写入，run 被唤醒。
4. 恢复时重新读取 quote 与权限。
5. 若报价变化，旧 approval 作废，重新预览。

### 4.5 幂等提交与验证

1. 控制面生成 operation_id 和 idempotency_key。
2. 先记录 INTENT_RECORDED。
3. 执行 create_order。
4. 超时则 OUTCOME_UNKNOWN，按 key 对账。
5. 成功后读取订单，核对金额、数量、供应商。
6. 保存 external_reference 和 VERIFIED。
7. 回写资产系统；失败则按 Saga 决定取消订单或人工处置。

### 4.6 完成

1. Completion Verifier 检查 success criteria。
2. 无 pending operation、无未解决 blocker。
3. 生成最终 artifact 与简短解释。
4. 状态置 SUCCEEDED 或明确的 PARTIAL/MANUAL_REVIEW。
5. 释放短期 grant，销毁 sandbox。

## 5. 可靠性 SLO

### 5.1 结果 SLO

- task success rate。
- pass^3 / 重复任务一致性。
- critical invariant violation = 0。
- unverified completion rate。
- uncompensated side-effect rate。

### 5.2 系统 SLO

- 创建 run 可用性。
- ready → start p95。
- time-in-state p95。
- stuck run 比例。
- checkpoint/recovery 成功率。
- OUTCOME_UNKNOWN 对账时间。
- cancellation convergence time。

### 5.3 效率 SLO

- cost per success。
- 每个成功条件的 token。
- p95 端到端时延。
- tool result inline token。
- cache hit 与无效重复调用。

### 5.4 人类协作 SLO

- approval wait time。
- approval expiry rate。
- 人工纠正/撤销率。
- confirmation precision/recall。
- 每任务人工分钟数。

不要把等待人工的时间算成模型延迟，但必须算入端到端用户时长。

## 6. Trace 结构

~~~text
invoke_workflow(run_9)
├── invoke_agent(planner)
│   └── chat(model_call_1)
├── execute_tool(search_quotes)
│   ├── policy_decision
│   └── mcp.tools.call
├── create_artifact(art_17)
├── invoke_agent(executor)
│   └── chat(model_call_2)
├── approval.wait(apr_3)
├── execute_tool(create_order)
│   ├── policy_decision
│   ├── operation_attempt_1
│   ├── reconciliation
│   └── verify_postcondition
└── completion_verify
~~~

推荐关联：

- trace_id：一次执行链。
- run_id：跨多条 trace 的业务任务。
- operation_id：一次逻辑副作用，下面可有多 attempt。
- artifact_id：大 payload 和证据。

正文默认不入 span。记录大小、hash、分类和 artifact ref。

## 7. 部署拓扑

### 小规模

- 单服务 API + worker。
- PostgreSQL 状态/outbox。
- 对象存储 artifact。
- 独立 sandbox runner。
- OTel collector。

这已能实现可靠基础，不需要先上多 Agent 或 A2A。

### 中大规模

- Control Plane 与 execution workers 分离。
- 模型、只读工具、写工具、代码 sandbox 独立 worker pool。
- 按租户/数据域隔离 namespace。
- durable workflow engine 管长任务。
- MCP gateway 管工具连接。
- A2A gateway 只放在跨团队/跨组织边界。
- policy bundle、tool registry、secret broker 独立。

扩展顺序应由瓶颈驱动，不能因为架构图完整就一次全部引入。

## 8. 发布策略：自主权分级

| Level | 能力 | 上线要求 |
|-------|------|----------|
| L0 | 只生成建议 | 内容 eval、引用、隐私 |
| L1 | 自动只读 | 细粒度授权、数据隔离、审计 |
| L2 | 生成写操作预览 | dry-run、diff、风险摘要 |
| L3 | 人工批准后写 | 参数绑定审批、幂等、验证、补偿 |
| L4 | 低风险自动写 | 明确白名单、限额、可撤销、在线监控 |
| L5 | 高自主长任务 | durable execution、强隔离、持续评测、事件响应 |

每个动作可有不同 Level，不要给整个 Agent 一个笼统“全自动”开关。

## 9. 设计评审模板

### 任务与边界

- [ ] 为什么必须用 Agent，而不是确定性 workflow？
- [ ] 目标、成功条件、失败/部分成功状态是否清楚？
- [ ] 自主权的时间、费用、数据、动作、并发边界是什么？

### 状态与恢复

- [ ] conversation/task/world/evidence 状态是否分离？
- [ ] checkpoint/replay 语义是否写清？
- [ ] 所有写动作是否幂等，结果未知是否先对账？
- [ ] 是否有 Outbox、补偿、取消和版本迁移？

### 工具

- [ ] 工具是否有 effect class、schema、owner、version？
- [ ] 是否采用 read → preview → approve → commit → verify？
- [ ] 大结果是否 artifact 化？

### 安全

- [ ] 身份委托链和 token audience 是否正确？
- [ ] PDP/PEP 是否在模型外？
- [ ] sandbox、网络、secret、memory、供应链边界是否完整？
- [ ] 审批是否抗 TOCTOU？

### 多 Agent

- [ ] 是否有真实并行性、单一 writer、隔离工作区和 verifier？
- [ ] 协调开销、backpressure、最大深度和失败隔离是否量化？

### 评测与观测

- [ ] 最终世界状态是否可评分？
- [ ] 是否报告 pass^k、区间、成本成功率和尾延迟？
- [ ] 是否有私有 holdout、挑战集和故障注入？
- [ ] trace 是否兼顾排障与隐私？

### 运营

- [ ] 是否有 staged autonomy、canary、rollback、kill switch？
- [ ] 是否定义 on-call runbook、人工接管和证据保全？

## 10. 最小验收场景

上线前至少通过：

1. 正常端到端。
2. 模型输出非法 schema。
3. 工具 429 与 retry-after。
4. 写操作远端成功但本地超时。
5. 同一队列消息重复 3 次。
6. worker 在关键 checkpoint 前后崩溃。
7. 审批期间报价变化。
8. 用户权限在等待期间撤销。
9. 恶意网页/邮件 prompt injection。
10. Skill/MCP tool schema 更新。
11. 子 Agent 超时、重复认领、返回污染 artifact。
12. 用户取消时已有部分副作用。
13. trace exporter 不可用。
14. 预算耗尽。
15. verifier 与生成 Agent 结论冲突。

系统应收敛到明确状态，不能无限 loop、重复副作用或静默成功。

## 11. 本章小结

- 生产 Agent 的核心不是一个大循环，而是 control plane、durable orchestrator、Harness、Tool Broker、状态/产物和 verifier 的协作。
- 数据库保存结构化事实与事件，artifact store 保存不可变大对象；队列只负责唤醒，不作为唯一真相。
- 高风险动作链路必须是 **preview → policy → approval → idempotent commit → independent verify**。
- SLO 要覆盖结果、系统、效率和人类协作；“平均答案质量”远远不够。
- 自主权按动作分级，逐步从建议、只读、预览、审批后写走向受限自动写。
