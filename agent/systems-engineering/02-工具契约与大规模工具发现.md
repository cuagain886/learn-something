# 02 · 工具契约与大规模工具发现

> 目标：把工具从“一个 JSON Schema 包装的函数”升级为可授权、可恢复、可评测的业务动作。Schema 只解决语法合法，工具契约还必须描述语义、效果、错误、权限和完成证据。

---

## 1. 工具是概率系统与确定性系统之间的边界

传统 API 的调用者是程序员写的确定性代码；Agent 工具的调用者是会探索、误解、重复尝试的模型。因此“对人类开发者看起来清楚”并不足够。

Anthropic 将工具描述为确定性系统与非确定性 Agent 之间的契约，并强调五件事：

- 选择真正需要的工具，而不是把所有内部 API 原样暴露。
- 用 namespace 建立边界。
- 返回对 Agent 有意义的上下文。
- 控制返回结果的 token 成本。
- 用真实任务评测持续优化工具定义。

这意味着 Tool API 不是把 REST/OpenAPI 自动转成 function calling 就结束了。中间需要一层 **Agent-oriented facade**。

---

## 2. 一个完整工具契约

建议目录中的工具定义至少有以下字段：

~~~yaml
name: procurement.orders.create
version: 3
summary: 根据已批准的报价创建采购订单

input_schema: ...
output_schema: ...

semantics:
  preconditions:
    - quote.status == VALID
    - approval.amount_hash == request.amount_hash
  postconditions:
    - exactly one order exists for idempotency_key
  invariants:
    - total_amount <= approved_amount

effects:
  class: IRREVERSIBLE_WRITE
  resources:
    - procurement:order
  external_side_effects: true

execution:
  timeout_seconds: 30
  retry_policy: RECONCILE_THEN_RETRY
  idempotency: REQUIRED
  cancellation: BEST_EFFORT
  compensation_tool: procurement.orders.cancel

security:
  required_scopes:
    - procurement.order:create
  approval_policy: amount_based
  data_classification: CONFIDENTIAL

result:
  max_inline_bytes: 8192
  artifact_on_overflow: true
  verifier: procurement.orders.get
~~~

模型不一定需要看到全部字段。目录可以生成两个视图：

- **模型视图**：名称、适用条件、参数、返回摘要、典型错误。
- **控制面视图**：权限、效果、幂等、审批、重试、补偿、审计。

这样既节省上下文，又避免把安全决策委托给模型。

## 3. 先按效果分类，再决定策略

### 3.1 推荐的效果分类

| 类别 | 例子 | 默认重试 | 默认审批 |
|------|------|----------|----------|
| **PURE** | 计算、格式转换 | 可直接重试 | 不需要 |
| **READ** | 查询订单、检索文档 | 通常可重试 | 敏感数据按权限 |
| **REVERSIBLE_WRITE** | 创建草稿、加标签 | 需幂等 | 按影响范围 |
| **IRREVERSIBLE_WRITE** | 发邮件、下单、转账、删除 | 先对账再重试 | 通常需要 |
| **PRIVILEGE_CHANGE** | 授权、改 ACL、创建凭据 | 极度保守 | 强制审批/双人规则 |

“POST”不等于写，“GET”也不必然安全；效果分类应基于业务语义。比如获取一次性下载链接可能泄露敏感数据，发送测试邮件仍产生外部副作用。

### 3.2 风险是多维的

可以计算结构化风险，而不是维护一个“危险工具名单”：

~~~text
risk = effect
     × data_sensitivity
     × target_scope
     × reversibility
     × monetary_value
     × external_visibility
~~~

同一个 send_email：

- 发给自己、草稿模式：低风险。
- 发给公司内部 3 人：中风险。
- 发给 10 万外部联系人：极高风险。

策略必须检查实际参数，而不只是工具名。

## 4. 参数 Schema：消除歧义，不只校验类型

### 4.1 尽量使用封闭枚举和有单位的字段

不推荐：

~~~json
{"amount": 100, "time": "tomorrow", "status": "ok"}
~~~

推荐：

~~~json
{
  "amount_minor": 10000,
  "currency": "CNY",
  "execute_at": "2026-07-19T09:00:00+08:00",
  "mode": "DRAFT"
}
~~~

原则：

- 金额说明币种和最小单位，避免浮点。
- 时间使用带时区的 ISO 8601，并明确 inclusive/exclusive。
- ID 与展示名分开，执行动作尽量使用不可变 ID。
- 不接受含糊的自由文本开关，如 yes/no/maybe。
- additionalProperties 默认关闭。
- 数组设置上限，字符串设置长度和格式。
- 可选字段明确“缺省”与“显式 null”的区别。

### 4.2 把选择过程拆成查询与提交

不要让模型凭模糊名称直接写：

~~~text
search_suppliers(query)
  → 返回 supplier_id、匹配依据、状态

preview_order(supplier_id, items)
  → 返回规范化金额、税费、风险、preview_hash

create_order(preview_hash, approval_id, idempotency_key)
  → 提交不可逆动作
~~~

这种 read → preview → commit 结构把实体解析、业务计算和最终副作用分开，也让审批能够绑定到精确预览。

## 5. 工具错误必须是可推理的代数

只返回字符串 “something went wrong” 会逼模型猜。建议统一错误类型：

| error_code | 含义 | Agent 可做什么 |
|------------|------|----------------|
| INVALID_ARGUMENT | 参数语义不合法 | 修参数，不重试原请求 |
| NOT_FOUND | 资源不存在 | 改查找策略或询问用户 |
| CONFLICT | 版本/状态冲突 | 重新读取后重新计划 |
| PERMISSION_DENIED | 当前身份无权 | 不得换工具绕过；请求授权 |
| APPROVAL_REQUIRED | 缺审批 | 进入等待，而非循环调用 |
| RATE_LIMITED | 限流 | 按 retry_after 调度 |
| TRANSIENT | 可恢复基础设施错误 | 有界重试 |
| PERMANENT | 当前请求永久失败 | 停止或换业务方案 |
| UNCERTAIN_OUTCOME | 请求可能已生效但未收到确认 | **先对账，禁止盲重试** |

统一结果 envelope：

~~~json
{
  "ok": false,
  "error": {
    "code": "UNCERTAIN_OUTCOME",
    "message": "提交后连接超时，订单是否创建未知",
    "retryable": false,
    "reconcile": {
      "tool": "procurement.orders.find_by_idempotency_key",
      "arguments": {"idempotency_key": "op_..."}
    }
  },
  "operation_id": "op_...",
  "trace_id": "trace_..."
}
~~~

UNCERTAIN_OUTCOME 是最容易漏掉、也最危险的类型：超时发生在服务端提交之后时，直接重试可能重复扣款或重复发信。

## 6. 幂等、前置条件与后置验证

### 6.1 幂等键由控制面生成

不要让模型随意生成或每次重试都换 key。典型作用域：

~~~text
idempotency_key =
  hash(tenant_id, run_id, logical_action_id, action_revision)
~~~

logical_action_id 表示“这一次业务意图”；修正金额后是新 revision，网络重试仍是同 revision。

### 6.2 乐观并发保护世界状态

写操作带 expected_version：

~~~json
{
  "order_id": "ord_123",
  "expected_version": 7,
  "patch": {"status": "APPROVED"}
}
~~~

若当前版本为 8，返回 CONFLICT，Agent 必须重新读取，不得把旧计划覆盖到新世界状态。

### 6.3 成功响应仍需验证

工具返回 ok=true 只证明调用链自报成功。高风险动作应检查后置条件：

- 创建订单后按 order_id 读取，核对供应商、金额、数量。
- 发文件后读取 ACL，确认没有意外扩大权限。
- 修改代码后跑测试与静态检查。
- 发布后访问健康端点并校验版本。

Verifier 最好与执行工具分开，避免同一 bug 同时制造错误和证明自己正确。

## 7. Observation 设计：给模型最少但足够的信息

工具原始输出可能是几 MB JSON。直接回填会产生三类问题：挤占上下文、暴露秘密、让注入内容进入高信任区。

建议返回：

~~~json
{
  "summary": "找到 3 个有效报价，最低总价 186000 CNY",
  "items": [
    {
      "quote_id": "q_1",
      "supplier_id": "s_7",
      "total_minor": 18600000,
      "currency": "CNY",
      "expires_at": "2026-07-19T12:00:00+08:00"
    }
  ],
  "truncated": true,
  "next_cursor": "cur_...",
  "artifact": {
    "id": "art_...",
    "sha256": "...",
    "media_type": "application/json"
  },
  "provenance": {
    "tool": "procurement.quotes.search@4",
    "observed_at": "2026-07-18T10:00:00+08:00"
  }
}
~~~

关键点：

- 支持过滤、投影、分页，别提供 list_all。
- 使用稳定 ID，摘要只作为阅读辅助。
- 标记 truncated，不能让模型把局部结果当全集。
- 不可信文本单独放入 data 字段并带 trust 标签。
- 密钥、token、内部栈、PII 默认不返回模型。

## 8. 大规模工具表面的三层策略

工具从 10 个增长到数百个时，不应把全部 schema 永久塞入上下文。

### 8.1 Namespace：先按业务域缩小搜索面

~~~text
crm.customers.*
crm.opportunities.*
billing.invoices.*
procurement.orders.*
~~~

namespace 名称表达所有者和边界。相邻工具的语义不应重叠；如果工程师无法明确判断何时用 A、何时用 B，模型更难判断。

### 8.2 Deferred loading / Tool Search：按需加载

截至 2026-07，OpenAI Agents SDK 已支持 ToolSearchTool、namespace 和 defer_loading；Anthropic 也提供 Tool Search。共同思想是：

1. 初始上下文只放工具组摘要。
2. 模型先搜索/选择 namespace。
3. 再加载少量精确 schema。
4. 记录“搜索了什么、加载了什么”，用于评测。

注意：**发现工具不等于授权工具**。搜索结果只说明可能相关，Broker 仍按身份和策略过滤可执行视图。

### 8.3 Programmatic Tool Calling：让代码处理批量中间数据

当任务需要调用几十次查询并聚合结果时，把每个原始结果都经过模型会浪费上下文。可让模型生成受限代码，在沙箱中调用只读工具、过滤和汇总，再把小结果返回。

适合：

- 对多个实体执行同构查询。
- join、排序、聚合、去重。
- 从大结果中提取满足条件的少量记录。

不适合直接放开：

- 不可逆写操作。
- 无网络/CPU/内存边界的任意代码。
- 携带长期密钥的环境。

工具搜索解决“找到哪些工具”，程序化调用解决“怎样高效组合”，两者互补。

## 9. 工具评测不能只测单函数

建立四层评测：

| 层次 | 测什么 | 示例 |
|------|--------|------|
| Schema | 参数是否合法 | 缺字段、越界、额外字段 |
| Selection | 是否选对工具 | 相似工具、无需工具、需先澄清 |
| Execution | 业务效果是否正确 | 最终数据库状态、幂等、冲突 |
| Recovery | 失败后是否安全 | 超时、重复响应、审批过期、部分成功 |

建议数据集包含：

- 正常任务与近邻工具干扰。
- 参数中缺少实体 ID，只给模糊名称。
- 明确不该调用工具的任务。
- 工具描述中未覆盖的边界条件。
- 返回巨大结果、空结果、分页结果。
- 429、500、超时且结果未知。
- 重复 delivery 和 worker 崩溃。
- 恶意工具结果中的 prompt injection。
- 无权限、权限刚过期、审批参数被修改。

Anthropic 的建议是先建立真实任务 eval，再迭代名称、描述、返回结构和 token 效率；不要只凭工具作者感觉优化。

## 10. 反模式

- **把内部 OpenAPI 全量自动暴露**：粒度和语义面向程序，不面向 Agent；攻击面也被放大。
- **一个万能 execute 工具**：Schema 看似简单，实际绕过细粒度策略、观测和评测。
- **工具名区分不清**：get_customer、find_customer、search_customer 语义重叠。
- **错误全是字符串**：模型无法区分修参、重试、等待和对账。
- **超时就重试写操作**：忽略 UNCERTAIN_OUTCOME。
- **审批只绑定工具名**：审批后模型可改变金额、收件人或目标资源。
- **模型生成幂等键**：每次 retry 生成新 key，幂等失效。
- **返回全部原始数据**：上下文、隐私和注入风险同时上升。
- **tool search 替代授权**：发现层与执行权限层混淆。

## 11. 检验清单

- [ ] 每个工具是否有 owner、version、effect class 和 required scopes？
- [ ] 写工具是否定义幂等键作用域、冲突语义和补偿？
- [ ] 是否存在 UNCERTAIN_OUTCOME 及对账路径？
- [ ] 金额、时间、ID、枚举是否无歧义？
- [ ] 高风险动作是否采用 read → preview → approve → commit → verify？
- [ ] 审批是否绑定规范化参数 hash 和资源版本？
- [ ] observation 是否支持分页、投影、artifact 和 provenance？
- [ ] 工具搜索与权限过滤是否分开？
- [ ] eval 是否覆盖选择、执行、恢复和恶意 observation？
