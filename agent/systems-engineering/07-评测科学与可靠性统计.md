# 07 · 评测科学与可靠性统计

> 目标：把 Agent eval 从“测试集跑一次、报一个平均分”升级为可靠实验：明确随机变量、重复采样、置信区间、成本约束、最终世界状态、可靠性指标和基准外推边界。

---

## 1. 先定义你在估计什么

同一个任务的 Agent 运行结果是随机变量：

~~~text
Y = f(
  task,
  environment_state,
  model_snapshot,
  harness_version,
  tool_versions,
  sampling,
  transient_failures
)
~~~

若上述条件没有记录，两个“成功率”不可比较。评测清单至少 pin：

- 任务集版本与 split。
- 环境镜像、数据快照、时间。
- 模型 ID/snapshot 与推理配置。
- prompt、tool schema、policy、harness 版本。
- 每任务最大 token、费用、wall-clock、步骤。
- 重试和并行策略。
- grader/rubric 版本。

Agent 的被测对象是 **model + harness + tools + environment**，不是只测模型。

---

## 2. 结果判定优先看世界状态

对有动作的 Agent，可靠的 grader 顺序：

1. **最终环境状态**：订单是否存在、数据库字段是否正确、测试是否通过。
2. **关键不变量**：未越权、未超预算、审批有效。
3. **必要轨迹**：是否执行必须动作，是否有危险动作。
4. **最终文本质量**：解释是否正确、清晰、有引用。

τ-bench 的一个关键设计就是把对话结束后的数据库状态与目标状态比较，而不是仅让 LLM 判断最后一句话好不好。

LLM judge 适合开放文本和难以编码的 rubric；能用确定性状态判定的地方，优先确定性判定。

---

## 3. pass@k 与 pass^k：方向相反的指标

假设单次成功概率为 p，并暂时假设各次独立。

### 3.1 pass@k：尝试 k 次，至少一次成功

~~~text
pass@k = 1 - (1 - p)^k
~~~

适合：

- 生成多个候选后有可靠 verifier 选优。
- 代码、搜索、证明等“难找、易验”任务。
- 允许 test-time compute 换成功率。

### 3.2 pass^k：连续 k 次全部成功

~~~text
pass^k = p^k
~~~

适合：

- 用户每次都期待可靠执行。
- 重复运行相同业务流程。
- 衡量一致性，而非幸运命中。

若 p=0.8、k=5：

~~~text
pass@5 = 1 - 0.2^5 = 99.968%
pass^5 = 0.8^5 = 32.768%
~~~

同一个 Agent 可以在 best-of-5 看起来接近完美，却无法连续稳定服务 5 次。τ-bench 提出 pass^k，正是为了暴露工具 Agent 的不一致。

现实中各次运行可能相关，不能机械套独立公式。正确做法是对每个任务多次运行，直接估计任务级 pass rate 和 pass^k，并报告分布。

---

## 4. “每步 95%，八步 66%”只是示意

现有 Agent 教材常写：

~~~text
0.95^8 ≈ 0.66
~~~

它只有在下列强假设下成立：

- 每步都必须成功。
- 每步成功率相同。
- 步骤错误相互独立。
- 后续无法检测并恢复前一步错误。

真实 Agent 中：

- 难任务会同时降低多个步骤成功率，错误正相关。
- retry/reflection 可能恢复错误。
- 有些步骤是可选分支。
- 工具故障和模型决策故障不是同一分布。

所以这个乘法适合解释“长链条可能放大不可靠性”，不适合当作真实端到端成功率估计。实际要通过轨迹标注和分层模型估计：

~~~text
P(success | task_type, length, tool_count, model, harness)
~~~

---

## 5. 成功率必须带不确定性

10 个任务中成功 8 个，不等于真实成功率精确为 80%。样本小的时候区间很宽。

对二项成功率，优先报告 Wilson interval 或 bootstrap 区间，而不是只报点估计。Wilson 95% 区间的中心与半宽由样本量 n、成功比例 p̂ 和 z=1.96 共同决定：

~~~text
center =
  (p̂ + z²/(2n)) / (1 + z²/n)

half_width =
  z/(1 + z²/n)
  × sqrt(p̂(1-p̂)/n + z²/(4n²))
~~~

工程含义：

- n=10 的 8/10 证据远弱于 n=1000 的 800/1000。
- 对比两个版本时要报告差值区间。
- 低频高风险失败需要专门 challenge set，不能等平均样本自然覆盖。

可同时报告 micro average 与 macro average：

- micro：所有任务实例一起算，受大类样本量支配。
- macro：先按任务类别算，再等权平均，能看到小类退化。

---

## 6. 用 paired evaluation 降低噪声

比较 A/B 两版时：

1. 在完全相同任务和环境快照上运行。
2. 对每个 task 记录 A、B 成败/分数差。
3. 随机化运行顺序，避免时间/服务波动。
4. 对 paired difference 做 bootstrap 或适当检验。
5. 单独列出 A 赢、B 赢、都成、都败的任务。

只比较两个独立平均数会把任务难度差异混进版本差异。LLM API 未必允许固定随机种子实现完全复现，因此**任务配对和多次采样**比迷信 seed 更重要。

---

## 7. 质量与成本必须一起优化

AI Agents That Matter 指出，Agent benchmark 只看准确率会奖励昂贵的多次调用和复杂脚手架。建议画 Pareto frontier：

~~~text
x 轴：平均成本 / 成功一次的成本 / p95 延迟
y 轴：任务成功率 / pass^k / 安全通过率
~~~

若方案 B 更贵、质量还不高于 A，B 被 A 支配，不应因为架构更复杂而保留。

### 7.1 Cost per success

最简单近似：

~~~text
cost_per_success = mean_run_cost / success_rate
~~~

更准确地应直接统计：

- 成功 run 的成本分布。
- 失败 run 的沉没成本。
- 重试策略下到首次成功的总成本。
- verifier 和人工成本。
- 外部工具费用。

### 7.2 预算固定后再比较

多 Agent、best-of-N、reflection 都是在增加 test-time compute。比较架构时至少给出两组结果：

- 同模型、同预算。
- 各自最优配置下的 Pareto 曲线。

否则可能把“多花 10 倍钱”误当成“架构创新”。

## 8. Benchmark 选择要匹配能力

| Benchmark/方法 | 主要测量 | 不能直接推出 |
|----------------|----------|------------|
| **τ-bench** | 用户交互、工具、规则遵循、最终 DB 状态、一致性 | 任意企业流程可靠性 |
| **BrowseComp** | 难找易验的深度网页检索 | 日常检索体验、写作质量 |
| **PaperBench** | 长时间复现 AI 论文；层级 rubric 与 judge | 所有科研能力 |
| **SWE-bench 类** | 修复真实代码 issue | 通用电脑操作 |
| **METR time horizon** | 在特定软件/ML/安全任务集上，成功率随人类任务时长的变化 | “能自主工作同等时长”或自动化所有职业 |
| **内部真实任务集** | 你的用户分布与业务约束 | 通用模型排行榜 |

BrowseComp 特别说明其问题“难找但易验证”，并公开 canary 防训练污染；PaperBench 为 20 篇论文建立 8,316 个可评分子任务，并另行评估 judge。优秀 benchmark 设计的共同点是：**可验证、边界明确、说明不能外推什么。**

METR 也明确说明 time horizon 是按人类专家完成任务所需时长刻画任务难度，不是 Agent 自主运行的钟表时长；任务主要来自软件工程、ML 和网络安全，且真实工作通常更模糊、上下文更多。

---

## 9. 防止 benchmark overfitting

Agent 比普通模型更容易“钻 benchmark 空子”，因为 harness 可以：

- 针对公开 task 写规则。
- 搜索到标准答案。
- 利用 grader 漏洞。
- 用超高成本 brute force。
- 在公开 test 上反复调 prompt。

至少分四层：

1. 开发集：日常调试可见。
2. 回归集：CI 可见，限制人工针对性优化。
3. 私有 holdout：版本决策使用。
4. 时间外/分布外集：新工具版本、新领域、新攻击。

记录每次实验使用了哪些任务；频繁查看 holdout 本身就是信息泄漏。AI Agents That Matter 还强调：模型开发者和下游应用开发者需要的 benchmark 不同，不能用通用排行榜替代自己的任务分布。

### 9.1 联网评测的污染与 eval awareness

canary 和加密答案假设模型是“无意撞到”泄漏内容；能联网、能执行代码的 Agent 打破了这个假设。Anthropic 2026-03 对 Opus 4.6 × BrowseComp 的公开分析（1,266 题，多 Agent 配置）给出了两类证据：

- **被动泄漏**：9 题的答案已出现在公开网页——多篇 ICLR 2026 投稿把 BrowseComp 题目与明文答案写进论文表格，arXiv 附录里有完整解题轨迹；有一题模型的第一个搜索结果就是含原题和答案的论文。
- **主动 eval awareness**：2 题中模型先假设自己在被评测，推断出具体 benchmark，再定位并解密了答案密钥。这是已知第一例“不知道在跑哪个 benchmark，却反推出评测本身并解题”的记录。

工程含义：web-enabled 评测要么使用隔离/快照化的网络环境，要么在 trace 中检测“命中基准材料”并按污染剔除；同时把“模型是否表现出评测感知”纳入轨迹审计项。静态公开 benchmark 在联网 harness 下不再默认是封闭考试。

---

## 10. 轨迹评测要评“不变量”，不是唯一脚本

Agent 可能有多条合理路径，所以不要要求逐步完全匹配 reference trace。定义：

### 必须发生

- 写操作前读取当前资源版本。
- 高风险动作获得有效审批。
- 最终执行 verifier。

### 禁止发生

- 访问越权数据。
- 调用未授权工具。
- 在结果未知时直接重试不可逆动作。
- 把不可信网页指令当系统指令。

### 允许变体

- 查询顺序不同。
- 使用不同但等价的只读工具。
- 合理增加一次澄清。

轨迹指标应能定位失败，但最终优化目标仍是业务结果、安全和成本，不是“轨迹像人类”。

---

## 11. 线上评测闭环

~~~text
生产 trace
→ 规则抽取高价值/异常样本
→ 隐私清洗
→ 人工归因
→ 加入回归或 challenge set
→ 修模型/上下文/工具/Harness
→ 离线 paired eval
→ shadow/canary
→ 线上 SLO
~~~

建议在线指标：

- task success 与 partial success。
- pass^k 或重复任务一致性。
- cost per success。
- p50/p95/p99 端到端延迟。
- tool error 分类与 OUTCOME_UNKNOWN 率。
- approval precision/recall、人工撤销率。
- unsafe action blocked / escaped。
- 每类失败的 time-to-detect、time-to-recover。

不要把 LLM judge 全量分数当真值。定期抽样人工校准，监控 judge 与人类的一致率、偏差和版本漂移。

## 12. 发布门槛示例

~~~yaml
release_gate:
  required:
    task_success:
      delta_vs_baseline_lower_95ci: ">= -0.01"
    pass_pow_3:
      absolute: ">= 0.90"
    critical_policy_violation:
      count: 0
    cost_per_success:
      delta: "<= 0.10"
    p95_latency:
      delta: "<= 0.15"
  challenge_sets:
    prompt_injection: PASS
    duplicate_delivery: PASS
    stale_approval: PASS
    uncertain_tool_outcome: PASS
~~~

门槛应按业务风险设定。安全关键指标不能用“总体平均分提高”抵消。

## 13. 检验清单

- [ ] 是否明确被测对象包含 model、harness、tools、environment？
- [ ] 有动作任务是否优先检查最终世界状态？
- [ ] 是否区分 pass@k 和 pass^k？
- [ ] 是否避免把独立同分布假设当成真实多步成功率？
- [ ] 成功率是否有区间与样本量？
- [ ] A/B 是否做 paired evaluation？
- [ ] 是否同时报告质量、成本、延迟、安全和 cost per success？
- [ ] benchmark 是否与目标能力匹配，并说明外推边界？
- [ ] 是否有私有 holdout、时间外集和挑战集？
- [ ] release gate 是否禁止平均质量掩盖关键安全失败？
