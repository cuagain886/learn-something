# Agent 系统工程 · 学习总览

> 定位：现有专题已经解释了 Agent 的循环、工具、上下文、编排、评估与安全；本专题继续向下追问：**当进程会崩、工具会重复执行、任务跨越数小时、多个 Agent 同时写状态、协议不断升级时，系统怎样仍然正确？**
>
> 资料快照：2026-07-18。文中把“已稳定标准”“实验特性”“工程经验”分开标注，避免把发布新闻当成生产保证。

---

## 0. 为什么还需要一个“系统工程”专题

一个演示级 Agent 通常只有几十行：

~~~text
用户目标 → LLM → 工具调用 → 工具结果 → LLM → 最终答案
~~~

生产系统却至少有四种彼此独立的状态：

| 状态 | 典型内容 | 主要故障 |
|------|----------|----------|
| **对话状态** | 消息、摘要、当前上下文 | 截断、污染、隐私泄漏 |
| **任务状态** | 目标、步骤、等待原因、预算、取消信号 | 进程重启后丢失、重复调度 |
| **世界状态** | 数据库、邮件、支付、代码仓库等真实副作用 | 重复执行、部分成功、无法回滚 |
| **证据状态** | 产物、引用、测试结果、审批、trace | 不可验证、不可审计、版本错配 |

只保存 messages 并不等于保存任务；保存 checkpoint 也不自动保证外部副作用只发生一次。生产可靠性的核心问题不再是“模型会不会思考”，而是：

1. **模型的不确定决策如何被确定性控制平面约束。**
2. **至少一次执行环境下，副作用如何做到业务幂等。**
3. **长任务如何暂停、恢复、取消、升级和审计。**
4. **多 Agent 如何避免重复认领、写冲突和错误传播。**
5. **MCP、A2A、Skills、OpenTelemetry 各自解决哪一层，哪些能力仍需应用自己实现。**
6. **评估如何从“跑一次看起来不错”升级为有置信区间、成本边界和可靠性目标的实验。**

这就是本专题与已有专题的边界：前者回答“系统如何保持正确”，后者更多回答“Agent 如何获得能力”。

## 1. 总体心智模型：概率大脑，确定性外骨骼

把 Agent 拆成两个平面：

~~~text
┌──────────────────── 概率决策平面 ────────────────────┐
│  目标理解 / 检索 / 规划 / 工具选择 / 结果综合 / 反思   │
└────────────────────────┬────────────────────────────┘
                         │ 结构化意图
┌────────────────────────▼────────────────────────────┐
│                确定性控制平面                         │
│ schema校验 → 鉴权/策略 → 审批 → 幂等执行 → 记账 → 审计 │
│ 超时/预算 → 重试/补偿 → checkpoint → pause/resume      │
└────────────────────────┬────────────────────────────┘
                         │ 受控副作用
                  外部系统 / 人类 / 其他 Agent
~~~

最重要的设计原则是：

> **模型提出意图，控制平面决定该意图能否、何时、以什么身份和语义执行。**

不要让模型同时充当请求者、授权者和执行者。自然语言可以表达业务目标，但不能替代数据库约束、访问控制、幂等键、事务边界或审计证据。

## 3. 五条必须守住的系统不变量

### 3.1 每个外部动作都能回答“五个谁”

任何写操作必须可追溯到：

- 谁提出：用户目标或上游 Agent。
- 谁决策：哪个模型、prompt、策略版本。
- 谁授权：用户、服务身份、审批者。
- 谁执行：哪个 worker、工具版本、目标资源。
- 谁验证：确定性断言、独立 verifier 或人工。

缺一个，事故后就可能只能看到“Agent 做了某事”，却无法判断权限和责任链。

### 3.2 恢复执行不得静默重复副作用

进程可重启、消息可重复投递、节点可 replay。任何工具写操作都应至少具备：

- 稳定的 operation_id / idempotency_key。
- 可查询的执行状态。
- 明确的重试分类。
- 必要时的补偿动作。
- 结果与调用参数的审计摘要。

### 3.3 状态必须有版本和所有者

messages、计划、工具 schema、prompt、模型、策略、工作流代码都可能变化。持久化任务必须记录版本；并发任务必须明确谁拥有哪部分状态，以及冲突如何解决。

### 3.4 完成必须由证据定义

“模型说完成了”不是完成。完成条件应尽可能转化为可执行验证：

- 测试通过、数据库到达目标状态、文件存在且 hash 匹配。
- 引用能打开且支持对应主张。
- 审批记录存在并覆盖实际参数。
- 不可自动判定时使用结构化 rubric，而不是一句“看起来不错”。

### 3.5 自主权必须有预算和可撤销边界

自主权不是布尔值，而是多维预算：

~~~text
Autonomy = 时间 × 成本 × 步数 × 数据范围 × 动作风险 × 并发度
~~~

每一维都应有上限、告警和取消路径。高风险动作还应具备预览、审批、补偿或人工接管。

## 4. 推荐学习顺序

### 第一轮：先建立运行时骨架

阅读 01 → 02 → 03。目标是能画出一个 Agent runtime，并说清：

- 模型调用为什么必须与工具执行解耦。
- 为什么 checkpoint 不等于 exactly-once。
- 为什么工具“返回 200”不等于业务成功。

### 第二轮：解决长任务和协作

阅读 04 → 05 → 06。目标是能设计：

- 一个跨天等待人工审批仍可恢复的任务。
- 一套 MCP 工具层与 A2A 跨系统层的边界。
- 多 Agent 的任务所有权、隔离工作区与合并协议。

### 第三轮：用评测和控制面收口

阅读 07 → 08 → 09 → 10。目标是形成：

- 有重复试验、置信区间、成本/成功 Pareto 前沿的评测报告。
- 基于身份、资源、动作和风险的策略决策。
- 带 SLO、威胁模型、回滚和证据链的上线设计。

## 5. 贯穿专题的案例：采购审批 Agent

后续章节用同一案例帮助落地：

> 用户要求采购 20 台开发机。Agent 需要收集需求、查询供应商、比较报价、生成采购单；超过额度时等待经理审批；审批后下单并回写资产系统。

这个案例同时包含：

- 读工具与写工具。
- 长时间等待。
- 敏感商业数据。
- 外部不可逆动作。
- 多角色协作。
- 部分失败与补偿。
- 可客观检查的最终世界状态。

一个合格实现不能只展示“模型成功调用了下单工具”，还要回答：

1. 同一任务重放会不会下两次单？
2. 审批时看到的金额与实际下单金额是否相同？
3. 报价过期后是否重新审批？
4. 资产回写失败时订单如何处理？
5. 工具升级后，等待中的旧任务能否恢复？
6. trace 是否泄露供应商密钥或个人信息？

## 6. 毕业标准

学完本专题，应该能独立完成一份 Agent 系统设计评审，并准确回答：

- Agent runtime、workflow engine、模型 API、MCP server 各自保存什么状态？
- 至少一次执行为什么是常态？如何用幂等键、事务 outbox 和补偿控制副作用？
- background model response、MCP task、A2A task 与业务工作流是什么关系？
- 多 Agent 并行的收益上限由什么决定？怎样避免共享工作区冲突？
- pass@k 与 pass^k 为什么代表相反的产品目标？
- 为什么审批不是越多越安全？怎样绑定审批对象，避免 TOCTOU？
- 如何设计一条不记录敏感正文、但仍可定位问题的 trace？
- 哪些协议是稳定版，哪些功能截至 2026-07-18 仍属实验？

## 7. 面试追问树

| 层次 | 追问 | 合格回答必须覆盖 |
|---|---|---|
| 定义 | Agent runtime/harness 与模型 API/工作流引擎分别负责什么？ | loop、policy、tool broker、state/effect、trace、durability 边界 |
| 机制 | checkpoint 到底保证什么？ | durable state，不保证外部 exactly-once；activity/idempotency/outbox/receipt |
| 反例 | HTTP timeout 后为什么不能直接重试？ | before/after commit 不可知、RESULT_UNKNOWN、query/reconcile/compensate |
| 落地 | 长任务、审批和升级如何恢复？ | task state machine、work item、schema/version、proposal hash、migration |
| 安全 | 自主权怎样形成可撤销边界？ | identity chain、PDP/PEP、JIT capability、budgets、kill switch |
| 评测 | 可靠性怎样用统计而非 demo 证明？ | repeated trials、pass^k、fault injection、CI、tail risk、cost/success |
