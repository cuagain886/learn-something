# 04 · 长任务与跨上下文连续性

> 目标：设计能运行数小时或数天的 Agent。关键不是“允许更多轮”，而是把工作拆成可验证的小事务，用持久化事实和产物跨越上下文窗口、进程和人工等待。

---

## 1. 三个经常混淆的“长”

| 类型 | 例子 | 主要机制 |
|------|------|----------|
| **长推理请求** | 强推理模型单次思考数分钟 | background response、轮询/webhook |
| **长对话** | 客服持续多轮沟通 | session、摘要、长期记忆 |
| **长业务任务** | 调研两天、等待审批、跨系统执行 | durable workflow、task state、events、artifacts |

Background mode 解决 HTTP 超时，不自动解决：

- 工具副作用的幂等。
- 跨数十个模型调用的工作流状态。
- 人工等待后的版本恢复。
- 进程崩溃与任务重新认领。
- 取消后的补偿。

同样，session 能保存对话历史，但不等于 durable business task。设计时必须先判断是哪一种“长”。

---

## 2. Task 是一等对象

长任务不能只由一串 messages 表示。建议数据模型：

~~~text
Task
  identity:
    task_id / tenant_id / owner / created_by
  objective:
    goal / constraints / success_criteria
  execution:
    status / revision / lease / deadline / budget
  plan:
    work_items / dependencies / owners / attempts
  continuity:
    progress_summary / next_action / blockers
  evidence:
    artifacts / citations / verifier_results
  control:
    approval_refs / cancellation / policy_version
~~~

其中 goal 与 success_criteria 要分开：

- goal：生成市场调研报告。
- success_criteria：覆盖 10 个指定竞争对手；每个定量主张有可访问来源；数据不早于 90 天；输出含 CSV 与 10 页以内摘要；事实检查通过。

目标描述意图，成功条件定义终止。

## 3. 跨窗口连续性的四类载体

### 3.1 结构化任务状态

保存能直接驱动控制流的事实：

- 已完成 work_item。
- 未解决 blocker。
- 当前预算。
- 等待的 event。
- 工具 operation 状态。

不要让新会话从自然语言摘要里猜这些事实。

### 3.2 进度账本

每个工作片段结束时写：

~~~markdown
## 本轮完成
- 报价收集：供应商 A/B/C，原始响应见 art_17
- 已验证 A/B 的税费，C 的报价明日过期

## 未完成
- 核对 C 的售后条款
- 生成标准化比较表

## 关键决策
- 统一按含税到岸价比较，决策记录 dec_09

## 下一步唯一入口
- 执行 work_item wi_23：核对 C 的售后条款

## 验证状态
- quote_schema_check: PASS
- source_freshness_check: FAIL(C)
~~~

账本是给下一班 worker 的交接，不是完整日志。它应简短、结构稳定、引用不可变产物。

### 3.3 不可变产物

原始数据、报告、代码、截图、测试日志以 artifact 保存：

~~~text
artifact_id
content_hash
media_type
producer
source_uri
created_at
trust_level
retention_class
parent_artifact_ids
~~~

摘要可以重写，artifact 不能被静默覆盖。新版本生成新 ID，并用 lineage 关联旧版本。

### 3.4 可执行验证器

验证器把“我记得做到哪里”变成“环境证明做到哪里”：

- 读取代码并跑测试。
- 检查数据库状态。
- 比对文件 hash。
- 检查引用可访问性与时间。
- 统计成功条件覆盖率。

长任务越长，越不能靠模型的自我叙述判断完成。

## 4. Initializer + Incremental Worker 模式

Anthropic 对长时间编码 Agent 的实践采用两种角色：

### 4.1 Initializer

首次运行只负责搭地基：

1. 把用户目标转成详细 feature/work-item 列表。
2. 建立环境、测试骨架和运行命令。
3. 创建进度文件和初始版本控制状态。
4. 验证最小端到端链路可运行。
5. 不试图一次完成全部功能。

### 4.2 Incremental Worker

每个后续会话：

1. 先读取进度、最近变更和环境真实状态。
2. 选择一个边界清晰、可在本轮验证的 work_item。
3. 实现并运行测试。
4. 只在验证通过后标记完成。
5. 留下干净工作区、变更记录和下一步。

这个模式可推广到调研、数据处理、合规审查。核心不是“编码 Agent 特例”，而是 **每个上下文窗口完成一个可提交事务**。

---

## 5. Context compaction 为什么不够

压缩解决 token 数量，不能保证：

- 关键不变量一定被保留。
- 已执行副作用不被误写为“计划执行”。
- 未完成与已完成边界准确。
- 引用和 artifact ID 不丢。
- 下一会话不因摘要语气而过早宣告完成。

因此上下文恢复顺序应是：

~~~text
1. 读取任务结构化状态
2. 读取工作区/世界状态
3. 执行验证器确认事实
4. 读取短进度摘要
5. 按需加载具体 artifact
6. 编译本轮上下文
~~~

摘要是索引，不是事实数据库。

---

## 6. Work item 应该像事务

一个好的 work item 具备：

- 单一可描述结果。
- 明确输入与输出 artifact。
- 所有依赖已满足。
- 可在本轮预算内完成。
- 有自动或人工验证方法。
- 失败不会污染其他 work item。
- 明确资源所有权。

不好的任务：

> 研究所有竞争对手并写出最终报告。

更好的拆分：

~~~text
wi_01 定义竞争对手清单和纳入标准
wi_02..11 每个竞争对手生成标准化事实卡
wi_12 校验事实卡来源新鲜度
wi_13 计算横向指标
wi_14 生成报告草稿
wi_15 独立事实核查
wi_16 修订并发布
~~~

拆分不是越细越好。过细会把上下文和协调开销放大；应以“一个 worker 能完整验证并提交”为粒度。

## 7. Lease、Heartbeat 与僵尸任务

分布式 worker 认领 work item 时使用 lease：

~~~json
{
  "work_item_id": "wi_23",
  "lease_owner": "worker_7",
  "lease_version": 12,
  "lease_expires_at": "2026-07-18T11:00:00Z",
  "heartbeat_at": "2026-07-18T10:59:30Z"
}
~~~

要求：

- 通过 compare-and-swap 原子认领。
- 心跳只能延长自己持有且版本匹配的 lease。
- lease 到期允许接管，但旧 worker 的后续写入必须因版本不匹配而失败。
- 外部副作用仍以 operation_id 幂等，不能只靠 lease 防重复。

Lease 解决“谁现在负责”，幂等解决“两个负责者意外执行时会怎样”。

## 8. 预算与长任务调度

长任务至少有四个预算：

| 预算 | 触发时动作 |
|------|------------|
| turn/step | 保存进度，重新规划或升级人工 |
| token/费用 | 降低上下文、切模型、停止低价值分支 |
| wall-clock/deadline | 取消未开始项，输出部分结果与缺口 |
| 并发/外部配额 | 排队、退避、按优先级分配 |

不要在接近预算耗尽时让模型“尽快完成”，这常导致草率收尾。Harness 应在阈值前触发 **handoff checkpoint**：

1. 停止创建新分支。
2. 收敛在途工作。
3. 验证并保存当前产物。
4. 写清未完成项与下一步。
5. 决定新会话、降级交付或人工接管。

## 9. 外部世界会变化：恢复时必须重验证

等待期间可能发生：

- 报价过期。
- 用户权限被撤销。
- 文件被他人更新。
- 库存变化。
- 工具 schema 升级。
- 安全策略收紧。

恢复不是从暂停行继续，而是：

~~~text
load checkpoint
→ validate versions
→ refresh volatile facts
→ re-evaluate policy
→ invalidate stale approval if needed
→ continue or re-plan
~~~

把事实分为：

- **immutable**：订单 ID、已签署审批记录、artifact hash。
- **stable-enough**：组织结构、产品目录，带 TTL。
- **volatile**：库存、价格、权限、外部页面，恢复必查。

上下文和计划中都应携带 observed_at 与 freshness policy。

---

## 10. 终止条件与“假完成”

长 Agent 常见两种假完成：

1. 看见已有进度就认为任务完成。
2. 产物存在但没有满足质量标准。

终止 gate：

~~~text
all required work_items terminal
AND no unresolved critical blockers
AND all success criteria have evidence
AND verifier suite passes
AND no pending irreversible operations
AND budget/accounting finalized
~~~

允许的终止状态应比 success/failure 更丰富：

- SUCCEEDED。
- PARTIAL_SUCCESS（列出未覆盖标准）。
- FAILED。
- CANCELLED。
- EXPIRED。
- MANUAL_REVIEW_REQUIRED。
- COMPLETED_WITH_UNCOMPENSATED_EFFECTS。

用户需要知道真实状态，而不是一个乐观的自然语言句号。

## 11. 长任务可观测性

除 trace 外，需要任务级指标：

- active / waiting / retry / stuck 数量。
- age 与 time-in-state。
- 每个 work item 的 attempts。
- heartbeat/lease 超时。
- 每完成一条 success criterion 的边际成本。
- context compaction 次数和恢复后回退次数。
- artifact 生成/验证失败率。
- 人工等待时间与审批过期率。

Stuck detector 不只看“多久没输出”，还看：

- 多轮未减少 remaining work。
- 重复相同工具参数。
- 相同错误循环。
- progress summary 无新 evidence。
- 在预算消耗增加时 verifier 分数不变。

## 12. 检验清单

- [ ] 是否区分长推理、长对话和长业务任务？
- [ ] task 是否有 success_criteria，而不只是 goal？
- [ ] 结构化状态、进度账本、artifact、验证器是否各司其职？
- [ ] 每个 work item 是否能在一轮内验证并提交？
- [ ] compaction 是否只作索引，而非唯一事实来源？
- [ ] worker 是否使用有版本的 lease 和 heartbeat？
- [ ] 恢复时是否重查 volatile facts、权限和审批有效性？
- [ ] 预算阈值是否触发干净 handoff，而非草率收尾？
- [ ] 终止是否由证据 gate 决定？
- [ ] 部分成功和未补偿副作用是否能如实表达？
