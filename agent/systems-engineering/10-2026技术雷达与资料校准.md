# 10 · 2026 Agent 技术雷达与资料校准

> 快照日期：2026-07-18。
>
> 目标：只记录能由规范、官方工程文档或论文直接支持的变化，并显式标注成熟度。框架排名、模型名称和价格变化太快，不把它们写成长期不变的知识。

---

## 1. 技术雷达

### Adopt：已经值得作为生产默认原则

| 主题 | 结论 | 依据 |
|------|------|------|
| 确定性控制平面 | 模型提出意图，策略、审批、执行、预算由代码强制 | OpenAI/Anthropic 安全实践、OWASP |
| 工具契约 | 工具需要效果、权限、幂等、错误和验证语义 | Anthropic 工具工程、durable runtime 实践 |
| 持久化任务状态 | 长任务必须可 pause/resume/recover，不能只存在内存/messages | OpenAI Agents SDK、LangGraph、Temporal/Dapr/DBOS |
| Artifact-first | 大结果、证据、代码和报告存不可变 artifact，context 只放引用与摘要 | 长任务 Harness 实践 |
| 评测成本联合优化 | 报成功率同时报费用、延迟、重复可靠性和区间 | AI Agents That Matter、τ-bench |
| 防御纵深 | 最小权限、沙箱、出站控制、审批、审计共同限制 blast radius | OWASP 2026、OpenAI/Anthropic |

### Trial：已有正式实现，适合受控试点

| 主题 | 当前状态 | 试点建议 |
|------|----------|----------|
| A2A 1.0 | 首个稳定发布版，支持发现、任务、artifact、版本协商和多 binding | 仅用于真实跨系统/跨组织委托，先做互操作和信任测试 |
| Agent Skills | 开放目录规范，多客户端采用，progressive disclosure 成熟 | pin 来源/版本/hash，在沙箱运行脚本 |
| Tool Search / deferred loading | OpenAI、Anthropic 均有官方能力 | 大工具面先 namespace，再按需加载；发现不替代授权 |
| Programmatic tool calling | 官方平台已有，让代码处理批量工具结果 | 只读/低风险聚合优先，严格沙箱和资源限制 |
| Durable workflow integration | OpenAI Agents SDK 列出 Dapr、Temporal、Restate、DBOS 集成 | 用真实故障注入验证，不把“集成存在”当成业务 exactly-once |
| 多 Agent 并行 | 研究与工程案例证明某些宽任务可获益 | 只在可分区、可验证、上下文隔离有价值时使用 |

### Assess：重要但仍在快速演化

| 主题 | 当前状态 | 风险 |
|------|----------|------|
| MCP Tasks | 2025-11-25 引入且明确标记 experimental | 生命周期和扩展仍可能变化；不要成为唯一业务状态 |
| OpenTelemetry GenAI conventions | 已覆盖 invoke_agent、execute_tool 等，但多项仍为 Development | pin 版本、加内部适配层、正文默认不采集 |
| Agent 身份/委托标准 | OAuth、mTLS、Agent Card 等有组件，但端到端责任与授权仍碎片化 | 不能把连接成功等同于信任成立 |
| 记忆安全与 provenance | OWASP 已单列 Memory & Context Poisoning | 框架普遍更重“记住”，轻“验证/失效/追溯” |
| 长任务能力指标 | METR Time Horizon 1.1 提供更新方法 | 任务域有限，不能外推为所有工作自动化 |

### Hold：除非有强证据，不要作为默认

| 做法 | 原因 |
|------|------|
| 一开始就自由 Swarm | 状态所有权、终止、成本和错误传播难控制 |
| 全部工具 schema 常驻上下文 | token 浪费、选择混淆、攻击面放大 |
| 只靠 prompt 防注入 | 概率防线有漏报，无法限制后果 |
| 高频人工确认所有动作 | approval fatigue，使确认失去意义 |
| 把 session/messages 当 durable state | 无法可靠表示副作用、审批、预算和版本 |
| Benchmark 单次最高分 | 混入幸运采样、成本和过拟合 |
| 根据媒体文章列“2026 十大框架” | 排名不可复现且快速过时 |

## 2. 2025–2026 真正发生的六个变化

### 2.1 从“框架 API”转向开放互操作层

- MCP 在 2025-11-25 继续演进工具/上下文连接规范，并进入 Linux Foundation 下的 Agentic AI Foundation 生态。
- A2A 发布 1.0 稳定版，明确跨独立 Agent 的任务与 artifact 语义。
- Agent Skills 与 AGENTS.md 将过程知识和仓库指令变成轻量、可移植约定。

变化不是“出现一个统一万能协议”，而是开始形成分层：

~~~text
Agent ↔ Agent       A2A
Agent ↔ Tool/Data   MCP
Agent ↔ Procedure   Skills
Agent ↔ Repository  AGENTS.md
Runtime ↔ Telemetry OTel GenAI
~~~

### 2.2 Harness 工程成为能力乘数

公开工程案例越来越强调：

- context compaction 不足以支持跨窗口长任务。
- initializer、增量 worker、进度账本、test oracle 与干净交接非常关键。
- 同一模型在不同工具描述、workspace、验证器和任务管理下表现差异显著。

这促使评价单位从“哪个模型更强”转向“哪个 model + harness + tool + environment 系统更可靠”。

### 2.3 工具使用从静态列表走向按需发现和代码组合

随着工具面扩大，两个问题变突出：

1. 将数百个 schema 放进上下文影响选择并消耗 token。
2. 每个中间结果都回到模型，批量聚合低效。

对应演进：

- namespace。
- deferred loading / tool search。
- programmatic tool calling。
- 大结果 artifact 化和 output trimming。

但大规模工具发现也扩大供应链和权限风险，因此授权视图必须由控制平面生成。

### 2.4 “长任务”从上下文问题升级为 durable execution 问题

OpenAI Agents SDK 已将 HITL state serialization、长审批和多种 durable execution 集成写入官方文档；MCP 也开始实验 Tasks。共同信号是：

> 长任务的核心不只是模型能思考多久，而是任务能否在故障、等待、取消和升级中保持正确。

工作流历史、幂等 activity、状态版本、事件唤醒和补偿正在成为 Agent runtime 的标准工程组件。

### 2.5 评估从“平均成功率”走向可靠性、成本与时间跨度

- τ-bench 用最终数据库状态判分，并用 pass^k 测连续一致性。
- AI Agents That Matter 要求成本控制、Pareto 比较、holdout 和可复现。
- BrowseComp 展示“难找、易验证”及 test-time compute 的价值，也明确其任务分布边界。
- PaperBench 用层级 rubric 拆长科研任务，并单独评估 LLM judge。
- METR Time Horizon 1.1 继续测量任务难度与成功率关系，同时公开强调不能把它解释为自主运行时长或全职业自动化。

### 2.6 安全重心从“模型拒绝”转向“控制 blast radius”

OWASP Agentic Top 10 2026 把身份、供应链、记忆污染、Agent 间通信、级联失败和人类信任纳入独立风险。OpenAI 与 Anthropic 的公开实践也共同强调：

- confirmations。
- sandbox/containment。
- 网络和秘密隔离。
- 运行时监控。
- 最小化登录/授权范围。

更准确的安全目标不是“模型永远不犯错”，而是：

> 错误/攻击发生时，Agent 无法静默越权、外泄或造成超出预定边界的不可逆后果。

## 3. 当前协议状态表

| 项目 | 截至 2026-07-18 的状态 | 需要 pin 的内容 |
|------|------------------------|-----------------|
| MCP | 当前规范目录 2025-11-25 | protocol version、capabilities、transport、auth |
| MCP Tasks | experimental | task capability、tool taskSupport、降级路径 |
| A2A | latest released 1.0.0 | Major.Minor、binding、extensions、Agent Card hash |
| Agent Skills | 开放规范 | skill source、version/hash；allowed-tools 仍 experimental |
| AGENTS.md | 开放仓库约定，已纳入 AAIF 首批项目 | 文件作用域、仓库 revision |
| OTel GenAI | 活跃演进，若干 operation/attribute 为 Development | semconv version、content capture policy |

生产文档应写“使用 MCP 2025-11-25 的哪些 capability”，而不是只写“支持 MCP”；应写“A2A 1.0 + binding”，而不是只写“Agent 可以互联”。

## 4. 模型与框架如何写才不过时

不建议在长期知识文档中写：

> X 是 2026 最强模型；Y 是多 Agent 主流第一框架。

建议写选择维度：

### 模型

- 目标任务的 held-out success / pass^k。
- tool calling 与 structured output。
- 长上下文退化，而非只看窗口上限。
- 延迟、成本、rate limit。
- 数据保留、地域、合规。
- 模型 snapshot 和弃用策略。

### Agent runtime

- durable execution 语义。
- HITL pause/resume 与序列化。
- 工具/MCP/A2A 支持边界。
- tracing 与开放导出。
- sandbox/secret/network controls。
- state schema、迁移、测试能力。
- 出问题时能否脱离框架下钻。

### 评测方式

每次“最新模型/框架”选型都应是一次带日期的实验报告，不写成无期限事实：

~~~text
as_of
versions
task_distribution
budget
results_with_ci
cost_latency
known_failures
decision_expiry
~~~

## 5. 资料可信度分级

| 等级 | 来源 | 用法 |
|------|------|------|
| A | 正式规范、RFC、官方 API reference | 事实和 MUST/SHOULD |
| B | 原始论文、官方系统卡、官方工程复盘 | 方法、实验和局限 |
| C | 开源实现源码/测试/issue | 验证真实行为，标版本 |
| D | 厂商博客/二手教程 | 发现线索，不单独支撑关键数字 |
| E | 聚合榜单、SEO “Top 10” | 不用于技术结论 |

引用数字时必须回答：

- 样本和任务是什么？
- 指标如何定义？
- 基线和预算是否一致？
- 是否内部 eval？
- 能否外推到当前场景？

例如 Anthropic 多 Agent research 的 90.2% 提升是其内部研究 eval 和特定 lead/subagent 配置的结果；不能改写成“多 Agent 普遍提升 90%”。

## 6. 对本仓库既有知识的校准

### 6.1 应保留的主线

- Workflow 与 Agent 分开。
- 从单 Agent 和简单模式开始。
- 上下文是有限预算。
- 多 Agent 只在单 Agent 有明确瓶颈时上。
- 安全依靠最小权限、沙箱、护栏和 HITL。
- 评测要看结果、轨迹和组件。

### 6.2 需要升级的表述

| 旧式表述 | 更准确表述 |
|----------|------------|
| checkpoint 后从断点继续 | 恢复可能重放节点；副作用必须幂等 |
| 工具失败就 retry | 先区分 transient、permanent、outcome unknown |
| 多 Agent = 多角色协作 | 多 Agent = 并发任务、状态所有权和验证问题 |
| 记忆 = 向量库 | 记忆还需 provenance、版本、失效、污染隔离 |
| trace 记录完整 prompt | 正文是敏感 opt-in，默认记 metadata/hash/ref |
| 人工确认更安全 | 确认要低频、高信息、参数绑定，否则产生疲劳 |
| MCP 是工具标准 | MCP 标准化连接；业务权限、幂等、恢复仍由应用负责 |
| 长上下文支持长任务 | 长任务还需要 artifact、进度账本和 durable execution |
| 成功率越高越好 | 同时看 pass^k、成本、尾延迟、安全与置信区间 |

### 6.3 应删除或降级的无来源数字

诸如“65% 的 Agent 失败来自上下文”“80% 取决于工具定义”“90% 场景某架构足够”“40% 企业应用将采用”等，如果没有可核验原始研究，应改为：

- 定性工程判断；或
- 明确限定为某一研究、数据集、产品版本的结果。

看似精确但不可追溯的百分比，比不写数字更误导。

## 7. 下一阶段值得追踪的问题

1. MCP Tasks 从 experimental 走向何种稳定生命周期。
2. A2A 1.x 的真实跨厂商互操作、TCK 与扩展治理。
3. Agent workload identity、委托凭据和跨组织责任模型。
4. Skills/Agent package 的签名、权限清单和供应链扫描。
5. OTel GenAI semantic conventions 的稳定化与隐私默认值。
6. 长任务 benchmark 如何覆盖模糊目标、真实组织上下文和人工协作。
7. 多 Agent 的错误相关性、验证瓶颈和成本扩展规律。
8. 记忆污染检测、claim lineage 与跨会话撤销。
9. 电脑操作 Agent 的安全 UI、watch mode 与可撤销事务。
10. 能否用形式化策略/类型系统约束 Agent 动作，而不仅是事后检测。

## 9. 本章结论

- 2026 的主线不是“所有东西都变成多 Agent”，而是 **开放协议分层 + Harness 工程 + durable execution + 受控工具面 + 可靠性评测 + containment**。
- 标准化正在发生，但成熟度不同：A2A 1.0 已稳定发布；MCP Tasks 和多项 OTel GenAI 语义仍在实验/开发阶段。
- 最新模型和框架会快速轮换，长期知识应保存选择方法、版本边界和实验结果，不保存无期限排行榜。
- 所有精确数字都必须携带任务分布、预算、版本和外推限制；没有一手依据的数字应删除或降级。
