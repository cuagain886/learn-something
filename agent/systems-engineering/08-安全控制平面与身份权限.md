# 08 · 安全控制平面与身份权限

> 目标：把安全从“Prompt 里提醒模型不要做坏事”提升为系统控制平面。重点是身份链、策略执行、最小权限、审批对象、秘密隔离、沙箱/出站控制与可恢复的事件响应。

---

## 1. Agent 安全的关键变化

聊天模型输出错误文本；Agent 可能读取私有数据、运行代码、修改权限、发消息和创建订单。风险由三项共同决定：

~~~text
Risk = capability × exposure × blast_radius
~~~

- capability：模型和工具能做什么。
- exposure：会接触哪些不可信输入。
- blast_radius：一旦出错能影响多少数据、资金和系统。

模型鲁棒性是防线之一，但不是安全边界。Prompt injection 仍是行业长期挑战；OpenAI 和 Anthropic 的公开安全材料都采用多层缓解，而不是声称已被“解决”。

---

## 2. 用 OWASP Agentic Top 10 建威胁模型

OWASP 2026 分类：

| ID | 风险 |
|----|------|
| ASI01 | Agent Goal Hijack |
| ASI02 | Tool Misuse & Exploitation |
| ASI03 | Identity & Privilege Abuse |
| ASI04 | Agentic Supply Chain Vulnerabilities |
| ASI05 | Unexpected Code Execution |
| ASI06 | Memory & Context Poisoning |
| ASI07 | Insecure Inter-Agent Communication |
| ASI08 | Cascading Failures |
| ASI09 | Human-Agent Trust Exploitation |
| ASI10 | Rogue Agents |

做设计评审时不要只问“会不会 prompt injection”，而要沿数据流检查：

~~~text
用户 / 网页 / 邮件 / RAG / Skill / MCP / 其他 Agent
  → 上下文与记忆
  → 模型决策
  → 工具/代码
  → 外部系统
  → artifact / trace / 新记忆
~~~

每个入口都可能污染后续；每个输出又可能成为下一 Agent 的输入。

## 3. 身份链：不要让“Agent”成为模糊超级用户

一次动作至少有六层身份：

1. **Human principal**：最终发起用户。
2. **Application client**：代表哪个应用。
3. **Run identity**：哪个任务实例。
4. **Agent role**：规划者、研究者、执行者或 verifier。
5. **Tool workload identity**：哪个工具服务/worker。
6. **Target resource identity**：目标 API 看到的调用主体。

审计应能回答：

~~~text
user u_7
delegated to run run_9
using agent procurement-executor@17
through tool order.create@3
under grant grant_12
acted on order ord_...
~~~

反模式：

- 所有 Agent 共用一个高权限 API key。
- 只记录“服务账号调用”，丢失用户和 run 委托链。
- 把用户 OAuth token 原样传给 MCP 下游。
- 把 session_id 当认证。

MCP Authorization 明确要求 token audience 绑定目标 resource，并禁止 token passthrough；下游调用应使用为下游签发的独立 token。

## 4. PDP / PEP：策略决策与执行分离

### 4.1 Policy Decision Point

接收结构化输入：

~~~json
{
  "principal": {"id": "u_7", "roles": ["buyer"]},
  "run": {"id": "run_9", "purpose": "hardware_procurement"},
  "agent": {"name": "procurement-executor", "version": 17},
  "action": {
    "tool": "procurement.orders.create",
    "effect": "IRREVERSIBLE_WRITE",
    "amount_minor": 18600000,
    "currency": "CNY"
  },
  "resource": {"supplier_id": "s_3", "tenant_id": "t_1"},
  "environment": {"time": "...", "risk_score": 0.72}
}
~~~

输出：

~~~json
{
  "decision": "REQUIRE_APPROVAL",
  "policy_id": "procurement-high-value@8",
  "obligations": {
    "approver_role": "procurement_manager",
    "expires_in_seconds": 3600,
    "bind_fields": [
      "supplier_id",
      "amount_minor",
      "currency",
      "items_hash"
    ]
  }
}
~~~

### 4.2 Policy Enforcement Point

Tool Broker 是 PEP：

- 无 PDP allow 不执行。
- 强制 obligations。
- 执行前再次校验策略与审批。
- 记录 policy version、输入 hash、decision。

OPA 这类 policy-as-code 引擎可把决策逻辑从 Agent 代码中解耦、版本化和测试；是否采用具体产品不是重点，重点是**策略由确定性系统强制执行**。

---

## 5. 最小权限应当是任务级、渐进式

静态角色往往过宽。更理想的是：

1. run 创建时只有只读最小权限。
2. 计划需要写动作时申请短期 capability。
3. capability 绑定目的、资源、动作、金额/数量、过期时间。
4. Broker 在执行时兑换成短期下游凭据。
5. 完成或取消后立即撤销。

Capability 示例：

~~~json
{
  "grant_id": "grant_12",
  "subject": "run_9",
  "action": "procurement.orders.create",
  "resource": "supplier:s_3",
  "constraints": {
    "max_amount_minor": 18600000,
    "currency": "CNY",
    "items_hash": "sha256:..."
  },
  "expires_at": "2026-07-18T12:00:00Z",
  "single_use": true
}
~~~

Agent 得到的是调用能力，不是长期 secret。

---

## 6. 审批必须绑定“实际将发生的动作”

无效审批：

> 是否允许采购 Agent 下单？ [允许]

有效审批对象：

~~~text
action: create_order
supplier: s_3
items_hash: ...
amount: 186000 CNY
shipping_address_id: addr_7
resource_version: quote_v19
preview_hash: ...
expires_at: ...
~~~

批准后任何绑定字段变化，都必须重新 preview 和审批。这防止 TOCTOU：

~~~text
审批时看到 18.6 万
→ 报价/参数被替换
→ 实际执行 86 万
~~~

执行前 PEP 重新读取 volatile state，校验 approval hash、资源版本、审批者权限和有效期。

---

## 7. 审批不是越多越安全

Anthropic 2026 的公开工程文章称其产品遥测中用户批准了约 93% 的权限提示，并据此讨论 approval fatigue。高频、低信息量确认会训练用户机械点击。

改进：

- 默认通过沙箱和最小权限自动允许低风险动作。
- 聚合一组同质、边界明确的只读动作。
- 高风险确认显示具体差异、目标、数据外发和不可逆性。
- 不允许模型用诱导语言替代系统生成的风险摘要。
- 记录用户在确认后立即撤销/修正的比例，评估确认质量。
- 对关键权限变化考虑双人审批或职责分离。

审批是针对剩余风险的最后闸门，不是用来弥补无限权限。

## 8. Containment：限制能做什么

### 8.1 运行隔离

- 每 run/Agent 独立容器或微 VM。
- 只读基础镜像，临时可写层。
- 明确 CPU、内存、进程、文件、时间配额。
- 默认无网络，按域名/端口 allowlist。
- 敏感目录不挂载；必要目录按只读/读写细分。
- 完成后销毁环境并按策略保留 artifact。

### 8.2 出站控制

Prompt injection 常见目标是数据外泄。仅限制“危险命令”不够，要限制网络：

- DNS/HTTP 代理执行 allowlist。
- 域名解析后防 SSRF、重定向到内网和云 metadata。
- 上传动作单独审批。
- 限制请求方法、大小、媒体类型。
- domain-scoped secrets 只对对应目标注入。

OpenAI Agents SDK 的 hosted container 文档支持禁网或 allowlist 网络策略及 domain-scoped secrets；这体现的是通用原则：**secret 由执行环境按目标注入，不进入模型上下文。**

### 8.3 电脑操作

GUI/浏览器工具要额外：

- 独立浏览器 profile。
- 非必要不登录敏感站点。
- 密码由用户 takeover 或 secret manager 填充。
- 发送、购买、权限修改前确认。
- 对敏感上下文采用持续监督/Watch mode。

## 9. 数据与指令的信任标签

每条上下文记录附：

~~~text
source
source_identity
trust_level
observed_at
integrity_hash
data_classification
allowed_uses
taint
~~~

基本规则：

- 网页、邮件、RAG 文档、工具文本结果都是 data，不可提升为 system instruction。
- 来自未信任来源的内容不能写入全局 memory/Skill/AGENTS.md。
- memory 写入需要 schema、来源和验证；读取时仍保留 provenance。
- 一个 Agent 的总结不能洗掉原始内容的 taint。
- 高风险决策回溯到原始 evidence，不只看摘要。

OWASP 将持久污染单列为 ASI06，原因正是一次不可信输入可能跨会话影响未来行为。

---

## 10. 供应链：Skill、MCP、Agent Card 都是代码

检查：

- 来源、签名、版本、hash、许可证。
- 更新是否自动扩大工具/网络/文件权限。
- Skill script 是否执行任意安装脚本。
- MCP server 是否请求不合理 OAuth scope。
- 工具描述/schema 是否在更新中改变效果。
- Agent Card 的 endpoint、认证和 JWS 签名。
- 依赖包、容器镜像、模型/harness 版本。

安装新 Skill 或 MCP server 应触发安全审查；运行时动态发现不能等同于动态信任。

## 11. Trace 与审计也会泄密

OpenTelemetry GenAI 字段明确警告 system instructions、tool arguments、tool results 可能敏感。建议分层：

### 默认运营 trace

- ID、版本、状态、耗时、token、错误码、参数 hash、payload 大小。
- 不记录正文、secret、完整 PII。

### 受控调试样本

- 明确采样和访问审批。
- 进入隔离存储，短保留期。
- 字段级脱敏和租户隔离。
- 下载/查看本身留审计。

### 合规审计

- 记录谁授权、执行了什么、结果 reference。
- 必要时使用加密 artifact，审计记录只放 hash。
- 与模型调试 trace 分开保留和授权。

“为了可观测把所有 prompt 永久保存”会创造一个高价值数据泄露面。

---

## 12. 安全事件响应

必须有控制面操作：

- 全局/租户/工具级 kill switch。
- 立即停止新调度。
- 吊销 run grants 和下游凭据。
- 冻结相关状态、artifact、trace，建立证据保全。
- 标记所有受污染 memory/Skill/artifact 的 lineage。
- 查找受影响的派生任务。
- 对已发生副作用执行补偿或通知。
- 修复后从可信 checkpoint 重建，不继续使用污染摘要。

事件演练至少覆盖：

- 恶意网页诱导外泄。
- MCP server 被替换。
- Skill 更新加入恶意脚本。
- Agent 身份凭据泄露。
- 共享 memory 被污染。
- 一个子 Agent 向其他 Agent 传播伪造消息。

## 13. 检验清单

- [ ] 是否按 OWASP ASI01–ASI10 做过威胁建模？
- [ ] 审计能否还原 human → run → agent → tool → resource 身份链？
- [ ] PDP 与 PEP 是否在模型之外？
- [ ] capability 是否任务级、短期、资源受限、可撤销？
- [ ] 审批是否绑定规范化参数、资源版本与过期时间？
- [ ] 是否测量并降低 approval fatigue？
- [ ] 代码/电脑工具是否在隔离环境运行，默认限制出站？
- [ ] secret 是否由 Broker/环境注入，从不进入模型上下文？
- [ ] 不可信数据的 taint/provenance 是否跨摘要和 memory 保留？
- [ ] Skill、MCP、Agent Card 是否纳入供应链治理？
- [ ] trace 默认是否不记录敏感正文？
- [ ] 是否演练 kill、revoke、freeze、lineage invalidation 和补偿？
