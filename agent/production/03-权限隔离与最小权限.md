# 03 · 权限隔离与最小权限

> 目标：掌握 Agent 安全**最根本、性价比最高**的一层——限制 Agent "能做什么"，让它**即使被骗也造不成严重后果**。涵盖最小权限、权限隔离、沙箱、能力域、思考与行动分离。

---

## 1. 核心思想：从"防被骗"转向"限后果"⭐⭐

[文档 02](02-Prompt注入与防御.md) 的结论是"注入没有银弹"。那怎么办？换思路：

> **既然无法保证模型不被骗，那就保证它即使被骗，也做不了坏事。**
>
> 这就是最小权限的精髓——不是去赌"模型不犯错"，而是设计成"犯了错也没有严重后果"。

这是为什么本层是**防御纵深里最该优先做、回报最高**的一层：它不依赖"检测出每一次攻击"（做不到），而是**从结构上限制破坏的天花板**。

---

## 2. 最小权限原则（Principle of Least Privilege）⭐

> **给 Agent（及其每个工具、每个 MCP server、每个子 Agent）只配完成其职责所需的最小权限——多一分都不给。**

经典例子（贯穿全课程）：
> 一个报销处理 Agent，**就不该有查询无关数据库、往外部端点发数据的能力**——**即使被注入指令要它这么做，它也做不到**，因为它根本没这个权限。

落地要点：
- **工具权限最小化**：只读任务就配只读工具，别给写/删能力（[context-engineering/01](../context-engineering/01-MCP模型上下文协议.md) 的 MCP 只读方法过滤）。
- **数据范围最小化**：只能访问该任务、该用户有权的数据子集（[rag/08](../rag/08-生产工程化与最佳实践.md) 的权限过滤，防越权）。
- **身份与凭证最小化**：Agent 用专属的、低权限的身份运行，不要复用高权限账号；凭证短期、可轮换、可撤销。
- **出站最小化**：限制能往哪些域名/地址发请求（防数据外发，[文档 02](02-Prompt注入与防御.md)）。

---

## 3. 权限隔离（Privilege Separation）

不只是"给得少"，还要"分得开"——把不同权限分配给不同的、互相隔离的组件：

- **按职责拆分 Agent/工具的权限域**：读数据的组件没有写权限；写数据的组件不直接消费外部不可信内容。
- **多 Agent 的权限隔离**（[orchestration/06](../orchestration/06-生产实践与反模式.md)）：每个 Agent 只有自己那摊的权限，一个 Agent 被攻破不殃及全局。
- **能力域（Capability Scoping）**：明确划定每个组件"能调哪些工具、能访问哪些资源、能执行哪些动作"的边界。

### 思考与行动分离（重要原则）⭐
延续 [文档 02](02-Prompt注入与防御.md) §6：

> **让"读取/推理不可信内容"的部分，与"执行有副作用动作"的部分分离。** 能读外部内容（网页、邮件、检索结果）的组件**没有**直接行动的权限；能行动的组件**不直接**消费不可信内容（动作请求需经校验/确认）。

这样，间接注入即使污染了"思考"，也碰不到"行动"——把注入的影响困在无害的区域。

---

## 4. 沙箱化（Sandboxing）⭐

对**会执行代码、读写文件、访问网络**的高危工具，必须在受限环境里跑：

- **代码执行**：在隔离的沙箱/容器里跑（受限文件系统、受限网络、资源配额、超时），别在主机环境直接执行模型生成的代码。
- **文件访问**：限定在指定目录，禁止越界（防读取敏感文件、防写系统位置）。
- **网络访问**：默认禁止，按需开白名单（防数据外发、防 SSRF）。
- **资源配额**：CPU/内存/时间上限，防失控消耗。

> 编码类 Agent 尤其危险（能生成并执行代码）——LlamaFirewall 专门有 **CodeShield** 做静态分析拦截不安全代码（[文档 04](04-护栏与人类介入.md)）。但静态检查也只是一层，沙箱是兜底。

---

## 5. 资源与速率限制（防"钱包拒绝服务"）

[文档 01](01-Agent安全威胁全景.md) 提到 DoW（Denial of Wallet）——诱导 Agent 无限循环/海量调用烧钱。权限层也要管资源：
- **步数/预算上限**（[agent-core/01](../agent-core/01-Agent循环与ReAct.md)）：单次任务的循环、token、成本上限。
- **限流（Rate Limiting）**：单用户/单会话的调用频率上限。
- **配额**：工具调用次数、外部 API 调用次数配额。

---

## 6. 把"最小权限"做进设计的检查问题

设计每个 Agent/工具时问：
1. **这个工具/Agent 真的需要写/删/外发权限吗？** 不需要就别给。
2. **被劫持后，用现有权限最多能造成什么破坏？** 破坏太大 → 收权限或加 HITL。
3. **读外部内容的组件和能行动的组件分开了吗？**
4. **执行代码/文件/网络的工具沙箱化了吗？**
5. **数据访问按用户/租户隔离了吗？**
6. **凭证是专属、低权、可撤销的吗？**
7. **有资源/速率上限防烧钱吗？**

> 把这些做成默认设计规范。**最小权限不是上线前补的，是设计时就定的。**

---

## 7. 常见坑

- **图方便给 Agent 大权限/复用高权限账号** → 被劫持后破坏面巨大。头号坑。
- **只"给得少"不"分得开"** → 一个组件被攻破殃及全局。要权限隔离。
- **读外部内容的组件直接拥有行动权限** → 间接注入直通行动。要思考-行动分离。
- **执行模型生成的代码不沙箱** → 任意代码执行，灾难。
- **数据不按用户/租户隔离** → 越权/串户泄露。
- **凭证长期有效、不可撤销** → 泄露后无法止损。
- **没有资源/速率上限** → 被 DoW 烧爆账单。
- **把安全当上线前的补丁** → 应是设计期的默认规范。

---

## 8. 本章小结

- **核心思想：从"防被骗"转向"限后果"**——让 Agent 即使被骗也造不成严重后果。这是防御纵深里**最根本、回报最高**的一层。
- **最小权限**：给 Agent/工具/MCP/子 Agent 只配最小必要权限（工具、数据范围、身份凭证、出站都最小化）；被注入也做不了没权限的事。
- **权限隔离**：按职责拆分权限域、多 Agent 互相隔离、能力域明确；**思考与行动分离**（读不可信内容的组件无行动权）。
- **沙箱化**：代码/文件/网络类高危工具在受限环境跑（隔离、白名单、配额、超时）。
- **资源/速率限制**：步数预算上限 + 限流 + 配额，防 DoW 烧钱。
- 最小权限是**设计期的默认规范**，用 7 个检查问题落地。
