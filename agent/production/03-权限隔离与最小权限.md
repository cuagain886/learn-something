# 03 · 权限隔离与最小权限：身份链、Capability 与策略执行点

> 目标：把“给 Agent 最小权限”落实为可验证的授权系统：区分用户、Agent workload、服务与资源身份；让每个 token 绑定 audience/scope/tenant/时间；在工具执行前由 PDP/PEP 做对象级判定，并防止 confused deputy 和凭证扩散。

---

## 1. Agent 不能成为新的超级用户

错误架构：

```text
所有用户 → Agent（共享 admin token）→ CRM / Email / DB / Cloud
```

它把所有身份和资源边界压扁。任何用户、网页或子 Agent 只要影响模型，就可能借 Agent 的 admin 权限横向访问。

目标架构：

```text
user identity + consent/delegation
             ↓
agent workload identity + task context
             ↓
PDP decision → PEP/tool gateway
             ↓
JIT audience-bound credential
             ↓
specific resource/action/object
```

模型只提出动作；**授权决定和凭证签发不由模型完成**。

---

## 2. 四种身份不能混用

| 身份 | 回答 | 示例 |
|---|---|---|
| Subject / Resource owner | 数据和授权属于谁 | 用户 Alice、租户 T17 |
| Delegator | 谁授权 Agent 代表其行动 | Alice 或组织管理员 |
| Workload / Actor | 实际发起调用的软件实例 | `spiffe://corp/agent/refund-worker` |
| Resource / Audience | token 要交给谁使用 | `https://erp.example.com/mcp` |

审计记录至少要回答：

```text
actor=refund-worker-7
acting_for=user:alice
tenant=T17
purpose=task:refund-829
action=refund.create
resource=order:O123
audience=payments-api
policy=refund-policy-v8
decision=allow
```

只记录“Agent 调用了退款工具”无法判断它是否有权代表该用户操作该订单。

---

## 3. 授权决策：不只是 RBAC

RBAC 适合表达“客服角色可看订单”，但 Agent 常需更细粒度条件：

\[
Allow=f(subject, actor, tenant, action, resource,
purpose, data, risk, time, approval, environment)
\]

可以组合：

- **RBAC**：岗位/服务角色；
- **ABAC**：租户、数据分类、金额、地区、时间、设备；
- **ReBAC**：用户是否拥有订单、Agent 是否受委托；
- **Capability**：一张不可伪造、范围很窄的行动授权；
- **Policy as Code**：版本化规则，由 PDP 统一求值。

示例策略：

```rego
allow if {
  input.actor.workload == "refund-agent"
  input.subject.tenant == input.resource.tenant
  input.action == "refund.create"
  input.resource.owner == input.subject.user_id
  input.amount <= input.policy.auto_refund_limit
  input.credential.audience == "payments-api"
  not input.data_taints[_] == "untrusted_bank_account"
}
```

高影响动作还需要有效 approval；策略结果应绑定输入 hash 和 policy version。

---

## 4. PDP/PEP：把授权放在模型之外

- **PDP（Policy Decision Point）**：根据身份、资源、动作和环境计算 allow/deny/require-approval；
- **PEP（Policy Enforcement Point）**：位于工具网关/API 前，真正执行拒绝；
- **PIP**：提供订单 owner、数据分类、风险、批准等属性；
- **PAP**：策略管理、评审、版本和发布。

```text
LLM → ActionProposal
          ↓
Tool PEP ── request facts ──► PDP/PIP
   │                            │
   ├─ deny                      ├─ allow + constraints
   └─ require_approval          └─ issue/obtain narrow credential
```

关键点：

- 每次实际执行都重新授权，不能因为模型在规划阶段“检查过”就跳过；
- 授权应针对资源对象和参数，不只针对工具名；
- PEP 不能信任模型声称的 user/tenant/approval，应从认证上下文和服务端状态读取；
- deny/default 与 policy evaluation failure 的处理必须明确，高风险默认 fail closed。

---

## 5. Token：scope 说明“能做什么”，audience 说明“对谁做”

一个 access token 只有 scope 不够。RFC 8707 Resource Indicators 让客户端声明目标 resource，授权服务器可签发 audience-restricted token，防止 token 被拿到另一个资源服务器使用。

推荐 token 约束：

```yaml
sub: user:alice             # 或 delegation subject
act: workload:refund-agent  # actor（若 token 格式/系统支持）
aud: https://payments.example.com
scope: refund:create
tenant: T17
resource_ids: [order:O123]
purpose: task:refund-829
exp: 2026-07-19T04:05:00Z
cnf: sender-constrained-key # 可用时绑定客户端/密钥
```

并非所有授权服务器都支持这些自定义约束；可把无法放进 token 的细粒度条件留给 API 端 PDP。

### 5.1 MCP 当前要求

MCP `2025-11-25` 授权规范要求客户端在授权和 token 请求中包含 RFC 8707 `resource`，服务器验证 token 是签给自己的。MCP 还明确禁止 **token passthrough**：

```text
client token (aud=mcp-server)
        ✗ 不可原样转发给 downstream-api

mcp-server 作为 downstream 的 OAuth client
        ✓ 获取另一个 aud=downstream-api 的独立 token
```

否则会造成 audience 绕过、审计丢失和 confused deputy。

---

## 6. Confused Deputy：Agent 安全的高频根因

“副手”拥有权限，攻击者诱导它替自己访问本无权访问的资源：

```text
attacker/user controls resource URL or object_id
   ↓
high-privilege Agent accepts it
   ↓
downstream sees Agent credential, not original user's limits
   ↓
cross-tenant data returned
```

防护：

1. 端到端传播并验证原始 subject/tenant/delegation；
2. 服务器端从已认证主体派生资源范围，不接受模型自报 owner；
3. token audience 和下游 token 分离；
4. 每个 object 做授权，不能只验证“可以调用 search”；
5. 禁止任意 URL/资源 ID，使用已解析且已授权的 server-side handle；
6. 响应按调用者权限过滤，防 IDOR/BOLA；
7. 审计 actor 与 subject，异常跨租户访问告警。

---

## 7. Capability：把授权缩小到一次具体动作

Capability 可以理解为“持有者可对某资源做某动作”的不可伪造票据：

```json
{
  "cap_id": "cap-938",
  "holder": "workload:refund-executor",
  "action": "refund.create",
  "resource": "order:O123",
  "constraints": {"amount_lte": 86, "destination": "original_method"},
  "proposal_hash": "sha256:...",
  "expires_at": "...",
  "max_uses": 1
}
```

优点：爆炸半径清晰、适合 JIT 和审批绑定。风险：bearer capability 一旦泄露即可被使用，所以要：

- 传输和存储保护，日志只记 hash；
- 短 TTL、单次使用、nonce/防重放；
- 绑定 holder/公钥或受控 channel；
- 明确 delegation 是否允许、最多几跳；
- 支持撤销或将不可撤销窗口做得很短。

Capability 不是“不需要身份”，而是把身份、资源和动作范围收紧到可验证委托。

---

## 8. JIT 凭证与 Workload Identity

不要把长期 API key 放进 prompt、环境变量全集或可读文件。更安全的流程：

```text
workload attestation
→ 获得短期 workload identity（如 X.509/JWT SVID）
→ PDP 允许某 task/action
→ broker 签发短期、单 audience、窄 scope token
→ executor 调用
→ token 到期/任务结束撤销
```

SPIFFE/SPIRE 是 workload identity 的一种实现路径，其 Workload API 可提供短期 SVID 和密钥；它解决“这个工作负载是谁”，不自动解决“它是否能代表 Alice 退款”，后者仍需 delegation 与业务策略。

凭证服务还应：

- 不把 secret 返回模型上下文；
- 只由执行器获得，Reader/Planner 不可读；
- 禁止通用 metadata service 访问，防 SSRF 窃取；
- 轮换、撤销、使用次数/金额限制；
- 每次使用产生安全审计和 resource receipt。

---

## 9. 工具权限不是“展示/隐藏工具”

不给模型展示某工具只能减少误调用，不能作为授权：攻击者可能直接调用 API、伪造 tool name，或利用另一个通用工具达到同一效果。

每个工具契约应声明：

```yaml
name: refund_create
effect: external_write
risk: high
required_scope: refund:create
resource_resolver: order_id -> order.owner, order.tenant
parameter_constraints:
  amount: "<= policy.allowed_amount"
idempotency: required
approval: conditional
network: payments-api-only
credential_mode: jit_audience_bound
```

Tool registry、host 展示和执行 API 三层都要控制；最终 PEP 以服务端事实授权。

## 10. 权限隔离与沙箱

### 10.1 拆分权限域

```text
Reader：外部内容读取；无私密数据、无写、无任意出站
Planner：生成 typed proposal；无凭证
Executor：不直接消费原始外部文本；只接收已验证 proposal
Auditor：只读 trace/receipt；不能执行业务动作
Approver：批准范围受限；不能修改执行参数后静默批准
```

一个组件被劫持时，攻击路径还需要跨越独立 PEP。

### 10.2 代码执行沙箱

至少限制：

- 独立低权用户/容器/VM，按风险选择隔离强度；
- 只读根文件系统、临时工作目录、路径 canonicalization；
- 默认无网络或目标 allowlist，禁止云 metadata；
- CPU、内存、进程数、磁盘、时间和输出配额；
- seccomp/AppArmor/SELinux 等系统调用/强制访问控制（依平台）；
- 无宿主 socket、无共享敏感 volume、无生产 credential；
- 任务结束销毁环境，artifact 经扫描后导出。

容器不是天然安全边界；面对敌意代码可使用更强 VM/microVM/沙箱，并持续打补丁。

---

## 11. 授权的 TOCTOU 与缓存风险

授权时资源属于 Alice，执行时可能已转移；批准时金额 86，执行时模型改成 860。防护：

- 读取资源 `version/etag`；
- approval/capability 绑定 `proposal_hash + resource_version`；
- 执行事务中 compare-and-swap；
- TTL 和单次使用；
- 权限撤销后缓存快速失效；
- 长任务恢复时重新授权，不沿用数小时前的 decision。

授权缓存 key 必须包含 subject、actor、tenant、action、resource、policy version 和关键属性，不能只按工具名缓存。

## 12. 评测与审计

### 12.1 必测攻击

- 跨租户 object ID；
- scope 正确但 audience 错；
- client token 被 MCP server 向下游 passthrough；
- 旧 approval/proposal 被重放；
- JIT token 过期/撤销后仍使用；
- Reader 试图读取 Executor credential；
- Agent 利用通用 HTTP/shell 绕过专用工具；
- concurrent update 触发 TOCTOU；
- sandbox SSRF 访问 metadata/本机服务。

### 12.2 审计不变量

```text
每个高影响 receipt 都有唯一 actor + subject + task + policy decision
token aud 必须等于实际 resource server
执行 proposal_hash == 批准 proposal_hash
跨租户拒绝率 = 100%（测试集内）
secret 不进入 model context / trace content
```

安全门槛应包括正常流量误拒率和审批容量，避免靠全部 deny 获得虚假安全。
