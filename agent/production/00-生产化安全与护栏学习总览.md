# 生产化、安全与护栏 · 学习总览

> 这是 [INDEX.md](../INDEX.md) 阶段 7 的专题导航。目标不是“给 Agent 加内容过滤”，而是构造一个可证明的控制面：不可信内容即使影响模型，也要继续跨越身份、授权、策略、审批、沙箱、出站和副作用一致性边界，才能造成高影响结果。

## 0. 安全模型：模型输出是 Proposal，不是 Authority

```text
用户/网页/邮件/工具/A2A（不可信输入）
  ↓ provenance + taint
Model / Planner
  ↓ typed ActionProposal
PDP / Guard / Approval
  ↓ allow + constraints + proposal hash
PEP / Tool Gateway
  ↓ JIT audience-bound capability
Sandbox / Business API
  ↓ receipt + world state
Verifier / Trace / Reconciliation
```

核心不变量：

1. 模型不能为自己授予权限；
2. 外部内容不能自动升级为系统 policy；
3. 工具名可见性不能代替执行端授权；
4. 人工批准必须绑定具体参数和资源版本；
5. 任何高影响副作用都要有幂等键、receipt 和对账路径；
6. 代码/配置回滚不能代替副作用补偿与凭证撤销。

## 1. 为什么 Agent 比聊天机器人多一个数量级的控制问题

Agent 将自然语言决策接到真实权限和世界状态：

\[
\text{content}\rightarrow\text{decision}\rightarrow
\text{credentialed action}\rightarrow\text{persistent effect}
\]

攻击者不一定攻破主机；只要控制 Agent 读取的邮件、网页、RAG chunk、工具描述或远程 Agent 消息，就可能借合法能力完成攻击。多步、memory、重试和多 Agent 又使攻击持久化、传播和级联。

因此安全不能只依赖 system prompt、注入检测器或另一个 LLM 审核。最关键的是模型外强制的**最小权限、对象级授权、能力隔离、出站控制、审批绑定、沙箱、预算和恢复**。

## 4. 六个贯穿原则

### 4.1 不可信内容的污点不能被自然语言“洗白”

摘要、模型改写、Agent handoff 不会自动把外部内容变可信。Provenance、owner、tenant、taint、TTL 和 lineage 必须跨转换传播。

### 4.2 身份链比“Agent 身份”更细

每次动作要区分：

```text
subject/resource owner
delegator
workload actor
target audience/resource server
task/purpose
```

MCP `2025-11-25` 要求 RFC 8707 resource/audience 绑定并禁止 token passthrough，正是为了避免 token 重定向和 confused deputy。

### 4.3 最小权限必须在执行点强制

隐藏工具、prompt 叮嘱、模型自检都不能替代 API/tool gateway 的对象级 PEP。凭证应 JIT、短期、单 audience、窄 scope，且不进入模型上下文。

### 4.4 HITL 批准的是 immutable proposal

Approval 绑定 `proposal_hash + resource_version + policy_version + TTL`；执行前再次校验并 CAS。参数变化、资源更新、批准过期都必须重新审批。

### 4.5 稳定性本身是安全边界

无限队列、重试风暴、取消不传播和 RESULT_UNKNOWN 会造成 ASI08 级联故障或重复副作用。全局预算、deadline、backpressure、bulkhead 和 recovery reserve 是安全控制。

### 4.6 每个控制都要能被证伪

```text
Threat → Control → Test → Telemetry → Owner → Drill → Recovery
```

“已加护栏”不构成证据。需要混淆矩阵、策略负面测试、trace invariant、fault injection、shadow/canary 和事故演练。

## 6. 面试追问树与回答主线

| 追问层级 | 典型问题 | 回答必须落到 |
|----------|----------|--------------|
| 定义 | 为什么模型输出只能是 proposal，不能是 authority？ | 模型是概率决策器；授权、参数校验、预算、审批和 effect 提交必须由确定性控制面强制 |
| 机制 | 注入内容如何一路变成真实事故？ | untrusted source → context/memory → proposal/tool arg → PEP/egress sink；用 provenance/taint、最小权限和出站控制切断路径 |
| 反例 | 注入检测准确率很高，为什么仍不构成安全证明？ | 分布外漏报必然存在；还可能发生身份滥用、供应链、RCE、记忆污染、级联失败和审批疲劳 |
| 落地 | 高风险退款怎样实现可批准、可恢复、不可换参？ | canonical proposal hash + resource/policy version + TTL，执行时 CAS；幂等键、receipt、`RESULT_UNKNOWN` 对账与补偿 |
| 评测 | 怎样证明控制有效且故障后能恢复？ | 正/负授权矩阵、attack challenge、fault injection、误拦/漏判、队列/重试风暴、credential revoke 和 reconciliation drill |

当被问“如何保证 Agent 安全上线”，建议按此回答：

1. 先列资产、主体、信任边界、高影响动作和最坏攻击链；
2. 用 OWASP ASI01–ASI10 检查遗漏，但保留传统 AppSec/IAM/SRE；
3. 所有外部内容带 provenance/taint，限制进入 policy、tool arg、egress 和 memory；
4. 模型只产 typed proposal，PDP/PEP 做对象级授权；
5. subject + workload + audience + task 构成身份链，凭证 JIT/短期/窄权；
6. 高风险 proposal 绑定 hash/version/TTL 审批，执行时 CAS；
7. 外部副作用有 idempotency/receipt/RESULT_UNKNOWN 对账与补偿；
8. 运行时有 admission/backpressure/deadline/global budget/recovery reserve；
9. 红队与 fault injection 同时测漏判、误拦、级联和恢复；
10. 用证据 gate 经 shadow/canary 发布，kill switch 能撤销凭证、处理在途任务和副作用。

## 7. 核心结论

- Prompt 注入是控制流攻击入口之一，不等于 Agent 安全全貌。
- XML/角色隔离是概率性缓解，模型外的 PEP、sandbox、egress 才是安全边界。
- 最小权限必须表达 actor/subject/tenant/action/resource/audience/purpose，而非一个共享 Agent 角色。
- 人类不是万能控制；审批疲劳、信任利用和 TOCTOU 必须系统治理。
- 高利用率、无限队列和多层重试会把可靠性故障放大为安全事故。
- 正式上线需要 Evidence Pack：每个主张有测试、阈值、owner、失效语义、演练和恢复动作。
