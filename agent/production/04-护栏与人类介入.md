# 04 · 护栏与人类介入：策略执行、审批绑定与可恢复暂停

> 目标：把 Guardrail/HITL 设计成一个有明确输入、输出、错误语义和审计证据的控制面。人类批准的不是“让 Agent 继续”，而是一份绑定参数、资源版本、有效期与影响范围的具体提案。

---

## 1. Guardrail 不是一个内容分类器

护栏应覆盖不同阶段与不同对象：

```text
untrusted input
  → ingestion guard（来源/格式/taint）
  → context guard（租户/数据分类/预算）
  → plan guard（目标/约束/必要证据）
  → action guard + PEP（身份/资源/参数/权限/幂等）
  → execution guard（sandbox/网络/配额）
  → output/egress guard（DLP/收件人/来源/内容）
  → persistence guard（memory/index/checkpoint 写入）
```

输入/输出审核只是其中两层。Agent 真正危险的地方常在 action、egress 和 persistence。

---

## 2. 护栏决策契约

不要让护栏只返回 `true/false`：

```json
{
  "decision": "require_approval",
  "policy_version": "payment-policy-v12",
  "reasons": ["new_destination", "amount_over_auto_limit"],
  "constraints": {
    "amount_lte": 5000,
    "destination_hash": "sha256:..."
  },
  "required_approver_roles": ["finance_reviewer"],
  "evidence_refs": ["artifact://invoice/...", "receipt://vendor-verify/..."],
  "expires_at": "2026-07-19T06:00:00Z"
}
```

推荐决策集合：

```text
ALLOW
ALLOW_WITH_CONSTRAINTS
DENY
REQUIRE_APPROVAL
ABSTAIN / POLICY_ERROR
```

对 `ABSTAIN/POLICY_ERROR` 要预定义 fail-open/fail-closed。高影响写动作通常 fail closed；低风险只读查询可降级，但必须记录。

---

## 3. 动作风险分级：不要只看模型置信度

可以将风险表示为：

\[
R=f(impact, reversibility, scope, privilege, data,
destination, novelty, provenance, confidence)
\]

| 等级 | 示例 | 默认控制 |
|---|---|---|
| R0 | 公开信息只读查询 | 自动允许 + 基础限流 |
| R1 | 对当前用户草拟内容、不发送 | 自动允许 + 输出检查 |
| R2 | 可逆内部写、影响单对象 | 参数/对象授权 + 完整审计，异常转人工 |
| R3 | 外发、删除、支付、部署、权限变更 | 人工审批 + JIT capability + 幂等/补偿 |
| R4 | 大范围、不可逆、监管/生命安全 | 双人/职责分离、带外验证，或禁止自动化 |

模型自报置信度只是一个经校准的弱信号。攻击者可让模型非常自信；高影响、不可逆和广范围不能因“置信度 99%”自动降级。

---

## 4. Approval Request：批准具体对象，而非模糊意图

```yaml
approval_id: apr-829
task_id: task-77
proposal:
  tool: payment.create
  args:
    invoice_id: I-19
    amount: 4800
    currency: CNY
    destination_id: vendor-31
proposal_hash: sha256:...
resource_versions:
  invoice: 18
  vendor: 7
requested_by:
  actor: spiffe://corp/agent/payment-planner
  subject: user:alice
risk:
  level: R3
  reasons: [new_destination]
evidence_refs:
  - artifact://invoice/I-19/sha256:...
  - receipt://vendor-out-of-band-check/...
scope:
  max_uses: 1
  expires_at: 2026-07-19T06:00:00Z
decision_options: [approve, reject, edit_and_resubmit]
```

审批 UI 应直接显示业务含义：谁、向谁、多少钱、什么数据将外发、是否新目的地、能否撤销；不要只显示 JSON 或 Agent 的自然语言摘要。

---

## 5. 防 TOCTOU：批准时和执行时必须是同一件事

攻击/竞态：人批准 86 元退款，等待期间订单或参数变更，执行器却退 860 元。

正确流程：

```text
proposal canonicalize
→ hash(proposal + resource_versions + policy_version)
→ human approval binds hash + constraints + TTL
→ executor reloads current resource
→ compare-and-swap / transaction checks versions
→ hash and approval revalidated
→ issue one-use JIT capability
→ execute with idempotency key
→ write receipt
```

若任一参数、资源版本、策略或影响范围变化，旧批准失效，必须重新提交。审批不能简单绑定 `task_id` 或“支付这个发票”的自然语言。

---

## 6. 人类也会失败：审批疲劳与信任利用

HITL 不是万能安全边界：

- 高频确认导致 habituation，用户机械点击批准；
- Agent 用自信、紧迫或模糊摘要影响判断（ASI09）；
- 审批者可能没有资源权限/专业知识；
- 批量审批隐藏单个异常；
- UI 把关键目的地/金额放在折叠区；
- 攻击者同时控制“证据”和 Agent 摘要。

缓解：

1. 只在风险转折点审批，避免每一步弹窗；
2. UI 显示原始/独立证据、差异和 taint，不只显示 Agent 理由；
3. 突出新增收件人、外域、金额变化、权限提升；
4. R4 使用 two-person rule/职责分离；
5. 审批速率上限、队列优先级、轮班与随机质检；
6. 高风险目的地做带外验证；
7. 统计误批、拒绝、撤销、平均等待和审批者分歧；
8. 训练审批者识别 prompt injection 与证据来源。

“有人点过批准”不等于责任和控制已经完成。

---

## 7. 批准、修改、拒绝、撤销的状态机

```text
DRAFT
  → PENDING
  → APPROVED ──► EXECUTING ──► SUCCEEDED
       │              ├──────► FAILED_KNOWN
       │              └──────► RESULT_UNKNOWN → RECONCILING
       ├─ EXPIRED
       └─ REVOKED
  → REJECTED
  → CHANGES_REQUESTED → new proposal/version → PENDING
```

关键语义：

- `edit_and_resubmit` 必须生成新 proposal/hash，不能在批准后原地改参数；
- approval 允许在执行前撤销；
- `RESULT_UNKNOWN` 不能盲目重试，先查询 receipt/world state；
- 执行失败后，批准是否还能重用要预定义，默认单次 capability 不复用；
- 拒绝理由可以反馈给规划器，但不能让规划器自动规避审批策略；
- 过期后恢复任务必须重新计算风险和授权。

---

## 8. 长期暂停与恢复

人类可能数小时或数天后批准。不能只把进程挂起在内存：

```text
1. 持久化 checkpoint：业务状态、proposal、versions、pending effect
2. 事务性创建 approval work item / outbox event
3. worker 释放资源
4. 人类决策写入不可变 decision record
5. 恢复时重新加载最新资源/策略/权限
6. 验证 hash、TTL、资源版本与 credential
7. 从安全节点重新执行；副作用前步骤应幂等
```

若框架的 interrupt/resume 会从节点开头重跑，interrupt 前的任何副作用必须幂等或移动到恢复后的专用节点。Checkpoint 只保存状态，不自动提供 exactly-once。

---

## 9. Guardrail 的组合与冲突

多个 guard 可能并行运行：

```text
policy/PDP: require_approval
DLP: deny
content safety: allow
budget: allow_with_constraints
```

聚合策略必须确定：

- `DENY` 是否总是优先；
- 哪些 `REQUIRE_APPROVAL` 可以被人覆盖，哪些监管规则不可覆盖；
- 超时/不可用按风险怎样 fail；
- 多个 constraints 怎样求交集；
- 决策证据和版本怎样保存；
- 护栏之间是否共享不可信内容并形成共同失败。

不要让一个通用 LLM “综合所有护栏再自由决定”。确定性聚合器应执行预定义优先级。

---

## 10. 护栏模型的校准与对抗

任何注入/PII/有害内容检测模型都可能有 FN、FP、分布漂移和对抗绕过。部署前需要：

- 独立人工 anchor、混淆矩阵、关键失败 recall/FPR；
- 按语言、长度、编码、模态、攻击类型分层；
- 候选内容中的 prompt injection 不能修改 guard rubric；
- shadow 观察误拦与漏拦，再按风险上线；
- guard 模型/阈值版本化，升级时双跑；
- 失败时由权限和 PEP 限制后果。

LlamaFirewall 等开源系统、云厂商 Guardrails 或自建规则/分类器都可以是组件；产品能力和 benchmark 数字会变化，选型应在自己的威胁集、正常流量和延迟预算上 spike，不把论文单项 ASR 外推为生产保证。

---

## 11. HITL 指标：不能只看“审批率”

| 类别 | 指标 |
|---|---|
| 安全 | 关键动作审批召回、旧提案执行率、越权/误批、撤销成功 |
| 质量 | 修改率、拒绝率、审批后业务成功、证据缺失率 |
| 人因 | p50/p95 等待、批量大小、审批速率、分歧、疲劳信号 |
| 自动化 | coverage–risk、低风险误升级、人工队列饱和度 |
| 恢复 | 过期、恢复失败、RESULT_UNKNOWN 对账时间、补偿成功 |

审批率低可能是系统变安全，也可能是危险动作没被识别；审批率高可能是风险高，也可能是策略过严。必须与 world-state 和错误类型联看。

---

## 12. 故障注入测试

- 批准后参数被篡改；
- 资源版本在等待期间变化；
- approval 到期/撤销与执行并发；
- 同一批准被两个 worker 重放；
- 执行提交后网络超时；
- 审批服务/策略服务不可用；
- reviewer 无权批准该租户/金额；
- evidence artifact 被替换或链接失效；
- checkpoint 在 schema 升级后恢复；
- guard detector 在多语言/编码变体下漏判；
- 人工队列堆积触发 deadline。

验证结果不仅是“是否拦截”，还包括 receipt、审计、补偿、用户通知和恢复状态。

## 13. 检验清单

- [ ] 能为 guardrail 定义多值决策和 fail-open/fail-closed 语义。
- [ ] 能把动作按 impact/reversibility/scope 等维度分级。
- [ ] 能设计绑定 proposal hash、resource version、TTL 的 Approval Request。
- [ ] 能用 CAS、one-use capability 和 receipt 防 TOCTOU/重放。
- [ ] 能解释审批疲劳与 ASI09 Human-Agent Trust Exploitation。
- [ ] 能设计长期 pause/resume、RESULT_UNKNOWN 与撤销状态机。
- [ ] 能校准护栏模型而不把 benchmark 数字当生产保证。
