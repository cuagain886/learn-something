# 05 · 生产部署与成本延迟治理：队列、Deadline、预算与尾延迟

> 目标：从“加缓存、上并行”进入生产运行时设计：理解利用率为何放大尾延迟，如何让 token/tool/人工队列背压，怎样传播 deadline 与预算、预留恢复资源，并在故障窗口中保持副作用一致性。

---

## 1. 生产 Agent 是多个受限资源组成的排队网络

```text
API ingress
  → admission queue
  → context/retrieval pool
  → model provider quota / token queue
  → tool-specific pools（DB / browser / code sandbox / MCP）
  → approval queue
  → finalization / egress guard
```

每一站都有：到达率 `λ`、服务时间 `S`、并发 `c`、重试、超时和下游限额。只优化模型生成时间，往往会把瓶颈推到工具、队列、审批或数据库。

---

## 2. 排队直觉：利用率接近 100% 时延迟会非线性爆炸

### 2.1 Little's Law

稳定系统中：

\[
L=\lambda W
\]

- `L`：系统内平均任务数（运行 + 排队）；
- `λ`：有效吞吐；
- `W`：平均停留时间。

如果每秒完成 10 个任务，平均停留 5 秒，系统平均约有 50 个任务在途。它用于容量 sanity check，但不直接给出尾延迟或因果。

### 2.2 Kingman 近似（单服务台直觉）

对 G/G/1 队列，平均等待可近似：

\[
W_q\approx \frac{\rho}{1-\rho}\cdot
\frac{C_a^2+C_s^2}{2}\cdot E[S]
\]

`ρ` 是利用率，`C_a/C_s` 是到达/服务时间变异系数。Agent 的服务时间通常长尾（循环步数不同、工具抖动），所以即使平均容量够，p99 仍可能很差。

这不是多服务台/复杂网络的精确公式，但给出三个工程杠杆：

1. 留出利用率余量；
2. 减少 burst 和服务时间方差；
3. 将长短任务、风险/租户分池，避免 head-of-line blocking。

## 3. Admission Control：系统满时必须拒绝、排队或降级

没有背压时，上游继续 fan-out，队列、内存和 provider quota 被耗尽，超时又触发重试风暴。

```text
request
  → authenticate / quota
  → estimate class + risk + cost
  → admission decision:
       accept now
       enqueue with bounded deadline
       degrade to simpler path
       return retry-after
       route to async/human
       reject
```

Admission key 不只是用户 QPS，还包括：

- 每租户并发/每日预算；
- model request/token per minute；
- browser/code sandbox 数量；
- 工具/API 配额；
- memory/checkpoint 写吞吐；
- 人工审批队列容量；
- 全局高影响动作速率。

队列必须有上限、deadline 和取消；“无限队列”只是把拒绝变成更晚的超时。

---

## 4. Budget Envelope：先预留，再消费

任务开始时定义跨层预算：

```yaml
budget:
  deadline_ms: 30000
  model_tokens: 18000
  model_calls: 8
  tool_calls: 12
  external_writes: 1
  cost_cents: 20
  retries: 2
  handoffs: 1
  recovery_reserve:
    time_ms: 5000
    tool_calls: 2
    cost_cents: 3
```

重要区别：

- **硬上限**：越过即拒绝/停止；
- **预留**：分支开始前占用最坏或估计预算，结束后退款；
- **恢复储备**：不能把全部预算花在正常路径，导致最后没资源做对账/补偿；
- **全局 vs 局部**：子 Agent 的预算来自父任务，不可各自重新拿一整份。

并行 fan-out 需要原子预留：若 5 个 worker 都认为“剩余 1000 token”，总消费会超 5 倍。可用中央 ledger/CAS 或分配不可超发的子预算。

## 5. Deadline Propagation：超时不是每层都重新计时

根请求有绝对 deadline `D`，每步得到剩余时间：

\[
remaining=D-now-reserve_{finalize}-reserve_{recovery}
\]

下游 timeout 应小于 remaining，并留出结果验证、补偿和响应时间。

错误做法：每层都设 30 秒，串行 6 层最坏 180 秒；父请求早已断开，下游仍继续烧钱和写状态。

```text
root deadline
  ├─ model timeout <= remaining - tool/finalize reserve
  ├─ tool timeout <= remaining - reconcile reserve
  ├─ approval: 转 async，不能占住同步请求
  └─ child task inherits earlier deadline
```

取消也要传播，但取消是 best effort：已提交外部副作用可能不能撤回，late result 必须进入 reconciliation，而不是简单丢弃。

## 6. 重试：预算、分类、抖动与重试风暴

仅对明确可重试且幂等的错误重试：

| 错误 | 策略 |
|---|---|
| 429/暂时不可用 | 尊重 `Retry-After`、指数退避 + jitter、全局 retry budget |
| validation/auth/policy deny | 不重试；修参数/重新授权/终止 |
| timeout-before-send | 可按幂等策略重试 |
| timeout-after-send / result unknown | 先按 idempotency key 查询 receipt，不能盲重试 |
| permanent business error | 降级/人工，不重试 |

设置**重试预算**，例如单位时间内 retry traffic 不超过正常流量的一定比例；具体值用故障实验校准。多层 SDK、Agent、网关、工具若都各重试 3 次，组合可能产生指数放大，应指定唯一重试 owner。

## 7. 并行化：降低关键路径，但可能增加成本和尾风险

串行延迟近似求和：

\[
T_{serial}=\sum_iT_i
\]

并行 fan-out 的 join 延迟更接近：

\[
T_{parallel}\approx \max_iT_i+T_{join}
\]

但只要一个慢分支决定 ALL join，p99 可能被最慢者放大。还会：

- 同时占用更多 quota；
- 重复 token/工具成本；
- 引入 cancel/late result 和状态合并；
- 放大失败面和外部服务负载。

应明确 ALL/ANY/quorum/deadline-partial 语义，支持 early cancel，使用并发上限与 bulkhead；比较时保持相同质量目标和总预算。

## 8. 成本模型：从 token 单价到 cost per successful task

任务成本：

\[
C=C_{model,in}+C_{model,out}+C_{tool}+C_{retrieval}
+C_{storage}+C_{guard}+C_{human}+C_{retry}+C_{recovery}
\]

不能只看主模型 token。人工审批、浏览器、搜索、沙箱、trace 存储、失败重试和事故处理都是真实成本。

核心指标：

\[
cost/success=\frac{\sum C_i}{\sum Y_i}
\]

配合：

- 首次成功/最终成功成本；
- 按任务族和租户成本；
- p95/p99 单任务成本；
- 预算触顶率、无进展成本；
- 质量—成本—延迟—风险 Pareto frontier。

### 8.1 降本手段及正确性条件

| 手段 | 节省 | 正确性风险 |
|---|---|---|
| 小模型路由 | 推理成本/延迟 | 错路由、高风险任务漏升级 |
| prompt/context caching | 重复前缀 | 安全域、模型/prompt 版本、TTL 错误 |
| semantic cache | 相似任务复用 | 用户/权限/时间/世界状态混用 |
| 上下文压缩 | 输入 token | 丢证据、约束和工具事务完整性 |
| 减少反思/候选 | 调用数 | 质量/可靠性下降 |
| batch | 吞吐 | 延迟、隔离和错误粒度 |

任何降本都要做配对 eval，尤其检查 cost/success 和关键风险，而不只是 cost/request。

## 9. 尾延迟治理

分解端到端 p99：

```text
queue wait
+ context/retrieval
+ model TTFT + generation
+ tool calls / retries
+ guardrails
+ checkpoint/event persistence
+ approval（通常异步）
+ finalization/egress
```

常用杠杆：

- 任务分类与 separate pools，避免长任务阻塞短任务；
- streaming 改善 TTFT，但不等于任务完成更快；
- hedged request 只用于幂等只读、超过阈值的高方差依赖，并计入额外成本；
- speculative/fallback 路由必须防重复副作用；
- deadline-aware 跳过非关键分支，而不是超时后突然截断关键事务；
- tool/provider circuit breaker 与 bulkhead；
- 长任务转 async，返回 task handle 而非维持 HTTP 连接。

不要只看平均延迟；按任务复杂度、模型路由、工具、租户和失败类型分层分析 p95/p99。

## 10. 状态、队列与 exactly-once 幻觉

队列可能 at-least-once delivery，worker 可能在“副作用提交后、ack 前”崩溃。生产需要：

- `task_id / logical_action_id / attempt_id`；
- 幂等键和业务唯一约束；
- outbox/inbox；
- lease + fencing token，防旧 worker 复活写入；
- effect receipt 与 `RESULT_UNKNOWN` 对账；
- Saga compensation；
- checkpoint schema/version migration。

Checkpoint 或消息“exactly once”配置不能自动让外部支付/邮件 exactly once。详见 [systems-engineering/03](../systems-engineering/03-持久化执行与故障恢复.md)。

## 11. Capacity Planning 与压力实验

### 11.1 工作负载模型

至少按以下维度生成负载：

- 到达：平稳、burst、日周期、单租户热点；
- 任务：短/长、步数、token、工具组合、审批比例；
- 故障：429、慢工具、timeout-after-commit、模型降级；
- 多租户：大客户 vs 小客户的公平性；
- 发布：新版本成本/步数分布变化。

### 11.2 测什么

```text
throughput vs concurrency
queue wait / service time / end-to-end p50,p95,p99
utilization + saturation point
model/tool quota and retry amplification
cost/success and budget exhaustion
trace/checkpoint drop/lag
cancel propagation and late result
recovery/compensation reserve sufficiency
```

用逐步加压寻找 knee point，在明显饱和前设置 admission/concurrency limit；再做 burst、soak 和 dependency chaos。自动扩容受冷启动和 provider quota 限制，不能假设实例数翻倍吞吐就翻倍。

## 12. 多租户公平与资源隔离

- per-tenant token bucket + global cap；
- weighted fair queue / priority class；
- 风险/交互请求可优先，但防永久饿死 batch；
- 独立 bulkhead 限制单工具/租户故障；
- 成本 attribution 与 hard/soft quota；
- trace、cache、memory、artifact 的安全域隔离；
- 高优先级不能绕过权限/安全 gate。

优先级继承和 deadline 应跨子任务传播，避免低优先级任务 fan-out 占满关键 worker。

## 13. 渐进发布与回滚

发布顺序见 [evaluation/06](../evaluation/06-线上持续评估与反模式.md)：offline → shadow → risk-scoped canary → 分层扩大。运行时还必须支持：

- config/model/prompt/tool/schema 独立版本与快速禁用；
- feature flag 按租户/任务/风险；
- kill switch 撤销新任务与 JIT credential；
- 在途任务按版本继续/取消/迁移策略；
- checkpoint 向后兼容与 dual-read；
- 已发生副作用的 reconciliation/compensation；
- 降级到只读、proposal-only、简单工作流或人工。

“回滚容器镜像”不等于回滚业务世界状态。

## 14. 面试追问

**问：为什么 CPU 只有 40%，p99 仍很高？**

瓶颈可能在 provider token quota、某工具连接池、队列分层或长尾任务；总体 CPU 平均会掩盖单资源饱和。要看各站 queue wait/service time/utilization 和任务分层。

**问：并行一定降延迟吗？**

只降低可并行部分的关键路径；ALL join 受最慢分支支配，并增加 quota、成本与失败面。要定义 join/cancel/backpressure 并实测 p99。

**问：超时后能不能重试？**

先判断副作用是否可能已提交。result unknown 时用幂等键查询 receipt/世界状态；盲重试会重复执行。
