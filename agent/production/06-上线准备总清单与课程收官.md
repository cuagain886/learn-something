# 06 · 上线证据包与端到端案例：从 Checklist 到可审计 Gate

> 目标：把“已完成最小权限/评测/回滚”从勾选框变成可审计证据。每个上线 gate 必须有 owner、适用范围、阈值、证据、失效模式、演练记录和 rollback 动作；并用退款 Agent 串起全课程的状态、工具、恢复、评测与安全。

---

## 1. Checklist 为什么经不起追问

```text
[x] 有权限控制
[x] 有评测
[x] 有监控
[x] 有回滚
```

面试官或审计者会继续问：

- 哪个身份、哪个资源、哪个动作？
- 权限在哪里强制，模型能否绕过？
- 评测总体、oracle、CI 和最差切片是什么？
- 监控丢数据时谁知道？
- 回滚能否处理在途任务和已执行退款？
- 谁批准上线，证据何时过期？

所以上线产物应是 **Go-Live Evidence Pack**，而不是一张静态清单。

## 2. Gate Record：最小审计结构

```yaml
gate_id: AUTH-OBJECT-01
claim: "退款 Agent 不能跨租户读取或操作订单"
scope:
  workflows: [refund-v8]
  tools: [order_get, refund_create]
owner: identity-platform
reviewer: payments-security
control:
  preventive: "tool PEP + object-level ReBAC"
  detective: "cross_tenant_denied trace invariant"
evidence:
  policy_tests: artifact://ci/authz-v18
  red_team: artifact://eval/cross-tenant-v5
threshold:
  attack_cases_blocked: "100% of approved suite"
  normal_false_denial_upper_95ci: "<= 0.5%"
failure_mode: fail_closed
rollback:
  immediate: "disable refund_create; proposal-only mode"
  reconciliation: "query receipts for all in-flight actions"
drill:
  last_run: 2026-06-21
  result: pass
valid_until: 2026-09-21
```

数值只是结构示例。门槛应由业务风险和基线校准，并同时限制安全漏判与正常流量误拒。

## 3. 发布证据包的八个 Gate

### G1 · Task / Architecture Gate

**主张**：任务边界清楚，Agent 复杂度确有必要。

证据：

- 任务 taxonomy、成功/失败/禁止状态；
- 固定工作流、单 Agent、multi-Agent 的 E0–E5 同预算消融；
- answer owner、handoff/join/cancel 语义；
- 最大步数/调用/成本/时间和 no-progress 停止条件；
- 高影响动作列表和可逆性分析。

阻断条件：无法定义 world-state success；无人对最终答案/副作用负责；复杂拓扑无实证收益。

### G2 · Tool / Effect Gate

**主张**：每个动作有 typed contract 和明确故障语义。

证据：

- JSON/schema、业务前置/后置条件；
- `read/internal_write/external_write/irreversible` effect 分类；
- 幂等键、receipt、timeout-after-commit/RESULT_UNKNOWN 对账；
- contract tests、fault injection、sandbox profile；
- MCP/工具版本、来源、SBOM/签名和撤销方式。

阻断条件：高影响工具接收任意 shell/URL；外部写无幂等/receipt；工具失败被统一盲重试。

### G3 · Identity / Authorization Gate

**主张**：每次执行可证明 actor、subject、tenant、resource、audience 与委托。

证据：

- 身份/数据流图；PDP/PEP 策略和对象级测试；
- JIT 短期 credential、audience/scope、token passthrough 负面测试；
- cross-tenant、confused deputy、撤销/过期、TOCTOU 测试；
- sandbox/egress 规则与 secret-scanning；
- actor + subject + policy decision 审计不变量。

阻断条件：共享 admin token；模型自报 tenant/owner；凭证进入上下文或 trace；无执行点强制。

### G4 · Context / Data Gate

**主张**：每个上下文块有来源、信任、版本、TTL、用途和数据分类。

证据：

- context manifest 与确定性 assembler；
- RAG ACL 在检索前执行，非检索后遮盖；
- provenance/taint 跨摘要、handoff、memory 传播；
- memory 写入门、隔离、supersedes、lineage 删除；
- DLP、数据驻留、retention 与删除演练；
- prompt/tool content capture 的 opt-in 策略。

阻断条件：跨租户 cache/index；外部内容被摘要后自动变可信；无法删除派生数据。

### G5 · Guardrail / HITL Gate

**主张**：高风险动作在执行前被正确策略或人类闸门控制。

证据：

- R0–R4 动作分级和 `ALLOW/DENY/REQUIRE_APPROVAL/ABSTAIN` 语义；
- approval 绑定 proposal hash、resource version、policy、TTL；
- guard/Judge 混淆矩阵和最差语言/攻击切片；
- 修改/拒绝/过期/撤销/重放/双 worker 竞态测试；
- 审批 UI、人因/疲劳指标、R4 双人或带外验证；
- 长期暂停/恢复和队列容量测试。

阻断条件：批准“继续执行”而非具体提案；参数变化后仍沿用批准；审批服务失败时高风险 fail open。

### G6 · Eval / Quality Gate

**主张**：候选在独立、可复现的目标分布上有实质收益且风险不回归。

证据：

- estimand、任务/环境分布、agent/environment seeds；
- world-state oracle、`pass^k`、coverage–risk、cost/success、worst-slice；
- dev/regression/locked holdout 分离和污染审计；
- Judge 人工 anchor、混淆矩阵、版本漂移门禁；
- 候选/基线配对效应、95% CI、MDE、非劣门槛；
- eval-infra failure 与 Agent failure 分开审计。

阻断条件：只报一次成功或总 Judge 分；逐题优化 holdout；严重安全失败被平均分抵消。

### G7 · Runtime / SRE Gate

**主张**：系统在预计负载和故障下有界、可背压、可恢复。

证据：

- SLO/error budget、queue topology、admission/concurrency limits；
- deadline propagation、全局预算 ledger、recovery reserve；
- burst/soak/chaos、429、慢工具、timeout-after-commit；
- p50/p95/p99 queue/service/e2e latency 和 cost/success；
- retry owner/budget、circuit breaker、bulkhead、公平队列；
- checkpoint migration、lease/fencing、outbox/inbox、补偿。

阻断条件：无限队列；每层重新计时；多层重试；取消后 late result 无对账。

### G8 · Rollout / Incident Gate

**主张**：能限制暴露、发现退化、撤销能力并处理已发生影响。

证据：

- shadow 写动作虚拟化证明；
- canary 风险范围、推进/停止规则和最小标签成熟度；
- kill switch、credential revoke、proposal-only/read-only 降级；
- 新请求、在途任务、状态 schema、memory 和副作用的 rollback runbook；
- 事故分级、值班/通讯/取证、用户与监管通知流程；
- game day：注入、工具投毒、队列饱和、错误退款、trace 丢失。

阻断条件：只能回滚代码，不能停止旧任务/撤销 token/核对副作用；关键告警无人负责。

## 4. 端到端案例：安全退款 Agent

### 4.1 需求与不变量

用户要求对重复扣款退款：

```text
I1 只能操作当前用户/租户拥有的订单
I2 金额 <= 已确认重复扣款金额
I3 退回原支付方式，修改目的地禁止自动化
I4 同一 logical refund 恰好一个业务 receipt
I5 > 自动额度或异常目的地必须审批
I6 回复中的退款状态与数据库/receipt 一致
```

### 4.2 组件与信任边界

```text
User
  ↓ authenticated task
Host / Orchestrator
  ├─ Context Assembler（订单/政策，ACL + provenance）
  ├─ Planner（无 credential，只产 ActionProposal）
  ├─ Policy PEP/PDP
  ├─ Approval Service（proposal hash/version/TTL）
  └─ Executor（JIT token, aud=payments-api）
        ↓ idempotency key
     Payments API → receipt → world-state verifier
```

外部邮件/网页 Reader 在独立只读域，不能接触支付能力；远程 Agent 只能返回带 provenance 的 evidence/artifact。

### 4.3 状态与 effect log

```yaml
task:
  id: refund-829
  version: 21
  owner: refund-orchestrator
  state: RESULT_UNKNOWN
proposal:
  hash: sha256:...
  order_id: O123
  amount: 86
  destination: original_method
approval:
  id: apr-88
  hash: sha256:...
  resource_version: 18
  expires_at: ...
effect:
  logical_action_id: refund-O123-duplicate-1
  idempotency_key: ...
  attempt: 2
  receipt_ref: null
budget:
  remaining_ms: 8200
  recovery_reserve_ms: 5000
```

### 4.4 关键故障窗口

**窗口 A：支付已提交，HTTP 超时。**

不能重新创建退款。状态置 `RESULT_UNKNOWN`，用 idempotency key 查询支付 receipt；查到则提交本地状态，确认未提交才重试。

**窗口 B：批准后订单变化。**

Executor 比较 `resource_version=18`；CAS 失败使旧 approval 失效，重新组装提案并审批。

**窗口 C：worker lease 过期后复活。**

新 worker 获得更高 fencing token；存储/API 拒绝旧 token 的写入，避免双执行。

**窗口 D：恶意政策网页。**

网页 taint 保留；它只能用于 evidence，不得改变退款目的地/权限。PDP 从签名/版本化内部 policy store 读取政策，egress 不允许任意域名。

### 4.5 评测设计

\[
\theta=E[\mathbb 1(I1\land I2\land I3\land I4\land I5\land I6)]
\]

测试按金额、政策版本、语言、工具故障、并发、注入、跨租户分层。每题多个 Agent/environment seed，报告：

- safe world-state success 与 `pass^3`；
- 重复副作用、越权、错误目的地（硬门槛）；
- coverage–risk/转人工；
- cost/success、p95/p99；
- 关键步骤条件成功和 recovery rate。

候选与基线在相同环境配对；locked holdout 做 CI/MDE 判断。Judge 只评用户解释质量，不判退款是否真实发生。

### 4.6 发布与事故演练

```text
shadow：写工具返回 fake receipt；比较 proposal
→ canary：低金额、原支付方式、单租户、人工审批
→ 扩大：满足成熟标签 + 无严重失败 + CI gate
→ 自动额度逐步提升，但高风险条件永久审批
```

Game day：注入邮件诱导改目的地、支付 timeout-after-commit、approval 重放、队列饱和、trace collector 丢包。验证 kill switch、read-only 降级、receipt 对账、凭证撤销和用户通知。

## 5. Release Decision 不是简单多数票

```yaml
decision: NO_GO
reason:
  - "G6 主指标提升，但跨语言注入 worst-slice 出现未拦截外发"
  - "G8 尚未完成在途退款 reconciliation drill"
allowed_next_step:
  - "继续 shadow；修复后只重开 G5/G6/G8 相关证据"
```

硬门槛不可被平均质量收益抵消。非硬门槛可做有时限的 risk acceptance，但必须由有权 owner 签署、记录补偿控制和到期日期。

## 6. 证据新鲜度与变更影响

| 变更 | 至少重开 |
|---|---|
| 模型/prompt/context assembler | G4/G5/G6，视行为重开 G8 |
| 工具 schema/实现/权限 | G2/G3/G5/G7/G8 |
| MCP/A2A server/供应链 | G2/G3/G4/G8 |
| policy/approval UI | G3/G5/G6/G8 |
| checkpoint/state schema | G2/G7/G8 |
| 数据/索引/ACL | G3/G4/G6 |
| Judge/grader | G6，线上时间序列需量尺桥接 |
| 流量/任务分布明显漂移 | G6/G7/G8 |

用 change manifest 自动计算需要重跑的证据集合，避免“代码只改一行”绕过系统级验证。

## 7. Owner 与职责分离

| 职责 | 典型 owner | 不应独自完成 |
|---|---|---|
| Agent 行为/工具 | Agent team | 自己批准高风险上线 |
| 身份与策略 | Identity/Security | 修改业务成功标准 |
| Eval/数据 | Eval platform + domain expert | 同一人生成题、调参并揭 holdout |
| SRE/runtime | Platform/SRE | 接受未评估的行为风险 |
| 业务风险 | Product/Operations | 绕过技术安全硬门槛 |
| 最终 go/no-go | 预定义 change authority | 用口头承诺替代缺失证据 |

## 8. 全课程能力地图（58 篇口径）

```text
agent/INDEX.md + DEPTH_AUDIT.md
├─ rag/                  9 篇：知识、检索、证据、数据生命周期
├─ agent-core/           9 篇：循环、工具、规划、决策与 test-time search
├─ context-engineering/  6 篇：MCP、上下文投影、记忆与压缩
├─ orchestration/        7 篇：ownership、状态、协议与并发
├─ evaluation/           7 篇：estimand、oracle、Judge、统计与线上实验
├─ production/           7 篇：威胁、身份、护栏、容量与上线证据
└─ systems-engineering/ 11 篇：runtime、恢复、一致性、SLO、安全与案例
```

真正的毕业标准不是“读完 58 篇”，而是能沿以下追问到底：

```text
定义 → 机制 → 假设 → 反例/故障窗口 → 控制 → 可观察证据
→ 评测/统计 → 发布 → 回滚/恢复
```

## 9. 最终检验清单

- [ ] 能将每个 go-live 勾选项改写成 Gate Record。
- [ ] 能解释八个 gate 的阻断条件和证据 owner。
- [ ] 能为退款案例写出 world-state 不变量和身份链。
- [ ] 能处理 timeout-after-commit、approval TOCTOU 和 lease resurrection。
- [ ] 能设计 locked eval、shadow、risk-scoped canary 与 rollback drill。
- [ ] 能说明哪些变更会让旧证据失效。
- [ ] 能区分代码回滚、任务回滚、凭证撤销和副作用补偿。
