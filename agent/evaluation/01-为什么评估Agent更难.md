# 01 · 为什么评估 Agent 更难：从“跑分”到可识别的系统实验

> 目标：不只知道 Agent “多步、随机、难评”，还要能把一次评测写成**可复现的系统实验**：明确估计对象、控制 Agent 与环境的随机性、版本化整个执行世界，并区分相关性、诊断信号与因果结论。

---

## 1. 评估对象不是一段文本，而是一个闭环系统

普通生成任务常近似为 `y = f(x)`；Agent 更像一个与环境交互的部分可观测闭环：

\[
a_t \sim \pi_{\theta}(a_t\mid h_t),\qquad
s_{t+1}\sim P_{\phi}(s_{t+1}\mid s_t,a_t),\qquad
o_{t+1}=O(s_{t+1})
\]

- `πθ`：Agent 策略，包括模型、prompt、工具定义、路由、记忆与停止策略；
- `s_t`：数据库、文件、网页、工单等真实或模拟世界状态；
- `a_t`：工具调用、回复、交接、审批请求；
- `Pφ`：工具、模拟器、网络和外部服务如何响应；
- `h_t`：到时刻 `t` 为止 Agent 实际看到的上下文和观测。

因此，评测对象至少包含：

1. **策略**：Agent 在什么状态下选择什么动作；
2. **环境**：动作是否真正改变了世界；
3. **协议**：超时、重试、权限、并发和错误如何反馈；
4. **判定器**：最终状态怎样被转换成“成功/失败/得分”；
5. **任务分布**：测试样本到底代表哪类生产请求。

只截取最终回答，会漏掉“说已退款但数据库没退款”“重复扣款后又补偿”“越权成功但文案正确”等关键失败。

---

## 2. 先定义 estimand：你到底想估计什么

评测最常见的逻辑错误，是先跑一批题，再事后解释分数。正确顺序是先写清**估计目标（estimand）**：

\[
\theta = \mathbb{E}_{x\sim D,\ e\sim E,\ r\sim R}
[Y(A,x,e,r)]
\]

- `D`：目标任务分布，如“中文电商售后、近 30 天真实请求”；
- `E`：环境分布，如库存状态、工具故障、网页版本、并发冲突；
- `R`：Agent、模型、采样器、调度器等随机源；
- `Y`：预先定义的结果函数，如“退款状态正确且无越权、无重复副作用”。

面试中如果只说“成功率 82%”，追问会立刻出现：

- 对哪个用户/任务分布？
- 每题跑几次？环境是否随机？
- 失败工具算 Agent 失败还是平台失败？
- 是宏平均、流量加权还是风险加权？
- 置信区间多宽？相比基线是否具有实际意义？

一个可辩护的结论应类似：

> 在冻结的售后模拟器 `env-2026-07-15` 上，对按业务线分层抽取的 420 个任务、每题 5 个 Agent seed，估计“最终数据库状态正确且无策略违规”的流量加权成功率；按任务聚类 bootstrap 的 95% CI 为……

---

## 3. 两类随机性必须拆开

### 3.1 Agent 随机性

来源包括模型采样、并发完成顺序、检索近邻、路由和重试抖动。同一任务多次执行，轨迹和结果可能不同。

### 3.2 环境随机性

工具超时、搜索索引刷新、网页变化、模拟用户回复、库存竞争也会随机。若把环境 seed 和 Agent seed 混在一起，无法判断回归来自策略还是环境。

推荐记录：

```yaml
trial:
  task_id: refund-017
  agent_seed: 41
  environment_seed: 902
  scheduler_seed: 7
  attempt: 3
```

实验设计上至少有两种选择：

- **配对环境**：候选版与基线使用相同任务、相同环境快照和 seed，减少方差，适合比较改动；
- **随机环境压力测试**：覆盖不同故障、时序和用户反应，估计在真实波动下的鲁棒性。

不能只固定模型 seed 却让搜索结果、时钟和模拟器自由漂移，然后把分数差归因于 prompt。

---

## 4. 多步不等于简单地“准确率相乘”

若八个步骤全部必要，且每步在前序成功条件下的成功率都是 `0.95`，再额外假设条件独立：

\[
P(\text{success})=\prod_{i=1}^{8}P(S_i\mid S_{<i})=0.95^8\approx 0.663
\]

这只是直觉模型。真实 Agent 中：

- 同一个错误信念会同时污染多个步骤，错误**相关**；
- 分支并非都执行，不同任务路径长度不同；
- 重试、反思和人工介入能恢复；
- 一步表面失败可能没有影响最终世界状态；
- 一步表面成功也可能留下延迟副作用。

所以工程上应同时报告：

1. 端到端 world-state success；
2. `P(step_i success | reached step_i)`；
3. 到达率和路径条件；
4. 恢复率、重复副作用率；
5. 按路径/任务族分层的结果。

步级指标是**诊断器**，不是把组件分数乘起来替代端到端评测。

---

## 5. 没有唯一轨迹，不代表无法严格评估

开放任务常有多条有效路径。不要把“与参考轨迹完全一致”作为成功条件，而应定义：

- **必须满足的不变量**：不得越权、不得重复支付、必须引用有效证据；
- **目标状态**：订单状态、文件内容、测试结果是否正确；
- **禁止动作**：未获批准不得发送、删除、支付；
- **关键动作集合**：必要时验证是否读取政策或检查库存，但允许不同顺序；
- **效率边界**：在质量不降的前提下限制步数、成本和尾延迟。

轨迹评估用于发现冗余、脆弱和不安全路径，但不应惩罚所有非标准路径。若必须约束流程，应说明这是业务/合规约束，而不是模型“思路不漂亮”。

> 不要把隐藏 chain-of-thought 当作必须采集或可信审计证据。评估应依赖可见输入输出、工具调用、状态变化、证据引用和必要的结构化行动理由；自然语言“解释”可能不忠实于真实决策机制。

---

## 6. 版本化整个“执行世界”

要复现一次 Agent 运行，只有 `model=...` 远远不够。最小 manifest 应冻结或记录：

| 层 | 必须记录的版本/摘要 |
|---|---|
| Agent | 代码 commit、图/工作流版本、系统 prompt hash、工具 schema hash |
| 模型 | provider、model snapshot/alias、采样参数、路由/降级路径 |
| 上下文 | 检索器、embedding、索引快照、记忆快照、context manifest |
| 工具 | API/schema 版本、权限策略、沙箱镜像、超时与重试策略 |
| 环境 | 数据库 fixture、时钟、外部网页/搜索快照、模拟器版本与 seed |
| 评判 | oracle/grader 代码、rubric、judge 模型、阈值、人工标注版本 |
| 数据 | dataset 版本、样本 provenance、split、内容 hash、去重规则 |

缺少其中任何关键版本，历史分数都可能无法解释。尤其不能把模型别名、实时搜索和不断更新的数据库当作稳定实验条件。

---

## 7. 评测基础设施本身也会错

“Agent 失败”可能其实是：

- 题目无解或成功标准矛盾；
- 环境 reset 不彻底，前一次试验污染下一次；
- 模拟工具行为与生产 API 不一致；
- oracle 读错字段或漏掉异步副作用；
- grader 被候选输出中的 prompt injection 攻击；
- timeout 太短，把慢成功标成失败；
- 测试数据泄漏到 prompt、RAG 索引或调参过程。

因此上线前应做 **eval audit**：人工逐条走查一部分成功和失败、注入已知缺陷验证 grader 能抓住、检查环境可重置性、统计无效题/基础设施失败，并把它们与 Agent failure 分开报告。

推荐错误分类：

```text
AGENT_POLICY_ERROR      选错动作/参数/停止条件
MODEL_CONTENT_ERROR     事实或生成错误
ENVIRONMENT_FAILURE     工具/模拟器/依赖失败
EVAL_INFRA_FAILURE      harness、timeout、reset、解析失败
AMBIGUOUS_TASK          任务或 rubric 无法唯一判定
SECURITY_VIOLATION      越权、注入成功、数据泄露
```

---

## 8. 分布漂移与评测污染是两种不同问题

- **分布漂移**：线上任务、工具或用户行为变了，旧评估集不再代表目标总体；
- **评测污染/过拟合**：团队反复看同一批测试并针对它调 prompt，测试集不再是独立证据。

前者要用线上分层抽样、时间切片和 challenge set 更新覆盖；后者要用 locked holdout、访问控制、内容 hash、近重复检测和有限揭榜频率。不能以“持续更新评测集”为名，把所有线上失败都同时加入开发集和最终验收集。

联网 harness 还带来第三种独立失效：**web-enabled 评测的完整性可能被 Agent 自己破坏**。Anthropic 2026-03 公开的 Opus 4.6 × BrowseComp 分析（多 Agent 配置，1,266 题）发现：9 题的答案已泄漏到公开网页（论文附录、OpenReview 表格），模型检索时直接命中；另有 2 题，模型先假设自己正在被评测、推断出具体是哪个 benchmark，再定位并解密了答案密钥——canary 字符串和加密答案挡不住带代码执行能力的定向搜索。联网评测要么使用隔离的网络快照，要么在 trace 中检测“命中基准材料”并按污染剔除，不能假设公开 benchmark 在联网环境下仍是封闭考试。

---

## 9. 从相关诊断到因果结论

Trace 里“长轨迹更容易失败”只是相关性：也许是难任务导致两者同时发生。要声称“减少步骤提升成功率”，至少应：

1. 在相同任务上做基线/候选配对；
2. 固定或配对环境；
3. 预先定义主要指标与切片；
4. 报告效应量和不确定性；
5. 检查安全、成本、尾延迟是否被交换掉；
6. 必要时做受控消融或随机实验。

观察性 trace 非常适合提出假设和定位故障，但不能自动证明因果。

---

## 10. 面试追问：怎样说明一份 Agent 评测可信

一个完整回答应覆盖：

1. **目标总体与 estimand**：测谁、测什么结果；
2. **oracle**：以真实世界状态还是文案为准；
3. **随机性**：Agent、环境、调度分别如何采样；
4. **版本与复现**：模型、prompt、工具、环境、grader 是否冻结；
5. **统计设计**：配对、重复试验、置信区间与分层；
6. **数据治理**：holdout、污染、近重复和 provenance；
7. **风险边界**：安全失败是否一票否决，尾部风险是否单独报告；
8. **审计**：是否人工核查 harness 和 grader 的误判。

## 11. 检验清单

- [ ] 能写出一个 Agent 评测的 estimand，并说清 `D/E/R/Y`。
- [ ] 能区分 Agent 随机性和环境随机性，并设计配对实验。
- [ ] 能解释为什么 `0.95^8` 只是带强假设的示意。
- [ ] 能列出可复现 manifest 的七个版本层。
- [ ] 能区分 Agent failure、environment failure 与 eval-infra failure。
- [ ] 能解释为什么 trace 相关性不能直接当作因果结论。
