# 01 · 为什么评估 Agent 更难

> 目标：理解 Agent 评估相比"评估单次 LLM 输出"的独特挑战。读完你会明白为什么不能只看最终答案，以及"误差累积"为什么是多步 Agent 的根本难题。

---

## 1. 评估单次输出 vs 评估 Agent

| | 单次 LLM 调用 | Agent |
|---|---|---|
| 评估对象 | 一个输出 | 一条**多步轨迹** + 最终结果 |
| 确定性 | 相对可控 | **高度不确定**（每步都可能走不同路径） |
| 标准答案 | 常有唯一/接近唯一答案 | 常**没有唯一正确路径**（多条路都能到目标） |
| 失败定位 | 看输出即可 | 要定位**失败在哪一步/哪次工具调用/哪次交接** |
| 评估成本 | 低（评一次） | 高（要评整条轨迹的多个环节） |

> 一句话：**评估单次输出像批改一道选择题；评估 Agent 像评判一整场解题过程——既要看最终答案，又要看每一步推理、用了什么工具、有没有绕路。**

---

## 2. 挑战一：不确定性（Non-determinism）

同一个任务，Agent 跑两次可能走**完全不同的路径**：
- 第一次：搜索 → 直接找到 → 回答。
- 第二次：搜索 → 没找到 → 改写查询 → 再搜 → 回答。

两次都可能"对"，但轨迹不同。这意味着：
- **不能用"精确匹配某条标准轨迹"来评**（太脆，合理的变体会被误判为错）。
- 评估要么看**结果**（不管过程怎么走，到没到目标），要么看**轨迹的质量属性**（每步合不合理），而不是"是否等于某条固定路径"。
- 单次跑的结果有偶然性，**评估常需多次采样取统计**（成功率而非一次成败）。

---

## 3. 挑战二：误差累积（Error Compounding）⭐ 多步 Agent 的根本难题

这是必须刻进脑子的一条：

> **多步任务里，每一步的错误会累乘。即使每步成功率很高，步数一多，端到端成功率也会暴跌。**

举例（一个广为引用的数字）：

> **每步成功率 95%，连续 8 步，端到端成功率 ≈ 0.95^8 ≈ 66%。**

```
步数:     1      2      3      4      5      6      7      8
单步95%: 95% → 90% → 86% → 81% → 77% → 74% → 70% → 66%
                                                      ↑ 端到端只剩 66%
```

含义极其重要：
- **多步 Agent 难做对，不是因为模型笨，而是因为概率累乘。** 步数越多越脆弱。
- 这解释了 [agent-core/01](../agent-core/01-Agent循环与ReAct.md) 的失败模式为什么常见——长链条里任何一步崩了，整体就崩。
- **工程启示**：① 尽量**减少步数**（能一步别两步，呼应"能简单就简单"）；② 必须做**步级评估**（[文档 02](02-Agent评估的维度与指标.md)）——找出是哪一步在拉低整体，而不是只盯着端到端那个数字干瞪眼。

> 反过来：把单步成功率从 95% 提到 99%，8 步端到端从 66% 升到约 92%——**每一步的小改进，在长链条里被放大成巨大的端到端收益。** 这就是步级评估的价值。

---

## 4. 挑战三：没有唯一标准答案 / 路径

很多 Agent 任务是开放的："帮我调研 X 并写报告"——没有唯一正确的报告，也没有唯一正确的调研路径。这让评估很难用"对照标准答案"的方式做：
- **结果**：怎么算"好报告"？需要多维度（完整性、准确性、相关性）、常需 LLM 裁判或人工。
- **轨迹**：怎么算"好的调研过程"？看是否高效、工具用得对、没绕路。

> 所以 Agent 评估大量依赖 **LLM-as-judge（按标准打分）** 和**轨迹的质量属性评估**，而不是简单的精确匹配（[文档 03](03-评估方法与LLM裁判.md)）。

---

## 5. 挑战四：失败定位难（尤其多步/多 Agent）

Agent 答错了，根因可能在：
- 某一步推理错了；
- 选错了工具 / 工具参数错了；
- 工具返回了坏数据；
- 上下文丢失/漂移（[context-engineering/02](../context-engineering/02-上下文工程基础.md)）；
- 检索没召回（[rag/07](../rag/07-RAG评估与可观测性.md)）；
- 多 Agent 的某次交接出错（[orchestration/06](../orchestration/06-生产实践与反模式.md)）。

> 要定位到具体环节，必须有**完整的执行轨迹（trace）**（[文档 05](05-可观测性与追踪.md)）。没有 trace，多步 Agent 的失败就是黑盒。

---

## 6. 这些挑战推导出的评估原则

把上面四个挑战翻译成行动原则（后续文档逐一落地）：

1. **结果 + 轨迹都要评**，别只看最终答案（应对：侥幸对/低效/不安全）。→ [文档 02](02-Agent评估的维度与指标.md)
2. **做步级评估**，定位是哪一步在拉低端到端（应对：误差累积）。→ [文档 02](02-Agent评估的维度与指标.md)
3. **多次采样看成功率**，别用单次成败下结论（应对：不确定性）。→ [文档 03](03-评估方法与LLM裁判.md)
4. **能确定性校验就确定性校验，开放任务才用 LLM 裁判**（应对：无唯一答案）。→ [文档 03](03-评估方法与LLM裁判.md)
5. **必须有完整 trace**（应对：失败定位难）。→ [文档 05](05-可观测性与追踪.md)
6. **尽量减少步数**（应对：误差累积）——这是 Agent 设计层面的启示（呼应 [agent-core/06](../agent-core/06-模式选择与组合.md) 的"能简单就简单"）。

---

## 7. 常见坑

- **只看端到端成功率** → 不知道是哪一步出问题，无从优化。要步级评估。
- **用精确匹配标准轨迹评** → 合理的路径变体被误判为错。看结果或质量属性。
- **单次跑就下结论** → 不确定性导致结论不可靠。多次采样。
- **忽视误差累积** → 以为"每步都挺准"就没事，结果端到端惨不忍睹。
- **没有 trace 就想调多步 Agent** → 黑盒，抓瞎。

---

## 8. 本章小结

- 评估 Agent ≠ 评估单次输出：要评**一条多步轨迹 + 最终结果**，且**没有唯一正确路径**。
- **不确定性**：同任务多次走不同路径 → 不能精确匹配轨迹，要看结果/质量属性，多次采样取统计。
- **误差累积（核心）**：每步 95% × 8 步 ≈ 66%——多步 Agent 难做对源于概率累乘；启示是**减少步数 + 做步级评估**（每步的小改进被放大成大收益）。
- **无唯一答案** → 大量依赖 LLM 裁判和轨迹质量评估。
- **失败定位难** → 必须有完整 trace。
- 这些挑战推导出 6 条评估原则，后续文档逐一落地。
