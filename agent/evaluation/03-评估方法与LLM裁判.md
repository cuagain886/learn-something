# 03 · 评估方法与 LLM 裁判

> 目标：掌握给 Agent 打分的三类方法——确定性校验、LLM 裁判、人工评估，尤其 **LLM-as-judge 的正确用法、偏差与校准**。读完知道什么指标该用什么方法评。

---

## 1. 三类评估方法（总览）

| 方法 | 怎么评 | 优点 | 缺点 | 适合评 |
|------|--------|------|------|--------|
| **确定性校验（Code-based）** | 写代码/规则断言 | 快、便宜、100%可靠、可复现 | 只能评"有明确正确答案"的 | 工具调用是否成功、格式是否合规、测试是否通过、是否命中预期值 |
| **LLM 裁判（LLM-as-judge）** | 让一个强 LLM 按标准打分 | 灵活、能评开放/主观质量、可规模化 | 有偏差、不稳定、需校准、有成本 | 答案质量、相关性、轨迹合理性、忠实度 |
| **人工评估（Human）** | 人按 rubric 打分 | 最准、能抓细微问题 | 慢、贵、不可规模化 | 校准基准、最终验收、高价值抽检 |

> 核心选择原则：**能确定性校验的，绝不用 LLM 裁判**（前者又快又准又便宜又可复现）。只有"没有明确正确答案"的开放/主观维度，才上 LLM 裁判。人工评估用来**校准** LLM 裁判和做最终把关。

---

## 2. 确定性校验（Code-based / Rule-based）⭐ 能用就优先

对"有客观正确答案"的东西，直接用代码判断：

```python
# 例：评工具调用和最终结果
assert tool_call.name == "get_weather"           # 选对了工具吗
assert "city" in tool_call.args                   # 传了必需参数吗
assert result_json_is_valid(output)               # 输出格式合规吗
assert expected_value in final_answer             # 命中预期事实吗
assert unit_tests_pass(generated_code)            # 代码通过测试吗（客观信号！）
```

- **适用维度**：工具选择准确率、参数正确性、输出格式、是否命中标准答案、代码能否运行、是否触发了禁止动作（动作安全的硬规则）。
- **优点**：这是评估里**最可靠、最该多用**的一类。客观信号（如单元测试）也是 [agent-core/03 反思](../agent-core/03-反思模式Reflection.md) 最有效的反馈来源。
- **局限**：评不了"这个报告写得好不好"这种主观质量——那是 LLM 裁判的活。

---

## 3. LLM-as-Judge（LLM 裁判）⭐ 开放任务的主力

让一个能力强的 LLM 扮演"评委"，按给定标准给 Agent 的输出/轨迹打分。

### 3.1 两种打分范式
- **打分（Scoring / reference-free）**：直接按 rubric 给分（如"忠实度 1~5 分"），无需标准答案。
- **对比（Pairwise）**：比较两个输出哪个更好。比绝对打分更稳（人和模型都更擅长"比较"而非"打绝对分")，常用于 A/B 对比两个版本。

### 3.2 用好 LLM 裁判的关键
- **给明确的评分标准（rubric）**：别说"评好不好"，要给具体维度和分级标准（"忠实度：5=所有论断都有出处，3=部分有，1=大量编造"）。
- **要求给出理由（reasoning）**：让裁判先说明判断依据再给分，提升一致性和可解释性。
- **结构化输出**：让裁判输出结构化的分数+理由，便于聚合。
- **裁判模型要够强**：裁判比被评的还弱就不可靠。

---

## 4. LLM 裁判的偏差与坑（必须知道）⚠️

LLM 裁判方便，但**绝不是中立可靠的**，有系统性偏差：

| 偏差 | 表现 |
|------|------|
| **长度偏好** | 倾向给更长的答案更高分（哪怕没更好） |
| **位置偏好** | pairwise 时偏好排在前面（或后面）的那个 |
| **自我偏好（Self-bias）** | 倾向给"和自己风格像"的输出更高分（用同家模型评同家输出尤甚） |
| **风格偏好** | 偏好自信、华丽的措辞，而非朴实但正确的 |
| **不稳定** | 同一输入多次打分可能不同 |

### 缓解手段
- **校准（Calibration）**⭐：用一小批**人工标注**样本校准裁判——确认它的打分和人类判断一致，再大规模用。**没校准过的 LLM 裁判分数不可信。**
- **降低随机性**：评估时设低 temperature；必要时多次打分取平均/多数。
- **对抗位置偏好**：pairwise 时**交换顺序各评一次**，结果一致才算数。
- **对抗长度偏好**：rubric 里明确"长度不计入质量"。
- **换一家模型当裁判**：避免自我偏好（别用 X 评 X）。
- **把能确定性校验的拆出去**：别让裁判评本可以用代码精确判断的东西。

> 一句话：**LLM 裁判是"带偏见的廉价评委"——用之前先用人工校准它，用的时候控制随机性和偏差。**

---

## 5. 蒸馏小裁判：让"全量评估线上流量"变得可行 ⭐

LLM 裁判的成本曾让人只能**抽样**评估线上流量。2026 的进展：

> **用蒸馏的小语言模型做裁判，成本比完整 LLM 裁判低约 97%**——便宜到可以**对 100% 的生产流量打分**，而不只是抽样子集。

- 做法：用强 LLM 裁判的打分作为"教师信号"，蒸馏出一个专门做某类评估的小模型。
- 价值：线上每一条都能评 → 质量监控从"抽样估计"变成"全量覆盖"，能更早发现退化（[文档 06](06-线上持续评估与反模式.md)）。
- 仍需用人工/强裁判定期校准这个小裁判。

---

## 6. 人工评估（Human Evaluation）

- **最准、能抓 LLM 裁判漏掉的细微问题**，但慢且贵、不可规模化。
- **主要用途**：① **校准 LLM 裁判**（金标准）；② 高价值场景的**最终验收/抽检**；③ 构建黄金评估集（[文档 04](04-评估数据集与CI.md)）。
- 实操：给标注者清晰 rubric，多人标注算一致性（避免单人主观）。

---

## 7. 应对不确定性：多次采样

[文档 01](01-为什么评估Agent更难.md) 的不确定性挑战在这里落地：

> Agent 同一任务多次跑结果可能不同，**单次成败不能代表真实水平**。应**多次运行取统计**——用"成功率（如 10 次成功 8 次 = 80%）"而非"这次成了/没成"来评估。尤其在对比两个版本时，要有足够样本量才能说"A 比 B 好"。

---

## 8. 方法与指标的对应（速查）

| 要评的维度 | 首选方法 |
|------------|----------|
| 工具选择/参数正确性 | 确定性校验 |
| 输出格式合规 | 确定性校验 |
| 代码能否运行/测试通过 | 确定性校验（客观信号） |
| 是否触发禁止动作 | 确定性校验（硬规则）+ 安全审查 |
| 任务完成度（有明确标准） | 确定性校验 |
| 任务完成度（开放） | LLM 裁判（rubric）+ 人工校准 |
| 答案质量/相关性/忠实度 | LLM 裁判（rubric）+ 人工校准 |
| 轨迹合理性/效率（开放） | LLM 裁判（reference-free） |
| 最终验收/校准基准 | 人工 |

---

## 9. 常见坑

- **能用代码判断却用 LLM 裁判** → 又贵又不可靠，还可能判错。
- **LLM 裁判不校准就用** → 分数带未知偏差，结论失真。头号坑。
- **忽视裁判偏差**（长度/位置/自我偏好）→ 系统性误判。
- **裁判温度高/单次打分** → 不稳定。降温、多次、pairwise 换序。
- **单次跑就比较两个版本** → 被不确定性误导。多次采样看统计。
- **用同家模型评同家输出** → 自我偏好放大。
- **蒸馏小裁判不再校准** → 漂移了也不知道。

---

## 10. 本章小结

- 三类方法：**确定性校验（能用就优先，最可靠）、LLM 裁判（开放任务主力，但带偏差需校准）、人工（最准，用于校准和验收）**。
- 选择原则：**能确定性校验绝不用 LLM 裁判**；只有开放/主观维度才上裁判。
- 用好 LLM 裁判：明确 rubric、要求给理由、结构化输出、裁判够强、优先 pairwise。
- **LLM 裁判有系统偏差**（长度/位置/自我/风格偏好、不稳定）——**用前必须人工校准**，用时降温、多次、换序、换家。
- **蒸馏小裁判**成本降约 97%，让全量评估线上流量成为可能（仍需定期校准）。
- 应对不确定性：**多次采样看成功率**，别用单次成败下结论。
