# 06 · 线上持续评估与反模式

> 目标：掌握 Agent 上线后如何**持续监控质量**——在线评估、用户反馈闭环、漂移检测，并系统化避坑。这是评估专题的收口。

---

## 1. 离线评估 ≠ 够了：为什么需要线上持续评估

[文档 04](04-评估数据集与CI.md) 的离线评估（CI 回归）管"上线前"。但上线后：
- **真实分布会变**：用户问的东西和你评估集里的不一样、且**随时间变**（新话题、新用法）。
- **依赖会变**：底层模型升级、外部 API 变化、知识库更新——都可能让 Agent 悄悄退化。
- **长尾和对抗**：真实世界有你没想到的输入和恶意尝试。

> 所以离线评估通过 ≠ 线上没问题。**必须持续监控线上质量**，形成"离线把关 + 线上监控 + 反馈回流"的完整闭环。

---

## 2. 线上评估怎么做

### 2.1 采样 vs 全量 ⭐
- **采样 + LLM 裁判**：对线上流量抽样，用 LLM 裁判（[文档 03](03-评估方法与LLM裁判.md)）跑质量指标。传统做法，成本可控但有盲区。
- **全量评估（2026 新可能）**：用**蒸馏小裁判**（成本降约 97%，[文档 03](03-评估方法与LLM裁判.md)）对**100% 流量**打分——质量监控从"抽样估计"变成"全量覆盖"，退化能更早发现。
- 实操：关键指标尽量全量（用便宜裁判），昂贵的深度评估用采样。

### 2.2 监控哪些信号
基于 [文档 05](05-可观测性与追踪.md) 的 trace，持续监控：
- **质量代理指标**：任务完成率、用户点踩率、"我不知道/资料未提及"的比例、转人工率、重试率。
- **轨迹健康**：平均步数、工具失败率、交接环检测、循环触顶比例。
- **成本/延迟**：token 消耗、p95/p99 延迟、单任务成本——异常飙升常是出问题的信号。
- **安全信号**：被注入尝试、越权动作拦截次数（[INDEX 阶段7](../INDEX.md)）。

### 2.3 告警
给关键指标设阈值告警（如"任务完成率跌破 X%""成本环比涨 50%"），**及早发现退化**而不是等用户投诉。

---

## 3. 用户反馈闭环 ⭐

线上最宝贵的评估信号来自真实用户：

```
用户反馈（点赞/点踩、追问、转人工、采纳/重写）
   ↓ 关联到对应的 trace（文档05）
定位：差评对应的轨迹哪一步出了问题
   ↓
回流：把失败案例加成评估用例（文档04）→ 修复 → 回归
```

- **显式反馈**：点赞/点踩、评分、纠错。
- **隐式反馈**：用户是否追问（暗示没答好）、是否转人工、是否采纳了答案/代码、是否重新提问。
- **价值**：反馈 + trace 让你能**精确定位差评背后是哪一步的问题**，并把它固化成回归用例——这是 Agent 越用越好的关键引擎。

---

## 4. 漂移检测（Drift Detection）

持续盯住"分布有没有变":
- **输入漂移**：用户问的内容类型变了（新话题占比上升）→ 评估集可能已不代表真实分布，需更新。
- **性能漂移**：同类任务的成功率/质量随时间下降 → 可能是模型/依赖/数据变化导致，要排查。
- **应对**：定期用线上真实流量刷新评估集（[文档 04](04-评估数据集与CI.md)）、模型/依赖升级时重跑全量评估回归。

---

## 5. 护栏即评估（Guardrails as Runtime Eval）

线上评估不只是"事后看"，也可以**实时拦截**（和 [INDEX 阶段7](../INDEX.md) 的安全护栏交汇）：
- **输入护栏**：进模型前检查（注入检测、越权意图）。
- **输出护栏**：出结果前检查（敏感信息、是否有据、是否触发禁止动作）——不合格则拦截/重试/降级。
- 这本质是"**实时的、会触发动作的评估**"：用一个快评估器在每个请求上把关。蒸馏小裁判让这变得便宜可行。

---

## 6. 完整评估闭环（把整个专题串起来）

```
┌─ 离线（上线前）─────────────────────────────┐
│  评估集（文档04）→ 多维指标（文档02）          │
│  × 评估方法（文档03）→ CI 回归 → 质量门槛      │
└──────────────────────────────────────────────┘
                    ↓ 通过则上线
┌─ 线上（上线后）─────────────────────────────┐
│  可观测 trace（文档05）→ 全量/采样在线评估     │
│  → 监控告警 + 护栏拦截                          │
│  → 用户反馈关联 trace → 捞失败                  │
└──────────────────────────────────────────────┘
                    ↓ 失败案例 + 漂移
              回流扩充评估集（文档04）→ 修复 → 回到离线回归
```

> 这个闭环就是 Agent 工程的"持续改进飞轮"：**线上发现问题 → 固化成离线用例 → 修复并回归 → 防止再发**。转得越快，Agent 越可靠。

---

## 7. 反模式（明确避免）

| 反模式 | 为什么错 | 正解 |
|--------|----------|------|
| **只做离线评估、上线就不管** | 真实分布/依赖会变，悄悄退化 | 线上持续评估 + 告警 |
| **没有用户反馈闭环** | 丢掉最宝贵的真实信号 | 显式+隐式反馈关联 trace 回流 |
| **采样太稀、漏掉问题** | 抽样盲区 | 蒸馏小裁判全量评关键指标 |
| **不监控成本/延迟** | 退化常先表现为成本/延迟异常 | 一并监控并告警 |
| **不检测漂移** | 评估集过时还自我感觉良好 | 定期用线上流量刷新评估集 |
| **失败案例不回流** | 同样的坑反复踩 | 失败→评估用例→回归 |
| **线上裁判不校准** | 监控数据本身不可信 | 定期人工校准（文档03） |
| **告警阈值缺失** | 等用户投诉才知道出事 | 关键指标设阈值告警 |

---

## 8. 本章小结

- **离线评估通过 ≠ 线上没问题**：真实分布、依赖、长尾会变，必须**线上持续评估**。
- 线上评估：**采样 + LLM 裁判**，或用**蒸馏小裁判全量覆盖**；监控质量代理指标、轨迹健康、成本/延迟、安全信号，并设**告警**。
- **用户反馈闭环**是最宝贵的信号：显式+隐式反馈关联 trace，定位差评对应的轨迹问题，回流成评估用例。
- **漂移检测**：盯输入漂移和性能漂移，定期用线上流量刷新评估集。
- **护栏即实时评估**：输入/输出护栏在每个请求上把关、拦截。
- 完整闭环 = **离线 CI 回归 + 线上监控/护栏 + 反馈回流扩集**，构成 Agent 的"持续改进飞轮"。
