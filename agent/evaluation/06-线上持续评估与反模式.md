# 06 · 线上持续评估：从 Shadow 到因果实验与安全回滚

> 目标：设计上线后的质量证据链。重点不是“给线上请求跑一个 Judge”，而是区分代理指标与真实业务结果，处理延迟标签和选择偏差，以 shadow/canary/受控实验逐步扩大暴露，并防止线上反馈污染独立评测。

---

## 1. 离线与在线回答不同问题

| 证据 | 回答的问题 | 不能证明什么 |
|---|---|---|
| 离线 locked eval | 在冻结任务/环境上是否优于基线 | 真实流量与依赖变化后的表现 |
| Shadow | 候选在真实输入上会如何决策 | 真正执行后的用户/业务结果 |
| Canary | 小比例真实暴露是否安全、稳定 | 全量和长周期效果 |
| A/B 随机实验 | 候选是否因果改善预定义结果 | 未覆盖群体、稀有灾难风险 |
| 观察性线上监控 | 何时、哪里异常，形成假设 | 变更与结果的因果关系 |
| 用户反馈 | 部分用户是否满意/受益 | 全体用户无偏质量 |

一条完整发布链通常是：

```text
离线门禁 → shadow → 小 canary → 分层扩大 →（适用时）A/B → 全量
                ↘ 任何阶段触发 guardrail / rollback / kill switch
```

高风险写动作不能在 shadow 中真实执行；要通过 dry-run、沙箱或 proposal-only 模式比较候选动作。

---

## 2. 指标分层：系统健康、质量代理与最终结果

### 2.1 系统/执行指标（快速）

- 错误、超时、队列深度、循环触顶、工具失败；
- p50/p95/p99、token、模型/工具调用、cost/success；
- 越权拦截、审批触发、重复副作用、补偿失败；
- trace 完整率和 telemetry drop rate。

### 2.2 质量代理（快但可能错）

- 在线 Judge 分、规则 pass、引用支撑率；
- 转人工、重试、澄清、复制/采纳、会话重开；
- 用户显式点赞/点踩。

### 2.3 最终业务结果（慢但更接近目标）

- 问题是否真正解决、工单是否重开；
- 退款/修复是否正确且无后续事故；
- 7/30 天留存、返工、投诉、合规事件；
- 人工处理总时间和全链路成本。

Goodhart 风险：把“少转人工”设目标，Agent 可能错误自信地自动处理；把“Judge 高分”设目标，系统可能学会写更讨 Judge 喜欢的文案。代理指标必须用延迟业务结果定期校验。

---

## 3. 延迟标签与归因窗口

某次回答今天看似成功，七天后工单重开才知道失败。需要事件级 join：

```text
run_id / task_id / user_pseudonym
  ├─ immediate: policy, tool receipt, judge, latency
  ├─ 24h: correction, escalation, duplicate action
  ├─ 7d: reopen, refund dispute, user outcome
  └─ 30d: retention / long-term loss
```

设计时明确：

- **label maturity**：一个 cohort 何时才算标签成熟；
- **attribution window**：哪些后续事件归因于这次运行；
- **censoring**：窗口结束前未观察到结果，不能直接当成功；
- **多次接触**：用户经历多个 Agent 版本时如何归因；
- **late correction**：已汇总的标签怎样回补并重算。

发布后前三天的成功率可能只包含即时代理，不能与标签已成熟的历史月份直接对比。

---

## 4. 用户反馈有严重选择偏差

愿意点踩的人、转人工的人、付费用户和沉默离开的人并非随机样本。常见偏差：

- 只有极好/极差体验的人反馈；
- UI 展示位置影响反馈概率；
- 失败后无法完成页面流程的用户根本看不到问卷；
- 不同 Agent 版本可能改变“是否产生标签”的机会；
- 支持团队只标注他们接触到的升级工单。

### 4.1 正确使用方式

1. 将显式/隐式反馈视为不同 label source；
2. 记录 `feedback_exposure`：用户是否有机会反馈；
3. 对无偏监控保留分层随机人工抽样；
4. 按业务、语言、风险、版本做分层估计；
5. 若按不等概率采样，记录 inclusion probability，并在适当假设下用 inverse propensity weighting；
6. 做 sensitivity analysis：未观测群体结果多差会改变结论？

IPW 只能校正已记录、建模合理的选择机制；对未观测混杂和极小 propensity 仍不可靠，需要截断权重、随机审计样本和稳健估计。

## 5. Shadow：验证决策，不产生真实影响

Shadow 将真实请求复制给候选，但用户仍收到基线结果，候选写动作被虚拟化：

```text
真实请求
├─ baseline → 真实工具/真实回复
└─ candidate → read-only snapshot + fake write tools → 不对用户可见
```

重点比较：

- 候选与基线的动作/路由/提案差异；
- 候选若真实执行会违反哪些不变量；
- 真实输入分布下的成本、延迟和依赖负载；
- 新模型/工具版本对 trace 和 schema 的兼容。

边界：shadow 不能观察候选回复引发的用户后续行为；读写时序、缓存和外部副作用也可能与生产不同。它适合发现问题，不等于线上效果证明。

---

## 6. Canary：控制爆炸半径

Canary 是小比例真实流量，必须按**风险与影响范围**设计，而不只是随机 1%：

- 先低权限、低金额、可逆任务；
- 限定租户、地区、工具和并发；
- 高影响动作保留人工审批；
- 设预算、速率、单用户/全局损失上限；
- 自动和人工 kill switch；
- 明确回滚后如何处理在途任务和已产生副作用。

### 6.1 示例推进门禁

```yaml
canary:
  stages: [0.5%, 2%, 10%, 25%, 50%]
  minimum_mature_labels_per_stage: 500
  hold_time: "at least one weekly cycle for final stages"
  stop:
    critical_policy_violation: "> 0"
    duplicate_side_effect: "> 0"
    p99_latency_relative: "> 1.30"
    safe_success_delta_lower_ci: "< -0.01"
  rollback:
    route_new_tasks_to_baseline: true
    cancel_or_reconcile_inflight: true
```

数值仅是结构示例。真实门槛由风险、基线和统计功效决定。

## 7. A/B 实验：什么时候能谈因果

适用于可安全随机化、版本间不会相互干扰、结果能被定义的场景。

### 7.1 随机化单位

- 按 request 随机：同一用户可能跨版本，容易串扰；
- 按 user/account 随机：减少体验混杂；
- 按 team/tenant 随机：避免共享数据/协作网络干扰；
- switchback：按时间窗口切换，适合共享资源但要处理时间趋势。

Agent 会写共享数据库、影响后续记忆或其他 Agent 时，SUTVA/无干扰假设容易被破坏，需 cluster randomization、隔离环境或专门建模 spillover。

### 7.2 实验协议

1. 预注册主要指标、MDE、样本量、停止规则和切片；
2. 做 A/A 测试验证分流、埋点和假阳性；
3. 检查 sample ratio mismatch；
4. 等待标签成熟，或使用预定义 sequential 方法；
5. 同时报告业务效应、CI、成本、尾延迟和安全门槛；
6. 分析 novelty、学习效应和长期回归。

不应为了实验把用户暴露给已知高风险候选；安全门禁优先于统计显著性。

## 8. Bandit 与自适应路由：省流量但推断更难

Bandit 会根据历史奖励把更多流量分给看似更好的版本，适合奖励快速、风险低且探索可接受的优化。Agent 场景的困难：

- 奖励常延迟、稀疏且是有偏 proxy；
- 策略改变后数据不再 iid；
- 早期噪声可能把流量锁到错误版本；
- 高风险失败不适合用探索来学习；
- context 与版本持续漂移，反事实支持不足。

必须记录每次动作的 policy、context、候选集合和 propensity：

```json
{
  "policy_version": "router-17",
  "chosen": "agent-B",
  "propensity": 0.23,
  "eligible_arms": ["A", "B"],
  "context_hash": "..."
}
```

这为 IPS、doubly robust 等 off-policy evaluation 提供必要条件，但仍依赖 overlap、正确 propensity 和混杂假设。极端权重和缺乏探索时，离线反事实估计会非常不稳定。

高风险动作应排除探索或加 hard guardrail/人工批准。

## 9. 在线 Judge：监控工具，不是业务真值

可采用风险分层：

```text
规则/小 Judge：大覆盖预筛
  ├─ 明确低风险 → 聚合监控
  ├─ 低置信/分歧 → 强 Judge
  └─ 高风险/潜在事故 → 人工 + 确定性 world-state 审核
```

必须：

- 在独立人工 anchor 上报告混淆矩阵和切片误差；
- Judge 版本变化做双跑和量尺桥接；
- candidate output 作为不可信数据，防 prompt injection；
- 记录采样概率，避免不同日期样本构成变化制造假趋势；
- 不因 Judge 低分自动执行不可逆动作。

“全量 Judge”也不等于全量真值，只是全量代理读数。

---

## 10. 漂移不是一个指标

| 漂移层 | 示例 | 检测/响应 |
|---|---|---|
| 输入 | 主题、语言、长度、攻击类型 | embedding/分类分布、PSI/MMD、分层抽样 |
| 环境 | 网页、库存、政策、API 行为 | dependency/version 监控、contract tests |
| 模型 | alias 后端、输出 schema、拒绝行为 | snapshot/route 记录、canary、回归 |
| 工具 | schema、权限、延迟、错误码 | consumer-driven contract、SLO |
| 策略 | prompt、router、memory、guardrail | config hash、实验与变更审计 |
| Judge | rubric、模型、阈值、parser | anchor 双跑、量尺桥接 |
| 标签 | 用户反馈率、成熟窗口、人工团队 | label-source 与 missingness 监控 |

输入分布变了不必然意味着性能变差；性能下降也可能发生在输入分布稳定但工具/政策已变的情况下。告警后需要 trace、版本和切片共同定位。

---

## 11. 反馈回流与独立证据隔离

线上失败应回流，但要避免“飞轮”污染所有评测：

```text
生产事件
├─ incident regression：具体失败，立即固化
├─ dev family：生成同族变体，用于修复
├─ future holdout pool：隐藏的同族新样本/未来时间切片
└─ training/finetune：若使用，记录 provenance 与授权
```

还要防止：

- 用户数据未经授权进入训练/评测；
- 线上 Judge 标签被当真值反复自训练，形成模型—Judge 共适应；
- 删除请求只删生产日志，没有传播到数据集/向量库/训练缓存；
- 直接把 canary 样本用于调参后仍把同一批当实验验证。

---

## 12. 回滚不是“把流量切回去”

Agent 可能有长任务和真实副作用。回滚 runbook 要回答：

1. 新请求如何立刻回基线；
2. 旧版本在途任务是否取消、继续还是交接；
3. 已发送/支付/写入怎样核对与补偿；
4. 新旧状态 schema、记忆和 checkpoint 是否兼容；
5. tool credential/权限是否撤销；
6. 事故 trace、receipt 和用户通知如何保全；
7. 修复后哪些 incident case 必须进入回归集。

自动 rollback 也要防抖和权限控制，避免监控噪声导致版本来回震荡。

## 13. 线上反模式

| 反模式 | 为什么错 | 修正 |
|---|---|---|
| 点踩率 = 失败率 | 反馈不是随机样本 | 记录 exposure + 随机审计样本 + 分层 |
| Judge 全量就有真值 | Judge 有偏差和漂移 | 人工锚点、world-state、量尺门禁 |
| 先全量再观察 | 爆炸半径不可控 | shadow → canary → 分层扩大 |
| 只看均值 | 稀有严重失败和小群体被掩盖 | p99、worst-slice、严重事件硬门槛 |
| 看到显著就停 | sequential peeking 膨胀假阳性 | 预定样本/序贯设计 |
| Bandit 自动最优 | 延迟奖励、探索风险、反事实偏差 | propensity、guardrail、OPE 审计 |
| 回滚只切路由 | 在途任务与副作用仍存在 | cancel/reconcile/compensate runbook |
| 失败全进同一 eval | holdout 被逐题优化 | regression/dev/hidden future 分流 |

## 14. 生产发布清单

- [ ] 主要业务 outcome、代理指标和 label maturity 已定义。
- [ ] Shadow 中所有写工具被虚拟化并验证无副作用。
- [ ] Canary 风险切片、暴露上限、停止与扩大条件已预注册。
- [ ] 分流单位、A/A、SRM、功效和 sequential 规则已准备。
- [ ] 用户反馈 exposure、采样概率和延迟 join 可追踪。
- [ ] Judge 已在人工 anchor 上校准且版本可桥接。
- [ ] 输入/环境/模型/工具/策略/Judge/标签漂移分别监控。
- [ ] 回滚覆盖新请求、在途任务、状态兼容和副作用补偿。
- [ ] 线上回流不会污染 locked holdout，数据授权与删除可传播。

---

## 15. 专题总论

可信的 Agent 评测不是一个排行榜分数，而是一条证据链：

```text
明确 estimand
→ world-state oracle + 风险不变量
→ 分层数据与独立 holdout
→ 校准过的 grader
→ 配对统计与不确定性
→ 可重建 trace
→ shadow/canary/受控实验
→ 延迟业务结果与安全回滚
```

面试中能把这条链讲清楚，就已经从“会用评测框架”进入“能设计可信 Agent 实验与发布系统”的层次。
