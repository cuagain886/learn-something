## 1. 核心心智模型

### 1.1 没有评估，就没有可迭代的 Agent ⭐⭐
这是整个专题、也是 Agent 工程最重要的一条：

> **如果你不能量化"这次改动让 Agent 变好还是变差了"，你就只能凭感觉调，永远在原地打转。**

Agent 有海量可调项（Prompt、工具定义、模式、上下文策略、模型、拓扑……），且**改一处会牵动全局**。评估是唯一能告诉你"改动有没有用"的客观信号。**评估能力，决定了你迭代的速度上限。**

### 1.2 评估 Agent ≠ 评估一次输出：要看"轨迹" ⭐
评估一个普通 LLM 调用，看"输出对不对"就行。但 Agent 是**多步过程**：

> 一个 Agent 可能**最终答案对了，但过程一塌糊涂**（绕了远路、调错工具又纠正、烧了 10 倍 token）；也可能**过程看着合理，最终却失败**。所以 Agent 评估要同时看：
> - **结果（Outcome）**：任务最终完成了吗？
> - **轨迹（Trajectory）**：过程中每一步的决策、工具选择、推理质量如何？

只看结果会漏掉"侥幸对/低效/不安全"的问题；只看轨迹会脱离"到底有没有解决问题"。**两者都要看。**

### 1.3 可观测是评估的前提，也是调试的第一现场 ⭐
> 要评估和调试 Agent，你必须能**看见它每一步实际做了什么**——收到什么上下文、想了什么、调了什么工具、返回什么、状态怎么变。

这就是**可观测性（Observability）/ 链路追踪（Tracing）**。没有 trace，你既无法定位失败发生在哪一环，也无法构建轨迹评估。**可观测是评估和调试的地基。**

      ↓

## 3. 本专题核心结论（剧透）

- **没有评估就没有可迭代的 Agent**——评估能力决定迭代速度。
- Agent 评估要**同时看结果（任务完成）和轨迹（工具选择/步骤效率/推理质量/动作安全）**，不能只看最终答案。
- **误差会累积**：95% 的单步成功率，8 步后端到端只剩约 66%——这解释了为什么多步 Agent 难做对，也是为什么要做**步级评估**。
- 评估方法分**确定性校验（能则优先，最可靠）、LLM 裁判（灵活但要校准防偏差）、人工（最准但贵）**；蒸馏小裁判让"全量评估线上流量"变得可行。
- **评估要进 CI**，像跑单元测试一样回归——这叫"评估驱动开发"。
- **可观测（trace/span + OpenTelemetry GenAI 语义约定）是评估和调试的地基**；工具按部署模式选（自托管 Langfuse/Phoenix、托管 LangSmith）。
