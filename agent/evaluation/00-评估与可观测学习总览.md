# Agent 评估与可观测性 · 学习总览

> 这是 [INDEX.md](../INDEX.md) 阶段 6 的展开专题。目标不是学会几个“Agent 指标”，而是能回答：**这个 Agent 在哪个总体、哪个环境和哪个风险约束下更好？证据是否独立、可复现、可校准？上线后怎样限制爆炸半径并验证真实业务结果？**

---

## 0. 为什么 Agent Eval 是系统工程与实验科学

Agent 不是一次 `input → text`，而是：

```text
任务分布
  → Agent 策略（模型/prompt/工具/记忆/路由）
  ↔ 环境（数据库/API/网页/用户/其它 Agent）
  → 状态变化、artifact、回复与副作用
  → oracle / grader / 延迟业务标签
  → 发布或回滚决策
```

因此评测必须同时处理：

- **决策论**：成功、成本、延迟和严重失败如何权衡；
- **实验设计**：测哪个总体，怎样控制 Agent/环境随机性；
- **测量科学**：oracle、LLM Judge 和人工标签有什么误差；
- **统计推断**：效应量、置信区间、MDE、配对与多重比较；
- **分布式可观测**：跨工具、队列、handoff 和副作用保留因果证据；
- **安全发布**：shadow、canary、kill switch、补偿和回滚；
- **数据治理**：评测污染、敏感 trace、保留与删除传播。

只报“成功率 85%”无法支持上线；需要说明这个数字怎样产生、误差多大、哪些失败被平均隐藏，以及线上暴露后如何证伪。

## 2. 核心心智模型

### 2.1 先写 estimand，再选指标

\[
\theta = \mathbb E_{x\sim D,e\sim E,r\sim R}[Y(A,x,e,r)]
\]

任何正式评测都要说明：

- `D`：目标用户/任务分布；
- `E`：环境和故障分布；
- `R`：Agent、模型、调度的随机性；
- `Y`：由什么 world-state oracle 或 grader 判定结果。

数据集、重复次数和统计方法都应由它推导，而不是凭固定经验数。

### 2.2 结果、风险与诊断三层

```text
发布层：world-state success、严重失败、cost/success、p99
可靠层：pass@k、pass^k、恢复、重复副作用、coverage–risk
诊断层：动作/参数/证据/工具/记忆/路由/交接/循环
```

诊断分不能代替业务结果，综合分不能抵消安全硬失败。

### 2.3 Judge 是测量工具，不是真值

LLM Judge 有位置、长度、风格、自我偏好和漂移，也可能被候选输出注入。可信使用要求：

```text
原子 rubric → 独立人工 anchor → 混淆矩阵/分群误差
→ 阈值与 abstain → shadow → Judge 版本漂移门禁
```

人工也有分歧，需双标、adjudication 和一致性统计。确定性 oracle 同样要用已知正反例测试。

### 2.4 Trace 是执行证据，不是因果证明

可观测应记录可见输入输出、工具调用、状态版本、策略/权限、artifact/receipt、handoff links 和结果验证。不要把隐藏 chain-of-thought 当作必须采集或可信审计证据。

Trace 能定位“失败怎样发生”，但“长轨迹导致失败”等因果结论仍需要配对实验、消融或随机化。

### 2.5 上线是逐步扩大暴露的实验

```text
locked offline eval
  → shadow（不产生真实副作用）
  → risk-scoped canary
  → A/B 或分层扩大
  → mature business labels
```

每一步都有预定义停止/推进条件、爆炸半径和 rollback/reconciliation runbook。

```text

 ↓

 ↓
```

1. 估计目标和任务 taxonomy；

3. 多层指标卡；
4. Judge anchor set 与混淆矩阵；
5. dev/regression/locked split；
6. OTel trace schema 与隐私策略；
7. canary gate 与回滚 runbook。

## 4. 必须掌握的公式与边界

### 4.1 多步条件成功示意

\[
P(success)=\prod_iP(S_i\mid S_{<i})
\]

只在步骤均必要、事件定义清楚时有解释价值；真实 Agent 有相关错误、分支、恢复和副作用，端到端仍需直接实测。

### 4.2 至少一次与持续可靠

对任务 `i` 的 iid 单次成功概率 `p_i`：

\[
pass@k_i=1-(1-p_i)^k,\qquad pass^k_i=p_i^k
\]

`pass@k` 只有在允许多试且有 selector 时才有产品意义；高可靠自动化更关心 `pass^k` 和严重失败。

### 4.3 校准与选择性自动化

\[
BS=\frac1N\sum_i(q_i-y_i)^2,
\qquad risk(\tau)=P(failure\mid q\ge\tau)
\]

模型的置信度必须被校准，abstain 阈值由 coverage、人工容量和失败损失共同决定。

### 4.4 每成功任务成本

\[
cost/success=\frac{\sum_i cost_i}{\sum_iY_i}
\]

它避免“便宜但总失败”的版本看起来成本更低。仍要配合成功率约束和 Pareto frontier。

## 5. 面试追问树与回答模板

| 追问层级 | 典型问题 | 回答必须落到 |
|----------|----------|--------------|
| 定义 | “Agent 成功率”究竟在估计什么？ | 目标总体、任务/环境分布、版本、预算、随机性和成功 oracle；即 estimand，而非一个脱离语境的百分比 |
| 机制 | 为什么 final answer Judge 不足以评有副作用的 Agent？ | 文案可能正确而数据库状态错误；优先检查 world state、receipt、安全不变量，再用 trace 定位因果链 |
| 反例 | 平均分显著上升，为什么仍可能不能上线？ | worst slice/CVaR 变差、关键风险 recall 下降、成本或尾延迟越界、环境漂移、Judge 偏差或多次试验不稳定 |
| 落地 | 如何证明新编排/模型“真的更好”？ | 同任务同环境配对、锁定 manifest、消融单变量、效应量与 CI、MDE/非劣界、locked holdout |
| 评测 | 离线通过后怎样在线验证且可回滚？ | shadow → 风险分层 canary → 必要时 A/B；预注册 guardrail、延迟标签、kill switch、在途对账与补偿 |

当被问“你如何评测一个 Agent”，不要只列指标。可以按以下顺序回答：

1. 定义目标总体、环境和成功/损失函数；
2. 用真实 world state、可执行测试和风险不变量构造 oracle；
3. 设计流量加权、风险切片、重复 trial 与 `pass^k`；
4. 开放质量才用 Judge，并用人工 anchor、混淆矩阵和换序校准；
5. dev/regression/locked holdout 分离，做 group split、污染检查；
6. 候选/基线在相同任务环境配对，报告效应量、CI、MDE 和非劣门槛；
7. 用版本化 trace 保留动作、状态、证据、receipt 和 handoff；
8. 经 shadow、risk-scoped canary、必要的 A/B 逐步发布；
9. 等待延迟业务标签成熟，校正反馈选择偏差；
10. 预置 kill switch、在途任务 reconciliation 和副作用补偿。

## 6. 本专题核心结论

- Agent Eval 是**对闭环系统做实验**，不是对最终文案打分。
- 先定义 estimand；“成功率”必须绑定任务、环境、随机性、oracle 和版本。
- 有行动能力时，**world-state oracle 与安全不变量优先**。
- `pass@k` 衡量多试至少一次成功，`pass^k` 衡量连续一致成功；二者产品含义相反。
- Judge 必须经人工锚点、混淆矩阵、偏差控制和版本漂移门禁。
- 独立 holdout、配对设计、CI、MDE、多重与序贯控制共同防止假提升。
- OTel GenAI 是重要方向，但截至 2026-07 已迁独立仓库且仍快速演进，应钉版本并保留业务扩展层。
- Trace 支持重建与诊断，不能自动证明因果；原文内容应按敏感等级 opt-in。
- 线上反馈有选择偏差且标签延迟；shadow/canary/A-B 各有不同证据边界。
- 回滚必须处理在途任务、状态兼容和已发生副作用，而不只是切流量。
