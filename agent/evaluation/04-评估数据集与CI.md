# 04 · 评估数据集与 CI：防污染、统计门禁与可复现发布

> 目标：把“评估进 CI”从一句口号落成完整实验协议：数据如何分层、怎样隔离 locked holdout、如何比较候选与基线、何时样本量足够，以及怎样避免随机波动、重复偷看和评测污染制造假提升。

---

## 1. Eval case 不是“问题 + 标准答案”

Agent 任务必须把环境、oracle 和风险约束一起版本化：

```yaml
id: refund-017
task: "用户要求退回重复收取的 86 元"
initial_state_ref: fixtures/refund-017-v3.json
allowed_tools: [get_order, get_policy, propose_refund, execute_refund]
success_oracle: safe_refund_v7
hard_invariants:
  - refund_count == 1
  - actor_scope in allowed_scopes
  - executed_proposal_hash == approved_proposal_hash
soft_rubric: user_explanation_v2
fault_profile: execute_timeout_after_commit
metadata:
  domain: after_sales
  difficulty: hard
  risk: high
  policy_version: 2026-06
provenance:
  source: sanitized_production_incident
  collected_at: 2026-07-03
  content_hash: sha256:...
```

任务文本相同但初始数据库、时钟或工具故障不同，实际上是不同实验条件。

## 2. 五类数据分区，各自职责不同

| 分区 | 用途 | 团队可见性 | 能否反复调参 |
|---|---|---|---|
| Train/生成集 | 训练分类器、合成任务、示例 | 可见 | 可以 |
| Dev | prompt/工具/策略迭代与错误分析 | 可见 | 可以，但要记录试验次数 |
| Regression | 固化已修 bug 和关键不变量 | 可见 | 可以，目标是防回归 |
| Locked holdout | 独立估计泛化、发布决策 | 限制访问 | 不应按样本逐条调参 |
| Challenge/red-team | 极端、对抗和新型风险 | 部分隐藏/轮换 | 仅用于专项风险判断 |

线上监控样本是第六类证据，但它受选择偏差、延迟标签和环境漂移影响，不能直接替代 locked holdout。

### 2.1 为什么“每修一个 bug 加一条”仍不够

这条原则适用于 regression set；如果同一失败也直接加入最终 holdout，并在其上持续优化，holdout 就失去独立性。正确做法是：

- 将具体失败加入回归集；
- 将其抽象成同族变体，部分进入 dev，部分保留到后续 holdout/challenge 刷新；
- 按时间批次保留未来数据，检验是否只是记住旧模式。

## 3. 从目标总体做分层，而不是随手收集题目

先定义生产任务 taxonomy，例如：

```text
业务域 × 难度 × 风险 × 语言 × 工具故障 × 上下文长度 × 用户权限
```

数据集需要同时服务三种估计：

1. **流量加权总体表现**：反映实际用户体验；
2. **宏平均/分层表现**：避免高流量简单题掩盖小切片；
3. **风险加权表现**：放大低频高损失事件。

训练/开发可以主动过采样困难和失败样本；最终报告时必须说明权重如何映射回目标总体。否则“50% 都是红队题”的评测成功率不能被解释成生产成功率。

---

## 4. 数据来源与 provenance

### 4.1 人工策划

适合业务关键路径和不可接受失败。关键不是固定“至少多少条”，而是覆盖目标分层并达到所需统计精度。几十条可以启动错误发现，但通常不足以证明小幅提升或低概率安全风险。

### 4.2 合成数据

适合系统组合边界：参数缺失、工具超时、并发冲突、政策版本和注入变体。必须验证：

- 任务是否可解、是否符合真实工具能力；
- 难度是否只是词面复杂；
- 生成模型是否把答案模式泄漏给 Agent；
- 合成分布与生产分布差异；
- oracle 是否独立于生成模型。

### 4.3 线上样本

最接近真实分布，但要做脱敏、权限和保留期治理。显式差评会过采样愤怒用户，沉默用户和成功任务可能缺失，不能把差评集合当作总体随机样本。

所有样本应保存来源、时间、转换链、标注版本、授权/脱敏状态和内容 hash，支持污染审计与删除传播。

## 5. 污染与近重复检测

### 5.1 泄漏渠道

- holdout 样本进入 prompt 示例、fine-tuning 或检索索引；
- 团队反复查看失败并逐题改规则；
- 同一线上会话的近重复被拆到 dev 与 test；
- 合成器从 test 模板改写出词面不同但语义相同的题；
- grader/reference 被 Agent 通过环境间接读取；
- 公共 benchmark 可能已出现在模型预训练或互联网资料中。

### 5.2 防护

1. 内容 hash + 数据血缘；
2. exact dedup、归一化文本 dedup；
3. embedding/MinHash 等近重复候选检索，再人工核查；
4. 按用户、会话、事故族或模板 group split，避免同族跨集；
5. holdout 访问审计与有限揭榜；
6. 时间切分和新环境状态；
7. 对公开 benchmark 结果标注 contamination uncertainty。

近重复阈值不是越严越好：误删真实分布的常见模式也会让测试失真，应保存匹配依据并抽检。

## 6. 比较候选与基线：优先配对设计

让 A/B 在相同任务、相同环境快照和 seed 上运行。令：

\[
d_i = Y_i^{(B)}-Y_i^{(A)}
\]

目标是估计平均配对差 `Δ=E[d_i]`，而不是分别估两个大方差均值再相减。配对能抵消任务难度差异。

### 6.1 二元成功指标

对每个配对任务，关注：

| | B 成功 | B 失败 |
|---|---:|---:|
| A 成功 | n11 | n10 |
| A 失败 | n01 | n00 |

只有 `n01`（B 修复）与 `n10`（B 回归）决定配对差。可用 McNemar 检验评估二元配对差；同时报告效应量 `(n01-n10)/N` 和置信区间，不能只给 p-value。

### 6.2 连续/复合指标

- 配对 bootstrap：按任务而不是按单次 trial 重采样；
- 若每任务多次运行，可用层级 bootstrap 或混合效应模型处理任务内相关；
- 长尾成本/延迟可比较分位点和超阈值率，不只比较均值。

随机重复运行不是独立新任务。把同一题 20 次当作 20 个独立样本会产生伪精确。

## 7. 置信区间、MDE 与功效

### 7.1 为什么“涨了 2 个点”不够

如果样本小或任务方差大，2 个点可能只是噪声。发布前应预先定义：

- 最小有业务意义的提升 `MDE`；
- 可接受的一类错误率 `α`；
- 目标功效 `1-β`；
- 基线成功率、任务相关性与预计失访/无效率；
- 安全/成本等非劣门槛。

再据此估算所需任务数和每任务 trial 数。低概率严重事件通常无法仅靠普通随机样本证明安全，需要风险过采样、故障注入、红队和形式化不变量共同覆盖。

### 7.2 Gate 应同时看效应与不确定性

示例：

```yaml
release_gate:
  primary:
    metric: safe_world_state_success
    rule: lower_95ci_delta >= 0.01
  non_inferiority:
    p95_latency_delta: upper_95ci <= 300ms
    cost_per_success_delta: upper_95ci <= 0.05
  hard:
    new_critical_security_failures: 0
```

这比“分数高于 85%”更能表达决策：主结果至少有实质提升，且成本/尾延迟没有超出容忍边界。

---

## 8. 多重比较与反复偷看

如果同时检查 30 个指标、20 个切片，总有几个会偶然显著。常用控制：

- 预注册一个或少数 primary metrics；
- 其余标为 secondary/exploratory；
- 对正式推断使用 Holm、Benjamini–Hochberg 等多重校正（选择取决于控制 FWER 还是 FDR）；
- 切片发现用于提出假设，再在新数据验证；
- 不要挑最好看的 seed、Judge 或时间窗口汇报。

每跑一小批就看结果，并在“刚好显著”时停下，会膨胀假阳性。需要早停时，应采用预先设计的 group-sequential、alpha-spending 或始终有效置信序列，而不是普通固定样本 p-value。

## 9. CI 分层：快检查、统计评测与发布验证

```text
PR（分钟级）
├─ schema/契约/不变量单测
├─ 小型确定性 smoke set
└─ 历史严重 bug regression

Nightly（小时级）
├─ 分层 dev/regression 全集
├─ 多 seed、故障注入、Judge 校准检查
└─ 成本/延迟/安全切片

Release candidate
├─ locked holdout（受控揭榜）
├─ 新旧版本配对统计检验
├─ manifest、数据和 grader 审计
└─ shadow/canary 与回滚条件
```

不是每个 PR 都必须跑昂贵 holdout。频繁触碰 holdout 本身就是过拟合渠道。

---

## 10. Flaky：先分类，不能用“多跑几次取最好”

| 来源 | 识别 | 处理 |
|---|---|---|
| Agent 随机 | 相同环境不同 seed 改变结果 | 预定多 trial，报告分布 |
| 环境随机 | 相同 Agent seed 工具/模拟器不同 | 固定快照；单独压力测试 |
| 基础设施故障 | reset、timeout、parser、限流 | 标为 eval-infra，修 harness 后重跑 |
| 题目歧义 | 人工/多个 grader 高分歧 | 修 rubric、标 invalid 或隔离 |
| 真正脆弱 | 微小扰动导致行为翻转 | 保留为鲁棒性失败，不应“去 flaky” |

可以隔离坏题或基础设施错误，但必须保留数量、原因和审计记录。不能删除所有不稳定失败来美化成功率。

## 11. Reproducibility manifest

每次正式评测应产出：

```json
{
  "run_id": "eval-20260719-rc2",
  "agent_commit": "...",
  "agent_config_hash": "...",
  "model_route": ["provider/model-snapshot"],
  "dataset": "refund-holdout-v5",
  "dataset_hash": "...",
  "environment_image": "sha256:...",
  "tool_schema_hash": "...",
  "grader_versions": ["safe_refund_v7", "judge_v4"],
  "seeds": {"agent": "...", "environment": "..."},
  "sampling_plan": "paired-5-trials-v2",
  "analysis_code_commit": "..."
}
```

同时保存逐任务结果和缺失/无效原因，不能只保留汇总分。

## 12. 面试高频追问

**问：为什么不固定 50 条黄金集？**

它可用于启动错误发现，但样本量取决于目标效应、方差、成功率、切片和风险。想证明 1–2 个百分点提升或极低严重失败率，通常需要远多于几十条，或使用更有力的配对/风险实验。

**问：CI 中候选成功率高 3%，为什么不能直接合并？**

要确认相同任务/环境配对、置信区间、MDE、是否多重挑选、Judge 是否同量尺，以及安全、成本和尾延迟是否回归。

**问：公开 benchmark 分高说明生产强吗？**

只能说明该 benchmark、该 harness 和可能受污染的公开分布上的表现；还需领域 world-state eval、工具/策略版本、成本和风险验证。
