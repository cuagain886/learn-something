# 04 · 评估数据集与 CI

> 目标：掌握怎么**建 Agent 评估集**、怎么把评估**放进 CI 做回归**——也就是"评估驱动开发（Eval-Driven Development）"。没有评估集和 CI，前面的指标和方法都落不了地。

---

## 1. 为什么需要评估集和 CI

[文档 00](00-评估与可观测学习总览.md) 说"没有评估就没有可迭代的 Agent"。但评估要落地，需要两个东西：
- **评估集（Eval Dataset）**：一批"任务 + 期望"，作为衡量的标尺。
- **跑评估的流程（最好在 CI 里）**：每次改动自动跑一遍，看指标涨跌。

> 目标心态：**像对待代码的单元测试一样对待 Agent 评估**——改完代码跑测试，改完 Agent 跑评估集。这就是"评估驱动开发"。

---

## 2. 评估集长什么样

Agent 评估集的每条样本通常包含：

```
{
  "task": "用户的输入/目标",                  // 必需
  "expected_outcome": "期望的结果/成功标准",   // 用于结果级评估
  "expected_tools": ["应该用到的关键工具"],     // 用于轨迹级评估（可选）
  "reference_trajectory": "理想路径的关键动作",  // 可选，注意不要求精确匹配
  "context": "初始状态/可用工具/环境",          // 复现所需
  "metadata": {"category": "...", "difficulty": "..."}  // 便于分类统计
}
```

- 结果级评估要 `expected_outcome`（或成功判定逻辑）。
- 轨迹级评估可选地给 `expected_tools` / 关键动作（不是精确路径，见 [文档 02](02-Agent评估的维度与指标.md)）。
- `metadata` 让你能**分类统计**（如"简单任务 95%、复杂任务 60%"），定位薄弱面。

---

## 3. 评估集从哪来（三个来源）

### 3.1 黄金集（Golden Dataset）—— 人工精标
人工挑选、标注的高质量样本。质量最高、最可信，但人工成本高。

> **建议**：哪怕只有 **30~50 条**精心挑选、覆盖典型场景和边界情况的样本，也远胜于没有。**先从小做起**，随迭代逐步扩充。（和 [rag/07](../rag/07-RAG评估与可观测性.md) 一个建议。）

### 3.2 合成生成（Synthetic）—— LLM 造
用 LLM 批量生成"任务 + 期望"：给它你的工具集/场景描述，让它生成多样的测试任务。
- **优点**：快速规模化、覆盖广。
- **缺点**：质量参差，**必须抽样人工审核**，剔除不合理/太简单的。
- 实用做法：合成生成 + 人工筛选，兼顾规模和质量。

### 3.3 线上真实流量 —— 最真实
从生产里捞真实用户任务（[文档 06](06-线上持续评估与反模式.md)），尤其是**失败案例**，回流成评估样本。
- **最贴近真实分布**，且能把"线上踩过的坑"固化成回归用例。
- 需要做好日志/trace 和脱敏（[INDEX 阶段7](../INDEX.md)）。

---

## 4. 评估集要覆盖什么（别只测"正常情况"）⭐

新手常只放"理想任务"，结果上线被各种意外打爆。一个好的评估集要覆盖：

- **典型场景（Happy Path）**：最常见的正常任务。
- **边界用例（Edge Cases）**：模糊的、信息不全的、超长的、多意图的输入。
- **失败/异常路径**：工具会失败时、检索为空时、用户给错信息时——Agent 是否优雅处理（[agent-core/01](../agent-core/01-Agent循环与ReAct.md) 的失败处理）。
- **安全/对抗用例**：prompt 注入尝试、诱导越权动作——Agent 是否守住（[INDEX 阶段7](../INDEX.md) 的红队测试）。
- **不同难度分层**：简单/中/复杂，便于看"复杂任务掉到多少"（呼应误差累积，[文档 01](01-为什么评估Agent更难.md)）。

> 每修复一个线上 bug，就**把它加成一条评估用例**——这样它永远不会再悄悄回归。这是评估集随时间变强的关键。

---

## 5. 评估进 CI：回归测试 ⭐

把评估集接进 CI/CD，每次改动（改 Prompt、换模型、改工具、调模式）自动跑：

```
改动 → CI 触发 → 在评估集上跑 Agent → 计算指标（任务完成率/工具准确率/成本…）
     → 和基线对比 → 涨了？合并。 跌了？拦截，回去查。
```

- **设质量门槛（Gate）**：如"任务完成率不得低于基线 X%、不得引入新的安全失败"，不达标就**阻止合并**。
- **对比而非绝对**：关注"相对基线涨跌"，因为绝对分受评估集影响。
- **控制成本/时间**：全量评估可能慢且贵——可分层（PR 跑小核心集，夜间/发版跑全量）。
- **注意不确定性**：CI 里评估也受 [文档 01](01-为什么评估Agent更难.md) 的随机性影响，关键用例可多次跑或设容差，避免 flaky。

> 这把"我感觉这次改好了"变成"任务完成率 78%→85%，工具准确率持平，成本-10%，可以合并"——**这就是工程化。**

---

## 6. 评估驱动开发（Eval-Driven Development）的工作流

把以上串成一个迭代闭环：

```
1. 定义任务和成功标准 → 建初始评估集（30~50条，覆盖典型+边界+失败+安全）
2. 跑基线，记录指标（任务完成/工具准确/成本/延迟）
3. 改动一处（Prompt/工具/模式/上下文策略/模型）
4. 跑评估集，对比基线 → 涨了保留，跌了回退
5. 线上发现新失败 → 加成新评估用例 → 回到 3
6. 定期人工校准 LLM 裁判、扩充评估集
```

> 核心纪律（贯穿所有专题）：**每一个改动都用评估验证收益**。这是 [agent-core/06](../agent-core/06-模式选择与组合.md)、[context-engineering/05](../context-engineering/05-工程实践与反模式.md)、[orchestration/06](../orchestration/06-生产实践与反模式.md) 反复强调的"用数据决定"的落地方式。

## 7. 常见坑

- **没有评估集就开始调** → 所有优化靠猜（[文档 00](00-评估与可观测学习总览.md) 的头号原则）。
- **评估集只有 happy path** → 上线被边界/失败/对抗用例打爆。
- **合成数据不审核** → 题目质量差，评估结论失真。
- **评估集不随迭代扩充** → 修过的 bug 悄悄回归。修一个加一条。
- **评估集泄漏进优化**（反复在同一批上调参过拟合）→ 留独立 held-out 集。
- **不进 CI、靠手动跑** → 容易忘、不一致、回归漏网。
- **CI 里 flaky** → 没考虑不确定性。关键用例多跑或设容差。
- **评估集不代表真实分布** → 离线涨点、线上翻车。多用线上真实流量。

---

## 8. 本章小结

- 评估落地需要**评估集 + 跑评估的流程（CI）**，目标是"像跑单元测试一样跑评估"——**评估驱动开发**。
- 评估样本含 task / 期望结果 / 关键工具 / 上下文 / 元数据；元数据支持分类统计定位薄弱面。
- 数据来源：**黄金集（精标，30~50 条起步）+ 合成生成（规模化，需审核）+ 线上真实流量（最真实，含失败回流）**。
- 评估集要**覆盖典型 + 边界 + 失败 + 安全 + 难度分层**，别只测正常情况；**每修一个 bug 加一条用例**。
- **评估进 CI 做回归**：设质量门槛、对比基线涨跌、分层控成本、处理 flaky。
- 工作流：建集→跑基线→改动→对比→线上失败回流→扩集，**每个改动用评估验证收益**。
