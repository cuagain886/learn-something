# 05 · 可观测性与追踪：从 span 树到可重建执行证据

> 目标：设计一套能回答“发生了什么、为什么失败、影响了什么”的 Agent 可观测系统，并理解 OpenTelemetry（OTel）GenAI 语义约定的当前成熟度、敏感内容治理、异步因果传播和 replay 的边界。

---

## 1. 可观测不等于把 prompt 全存下来

生产 Agent 需要同时回答四类问题：

1. **健康**：请求、错误、饱和度、成本、p95/p99 延迟怎样；
2. **执行**：走了哪条控制流、调了什么工具、状态如何变化；
3. **结果**：真实世界状态是否改变、是否出现重复副作用；
4. **治理**：谁以什么权限、基于哪个批准和证据执行了动作。

完整 prompt/completion 只是可能的证据之一，而且可能包含 PII、密钥、医疗/财务数据和受版权保护内容。**默认全量记录原文既不是可观测的必要条件，也通常不是安全默认值。**

更合理的设计是“结构化元数据默认采集、内容按风险与授权 opt-in、原文和 hash/引用分层存储”。

## 2. Trace、Span、Event、Log、Metric 与 Artifact

| 信号 | 语义 | Agent 示例 |
|---|---|---|
| Trace | 一次端到端因果工作单元 | 从用户请求到任务完成/挂起 |
| Span | 有开始/结束的操作 | 模型调用、工具调用、路由、审批等待 |
| Event | span 内的瞬时事实 | token stream error、重试、状态变更 |
| Log | 独立或关联 trace 的记录 | 策略拒绝、异常堆栈、审计事件 |
| Metric | 可聚合数值时间序列 | 成功率、p99、队列深度、cost/success |
| Artifact | 大型/持久结果 | 报告、代码补丁、截图、工具原始回执 |

不要把大型网页、文件或完整模型内容塞进 span attribute。span 里保存内容地址、hash、大小、分类和访问控制；artifact 由合适的对象存储和生命周期策略管理。

## 3. 推荐的 span 拓扑

```text
agent.run                             # 业务任务根 span
├─ context.assemble                   # 输入选择与预算
│  ├─ retrieval.query
│  └─ memory.read
├─ gen_ai.inference                   # 模型/响应调用
├─ tool.call                          # 外部动作
│  └─ http.client / db.client         # 现有 OTel 网络/数据库 span
├─ policy.evaluate                    # 权限/护栏
├─ approval.wait                      # 可跨很长时间，或以状态事件表示
├─ handoff.send ── link ── agent.run  # 跨 worker / 跨 Agent
├─ compensation.execute
└─ result.verify                      # world-state oracle
```

具体 span 名称应跟随团队固定的语义版本；这里表达的是职责，不是声称所有名称都已被 OTel 标准化。

### 3.1 Span 边界原则

- 有独立延迟、错误、重试或所有权的操作值得成为 span；
- 高频 token/chunk 不宜每个一个 span，可用 event/metric；
- 异步 fan-out/fan-in 要保留 parent/link，不能强行画成错误的同步树；
- 等待人类数小时不宜让所有后端无限保留活动 span，可持久化 task state，并在恢复时关联原 trace；
- 一次重试应有独立 attempt 属性/span，不能覆盖原失败。

## 4. Trace 不变量：先定义“必须可回答的问题”

埋点不是字段越多越好。可从不变量反推 schema：

### 4.1 可重建不变量

对任一高影响动作，必须能查询：

- `task_id / trace_id / run_id / attempt_id`；
- 动作前的提案 hash、批准 hash、执行 hash；
- 发起者、Agent 身份、有效权限/租约/策略版本；
- 工具 schema 与实现版本、幂等键；
- 输入状态版本与输出 receipt；
- 失败、重试、补偿和最终世界状态。

### 4.2 因果与顺序不变量

- 所有工具结果必须关联对应调用；
- handoff 接收必须能链接发送事件和 envelope 版本；
- join 结果要能关联所有采用/丢弃的分支；
- 重试必须保留同一逻辑操作 ID 和不同 attempt；
- 取消后仍完成的 late result 必须标记并被 reconciliation 处理；
- 最终答案必须关联它实际采用的证据/工具结果，而非所有可用上下文。

### 4.3 完整性不变量

```text
tool_call.started - tool_call.finished ∈ {0, 1}
成功完成的高影响 tool_call 必须有 receipt
任何 receipt 必须能映射到唯一 logical_action_id
被批准的 proposal_hash 必须等于实际执行的 proposal_hash
```

可以定期运行 trace-linter 检查这些不变量。没有完整性检查的 trace 可能只是在稳定地丢数据。

## 5. 最小字段模型

```yaml
identity:
  trace_id: ...
  span_id: ...
  task_id: ...
  run_id: ...
  logical_action_id: ...
  attempt: 2
versions:
  agent_commit: ...
  workflow_version: ...
  prompt_hash: ...
  model_snapshot: ...
  tool_schema_hash: ...
  policy_version: ...
  context_manifest_hash: ...
operation:
  kind: tool.call
  status: error
  error_type: timeout_after_commit
  start_time: ...
  duration_ms: 8200
effect:
  idempotency_key_hash: ...
  input_state_version: 19
  receipt_ref: artifact://...
  output_state_version: 20
privacy:
  content_capture: metadata_only
  data_classification: confidential
  retention_class: 7d
```

高基数字段（原始 query、用户 ID、tool args）不应直接成为 metric label；否则会造成时序系统成本爆炸和隐私泄露。它们应存在受控 trace/log/artifact 中，并使用 hash/tokenization 或访问代理。

## 6. OpenTelemetry GenAI：方向明确，版本仍需钉死

截至 2026-07：

- OTel 核心 semantic conventions 页面显示 1.43.0；
- GenAI 约定已经从核心 semantic-conventions 仓库页面迁移到独立的 [`open-telemetry/semantic-conventions-genai`](https://github.com/open-telemetry/semantic-conventions-genai)；
- 该独立仓库覆盖 GenAI client、Agent、MCP、provider-specific 的 spans/metrics/events；
- 仓库当前 README 的 Schema URL 仍标为 TODO，GitHub 页面也未显示正式 release。

这说明它是重要的互操作方向，但**不能承诺“按一次标准埋点，所有后端无损通用”**。不同 SDK、自动插桩库和后端对实验字段、events、内容捕获和 Agent/MCP 操作的支持可能不同。

工程策略：

1. 固定使用的 semantic-convention commit/tag/schema 版本；
2. 尽量采用稳定的 OTel 通用 HTTP/RPC/DB/error 属性；
3. 对尚未稳定的 GenAI/Agent 字段建立内部兼容层；
4. 增加业务字段，如 `task.id`、`policy.version`、`proposal.hash`；
5. 在候选后端做字段/links/events/采样的互通测试；
6. 保存 schema migration，避免升级后历史查询静默失效。

OTel 解决信号传输与公共语义的一部分，不替你定义业务成功、权限不变量或数据保留政策。

## 7. 跨进程、异步与多 Agent 传播

### 7.1 W3C Trace Context

HTTP 跨服务传播通常使用 W3C `traceparent`/`tracestate`。这使不同服务能把 span 关联到同一 trace，但要注意：

- 外部不可信调用方可伪造 trace context，应验证/重建安全边界；
- trace ID 不是认证凭证，绝不能据此授予权限；
- 消息队列可能一条消息多个消费者，应使用 messaging 语义和 span links；
- 批处理聚合多个上游时，一个 parent 不足，应关联多个 links。

### 7.2 Handoff/A2A

跨 Agent envelope 应包含或关联：

```json
{
  "task_id": "...",
  "handoff_id": "...",
  "traceparent": "...",
  "sender_span_id": "...",
  "context_manifest_hash": "...",
  "artifact_refs": ["..."],
  "deadline": "...",
  "policy_context_ref": "..."
}
```

如果跨组织不允许共享 trace ID，也应通过受控 correlation ID 和双方审计 receipt 建立映射，而不是把全部内部 trace 暴露给对方。

## 8. 内容采集与安全治理

### 8.1 默认策略

| 数据 | 默认 | 例外 |
|---|---|---|
| 模型/工具版本、token、延迟、status | 记录 | 极少 |
| prompt/completion 原文 | 不默认全量 | 获授权的调试/评测采样 |
| tool args/results | schema 摘要 + hash/ref | 低敏且短小可白名单 |
| 用户/会话标识 | 假名化/tokenize | 受控审计系统保存映射 |
| secrets/auth header | 永不记录 | 无 |
| embedding/vector | 按潜在个人数据治理 | 不能假设不可逆 |

### 8.2 采集管线

```text
instrumentation
  → allowlist/drop known secrets
  → DLP/classification
  → tokenize/pseudonymize
  → sampling
  → encryption + tenant isolation
  → retention/deletion policy
  → audited analyst access
```

仅在 UI 上“打码”但后端仍存原文，不算脱敏。还要验证备份、导出、缓存和下游评测集的删除传播。

### 8.3 Cardinality 与成本

- metric label 保持低基数；
- 大内容以 artifact ref 保存；
- span attribute 设长度上限并记录 `truncated=true` 与原内容 hash；
- 对 stack trace、tool output 做独立配额；
- 监控 telemetry 自身的丢弃率、队列和成本。

## 9. 采样：错误与稀有风险不能被平均丢掉

### 9.1 Head sampling

请求开始时决定是否采样，开销低，但尚不知道结果是否失败，容易漏掉罕见错误。

### 9.2 Tail sampling

观察完整 trace 后按 error、延迟、成本、风险或特定工具决定保留，诊断价值高，但 collector 需要缓存和资源。

### 9.3 分层混合策略

```text
100%：关键安全事件、越权拦截、高影响写动作、eval/incident trace
高比例：错误、超时、p99、高成本、低置信、Judge 分歧
分层抽样：各业务/语言/租户/模型/工具版本
低比例：稳定低风险成功流量
```

必须记录 sampling probability/decision，线上统计若受不等概率采样影响，分析时需要权重。只保存失败 trace 会使你无法估计失败率，也缺少正常对照。

## 10. Replay、重放与反事实的边界

### 10.1 三种“重放”不是一回事

1. **Trace visualization**：重看历史事件，不重新执行；
2. **Deterministic replay**：用记录的工具响应/环境快照重建同一执行；
3. **Counterfactual evaluation**：在相同任务环境上运行另一个 Agent/策略。

Trace 只有在保存了模型/工具/环境版本、实际上下文、状态、随机 seed 和外部响应时，才可能接近 deterministic replay。第三方模型和实时网页经常无法完全复现。

### 10.2 重放有副作用风险

生产 trace 不能直接对真实支付、邮件、删除 API 重放。应使用：

- read-only/sandbox environment；
- recorded response 或 fake tool；
- 幂等键与 side-effect firewall；
- 明确禁止 replay credential；
- 环境 reset 和 artifact 隔离。

### 10.3 Trace 不能证明因果

“失败 trace 平均多 5 步”可能是难任务同时导致多步与失败。trace 支持假设生成和机制检查；要证明改动有效，仍需配对评测、消融、shadow 或随机实验。

## 11. 可观测平台选型：先验证能力，不背产品表

产品功能变化很快。选型 spike 至少验证：

- OTel OTLP 接入、span links、events 和自定义属性是否无损；
- prompt/tool 内容能否字段级关闭、脱敏和按租户隔离；
- tail sampling、保留期、删除、导出和数据驻留；
- 高基数查询、长 trace、多 Agent DAG 与 artifact link；
- eval dataset、人工标注、grader 版本和 trace 回流；
- 自托管/托管运维成本、RBAC/SSO/审计、锁定风险。

Langfuse、Phoenix、LangSmith、Braintrust 与通用 APM 都可作为候选，但应以当前版本的 spike 结果而不是静态功能表做决策。
