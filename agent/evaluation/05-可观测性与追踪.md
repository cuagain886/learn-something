# 05 · 可观测性与追踪

> 目标：掌握如何"看见 Agent 内部发生了什么"——链路追踪（trace/span）、要记录什么、OpenTelemetry GenAI 语义约定，以及工具选型。可观测是评估和调试的地基。

---

## 1. 为什么可观测是地基

[文档 01](01-为什么评估Agent更难.md) 说 Agent 失败定位难、[文档 02](02-Agent评估的维度与指标.md) 的轨迹/步级评估都需要"知道每一步发生了什么"。这些都依赖**可观测性（Observability）**：

> **可观测 = 系统化地采集并分析 Agent 的动作、决策、上下文，让它的行为变得可理解、可控、可优化。** 它超越"系统健康"（CPU/内存），深入到**决策轨迹**——prompt、推理、工具调用、状态变化。

没有它：
- 出问题不知道在哪一步（黑盒）。
- 没法做轨迹评估（[文档 02](02-Agent评估的维度与指标.md)）。
- 没法捞线上真实/失败流量回流评估集（[文档 04](04-评估数据集与CI.md)）。

> **可观测是评估和调试的第一现场。** 一个不可观测的 Agent，几乎不可能在生产里迭代好。

---

## 2. 核心概念：Trace 与 Span ⭐

借用分布式系统的追踪概念：

- **Trace（追踪）**：一次完整的 Agent 执行（从用户请求到最终响应）的全过程记录。
- **Span（跨度）**：Trace 里的一个**步骤/操作**，可嵌套形成树状结构。

```
Trace（一次"调研并写报告"请求）
├─ Span: 接收请求 / 上下文组装
├─ Span: LLM 调用①（规划）        [输入prompt, 输出, token, 延迟]
├─ Span: 工具调用 web_search       [参数, 返回, 延迟, 成功/失败]
├─ Span: LLM 调用②（推理是否够）
├─ Span: 工具调用 fetch_page
│   └─ Span: 检索子操作（RAG）      [召回chunk, 分数]
├─ Span: Agent 交接 → 写作Agent    [带了什么上下文]   ← 多Agent
└─ Span: LLM 调用③（生成最终答案）  [输出, token, 延迟]
```

> 这个**嵌套的 span 树**就是 Agent 的"轨迹"。它让你能精确看到：每步做了什么、花了多少 token/时间、在哪一步出的错——直接支撑 [文档 02](02-Agent评估的维度与指标.md) 的轨迹/步级评估。

---

## 3. 要记录什么（埋点清单）⭐

对每个请求，一条完整的 trace 应包含：

| 类别 | 记录内容 |
|------|----------|
| **输入/上下文** | 原始 query、改写后 query、**每步实际进入上下文的内容**（[context-engineering/05](../context-engineering/05-工程实践与反模式.md) 强调的"调试第一现场"） |
| **LLM 调用** | 每次调用的 prompt、输出、模型、temperature、token 用量、延迟 |
| **工具调用** | 工具名、参数、返回、成功/失败、延迟 |
| **检索/记忆** | 召回了什么、分数、用了哪些记忆（[rag/](../rag/00-RAG学习计划总览.md)、[context-engineering/03](../context-engineering/03-Agent记忆系统.md)） |
| **状态/控制流** | 状态怎么变、走了哪条边、循环了几次（[orchestration/03](../orchestration/03-状态管理与控制流.md)） |
| **多 Agent** | 谁交接给谁、带了什么上下文（[orchestration/06](../orchestration/06-生产实践与反模式.md)） |
| **结果** | 最终输出、是否完成、总 token、总延迟、总成本 |
| **元数据** | 用户/会话 ID、时间戳、版本（便于按维度分析、复现、关联反馈） |

> 关键提醒（呼应 [context-engineering/05](../context-engineering/05-工程实践与反模式.md)）：**一定要记录"每步实际进入上下文的内容"**——排查"模型为什么这么决策"时，你必须知道它当时到底看到了什么。这是最容易漏记、又最关键的一项。

## 4. OpenTelemetry GenAI 语义约定 ⭐ 2026 的标准化方向

早期各家可观测工具的埋点格式各不相同，换工具就要重新埋点。2026 的方向是**标准化**：

> **OpenTelemetry（OTel）的 GenAI 语义约定**：为 AI 工作负载标准化 span 类型、属性名、指标定义。GenAI 可观测 SIG 从 2024 年 4 月启动，到 2026 初覆盖四个方面：**LLM 客户端 span、Agent span、事件（捕获 prompt/completion 内容）、指标**。

意义：
- **一次埋点，到处可用**：用标准 OTel 埋点，trace 能发往任意支持该约定的后端，**无需绑定某家 SDK**。
- **生态支持广**：LangSmith 已支持 OTel（可吃 OpenLLMetry 格式 trace）；Datadog、New Relic、Dynatrace 等也原生支持 GenAI 语义约定，OTel 埋点的 Agent 代码无需改 SDK 即可把数据发过去。
- **注意状态**：截至 2026 年初，多数 GenAI 语义约定仍是**实验性（experimental）**，API 尚未完全稳定——能用但要留意变动。

> 工程建议：**新项目优先按 OTel GenAI 语义约定埋点**，避免被单一厂商锁定；同时知道它还在演进中。

## 5. 可观测工具选型（2026）

| 工具 | 形态 | 特点 |
|------|------|------|
| **Langfuse** | 开源/自托管 | 专为 LLM 可观测打造，内置 prompt 管理、打分；2026 加了在线评估、prompt 版本、数据集工作流。支持 OTel |
| **Arize Phoenix** | 开源 | LLM 可观测 + 内置评估 + 实验跟踪。学习/自托管友好 |
| **LangSmith** | 托管 SDK | LangChain 出品，支持 OTel；trace + 评估 + 数据集一体 |
| **Braintrust** | 托管 | 评估 + 可观测，偏开发体验 |
| **Helicone** | 代理网关 | 零代码改动的成本/用量追踪（挂在 API 网关层） |
| **Datadog/New Relic/Dynatrace** | 通用 APM | 原生支持 GenAI 语义约定，适合已用这些 APM 的团队 |

### 按"部署模式优先、功能其次"选型 ⭐
```
要数据驻留/成本可控、想自托管   → Langfuse、Arize Phoenix
要快速上手 + 内置评估（托管）    → LangSmith、Braintrust
只想零改动追踪成本/用量         → Helicone（代理网关）
已重度使用某 APM               → 看它是否支持 GenAI 语义约定（多数已支持）
```

> 学习阶段推荐先用 **Phoenix 或 Langfuse**（开源、本地能跑、带评估），把 trace 跑起来、看懂一条 Agent 的执行轨迹长什么样。

## 6. 可观测 → 评估的闭环

可观测不只是"看"，它直接喂养评估（[文档 02-04](02-Agent评估的维度与指标.md)）：

```
线上 trace ──→ 提取轨迹 ──→ 轨迹/步级评估（工具选择、步骤效率…）
           ──→ 捞失败案例 ──→ 回流成评估用例（文档04）
           ──→ 采样 + LLM裁判 ──→ 线上质量持续监控（文档06）
           ──→ 关联用户反馈 ──→ 定位差评对应的轨迹问题
```

> 现代平台（Langfuse、Phoenix、LangSmith）**把可观测和评估做在一起**：trace 进来，可直接在上面跑评估、标注、回流数据集——这是 2026 的主流形态。

---

## 7. 常见坑

- **没有 trace 就想调多步 Agent** → 黑盒，抓瞎。可观测是地基。
- **只记最终输出、不记中间步骤** → 看不到轨迹，定位不了失败在哪步。
- **不记"每步进入上下文的内容"** → 没法解释模型为什么这么决策。最该记又最常漏。
- **自定义埋点格式、不用标准** → 换工具要重埋。优先 OTel GenAI 约定。
- **trace 里记录敏感数据不脱敏** → 隐私/合规风险（[INDEX 阶段7](../INDEX.md)）。
- **可观测和评估割裂** → trace 看了就完了，没喂回评估闭环。
- **采样太稀**（成本顾虑）→ 漏掉问题；可用蒸馏小裁判全量评（[文档 03](03-评估方法与LLM裁判.md)）。

---

## 8. 本章小结

- **可观测是评估和调试的地基**：采集 Agent 的决策轨迹（prompt/推理/工具/状态），让行为可理解、可定位。
- **Trace（一次执行）+ Span（嵌套的步骤）** 构成 Agent 的轨迹树，直接支撑轨迹/步级评估。
- 埋点要记全：输入/上下文（尤其**每步实际进入上下文的内容**）、LLM 调用、工具调用、检索/记忆、状态/控制流、多 Agent 交接、结果、元数据。
- **OpenTelemetry GenAI 语义约定**是 2026 标准化方向（LLM/Agent span + 事件 + 指标），一次埋点到处可用、避免厂商锁定，但仍在实验阶段。
- 工具按**部署模式优先**选：自托管(Langfuse/Phoenix)、托管(LangSmith/Braintrust)、网关(Helicone)；学习先用 Phoenix/Langfuse。
- 可观测要和评估**闭环**：trace → 轨迹评估 / 失败回流 / 线上监控 / 关联反馈。
