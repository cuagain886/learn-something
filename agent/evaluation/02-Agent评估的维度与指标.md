# 02 · Agent 评估的维度与指标

> 目标：搞清楚到底**评什么**。Agent 评估分三个层次——结果、轨迹、组件，每层有对应指标。读完能为自己的 Agent 设计一套评估指标。

---

## 1. 三个评估层次（总览）

```
┌─────────────────────────────────────────────────────────┐
│ ① 结果级（Outcome）：任务最终完成了吗？质量如何？          │ ← 最终信号
├─────────────────────────────────────────────────────────┤
│ ② 轨迹级（Trajectory）：过程中每步决策/工具/推理好不好？    │ ← 过程质量
├─────────────────────────────────────────────────────────┤
│ ③ 组件级（Component）：单个工具/检索/记忆/子Agent 各自如何？│ ← 定位根因
└─────────────────────────────────────────────────────────┘
```

> [文档 01](01-为什么评估Agent更难.md) 说过：**只看结果会漏掉"侥幸对/低效/不安全"；只看轨迹会脱离"到底解决没"。三层都要看，各有用途。**

---

## 2. 结果级指标（Outcome）

评"任务到底成没成、好不好"。

### 2.1 任务完成度（Task Completion / Goal Accuracy）⭐ 最重要的端到端信号
> Agent 有没有完成用户给的任务、达成目标？这是"Agent 到底有没有用"最清晰的端到端信号。

- 二元（成功/失败）或分级（完全/部分/未完成）。
- 怎么判定：有明确成功标准的（如"订到票""测试通过")可**确定性校验**；开放任务（"写好报告")用 **LLM 裁判**或人工按 rubric 打分（[文档 03](03-评估方法与LLM裁判.md)）。

### 2.2 最终答案质量
- **正确性（Correctness）**：答案事实对不对（对照 ground truth 或 LLM 裁判）。
- **相关性（Relevance）**：是否切题回应了请求。
- 若是 RAG 类，还看 **Faithfulness（忠实度）/ 是否有出处**——直接用 [rag/07](../rag/07-RAG评估与可观测性.md) 的指标，本专题不重复。

---

## 3. 轨迹级指标（Trajectory）⭐ Agent 评估的特色

评"过程走得好不好"。业界（如 ai-evaluation SDK）常用的一组**轨迹指标**：

| 指标 | 含义 | 为什么重要 |
|------|------|-----------|
| **工具选择准确率（Tool Selection Accuracy）** | 每步是否选对了工具、传对了参数 | Agent 能力的关键；选错工具一步错步步错。模板化评估通常能到 70~90% precision |
| **步骤效率（Step Efficiency）** | 有没有用最少必要步数完成，有无绕路/重复 | 直接关系成本、延迟，也反映推理质量 |
| **目标进展（Goal Progress）** | 每一步是否在朝目标推进 | 检测"跑偏/计划放弃"（[agent-core/01](../agent-core/01-Agent循环与ReAct.md)） |
| **推理质量（Reasoning Quality）** | 每步的思考是否连贯、有据 | 步级 faithfulness，定位"哪一步的逻辑崩了" |
| **动作安全（Action Safety）** | 有没有执行危险/越权动作 | 安全护栏的评估面（[INDEX 阶段7](../INDEX.md)） |
| **轨迹总分（Trajectory Score）** | 整条路径的综合质量 | 一个汇总视角 |

### 步级评估（Step-level）⭐ 对抗误差累积的关键
[文档 01](01-为什么评估Agent更难.md) 讲过误差累积（95%×8≈66%）。**步级评估就是把端到端那个数字拆开，看到底是哪一步在拉低整体。**

> 没有步级评估，你只看到"端到端 66%"，却不知道是第 3 步的工具老选错、还是第 6 步老跑偏。**步级指标让你能精准修那一步，而每步的小改进会被长链条放大成大的端到端收益。**

### 轨迹评估的两种参照方式
- **有参考轨迹（reference-based）**：和一条/多条"理想轨迹"比（但注意 [文档 01](01-为什么评估Agent更难.md) 的"无唯一路径"——别要求精确匹配，比的是"是否包含必要的关键动作")。
- **无参考（reference-free）**：用 LLM 裁判直接评"这条轨迹合不合理、高不高效"，无需预设标准路径。开放任务常用。

---

## 4. 组件级指标（Component）

把 Agent 拆成组件，各自评——用于**定位根因**和**单独优化**（像单元测试）。

- **检索组件** → 用 [rag/07](../rag/07-RAG评估与可观测性.md) 的 Context Recall/Precision、Faithfulness。
- **记忆组件** → 该记的记住没（召回）、取回的相关吗（精度）、过时的失效没（[context-engineering/03](../context-engineering/03-Agent记忆系统.md)）。
- **单个工具** → 调用成功率、参数正确率、返回质量。
- **多 Agent 的交接** → 路由/交接决策对不对（[orchestration/06](../orchestration/06-生产实践与反模式.md)）。
- **单个子 Agent** → 在它那一摊上单独评。

> 组件级 + 轨迹级 + 结果级配合：**结果级告诉你"有没有问题"，轨迹级告诉你"问题在哪一步"，组件级告诉你"那一步的哪个部件坏了"。** 逐层下钻定位。

---

## 5. 横切指标：成本、延迟、安全

除了"对不对"，生产还要评"代价"和"安不安全"：

- **成本**：完成一个任务消耗多少 token / 多少钱、调用了几次 LLM/工具。多步 Agent 尤其要盯（[orchestration/06](../orchestration/06-生产实践与反模式.md)）。
- **延迟**：端到端耗时、各阶段延迟（p50/p95/p99）。
- **安全/合规**：有没有越权动作、有没有泄露、有没有被注入带偏（动作安全指标 + [INDEX 阶段7](../INDEX.md)）。

> **质量、成本、延迟、安全要一起看**：一个又准又安全但每次 $5、要等 2 分钟的 Agent，可能不如一个 90 分但快又便宜的。评估要呈现这个全貌。

---

## 6. 怎么为自己的 Agent 选指标（实操）

不要一上来就堆所有指标。按这个顺序：

```
1. 必选：任务完成度（端到端信号）—— 没它无从谈起
2. 加轨迹：工具选择准确率 + 步骤效率 —— 多步 Agent 的核心
3. 按需加：
   - 用了检索/记忆？→ 加对应组件指标（rag/07、ctx/03）
   - 开放生成任务？→ 加 LLM 裁判的质量/相关性
   - 长链条老跑偏？→ 加目标进展 + 步级推理质量
   - 有危险动作？→ 加动作安全
4. 横切：成本、延迟、安全 一并记录
```

> 和前面专题一样的纪律：**先量最关键的（任务完成 + 工具选择），再按观察到的问题加细分指标。** 别为了全面而把评估搞得没法维护。

---

## 7. 常见坑

- **只评任务完成度** → 不知道过程多差、多贵、多不安全，也无法定位问题。
- **不做步级评估** → 误差累积下只看到端到端低分，修不到点上。
- **轨迹评估要求精确匹配标准路径** → 合理变体被误判（[文档 01](01-为什么评估Agent更难.md)）。比"必要关键动作"。
- **不评成本/延迟** → 上线发现又慢又贵。
- **指标堆太多** → 维护不动、抓不住重点。先抓关键。
- **组件指标和端到端脱节** → 组件都"达标"但端到端还是差（组件标准定得不对，要对齐真实任务）。

---

## 8. 本章小结

- Agent 评估分三层：**结果级（任务完成/答案质量）、轨迹级（过程质量）、组件级（定位根因）**，三层配合逐层下钻。
- **任务完成度**是最重要的端到端信号；开放任务用 LLM 裁判/rubric。
- **轨迹指标**是 Agent 特色：工具选择准确率、步骤效率、目标进展、推理质量、动作安全、轨迹总分。
- **步级评估是对抗误差累积的关键**——拆开端到端，定位拉低整体的那一步，小改进被放大成大收益。
- 组件级复用 [rag/07](../rag/07-RAG评估与可观测性.md)（检索）、[context-engineering/03](../context-engineering/03-Agent记忆系统.md)（记忆）、[orchestration/06](../orchestration/06-生产实践与反模式.md)（交接）。
- **质量/成本/延迟/安全一起看**；选指标遵循"先关键后细分"。

## 9. 检验清单

- [ ] 能说出评估的三个层次及各自用途（有没有问题/问题在哪步/哪个部件坏）。
- [ ] 能列出至少 4 个轨迹级指标。
- [ ] 能解释步级评估为什么是对抗误差累积的关键。
- [ ] 知道轨迹评估为什么不能要求精确匹配标准路径。
- [ ] 能为一个给定的 Agent 按"先关键后细分"选出合理的指标集。
