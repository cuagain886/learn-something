# 01 · RAG 基础与核心原理

> 目标：建立对 RAG 的全局认知。读完能在白板上画出完整管线，并解释每个环节解决什么问题。

---

## 1. 什么是 RAG

**RAG（Retrieval-Augmented Generation，检索增强生成）** 是一种把"信息检索"和"大模型生成"结合起来的技术范式：

> 在让大模型回答问题之前，先从一个外部知识库里**检索**出与问题最相关的若干段资料，把这些资料连同问题一起塞进 Prompt，让模型**基于这些资料**来生成答案。

用一个类比：闭卷考试 vs 开卷考试。
- 纯大模型 = 闭卷考试，全凭脑子里记的（训练时学的）东西答题，记错了就是幻觉。
- RAG = 开卷考试，先翻书找到相关章节，再照着写答案，答案有出处、不容易编。

### RAG 的三个字母对应三件事

- **R（Retrieval 检索）**：从知识库里找出相关内容。这是 RAG 的核心难点，决定效果上限。
- **A（Augmented 增强）**：把检索到的内容拼进 Prompt，"增强"模型的输入上下文。
- **G（Generation 生成）**：模型基于增强后的上下文生成最终答案。

---

## 2. 为什么需要 RAG（它解决了什么问题）

大模型（LLM）有几个结构性短板，RAG 是当前最实用、成本最低的应对方案：

| 短板 | 含义 | RAG 如何解决 |
|------|------|--------------|
| **知识截止** | 模型只知道训练数据截止日期之前的事 | 知识库可随时更新，无需重训模型 |
| **私域知识缺失** | 模型不知道你公司的内部文档、产品手册 | 把私有文档放进知识库即可 |
| **幻觉** | 模型会自信地编造事实 | 强制模型"基于给定资料"回答，可约束、可核查 |
| **不可溯源** | 无法知道答案出处 | 检索到的 chunk 自带来源，可标注引用 |
| **更新成本高** | 知识变了要重训模型，极贵 | 改知识库里的一条记录即可，秒级生效 |

### 一个关键认知：RAG 不是为了"省钱"，是为了"可控"

很多人以为 RAG 的价值是"比微调便宜"，其实更核心的价值是**可控、可更新、可溯源**。在企业场景（金融、法律、医疗、客服），"答案能指出处"往往是硬性合规要求，这是纯大模型给不了的。

## 3. RAG 完整管线（最重要的一张图）

RAG 系统分为**两条链路**：离线建库（Indexing）和在线问答（Querying）。

```
═══════════════ 离线阶段：Indexing（建库，只做一次 / 定期更新）═══════════════

  ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────────┐
  │ 原始文档  │ → │ 解析/清洗 │ → │  分块     │ → │  嵌入     │ → │ 存入索引      │
  │ PDF/网页 │   │ Parse    │   │ Chunking │   │Embedding │   │ 向量库+倒排   │
  └──────────┘   └──────────┘   └──────────┘   └──────────┘   └──────────────┘
                  (文档→纯文本)  (切成小段)    (文本→向量)     (建立可检索结构)

═══════════════ 在线阶段：Querying（每次用户提问都走一遍）═══════════════

  ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐
  │ 用户问题  │ → │ 查询改写  │ → │  检索     │ → │  重排序   │ → │ 拼 Prompt │ → │ LLM 生成  │
  │ Query    │   │(可选优化) │   │ Retrieve │   │ Rerank   │   │ Augment  │   │ Generate │
  └──────────┘   └──────────┘   └──────────┘   └──────────┘   └──────────┘   └──────────┘
                                  (找候选)      (精排取top)    (上下文)       (出答案)
```

### 逐环节职责说明

**离线阶段：**
1. **解析/清洗（Parse）**：把 PDF、Word、HTML、PPT 等转成干净的纯文本，处理表格、图片、页眉页脚。→ 详见 [文档 02](02-数据处理与分块策略.md)
2. **分块（Chunking）**：把长文档切成适合检索的小段（chunk）。切法直接决定召回质量。→ [文档 02](02-数据处理与分块策略.md)
3. **嵌入（Embedding）**：用嵌入模型把每个 chunk 转成一个高维向量（一串数字），语义相近的文本向量也相近。→ [文档 03](03-嵌入模型与向量数据库.md)
4. **存入索引（Index）**：把向量存进向量数据库（建 HNSW 等索引加速搜索），同时常常建一份 BM25 倒排索引用于关键词检索。→ [文档 03](03-嵌入模型与向量数据库.md)

**在线阶段：**
5. **查询改写（Query Transformation，可选）**：用户的原始问题往往不适合直接检索（太短、有指代、口语化），先优化它。→ [文档 05](05-查询理解-改写路由与转换.md)
6. **检索（Retrieve）**：把查询也转成向量，在向量库里找最相近的 chunk；同时跑 BM25 找关键词匹配的 chunk；融合两者。→ [文档 04](04-检索策略-混合检索与重排序.md)
7. **重排序（Rerank）**：用更精确（但更慢）的模型，对召回的候选重新打分排序，取最相关的 top-k。→ [文档 04](04-检索策略-混合检索与重排序.md)
8. **拼 Prompt（Augment）**：把 top-k 的 chunk 按模板拼进 Prompt，附上"请基于以下资料回答、并标注出处"的指令。
9. **生成（Generate）**：LLM 基于增强后的上下文生成答案。

> **记住数据流向，几乎所有 RAG 优化都是在改进这九个环节中的某一个。** 当系统效果不好时，按这条链路逐环节排查，就能定位问题在哪。

## 4. 向量与语义检索：为什么"向量"能检索"语义"

这是 RAG 最核心的原理，必须理解（但不需要懂 Transformer 内部）。

### 4.1 嵌入（Embedding）是什么

嵌入模型把一段文本映射成一个固定长度的向量（比如 1024 个浮点数）。这个向量是文本"语义"的数值表示。关键性质：

> **语义相近的文本，向量在空间中也靠得近；语义无关的文本，向量离得远。**

例如 "怎么重置密码" 和 "忘记密码如何找回" 这两句话用词不同，但向量会很接近；而 "今天天气真好" 的向量离它们很远。

### 4.2 怎么衡量"近"

最常用的是**余弦相似度（Cosine Similarity）**：衡量两个向量方向的夹角。

- 夹角越小 → 越相似 → 余弦值越接近 1。
- 完全无关 → 余弦值接近 0。

所以"语义检索"的本质就是：把问题转成向量，在向量库里找与它**余弦相似度最高**的若干个 chunk 向量。这就是 **ANN（Approximate Nearest Neighbor，近似最近邻）搜索**。

### 4.3 为什么是"近似"

精确地在百万级向量里找最近邻很慢（要和每个向量都算一遍）。生产中用 **HNSW、IVF** 等索引，用一点点精度损失换巨大的速度提升。→ 详见 [文档 03](03-嵌入模型与向量数据库.md)。

## 5. RAG vs 微调 vs 长上下文：什么时候用哪个

这是面试和架构决策里最常见的问题。三者不是互斥的，但各有适用场景。

| 方案 | 本质 | 擅长 | 不擅长 | 成本 |
|------|------|------|--------|------|
| **RAG** | 外挂可检索知识库 | 注入**事实/知识**、需溯源、知识频繁更新 | 改变模型的"风格/能力" | 中（建库+检索） |
| **微调（Fine-tuning）** | 改模型权重 | 改变**风格、格式、领域语气**、固化技能 | 注入大量事实（易遗忘、难更新） | 高（训练+数据） |
| **长上下文（Long Context）** | 把全部资料直接塞进 Prompt | 资料少、一次性、要求全局理解 | 资料量大（贵、慢、有"迷失在中间"问题） | 按 token 计费，量大时极贵 |

### 决策口诀

- **要"知道什么"（知识/事实）→ RAG**
- **要"怎么表达 / 会做什么"（风格/技能）→ 微调**
- **资料就几页、用完即弃 → 直接长上下文**
- 实际生产中常常 **RAG + 微调组合**：微调让模型更懂领域术语和输出格式，RAG 提供实时事实。

### "长上下文会取代 RAG 吗？"

不会完全取代，原因：
1. **成本**：百万 token 上下文每次调用极贵，RAG 只塞最相关的几千 token。
2. **延迟**：上下文越长，首字延迟越高。
3. **"迷失在中间"（Lost in the Middle）**：模型对长上下文中间部分的信息利用率下降，塞太多反而干扰。
4. **可更新/可溯源**：知识库改一条就生效，且能精确标注出处。

长上下文反而让 RAG 更好用了——可以放更多检索结果进去。两者是互补关系。

## 6. 朴素 RAG（Naive RAG）的典型失败模式

理解基础 RAG 会在哪里失败，才知道后面的文档为什么要引入那些技巧。

| 失败现象 | 根因 | 对应的解法（后续文档） |
|----------|------|------------------------|
| 没找到相关资料（漏召回） | 分块太碎/太大、纯向量检索覆盖不全 | 优化分块 [02]、混合检索 [04] |
| 找到了不相关的（噪声多） | 召回 top-k 太宽、没有精排 | Cross-Encoder 重排 [04] |
| 用户问得模糊/有指代 | 原始 query 不适合检索 | 查询改写/HyDE [05] |
| chunk 内容对，但缺上下文 | 分块时丢失了所属章节/背景 | Contextual Retrieval、父子分块 [02][06] |
| 需要跨多个文档综合 | 单次检索拿不全 | Multi-Query、Agentic RAG [05][06] |
| 模型不按资料答、乱编 | Prompt 约束不够 / 资料没放对 | Prompt 工程、评估 faithfulness [07] |
| 关系型/全局型问题答不了 | 向量检索只擅长局部语义匹配 | GraphRAG、RAPTOR [06] |

> 这张表是整套文档的"问题地图"。每学一个技巧，都回来对照它解决了哪个失败模式。

## 7. 评估 RAG 的两个维度（先建立意识）

后面 [文档 07](07-RAG评估与可观测性.md) 会详细讲，这里先建立心智：评估 RAG 要分开看**检索**和**生成**。

- **检索质量**：找回的资料对不对、全不全？（Context Recall / Context Precision）
- **生成质量**：答案是否忠于资料、是否答到点上？（Faithfulness / Answer Relevancy）

**这种拆分极其重要**：当答案错了，先看检索指标——如果资料根本没找回来（recall 低），那是检索的锅，调 Prompt 没用；如果资料找回来了但答案还是错（faithfulness 低），才是生成/Prompt 的问题。

---

## 8. 本章小结

- RAG = 先检索相关资料、再让模型基于资料生成答案，解决知识截止、幻觉、不可溯源、私域知识等问题。
- RAG 分**离线建库**和**在线问答**两条链路，共九个核心环节，所有优化都落在这些环节上。
- 语义检索的原理：嵌入模型把文本变成向量，语义近 → 向量近 → 用 ANN 搜索找最近邻。
- RAG（注入知识）、微调（改风格/技能）、长上下文（少量一次性资料）各有适用场景，常组合使用。
- 朴素 RAG 有一张"失败模式地图"，后续每个技巧都对应解决其中一类问题。
- 评估必须拆成"检索质量"和"生成质量"两个维度。
