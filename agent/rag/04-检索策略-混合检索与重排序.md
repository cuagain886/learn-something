# 04 · 检索策略：混合检索与重排序

> 目标：理解为什么生产 RAG 几乎都用"混合检索 + 重排序"，掌握这套**准确率核心三件套**：稠密检索、稀疏检索（BM25）、融合（RRF）、Cross-Encoder 重排。

---

## 1. 两种基础检索：稠密 vs 稀疏

### 1.1 稠密检索（Dense Retrieval / 向量检索）

就是 [文档 01](01-RAG基础与核心原理.md)/[03](03-嵌入模型与向量数据库.md) 讲的：把 query 和 chunk 都变成向量，找最近邻。

- **擅长**：**语义匹配、同义改写**。"怎么重置密码" 能匹配到 "忘记密码的找回流程"，即使一个词都不一样。
- **盲区**：**精确词、罕见词、专有名词、产品编号、代码标识符**。向量检索对 "错误码 0x80070005"、"型号 SKU-12345" 这种**字面精确**的查询经常失手——因为这些 token 在语义空间里没什么"语义"，模型也没见过。

### 1.2 稀疏检索（Sparse Retrieval / 关键词检索）—— BM25

**BM25** 是经典的关键词检索算法（搜索引擎几十年的看家本领），基于词频统计。直觉：

- 一个词在某文档里**出现得越多**（TF，词频）→ 这个文档越可能相关。
- 但一个词在**所有文档里都常见**（如"的"、"是"）→ 它没区分度，降权（IDF，逆文档频率）。
- BM25 还做了"长文档惩罚"和"词频饱和"（出现 100 次不比 10 次重要 10 倍）。

- **擅长**：**精确词、专有名词、编号、代码、罕见术语**——字面命中就给分。
- **盲区**：**同义/改写**。用户说"汽车"、文档写"轿车"，BM25 匹配不上（除非做同义词扩展）。

### 1.3 关键认知：两者互补，盲区正好相反

| | 稠密（向量） | 稀疏（BM25） |
|---|---|---|
| 同义/改写查询 | ✅ 强 | ❌ 弱 |
| 精确词/编号/专名 | ❌ 弱 | ✅ 强 |
| 需要训练/嵌入 | 是 | 否（开箱即用） |
| 可解释性 | 差（黑盒） | 好（看命中词） |

> 正因为**盲区互补**，把两者结合起来的**混合检索**成了生产标配。

---

## 2. 混合检索（Hybrid Search）⭐ 生产默认

**做法**：同时跑稠密检索和稀疏检索，各取 top-N，再把两个排序列表**融合**成一个。

> 混合检索已成为 OpenSearch、Elasticsearch、Weaviate、Vespa、Qdrant 等的**生产默认配置**。

```
                  ┌──→ 向量检索 ──→ top-20 (列表A) ──┐
用户 query ───────┤                                  ├──→ 融合 ──→ 统一 top-k
                  └──→ BM25 检索 ──→ top-20 (列表B) ──┘
```

### 2.1 怎么融合：RRF（Reciprocal Rank Fusion，倒数排名融合）⭐

直接把两种检索的**分数**相加是不行的——向量的余弦相似度（0~1）和 BM25 的分数（可能是 0~30）**量纲完全不同**，无法直接比较。

**RRF 的聪明之处：只看排名，不看原始分数。** 一个文档在某个列表里排第 `r` 位，就贡献 `1/(k + r)` 的分数（`k` 是常数，常用 60），把它在所有列表里的贡献加起来作为最终分。

```python
def rrf(rankings: list[list[str]], k: int = 60) -> dict:
    scores = {}
    for ranking in rankings:           # 每个检索器的有序结果列表
        for rank, doc_id in enumerate(ranking, start=1):
            scores[doc_id] = scores.get(doc_id, 0) + 1 / (k + rank)
    return dict(sorted(scores.items(), key=lambda x: -x[1]))
```

- **优点**：无需调权重、无需归一化、对量纲不敏感、鲁棒。**生产首选融合方法**。
- 在多个文档里都排名靠前的，自然得分最高。

### 2.2 加权融合（替代方案）

也可以把分数归一化后加权：`final = α · dense + (1-α) · sparse`。
- 缺点：要调 `α`、要归一化、对分数分布敏感。
- 一般不如 RRF 省心，除非你想精细控制两者权重。

### 2.3 实战效果

混合检索 + Cross-Encoder 重排的级联方案，相比纯向量检索，生产中观察到 **RAG 准确率提升约 48%**。这就是为什么它是默认配置。

## 3. 重排序（Reranking）⭐ 精度提升的最大来源

### 3.1 为什么需要重排

第一阶段检索（向量/BM25）追求**高召回、低延迟**，所以会"广撒网"取 top-20~100，里面**混着不少噪声**，且排序不够精准（因为用的是"快但糙"的方法）。

**重排**：用一个**更精确但更慢**的模型，对这批候选**重新精细打分排序**，取最相关的 top-3~5 给 LLM。

> 经验：**重排是整条链路里精度收益最大的一环**。"先广召回 → 再精排"是生产 RAG 的主导模式。

### 3.2 Bi-Encoder vs Cross-Encoder（核心区别）

这是必须理解的概念：

- **Bi-Encoder（双塔，就是普通嵌入模型）**：query 和 doc **分别独立**编码成向量，再算相似度。
  - 因为 doc 向量可以**预先算好存库**，检索时只需算 query 向量 → **极快**，适合从海量库里粗筛。
  - 代价：query 和 doc 编码时**互相看不到**，交互信息少 → **精度有上限**。

- **Cross-Encoder（交叉编码器，重排模型）**：把 `query + doc` **拼在一起**送进模型，让两者**充分交互**，直接输出一个相关性分数。
  - 精度高得多（看到了 query 和 doc 的细粒度匹配）。
  - 代价：**每个候选都要跑一次模型**，无法预计算 → **慢、贵**。所以只能用在"少量候选"的重排阶段，不能用于全库检索。

```
检索阶段（Bi-Encoder）：1次编码 query + 预存的百万 doc 向量 → 快 → 取 top-50
重排阶段（Cross-Encoder）：query×50 个候选各跑一次 → 慢但准 → 取 top-5
```

这就是"**两阶段检索**"的本质：用便宜的 Bi-Encoder 把候选从百万缩到几十，再用昂贵的 Cross-Encoder 把几十精排到几个。

### 3.3 主流重排模型

| 模型 | 形态 | 备注 |
|------|------|------|
| **Cohere Rerank** (v3) | API | 效果好、多语言、省心，生产常用 |
| **bge-reranker** (v2-m3 等) | 开源 | 中文强、可自托管，首选开源方案 |
| **jina-reranker** | 开源/API | 长文档友好 |
| **Voyage rerank** | API | 质量第一梯队 |

### 3.4 重排参数与权衡

- **召回多少给重排？** 第一阶段取 top-`N`（常见 20~100）。`N` 大→召回更全但重排更慢更贵。
- **重排后保留几个？** top-`k`（常见 3~5）给 LLM。太多→噪声+成本+"迷失在中间"；太少→可能漏关键信息。
- **延迟**：Cross-Encoder 重排是延迟大头，N 越大越慢。可用更小的重排模型或减小 N 来权衡。

### 3.5 ColBERT / 后期交互（Late Interaction）—— 折中方案

ColBERT 这类**后期交互**模型介于 Bi 和 Cross 之间：doc 存成**多个 token 级向量**（不是单个向量），检索时做 token 级的细粒度匹配（MaxSim）。比 Bi-Encoder 准、比 Cross-Encoder 快，但**存储成本高**（每 doc 存很多向量）。属于进阶选项。

## 4. 生产级检索的完整管线（标准模板）

把前面所有东西串起来，这就是**生产 RAG 的标配检索链路**：

```
用户 query
   │
   ├─[可选] 查询改写/扩展 (见文档 05)
   │
   ├──→ 向量检索 (Bi-Encoder, top-50) ──┐
   │                                     ├─→ RRF 融合 → top-30
   └──→ BM25 检索 (top-50) ─────────────┘
                                          │
                          [可选] 元数据过滤（权限/时效）
                                          │
                          Cross-Encoder 重排 → top-5
                                          │
                          拼进 Prompt（带出处）→ LLM 生成
```

**这套"混合检索 + RRF + 重排"应当作为你的基线**。90% 的场景，把这套做扎实就够了，比急着上 GraphRAG 实在得多。

## 5. 一次检索 vs 迭代检索（One-shot vs Iterative）

- **一次检索（One-shot）**：检索一次就生成答案。简单、快，适合**单跳问题**（答案在某一两个 chunk 里）。
- **迭代检索（Iterative / Multi-step）**：检索→看结果→再检索，循环多轮。适合**多跳问题**（需要综合多处信息，前一步的答案决定下一步搜什么）。

研究表明：简单问题用一次检索就够，强行迭代反而增加成本和出错机会；复杂多跳问题才值得迭代。**根据问题复杂度自适应选择**（这也是 Adaptive RAG / Agentic RAG 的思想，见 [文档 06](06-高级RAG架构.md)）。

## 6. 常见坑

- **只用纯向量检索**：遇到编号、专名、代码就漏召回，这是新手最常见的效果瓶颈。
- **直接相加两种检索的分数**：量纲不同，结果混乱。用 RRF。
- **不做重排**：召回的 top-k 噪声多、排序糙，白白损失精度。
- **重排候选 N 太小**：第一阶段就漏了的，重排也救不回来（重排只能排序，不能凭空找回漏掉的）。
- **给 LLM 塞太多 chunk**：以为越多越好，结果触发"迷失在中间"、增加成本、引入噪声。
- **重排模型和场景语言不匹配**：中文场景用了纯英文重排模型。
- **忽略延迟预算**：混合检索+重排的总延迟没控制，用户体验差。

---

## 7. 本章小结

- 稠密检索擅长语义、稀疏检索（BM25）擅长精确词，**盲区互补** → 合起来用就是**混合检索**（生产默认）。
- 融合多路检索结果用 **RRF**（只看排名、免调权重、鲁棒），别直接相加原始分数。
- **重排是精度收益最大的一环**：用 Cross-Encoder（query+doc 一起编码，准但慢）对召回候选精排取 top-k。
- 理解 **Bi-Encoder（快、粗筛）vs Cross-Encoder（慢、精排）**，这是"两阶段检索"的根基。
- **基线模板 = 混合检索 + RRF + Cross-Encoder 重排**，先把它做好再谈高级架构。
- 单跳问题一次检索，多跳问题迭代检索，按复杂度自适应。
