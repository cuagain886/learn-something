# 02 · 数据处理与分块策略

> 目标：掌握从"原始文档"到"可检索 chunk"的全过程。这是**性价比最高的优化环节**——分块烂了，后面再好的检索和模型都救不回来。

---

## 1. 为什么分块如此重要

RAG 检索的最小单位是 **chunk（文本块）**。分块决定了：

- **召回粒度**：chunk 太大 → 一个块里混入大量无关内容，向量被"稀释"，检索不准；chunk 太小 → 语义不完整，检索到了也没法回答。
- **上下文完整性**：一个 chunk 是否包含回答问题所需的完整信息。
- **成本与延迟**：chunk 越多，建库嵌入成本越高、检索时计算量越大。

> 对长、多主题、结构混乱的文档，分块是重要杠杆之一；但解析/OCR 错误、语料缺失、权限过滤、检索器和生成器也可能是主瓶颈。若文档本身短小、聚焦且和问题高度对应，过度分块反而会降低准确率。

---

## 2. 完整的数据处理流程

分块只是数据处理的一环，完整流程是：

```
原始文件 → ① 解析(Parse) → ② 清洗(Clean) → ③ 分块(Chunk) → ④ 元数据富化(Enrich) → 嵌入
```

### 2.1 解析（Parsing / 文档提取）

把各种格式转成结构化文本。这一步的质量经常被低估，但**烂输入 = 烂输出**。

| 文件类型 | 难点 | 推荐工具 |
|----------|------|----------|
| PDF（文本型） | 多栏、页眉页脚、断行 | PyMuPDF (fitz)、pdfplumber |
| PDF（扫描件/图片） | 需要 OCR | Tesseract、PaddleOCR、云端 OCR |
| 复杂版式 PDF | 表格、图表、公式 | LlamaParse、Azure Document Intelligence、unstructured |
| Word/PPT | 样式、嵌入对象 | python-docx、unstructured |
| HTML/网页 | 导航栏、广告、JS 渲染 | trafilatura、readability、BeautifulSoup |
| Markdown | 相对干净，保留结构 | 直接按标题分块最理想 |

**工程要点：**
- **表格是重灾区**：把表格暴力转成纯文本会丢失行列关系。处理方式：转成 Markdown 表格、转成 HTML、或对每行生成"自然语言描述"。
- **图片/图表**：要么 OCR 提取文字，要么用多模态模型生成图片描述（caption）再嵌入。
- **保留结构信息**：解析时尽量保住标题层级、页码、章节路径——这些是后面元数据富化的金矿。

### 2.2 清洗（Cleaning）

- 去掉重复的页眉/页脚、水印、导航栏、版权声明。
- 修复被错误断开的句子/单词（PDF 跨行常见）。
- 统一空白字符、去掉乱码。
- **注意别清洗过头**：过度清洗可能删掉有意义的格式（如代码缩进、列表结构）。

## 3. 主流分块策略（核心）

下面按复杂度排列。固定/递归切分适合作为**可复现基线**；结构、语义、late chunking 与 parent-child 是针对不同证据跨度和成本约束的候选，不能按“高级”二字推断一定更好。

### 3.1 固定大小分块（Fixed-size Chunking）

最简单：按固定字符数/token 数硬切，配合重叠。

- **优点**：极简单、快、可预测。
- **缺点**：会从句子/单词中间切断，破坏语义。
- **适用**：快速原型、对质量要求不高的场景。基本只作为 baseline。

### 3.2 递归字符分块（Recursive Character Splitting）：可复现基线之一

按一组**分隔符的优先级**递归切分：先尝试按段落（`\n\n`）切，太大就按句子（`\n`、`。`）切，还太大再按词/字符切。这样**尽量在自然边界处断开**。

> **可用于首轮实验的启发式配置**：chunk 大小 **400~512 token**，重叠 **10~20%**。它不是跨语料的“最佳值”；最终应按文档结构、答案跨度、嵌入模型和召回/成本曲线调优。

```python
from langchain_text_splitters import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(
    chunk_size=512,          # 目标块大小（按 token 更准，需配 tokenizer）
    chunk_overlap=80,        # 重叠，约 15%
    separators=["\n\n", "\n", "。", "！", "？", " ", ""],  # 中文要加中文标点
)
chunks = splitter.split_text(text)
```

**为什么需要重叠（overlap）？** 防止"答案正好被切在两个 chunk 的边界上"导致两边都不完整。重叠让边界信息在相邻块里都保留一份。

**中文注意**：默认分隔符是英文的，中文必须把 `。！？；` 等加进 `separators`，否则会按字符乱切。

### 3.3 按文档结构分块（Structure-aware / Document-based）

利用文档自带的结构来切：Markdown 按标题（`#`/`##`），代码按函数/类，HTML 按标签，PPT 按页。

- **优点**：保留标题、页、函数等原始结构和 lineage；但原始结构未必与答案证据边界一致，表格、跨段定义和引用仍可能被切断。
- **适用**：结构清晰的文档（技术文档、Wiki、代码库、Markdown 笔记）。
- **常见做法**：Markdown 按标题切，并把标题路径（如 `产品手册 > 安装 > 常见问题`）作为元数据存进每个 chunk。

### 3.4 句子级分块（Sentence-based）

按句子边界切，再把若干句子组合成 chunk。比固定切更尊重语义，介于固定和语义之间。

### 3.5 语义分块（Semantic Chunking）⭐ 进阶

不按固定长度，而是**按语义相似度**决定在哪里断开：逐句嵌入，当相邻句子的向量相似度"突然下降"时（话题转变），就在这里切一刀。

- **原理**：相邻句子语义连贯就归一块，话题一变就断开。
- **效果**：在话题边界与固定长度边界经常错位的语料上可能改善召回；收益必须用同一评测集与固定检索预算对比，不能套用统一提升比例。
- **代价**：要对**每个句子都做嵌入**，建库成本和延迟显著上升。
- **适用**：文档主题混杂、内部话题切换频繁、且对召回质量要求高的场景。

```python
# LlamaIndex 的语义分块器示意
from llama_index.core.node_parser import SemanticSplitterNodeParser
splitter = SemanticSplitterNodeParser(
    buffer_size=1,                  # 比较时前后看几句
    breakpoint_percentile_threshold=95,  # 相似度跌破此分位 → 断开
    embed_model=embed_model,
)
```

### 3.6 LLM 分块（LLM-based / Agentic Chunking）

直接让大模型按任务或主题边界切分。它更灵活，但**不保证质量最高**：可能遗漏文本、改写事实、边界不稳定，也增加成本与版本漂移。适合高价值、小规模语料的候选方案，必须和结构化/递归 baseline 做保真与检索评测。

### 3.7 晚分块（Late Chunking）⭐ 2024-2025 重要新技术

**解决的问题**：传统分块是"先切块、再各自嵌入"，每个块**孤立地**被嵌入，丢失了全局上下文（比如块里出现的代词 "它" 指代的是前文的什么，块自己不知道）。

**Late Chunking 的做法是反过来**：
1. **先把模型有效窗口内的文档段**送进支持 token-level pooling 的长上下文嵌入模型，得到 contextualized token 向量；超长文档仍需窗口/层级策略。
2. **之后再**按边界把这些 token 向量切开，对每个块的 token 向量做池化（平均）得到块向量。

> 因为嵌入发生在切分**之前**，chunk 向量包含其编码窗口内的上下文，有机会缓解块孤立和指代丢失；它不是无限文档的真正“全局语义”，池化仍可能稀释局部证据。

- **候选收益**：对指代多、上下文依赖强的语料可能改善表征；必须与普通 chunk embedding 在相同维度、索引/检索预算下比较。
- **前提**：目标 embedding 模型明确支持足够长的 token-level contextualization/pooling；记录 tokenizer、有效窗口、池化方式和截断率。
- **对比 Contextual Retrieval**：两者都为解决"块丢失上下文"，但 Late Chunking 靠模型机制（嵌入时看全文），Contextual Retrieval 靠 LLM 给每块生成一段上下文说明再嵌入。→ 见 [文档 06](06-高级RAG架构.md)。

### 3.8 父子 / 小块索引大块返回（Parent-Document / Small-to-Big）：证据重建候选

**核心矛盾**：检索候选通常希望局部可区分，证据使用又可能需要邻域。Small-to-Big 尝试分离索引粒度与返回粒度：

- **索引/检索用小块**（如句子或 256 token），保证检索精准。
- **命中后，返回它所属的大块/父文档**（如整段或整节）作为候选上下文；是否完整仍取决于父边界、跨父证据和 token 预算。

```
文档 → 切成大块(父, 2000 token) → 每个父块再切小块(子, 256 token)
索引：只嵌入子块
检索：用 query 匹配子块 → 找到命中的子块 → 返回其父块给 LLM
```

这是常见且实用的模式，但并非无副作用：多个子块可能反复返回同一父块，父块过大会稀释证据、增加 token，并扩大敏感内容暴露范围。需要父块去重、token 预算、ACL 一致性和“命中子块在父块中的证据定位”。

## 4. 分块参数怎么定（决策指南）

没有放之四海皆准的参数，但有决策框架：

### 4.1 chunk 大小

| 证据/查询形状 | 首轮候选（不是推荐值） | 必须观察的失败 |
|---------------|-------------------------|----------------|
| 短、局部事实 | 128/256/384 token | evidence containment、碎片率、同义短块误召回 |
| 混合长度文档问答 | 256/512/768 token | recall@budget、重复候选、reranker 截断与上下文稀释 |
| 长叙事、表格跨行、多跳证据 | 512/1024 + parent/neighbor expansion | 单纯放大 chunk 可能降低定位精度；要测 evidence-set completeness 与最终 token 成本 |

**实验法则**：
- 不知道选多大时，先跑一个小网格，例如 `{256, 512, 1024} × {0%, 10%, 20% overlap}`；固定召回候选数、最终上下文 token 和 reranker 预算，画质量—延迟—索引体积曲线。
- chunk 必须按**实际 embedding tokenizer 和当前模型版本**计数，并显式检测 truncation；不能从模型营销窗口推断有效证据长度。
- 生成端不是只满足“未超窗口”：还要限制最终证据预算、重复率、位置分布和无关上下文比例。

### 4.2 重叠（overlap）

- 对平坦文本，可把 `0/10/20%` 当候选；重叠增大可能提高边界 containment，也会增加索引体积、近重复命中和上下文浪费。
- 结构边界也可能切断跨段定义、表格或引用；与其机械 overlap，常用 parent/neighbor expansion 恢复上下文，并单独测额外 token 与错误关联。

### 4.3 一个重要提醒

> **分块参数必须配合评估来调**（[文档 07](07-RAG评估与可观测性.md)）。“我感觉 256 比 512 好”不可接受；至少同时测 span containment/fragmentation、检索 recall@budget、重复率、claim evidence completeness、最终正确性、延迟和存储成本。单个 Context Recall 分数不能定位分块是否是根因。

## 5. 元数据富化（Metadata Enrichment）⭐ 容易被忽视但极有用

给每个 chunk 附加结构化元数据，检索时既能**过滤**也能**增强**。

常见元数据：
- `source`：来源文件名 / URL（用于溯源、引用）
- `title` / `section_path`：所属标题路径（如 `手册 > 安装 > FAQ`）
- `page`：页码
- `date` / `author` / `doc_type`：时间、作者、文档类型
- `chunk_id` / `parent_id`：用于 Small-to-Big 关联父块

**两大用途：**

1. **元数据过滤（Metadata Filtering）**：检索时先按元数据筛选范围，再做向量搜索。例如"只在 2025 年之后的财报里搜"、"只在该用户有权限的文档里搜"。这对**权限隔离、时效过滤**至关重要。

2. **上下文增强**：把标题路径拼到 chunk 文本开头再嵌入（轻量版 Contextual Retrieval），让块知道自己"属于哪一节"，提升检索相关性。

```python
chunk = {
    "text": f"[来源: {title} > {section}]\n{content}",  # 标题拼进文本
    "metadata": {"source": fname, "page": 12, "date": "2025-03", "section_path": section}
}
```

## 6. 不同文档类型的分块策略选择

| 文档类型 | 推荐策略 |
|----------|----------|
| Markdown / Wiki / 技术文档 | 按标题结构分块 + 标题路径入元数据 |
| 长篇 PDF 报告 / 书籍 | 递归分块 / 语义分块 + Small-to-Big |
| 法律合同 / 条款 | 按条款/编号结构分块（保持条款完整） |
| 代码库 | 按函数/类分块（用 AST 或语言感知 splitter） |
| FAQ / 知识卡片 | 一问一答为一个 chunk，不再切 |
| 对话记录 / 客服日志 | 按对话轮次或话题分块 |
| 表格密集型（财报） | 表格单独成块（转 Markdown），叙述文字另切 |

## 7. 常见坑

- **中文按英文分隔符切**：忘了加中文标点，导致按字符乱切。
- **表格被切碎**：行列关系丢失，模型读不懂。先把表格转成 Markdown/HTML 整体保留。
- **chunk 里全是噪声**：页眉页脚、目录、参考文献没清洗，污染向量。
- **重叠开太大**：同一段内容在多个块里重复，检索 top-k 全是近似重复，浪费上下文。
- **嵌入超长被截断**：chunk 超过嵌入模型最大长度，尾部被悄悄丢弃却不报错。
- **只切不富化**：没存来源/页码，导致无法溯源、无法做权限过滤。
- **一套参数用到底**：不同文档类型用同一套分块参数，效果参差。

## 8. 深入：Chunking 是 Query–Evidence Span 的联合设计

### 8.1 从答案证据跨度反推块，而不是背固定 token 数

对评测问题 `q_i` 标注支持答案所需的最小证据 span 集 `E_i={e_i1,...}`。一个分块方案 `S` 会产生 chunks `C(S)`，关键事件不是“块大约 512 token”，而是：

```text
Containment：单个/少量 chunk 是否完整包含证据 span
Fragmentation：一个证据被切到多少块
Dilution：返回块中与证据无关的 token 比例
Redundancy：top-k 中重复内容/同一父块比例
Reachability：在 ACL/时间过滤后证据是否仍可检索
```

可定义：

\[
contain@k_i=\mathbb 1[\exists C'\subseteq top_k,
\ |C'|\le m,\ E_i\subseteq \cup C']
\]

其中 `m` 是生成器能可靠组合的块数。对多跳问题，强求一个 chunk 包含所有证据反而不合理，应标注各 hop 及连接关系。

### 8.2 解析保真是分块的前置 oracle

在调 chunk 前先抽样验证：

- 文字是否遗漏、乱码、顺序错乱；
- 表格单元格与行列 header 是否可恢复；
- 标题层级、列表、代码缩进、公式/脚注是否保留；
- 页码/坐标是否能映射回原文；
- OCR confidence 与图片/扫描页覆盖；
- 同一文档是否因重复页眉/附件被多次入库。

如果 answer span 在 parse 后已丢失，任何 embedding/chunk 调参都无法召回。

### 8.3 Chunk 数据模型要支持版本和删除

```yaml
chunk_id: sha256(doc_version + byte_span + chunker_version)
doc_id: policy-19
doc_version: 2026-07-01
parent_id: section-4.2
byte_span: [18290, 19722]
token_span: [4031, 4388]
section_path: ["退款政策", "特殊情形"]
content_hash: sha256:...
parser_version: pdf-layout-v6
chunker_version: structure-512-v4
acl_ref: acl://policy-19-v3
valid_time: [2026-07-01, null]
indexed_at: ...
source_ref: artifact://...
```

稳定的 `doc_id/version/span` 支持引用定位、重建对比、增量删除和 lineage。用随机 UUID 而不保留 span，会让更新、去重和引用验证困难。

### 8.4 Parent–Child 的一致性约束

父子模式至少满足：

1. 子块和父块属于同一 `doc_version/ACL/security_domain`；
2. 命中子块必须可定位到父块中的 exact span；
3. 多个子块命中同一父块时去重并聚合分数；
4. 父块返回前再次做权限与有效期检查；
5. 父块过大时按 evidence-centered window 截取，而不是固定整节；
6. 删除/更新父文档时子向量不可残留。

### 8.5 重叠的真实代价

设原始 token 数 `T`、块长 `L`、重叠 `O`，理想化块数约：

\[
n\approx \left\lceil\frac{T-L}{L-O}\right\rceil+1
\]

`O` 增大不仅增加嵌入/存储，还会让相邻重复块占满 top-k。报告：

- index expansion ratio：索引 token / 去重语料 token；
- top-k unique-token ratio；
- same-parent duplication；
- evidence containment 与成本曲线。

### 8.6 可复现的分块消融

保持 embedding、检索器、候选数、reranker、生成器和上下文 token 预算不变，只改变 chunker：

```text
S0 整文档/自然单元 baseline
S1 递归固定长度（多个 L/O）
S2 结构化
S3 parent-child
S4 late/contextual/semantic（按实际适用）
```

按文档类型和答案 span 长度分层，报告 `evidence contain@k`、Recall@k、unique-token ratio、answer/citation correctness、index size、p95 与 cost/success。若一次同时换 embedding 和 chunk，无法归因收益。

### 8.7 Chunking 的安全边界

- ACL 必须继承且不可在父子/摘要时变宽；
- chunk 不应跨租户、文档保密级别或互斥时间版本拼接；
- 外部内容的 provenance/taint 跨 contextualization/summary 保留；
- “标题前缀”可能包含用户可控注入，也应视为数据；
- right-to-delete 要删除原 chunk、向量、稀疏索引、缓存、父块、摘要和派生图节点。

## 9. 本章小结

- 数据处理 = 解析 → 清洗 → 分块 → 元数据富化，每步都影响最终效果。
- 固定/递归字符分块是便于复现的 baseline；结构清晰时应把结构边界作为候选，但仍要处理跨段证据。
- 语义分块、Late Chunking 与 Small-to-Big 分别改变边界判定、表征上下文和返回粒度；它们可能改善某类错误，也可能增加建库成本、派生一致性或上下文稀释，必须同预算消融。
- 元数据承载 ACL、时间、版本、父子 lineage 和删除范围，是正确性契约，不只是“提高相关性”的附加标签。
- 所有分块参数都要**配合评估**来调，不能凭感觉。

## 10. 检验清单

- [ ] 能说清"chunk 太大 / 太小"分别带来什么问题。
- [ ] 知道为什么需要 overlap，以及结构化分块为什么常不需要。
- [ ] 能解释 Late Chunking 和传统分块的区别，以及它解决什么问题。
- [ ] 理解 Small-to-Big 如何同时兼顾"检索精准"和"上下文完整"。
- [ ] 知道元数据过滤在权限/时效场景的作用。
- [ ] 能用 evidence containment/fragmentation/dilution 而非固定 token 经验评估分块。
- [ ] 能设计带版本、span、ACL、lineage 的 chunk 数据模型。
- [ ] 能说明 parent-child 的去重、权限和删除一致性风险。
