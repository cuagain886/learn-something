# 03 · 嵌入模型与向量数据库

> 目标：理解 chunk 如何变成向量、向量如何被高速检索，并掌握嵌入模型和向量库的选型。

---

## 1. 嵌入模型（Embedding Model）

### 1.1 嵌入在做什么

嵌入模型把一段文本编码成一个固定长度的向量（如 768、1024、1536 维）。核心性质（[文档 01](01-RAG基础与核心原理.md) 讲过）：**语义相近的文本，向量也相近**。

RAG 里嵌入用在两处，必须落在**兼容的向量空间**：
- 建库时：嵌入每个 chunk。
- 检索时：嵌入用户的 query。

> 对大多数单编码器 API，query/document 必须使用同一模型版本及其规定的输入模式；也有专门训练的双塔模型使用不同 query/doc encoder，但二者是联合训练的兼容空间。不能随意混搭。更换任何一侧的表示版本，通常都要构建新索引并原子切换。

### 1.2 关键概念

- **维度（dimension）**：向量长度。更高维会增加存储/计算，但不保证在目标任务上更准；表示训练、语言和任务匹配更重要。
- **对称 vs 非对称检索**：
  - 对称：query 和文档形态相似（句子找句子）。
  - **非对称：短 query 找长文档**（RAG 的典型情况）。很多模型需要给 query 和 doc 加不同的**前缀指令**（如 bge 系列要求 query 前加 `"为这个句子生成表示以用于检索相关文章："`），不加会明显掉点。**务必看模型文档**。
- **归一化（normalization）**：很多模型输出需归一化后用余弦相似度，否则用内积。

### 1.3 嵌入模型选型（2025-2026 快照）

可评估的模型族包括托管 API（OpenAI `text-embedding-3`、Cohere、Voyage 等）和可自托管模型（BGE、E5、Jina 等）。这些名称用于建立候选集，不构成实时排行榜；版本、输入长度、授权、价格和能力会变化，应查当前 model card/API 文档。

用目标数据做 bake-off，至少固定并记录：

| 维度 | 要验证的内容 |
|---|---|
| 任务 | 非对称检索、多语言、代码、长文档、领域术语 |
| 输入契约 | query/doc prefix、最大 token、截断、归一化、距离函数 |
| 质量 | exact-index Recall@k/nDCG、hard negatives、关键切片 |
| 系统 | embedding 吞吐、p95、批大小、向量维度、索引内存 |
| 治理 | 数据驻留、保留/训练政策、许可证、模型版本可钉死性 |
| 迁移 | shadow dual-index、回填时间、回滚与旧向量删除 |

MTEB/C-MTEB 适合筛选候选，不能替代领域 query–evidence 评测。

### 1.4 Matryoshka（套娃）嵌入

只有明确按 Matryoshka/维度截断目标训练并在文档中支持的模型，才能安全测试截断维度。不能把任意向量直接截短。对每个候选维度重新测 Recall@k、索引内存、延迟和重排后的端到端质量。

## 2. 向量索引：为什么检索能这么快

逐个计算相似度是精确的 (O(Nd)) 扫描；在当前数据规模/硬件/过滤条件下若不满足延迟 SLO，才需要 **ANN（近似最近邻）**。ANN 以可测的 recall 损失换取吞吐/延迟收益，exact search 应保留为离线 oracle。

### 2.1 HNSW（Hierarchical Navigable Small World）：图式 ANN 候选

HNSW 被多种向量检索实现采用，但支持的过滤、更新、压缩、持久化与参数语义不同，选型时必须以目标数据库版本为准。

**直觉**：把向量组织成一个**多层的"小世界"图**。上层稀疏（少量节点、长连接，用于快速跳到大致区域），下层密集（精细定位）。检索时从顶层入口出发，逐层向下"贪心地"跳向离 query 更近的邻居，最后在底层精确定位。像在地图上先看省级、再市级、再街道。

- **优点**：查询极快、召回率高、支持动态插入。
- **缺点**：**内存占用大**（图结构常驻内存）、构建较慢、删除/更新不如重建干净。
- **关键参数**：
  - `M`：每个节点的连接数。增大通常改善图连通性，也增加内存与构建成本；合法范围和默认值依实现/版本，不把固定区间当通用调参结论。
  - `ef_construction`：构建时的搜索宽度。大→索引质量高但建得慢。
  - `ef_search`：查询时的搜索宽度。**大→召回高但查询慢**（这是查询时调"质量 vs 速度"的旋钮）。

### 2.2 IVF（Inverted File Index）

先用聚类把向量空间分成若干"桶"（cell），查询时只搜最近的几个桶。

- **优点**：内存比 HNSW 省、构建快。
- **缺点**：召回率通常不如 HNSW；需要训练（聚类）。
- 常与 **PQ（Product Quantization，乘积量化）** 组合成 `IVF-PQ`：把向量压缩成短码，**大幅省内存**，代价是精度下降。十亿级、内存受限时常用。

### 2.3 量化（Quantization）—— 省内存的关键

向量很占内存（百万条 1024 维 float32 ≈ 4GB）。量化用低精度表示换内存：

- **标量量化（SQ）**：例如 float32 → int8，原始向量载荷约缩小 4 倍，但索引图/元数据不同比例缩小；精度损失依数据和实现而定，必须评测。
- **二值量化（Binary）**：每维压成 1 bit，省 32x，配合重排可用，精度损失较大。
- **乘积量化（PQ）**：分段聚类编码，压缩率极高，十亿级用。

### 2.4 索引选型口诀

- **中等规模、追求低延迟高召回、内存充足** → 常从 HNSW baseline 开始。
- **内存紧张 / 超大规模** → 评估 IVF/PQ、磁盘索引、分片或 HNSW + 量化。
- 规模不是唯一变量；过滤选择率、更新率、并发、租户隔离和恢复目标会改变选择。

## 3. 向量数据库选型（2025-2026）

向量库 = 存向量 + 建索引 + 支持过滤 + 提供检索 API。

### 3.1 候选系统与评测维度

候选可包括 pgvector、Elasticsearch/OpenSearch、Qdrant、Milvus、Pinecone、Weaviate、Vespa 及本地嵌入式库。产品能力和性能随版本变化，不应静态宣称某个库“过滤最强”或某个规模一定舒适。

### 3.2 选型 spike

在生产形状的数据上验证：

```text
数据：向量数/维度、metadata 大小、删除率、冷热分布
查询：top-k、过滤选择率、dense+sparse、并发与 burst
质量：相对 exact search 的 ANN Recall@k
性能：p50/p95/p99、吞吐、build/compact/backup/restore 时间
一致性：写后读、删除可见性、snapshot/dual-index、故障恢复
隔离：租户/ACL pre-filter、cache 安全域、加密与审计
运维：扩容、升级、回滚、成本、数据驻留与锁定
```

已有数据库可降低组件复杂度，但只有在质量、尾延迟、更新和隔离满足 SLO 时才是更优选择。

> **重要提醒**：很多库都宣称"支持 HNSW 向量搜索"，但**"能跑 HNSW" ≠ "生产可用"**。生产可用还要看：**元数据过滤性能、并发吞吐、增量更新/删除、持久化与备份、水平扩展、监控**。很多团队是在生产压力下才发现选错了库。

### 3.3 不容忽视的能力：带过滤的向量搜索（Filtered Search）

实战中几乎一定会用到"**在满足某些元数据条件的子集里做向量搜索**"（如按租户、按时间、按权限）。这件事比想象的难：
- **先过滤再搜（pre-filter）**：精确，但可能破坏 HNSW 图的连通性，过滤太狠时召回掉点甚至变慢。
- **先搜再过滤（post-filter）**：快，但可能 top-k 过滤后剩不下几个，召回不足。
- Qdrant、Milvus 等在这块做了专门优化。**如果你的场景重度依赖过滤（多租户 SaaS 必然如此），把它作为选型的一等公民。**

## 4. 建库工程实践

### 4.1 批量嵌入

- **批处理（batching）**：嵌入 API/模型都支持批量，逐条调用会慢几十倍、贵几倍。
- **限流与重试**：API 嵌入要处理 rate limit、超时重试（指数退避）。
- **成本估算**：百万 chunk × 平均 token 数 × 单价，先算账。降维（Matryoshka）能省存储。

### 4.2 增量更新与删除

知识库不是建一次就完事，文档会增删改。设计时就要想清楚：
- **怎么定位一个文档对应的所有 chunk**？（用 `doc_id` 元数据关联，删文档时按 `doc_id` 批量删 chunk。）
- **更新一个文档** = 删旧 chunk + 插新 chunk。
- HNSW 的删除是"标记删除"，删多了图会退化，定期需要 **rebuild/compact**。
- 详见 [文档 08](08-生产工程化与最佳实践.md) 的增量更新章节。

### 4.3 别忘了同时建 BM25 索引

生产 RAG 几乎都用**混合检索**（[文档 04](04-检索策略-混合检索与重排序.md)），所以建库时除了向量索引，通常还要建一份 **BM25/全文倒排索引**。有的库（ES、Weaviate、Qdrant、Milvus）原生支持稀疏向量/全文，pgvector 可配合 PG 全文检索或额外用 `pg_search`/Elasticsearch。

## 5. 常见坑

- **query 和 doc 用了不同嵌入模型 / 忘加 query 前缀** → 检索质量莫名其妙地差。
- **换了嵌入模型但没重建索引** → 新旧向量混在一起，全乱。
- **维度选太高** → 存储和内存爆炸，其实降维后效果差不多。
- **没开量化** → 内存成本居高不下。
- **HNSW `ef_search` 默认值太小** → 召回不足；太大 → 查询慢。要按评估调。
- **过滤场景没测性能** → 上线后发现带过滤的查询又慢又漏。
- **建库时没存 `doc_id`** → 后期无法增量更新/删除单个文档。

## 6. 深入：ANN 是可测的近似层，不是透明加速器

### 6.1 用 exact search 建立 ANN recall oracle

在可承受的分层样本或完整小索引上做 brute-force exact nearest neighbors，记真实 top-k 为 `G_k(q)`，ANN 结果为 `A_k(q)`：

\[
ANN\ Recall@k=\frac{|G_k(q)\cap A_k(q)|}{k}
\]

它测的是“索引是否找回嵌入空间中的真近邻”，不是“真近邻是否是业务相关证据”。两层必须分开：

```text
embedding/relevance quality：exact neighbors 是否相关
ANN quality：近似索引是否找回 exact neighbors
```

若 exact 检索已错，增大 `ef_search/nprobe` 不会修复语义表示。

### 6.2 参数曲线，而非单点配置

HNSW：

- `M` 增大通常提高图连通/召回，也增加内存与构建；
- `ef_construction` 影响构建质量/时间；
- `ef_search` 是查询时 recall–latency 旋钮，通常应 `>=k`，具体曲线实测。

IVF：

- `nlist` 决定桶数；
- `nprobe` 决定查询探测多少桶，越大通常召回/延迟都升；
- PQ code size、训练样本和 residual/OPQ 等实现影响压缩误差。

对每个过滤选择率、top-k 和任务切片画：

```text
ANN Recall@k vs p95/p99 latency vs QPS vs memory
```

最终还要看端到端 answer/citation correctness；ANN recall 的小损失可能被 reranker 恢复，也可能恰好丢掉唯一证据。

### 6.3 量化的两阶段恢复

常见路径：压缩向量粗召回较多候选，再用原始/高精度向量或 cross-encoder 重排：

```text
quantized ANN top-200
→ full-precision similarity top-60
→ cross-encoder top-8
```

如果只保留压缩码，就无法做全精度恢复；如果保存全向量，内存/磁盘节省要按整个系统重新计算。评估量化时固定候选预算，报告召回损失和总成本。

### 6.4 Filtered ANN 的正确性

三种典型策略：

| 策略 | 风险 |
|---|---|
| pre-filter | 子图/候选过小，索引实现可能退化或改走 brute-force |
| post-filter | top-k 被过滤光，且可能泄露不应参与打分的数据 |
| iterative/oversample | 多轮扩大候选，延迟不稳定，需上限 |

多租户/ACL 场景中，**安全过滤必须在未授权内容可返回或进入共享 cache 前强制**。为了召回先做跨租户全局搜索再 post-filter，可能违反安全与侧信道要求。应在真实选择率（100%、10%、1%、0.01%）下测质量和 p99。

### 6.5 更新、删除与快照一致性

索引记录至少带：

```yaml
doc_id: ...
doc_version: ...
chunk_id: ...
embedding_model_version: ...
embedding_input_hash: ...
index_snapshot: ...
valid_from: ...
valid_to: ...
acl_version: ...
tombstone: false
```

常见故障窗口：

- 向量已写、metadata/ACL 未写；
- 新版本已写，旧版本未删，查询返回冲突；
- tombstone 已产生，HNSW/缓存仍返回；
- embedding 模型升级时新旧空间混合；
- snapshot 切换后 sparse/dense 指向不同版本。

解决路径见 [08](08-生产工程化与最佳实践.md)：构建不可变新 snapshot、验证后原子切 alias，旧 snapshot 保留回滚，删除通过 lineage 传播并有 SLA。

### 6.6 多租户隔离选择

| 方式 | 优点 | 风险/代价 |
|---|---|---|
| 共享索引 + tenant pre-filter | 利用率高 | 策略/缓存 bug 爆炸半径大，过滤性能敏感 |
| namespace/partition per tenant | 隔离较强 | 小分区多、运维和碎片化 |
| 独立集群/库 | 最强隔离/驻留 | 成本最高、容量利用低 |

按数据敏感度和租户规模分层，不必所有租户同一方案。无论哪种，query embedding、cache key、backup/restore 和 trace 都要包含安全域。

## 7. 本章小结

- 嵌入模型把文本变向量，**query 和 chunk 必须用同一模型**，换模型要重建索引；注意非对称检索的 query 前缀。
- 模型名和排行榜只用于筛选候选；必须在自己的语言、领域、hard negatives、输入契约和治理约束上评测。
- **HNSW** 常用，关键旋钮包括 `M/ef_construction/ef_search`；IVF/PQ 和量化适合不同内存/规模约束，均需画 recall–latency–memory 曲线。
- 量化不是免费午餐；可用“压缩粗召回 + 全精度/交叉编码器重排”恢复部分损失。
- 数据库选型以生产 shape 的 spike 为准，特别验证过滤、更新/删除、snapshot、备份恢复和多租户隔离。
- "能跑 HNSW" ≠ "生产可用"，要看过滤性能、并发、增量更新、备份。
- 建库时一并考虑 **BM25 索引**和**增量更新方案**。

- [ ] 能根据数据规模/过滤需求/运维能力选出合适的向量库。
