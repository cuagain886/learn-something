# 05 · 查询理解：改写、路由与转换

> 目标：把原始请求解析成保留约束、来源可追踪的 intent/query contract，再决定是否改写、分解、路由或拒答。转换可能提高某些切片召回，也可能丢失否定、实体、时间、租户和授权约束，因此原查询必须保留并参与对照。

---

## 1. 为什么需要查询转换

检索的输入是用户的原始问题，但它经常**不适合直接拿去检索**：

- **太短/信息不足**："价格呢？" —— 缺主语，检索不到东西。
- **有指代/依赖上下文**：多轮对话里"它支持这个吗？"——"它""这个"指代前文。
- **口语化/含噪声**："那个啥，就是登录不上去咋整" —— 和文档书面语对不上。
- **过于宽泛/复合**："对比 A 和 B 的优缺点并给出建议" —— 一次检索覆盖不全。
- **词汇不匹配**：用户用词和文档用词不一致（向量检索能缓解，但不总能）。

> 核心思想：可把 query 规范化、扩展或拆解，但每次转换也可能丢约束、引入事实和扩大攻击面。原查询必须保留并参与评测/回退，转换收益要在相同检索预算下验证。

---

## 2. 主流查询转换技巧

### 2.1 查询改写（Query Rewriting）

用 LLM 把原始问题改写得更清晰、更完整、更适合检索。

**最常见也最重要的两个子任务：**

1. **指代消解 / 多轮改写（Conversational Query Rewriting）**：把依赖上下文的追问改写成独立完整的问题。它常有价值，但若指代有多个可能对象，应澄清或保留多个假设，而不是强行选一个。
   ```
   历史：用户问"介绍下你们的企业版套餐" → 助手回答...
   追问："它支持 SSO 吗？"
   改写后："企业版套餐是否支持 SSO 单点登录？"  ← 拿这个去检索
   ```
   不做这一步，"它支持 SSO 吗" 这种 query 几乎检索不到正确内容。

2. **规范化/澄清**：去口语、补全术语、纠错别字。

### 2.2 多查询（Multi-Query / Query Expansion）⭐

让 LLM 把一个问题**改写成多个不同角度的版本**，每个版本各自检索，再把结果合并去重。

```
原问题："如何提升 RAG 的检索效果？"
LLM 生成多个变体：
  - "RAG 检索准确率优化方法"
  - "提高向量检索召回率的技巧"
  - "RAG retrieval 召回精度提升策略"
→ 每个变体各检索 top-k → 合并去重 → 重排
```

- **原理**：单个 query 的措辞可能"碰巧"和正确文档对不上，多个角度并行能**对冲语义错配**，提升召回。
- **代价**：多次检索 + 一次 LLM 改写，延迟和成本上升。
- **适用**：召回是瓶颈、问题可以多角度表述的场景。

### 2.3 HyDE（Hypothetical Document Embeddings，假设性文档嵌入）⭐

**反直觉但很有效**：不直接用 query 去检索，而是**先让 LLM 凭空"编造"一个假设的答案文档**，再用这个**假答案的向量**去检索。

```
query："光合作用的暗反应在哪里进行？"
  ↓ LLM 生成一段假设答案（可能有错，没关系）：
  "光合作用的暗反应（卡尔文循环）发生在叶绿体的基质中，利用光反应产生的 ATP 和 NADPH..."
  ↓ 嵌入这段假答案，用它的向量去检索真实文档
```

- **原理假设**：生成一个“像相关文档”的表示，可能缩小短 query 与长文档的分布差异。但假设文档中的错误实体/数字也会把检索带偏，因此应与原 query 并行召回并做来源无关的重排，不能把 HyDE 文本当证据。
- **代价**：每次检索前多一次 LLM 调用（延迟+成本）。
- **适用**：query 很短/很稀疏、问题和文档形态差异大的场景。**Multi-HyDE**（生成多个假设文档）可进一步提升，研究在金融 RAG 等场景有效。

### 2.4 查询分解（Query Decomposition）⭐

把一个**复合/多跳问题**拆成几个**子问题**，分别检索回答，再综合。

```
复合问题："对比 iPhone 15 和 Pixel 8 的相机和续航，哪个更适合摄影爱好者？"
分解为：
  1. iPhone 15 的相机参数？
  2. Pixel 8 的相机参数？
  3. iPhone 15 的续航？
  4. Pixel 8 的续航？
→ 各自检索回答 → 汇总综合 → 给出对比结论
```

- **适用**：**多跳推理、对比类、需要综合多个事实**的复杂问题。
- 这与 [文档 04](04-检索策略-混合检索与重排序.md) 的"迭代检索"和 [文档 06](06-高级RAG架构.md) 的 Agentic RAG 密切相关——子问题之间若有依赖，就需要**逐步**分解（先答 1 才知道怎么问 2）。

### 2.5 退一步提问（Step-Back Prompting）

让 LLM 先把具体问题"抽象"成一个更宏观的问题，先检索背景知识，再回到具体问题。

```
具体问题："2024 款 Model 3 长续航版的电池容量是多少？"
退一步："Tesla Model 3 各版本的电池规格" ← 先检索这个拿到背景
```

适合需要背景知识支撑的细节问题。

## 3. 路由（Routing）⭐ 多数据源 / 多策略场景必备

当系统有**多个知识库 / 多种检索策略 / 多种工具**时，需要先判断"这个问题该去哪查、用什么方式查"。

### 3.1 数据源路由（Datasource Routing）

```
                  ┌─ 是"产品功能"问题 → 查 产品文档库
用户 query → 路由器┼─ 是"订单/账单"问题 → 查 业务数据库(SQL)
                  ├─ 是"政策法规"问题 → 查 法规知识库
                  └─ 是闲聊/通用问题 → 直接让 LLM 回答（不检索）
```

### 3.2 策略路由（按问题复杂度选检索策略）

- 简单事实问题 → 一次混合检索就够。
- 复杂多跳问题 → 走查询分解 / 迭代检索。
- 不需要外部知识的问题（"你好"、"帮我翻译这句"）→ **跳过检索**，直接生成。

> **"判断是否需要检索"本身就是一个重要决策**。无脑对每个 query 都检索会引入噪声、增加延迟。Self-RAG / Adaptive RAG 的核心之一就是让模型决定"要不要检索、检索几次"。

### 3.3 路由的实现方式

- **LLM 路由**：让 LLM 做分类决策（灵活，但多一次调用、有延迟）。
- **嵌入路由（Semantic Routing）**：预先给每个路由分支准备一些示例 query 嵌入，新 query 嵌入后找最近的分支（快、便宜，无需 LLM）。
- **规则/分类器路由**：关键词规则或训练一个小分类器（最快，但需维护）。

## 4. 这些技巧怎么组合（决策指南）

不要全都上，按需选择。一个实用的组合策略：

```
多轮对话？        → 必做：指代消解改写
query 很短/稀疏？  → 考虑 HyDE
召回是瓶颈？       → 考虑 Multi-Query
复合/多跳问题？    → 查询分解
有多个数据源？     → 路由
不一定需要检索？   → 加"是否检索"判断
```

**成本意识**：每个查询转换技巧都意味着**额外的 LLM 调用 / 多次检索**，会增加延迟和费用。**先用评估确认它确实带来收益，再加进生产链路**，别堆砌。

## 5. 与生成端的衔接：Prompt 工程要点

查询转换和检索之后，把 chunk 拼进 Prompt 时的几个关键约束（避免幻觉、保证溯源）：

- **明确指令**："仅根据以下提供的资料回答；若资料中没有答案，明确说'资料中未提及'，不要编造。"
- **强制溯源**："在答案中用 [1][2] 标注每条信息来自哪个资料块。"
- **结构化资料**：给每个 chunk 编号、附来源元数据，便于模型引用。
- **处理冲突**：多个 chunk 信息矛盾时，指示模型指出冲突而非随意选一个。
- 这部分的效果要用 **Faithfulness（忠实度）** 指标来评估，见 [文档 07](07-RAG评估与可观测性.md)。

## 6. 常见坑

- **多轮对话不做指代消解**：追问检索全错，却以为是检索器的锅。
- **无脑给所有 query 做 HyDE/Multi-Query**：简单问题被过度处理，延迟飙升、成本浪费。
- **查询分解过度**：把简单问题硬拆，引入噪声、答案发散。
- **该不检索的也检索**："你好""谢谢"也去查知识库，引入无关上下文。
- **改写改变了原意**：LLM 改写时"自作主张"扭曲了用户意图。改写 Prompt 要保守、保意图。
- **不评估就上**：加了一堆查询转换，没量化收益，可能反而变差还更贵。

## 7. 深入：保真改写、路由代价与可恢复失败

### 7.1 查询不是一个字符串，而是意图契约

将原查询解析为不可丢失的约束：

```yaml
query_id: q-193
original: "对比去年两个版本在中国的企业价格，只用官方资料"
intent: compare
entities: [product-A, product-B]
time_range: [2025-01-01, 2025-12-31]
region: CN
requested_fields: [enterprise_price]
source_constraints: [official]
language: zh-CN
uncertainties: []
conversation_refs:
  "两个版本": [product-A, product-B]
```

改写 `r(q,h)` 必须满足保真约束：

```text
实体不增不减
时间/地区/单位/否定/比较对象不变
来源与权限约束不变
不把模型猜测加入“用户事实”
```

可对 original/rewrite 做结构化 diff；高风险或歧义变更触发澄清。

### 7.2 Query provenance

每个派生 query 带 lineage：

```yaml
derived_query: "2025 中国 product-A 企业版官方定价"
parent_query_id: q-193
transform: decomposition-v4
purpose: subquestion-1
preserved_constraints: [time_range, region, source_constraints]
introduced_assumptions: []
generator_version: ...
```

这样才能知道某个错误证据是原 query、改写、HyDE 还是某个子问题引入的。派生 query 也是不可信模型输出，不能决定 tenant、ACL 或扩大数据源权限。

### 7.3 原查询并行是重要保险

常见安全组合：

```text
original query ──► sparse+dense ─┐
conservative rewrite ────────────┼─► union/dedup ► rerank(original intent)
optional HyDE / expansions ──────┘
```

重排使用原始意图契约，而不是只用可能漂移的改写。若预算有限，可给原 query 保留最低候选配额，避免 expansion 全部同向漂移。

### 7.4 Multi-Query 的预算与相关性

生成 `m` 个 query、每个 top-`n` 并不等于得到 `m×n` 个独立证据；变体高度相关，会重复召回。报告：

- query semantic diversity 与约束保真率；
- union unique candidates / total candidates；
- 每个变体的独占 relevant hit；
- marginal recall gain per extra query；
- 总检索/rerank 成本与 p95。

用相同总候选预算比较“1×100、5×20、10×10”，否则多查询只是花更多预算。

### 7.5 查询分解要显式依赖和 join

```yaml
subquestions:
  - id: s1
    query: "product-A 2025 CN enterprise price official"
    depends_on: []
  - id: s2
    query: "product-B 2025 CN enterprise price official"
    depends_on: []
  - id: s3
    template: "compare {s1.price} and {s2.price} with same tax basis"
    depends_on: [s1, s2]
join:
  required: ALL
  invariants: [same_currency, same_tax_basis, same_period]
```

若子问题结果单位/时间不同，直接 join 会得到伪比较。多跳链还要记录每一 hop 的 evidence 与实体绑定，防中间错误继续扩散。

### 7.6 路由是带错分代价的分类问题

设真实路由 `z`、预测路由 `ẑ`，不同错路由代价不同：

\[
Risk(route)=\sum_{i,j}P(z=i,\hat z=j)C_{ij}
\]

例如把“余额查询”错送 FAQ 只是答不出；把当前租户请求错送全局敏感库是安全事故。路由器应输出：

```json
{
  "routes": ["official-pricing-index"],
  "confidence": 0.71,
  "abstain": false,
  "reasons": ["official-only", "pricing"],
  "policy_constraints": ["tenant=T17", "region=CN"]
}
```

低置信时可并行安全候选源、澄清或走通用低权路径；不能为了召回自动扩大到用户无权数据源。

### 7.7 Retrieval necessity 的决策

“是否检索”也需校准：

| 错误 | 后果 |
|---|---|
| 该检索却跳过 | 过时/无依据回答 |
| 不该检索却检索 | 噪声、延迟、隐私暴露、注入面 |

可用三路决策：`retrieve / no_retrieve / abstain_or_clarify`，在人工标注的任务类型上报告混淆矩阵和 cost-sensitive risk；高时效/需引用问题可由规则强制检索权威源。

### 7.8 查询漂移检测

自动检查：

- 原/改写实体、数字、日期、地区、单位集合差异；
- negation 和 modality（必须/可以/不得）变化；
- 改写后检索结果与原 query 结果是否完全分离；
- retrieved evidence 是否支持新引入术语；
- 不同 rewrite seed 是否产生不稳定路由。

检测到漂移时的回退顺序：原 query → 保守规范化 → 并行多个假设 → 向用户澄清。不要无限“再改写一次”。

### 7.9 对抗与隐私

Conversation history、检索建议和用户 query 均可含注入。Query transformer：

- 不能输出新权限/tenant/filter；
- 不应把私密会话内容发送到不必要的数据源；
- 搜索 query 本身可能外泄敏感词，要做分类/脱敏/允许域控制；
- HyDE/expansion 不得进入最终证据或长期 memory 的“事实”层；
- 全部派生 query、路由、版本和候选来源应可追踪。

### 7.10 消融协议

```text
Q0 original only
Q1 conservative rewrite + original
Q2 multi-query（固定总候选）
Q3 HyDE + original（固定总候选）
Q4 decomposition with dependency graph
Q5 learned/LLM route + abstain
```

按指代、错别字、精确 ID、多跳、时间/地区约束和无检索任务分层；报告 constraint preservation、route confusion/cost、candidate recall、answer/citation correctness、cost/success 和 p95。

## 8. 本章小结

- 用户原始 query 可能不适合直接检索，但转换会引入漂移；必须保留原 query、意图约束和 lineage。
- 指代消解常有价值，歧义时应澄清或保留多假设，不能强行补全。
- **Multi-Query**：多角度改写并行检索，对冲语义错配，提升召回。
- **HyDE**：先让 LLM 生成假设答案，用假答案向量去检索，解决"问题和答案形态不一致"。
- **查询分解**：拆解复合/多跳问题，分别检索再综合。
- **路由**：多数据源/多策略时先判断"去哪查、怎么查、要不要查"。
- 这些技巧**按需组合、用评估验证收益**，别堆砌（每个都加延迟和成本）。

## 9. 检验清单

- [ ] 能解释为什么多轮对话必须做查询改写（指代消解）。
- [ ] 能说清 HyDE 的原理：为什么"用假答案去检索"反而更准。
- [ ] 知道 Multi-Query 和查询分解的区别（前者同一问题多角度，后者拆成子问题）。
- [ ] 理解"判断是否需要检索"本身的价值。
- [ ] 知道每个查询转换都有成本，要用评估决定是否采用。
- [ ] 能写出 query intent contract，并检查实体/时间/地区/否定的保真。
- [ ] 能设计原查询并行、派生 query lineage 与漂移回退。
- [ ] 能用 cost matrix、置信度和 abstain 评估路由，而不只报准确率。
