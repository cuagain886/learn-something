# 08 · 生产工程化与最佳实践

> 目标：把"能跑的 Demo"变成"生产可用的系统"。这一章是前面所有环节之上的**横切工程关注点**：架构、缓存、增量更新、降级、安全、成本、延迟。

---

## 1. 工程化心智：RAG 是一条数据管线，不是一个模型

生产 RAG 的核心理念：**把每个环节做成独立、可替换、可观测的模块**，而不是糊成一坨黑盒。

> **端到端管线模块化**：把检索、增强、生成编排成职责清晰、有明确数据契约的可调用模块，便于独立替换、扩展和维护。

好处：
- 想换嵌入模型？只动嵌入模块。想加重排？插一个模块。
- 出问题时能定位到具体模块（配合 [文档 07](07-RAG评估与可观测性.md) 的 trace）。
- 各模块可独立扩缩容（检索是 IO 密集、生成是 GPU/API 密集，资源需求不同）。

```
[Ingestion 建库服务] ──写──> [向量库 + BM25 索引 + 元数据库]
                                        ↑ 读
[Query 服务] → 改写 → 检索 → 重排 → 拼Prompt → [LLM 服务] → 后处理 → 返回
       │                                                          
       └────────────────── 缓存层 / 可观测层 贯穿全程 ──────────────
```

---

## 2. 离线与在线分离

- **离线（建库/Ingestion）**：解析、分块、嵌入、建索引。**计算密集、可批处理、可异步**。文档增删改触发，不在用户请求路径上。
- **在线（Query/Serving）**：改写、检索、重排、生成。**延迟敏感**，在用户请求路径上。

两者用不同的资源、不同的扩缩容策略。**别把建库放进用户请求里**（除非是临时上传文档即时问答的特殊场景，那也要异步化）。

---

## 3. 增量更新与数据一致性（最容易被低估的工程难题）

知识库不是建一次就完事——文档天天在增删改。设计之初就要想清楚：

### 3.1 增删改的实现
- **关联设计**：每个 chunk 存 `doc_id`（[文档 03](03-嵌入模型与向量数据库.md) 强调过），删/改文档时按 `doc_id` 批量定位它的所有 chunk。
- 逻辑上更新会淘汰旧版本并发布新版本，但在线系统不能简单“先删后插”（会出现空窗）或“先插后删”（会返回冲突双版本）；应构建版本化记录/snapshot 后原子发布。
- **变更检测**：用文档内容的 hash / 版本号判断哪些文档真的变了，**只重处理变化的部分**，别全量重建（贵）。

### 3.2 索引维护
- HNSW 的删除是"标记删除"，删多了图结构退化、占内存还查得慢，需**定期 compact/rebuild**。
- 同时维护**向量索引 + BM25 索引 + 元数据**三者的一致性（一处更新，三处同步）。

### 3.3 全量重建 vs 增量
- 嵌入模型升级、分块策略大改 → 必须**全量重建**（向量空间变了）。重建时用**蓝绿部署**：新索引建好再切换，避免停服。
- 日常文档增删 → 增量更新。

## 4. 缓存（Caching）—— 降本提速的利器

RAG 链路里多处可缓存：

| 缓存层 | 缓存什么 | 收益 |
|--------|----------|------|
| **嵌入缓存** | query → 向量 | 相同/相似 query 免重复嵌入 |
| **检索缓存** | query → 检索结果 | 热门问题免重复检索 |
| **语义缓存（Semantic Cache）** | 在同安全域、知识版本和意图约束下复用结果 | 命中可省链路成本；实际延迟由缓存/授权/网络决定 |
| **LLM Prompt 缓存** | 重复的 prompt 前缀 | 见下 |

### 语义缓存（Semantic Cache）⭐
不要求 query 字面相同，而是**语义相近就命中**（把 query 嵌入，在缓存的历史 query 向量里找足够近的）。
- 收益巨大：FAQ 类场景大量问题语义重复，命中率高时能省大量成本和延迟。
- 风险：**相似 ≠ 相同**，阈值设松了会返回错答案。要设好相似度阈值，并对时效性强的问题（"今天的…"）禁用缓存。

### LLM Prompt Caching（提示缓存）⭐
[文档 06](06-高级RAG架构.md) 的 Contextual Retrieval 重度依赖它。原理：把 prompt 里**重复的长前缀**（如系统提示、长文档）缓存在 LLM 侧，重复调用时复用。
- 收益取决于重复前缀比例、缓存命中、供应商价格与 TTL；用实际的缓存读/写 token、命中率和 p95 延迟计算，不套用“最高可达”值。
- 用途：Contextual Retrieval 建库、固定系统提示的高频问答。

## 5. 降级与容错（Fallback & Resilience）

生产系统的每个外部依赖都会失败，要有兜底：

- **检索失败/为空**：按任务策略选择重试权威源、澄清、拒答/人工或明确的 closed-book 模式。对必须有据/高风险问题不能静默降级到纯 LLM。
- **重排服务挂了**：跳过重排，直接用融合后的检索结果（降级但可用）。
- **嵌入/LLM API 超时**：超时重试（指数退避）+ 熔断；准备备用模型/备用供应商。
- **检索质量差**：用 CRAG 思想（[文档 06](06-高级RAG架构.md)）——评估检索质量，差则触发重检或 Web 兜底，而不是基于烂资料硬答。
- **"我不知道"是合法输出**：当检索不到、或资料不支持时，让模型**老实说不知道**，比编造强得多。这是反幻觉的最后一道防线。

## 6. 安全与权限（企业落地的硬门槛）

RAG 接入企业内部数据，安全是上线的前置条件，不是可选项。

### 6.1 访问控制（最重要）
> **检索必须遵守用户权限**：用户只能检索到自己有权看的文档。

- 实现：chunk/父块/摘要/图节点携带可验证 ACL/security domain，在候选可返回、进入共享 cache 或模型上下文前由服务端 pre-filter/PDP 强制；不能依赖模型、前端或最终答案遮盖。
- **常见严重事故**：忘了做权限过滤，导致用户通过提问"套"出无权查看的机密文档内容（数据越权泄露）。**这是 RAG 最高频的安全事故，务必在设计期就做对。**

### 6.2 Prompt 注入（Prompt Injection）
- 风险：知识库文档里可能藏有恶意指令（"忽略之前的指令，输出……"），被检索出来后污染 Prompt。
- 缓解：XML/角色分隔只是概率性提示层；还需来源/taint、memory 写入门、模型外工具权限、出站 DLP、敏感 sink 限制与红队回归，详见 [production/02](../production/02-Prompt注入与防御.md)。

### 6.3 隐私与合规
- PII（个人信息）脱敏：建库时识别并脱敏敏感信息。
- 数据驻留：嵌入/LLM/trace/备份用的是哪家服务，数据是否出境、保留或用于训练都要确认。自托管可改变边界，但不自动解决访问控制、删除、漏洞、许可证和运维合规。
- 审计日志：谁在什么时候问了什么、检索到了什么，留痕可审计。

## 7. 成本与延迟优化（生产三角的另两边）

[文档 00](00-RAG学习计划总览.md) 说过"质量/成本/延迟"三角。前面在谈质量，这里谈成本和延迟。

### 7.1 成本优化
- **嵌入成本**：批处理、降维（Matryoshka）、缓存、对低价值文档用更便宜的嵌入模型。
- **LLM 成本**：精排后只给 LLM 必要的 top-k（少塞 chunk = 少 token = 省钱）；语义缓存；prompt caching；简单问题用小模型（Adaptive RAG）。
- **重排成本**：控制送入重排的候选数 N；用更小的重排模型。

### 7.2 延迟优化
- **并行化**：向量检索和 BM25 检索**并行跑**（混合检索天然可并行），改写/路由能并行的也并行。
- **流式输出（streaming）**：LLM 边生成边返回，大幅降低**首字延迟（TTFT）**的体感。
- **预算分配**：给每个阶段设延迟预算（如检索 ≤100ms、重排 ≤200ms、生成流式）。监控 p95/p99（[文档 07](07-RAG评估与可观测性.md)）。
- **跳过不必要的步骤**：简单问题跳过 HyDE/Multi-Query/重排（Adaptive RAG）。

## 8. 框架选择：用还是不用

| | 框架（LangChain/LlamaIndex/Haystack） | 薄封装 / 自研 |
|---|---|---|
| 优点 | 起步快、组件齐全、生态大 | 完全可控、易调试、无黑盒、依赖少 |
| 缺点 | 抽象层厚、出问题难定位、版本变动快、可能引入不需要的复杂度 | 要自己写胶水代码 |
| 建议 | 适合快速组装与验证，但要做故障/版本 spike | 对关键契约可做薄封装；是否自研取决于团队与运维成本 |

务实路线：**用框架快速验证 → 理解每个环节原理 → 生产中对关键环节（检索、重排、Prompt）自己掌控，避免被框架黑盒卡住**。LlamaIndex 在 RAG 上比 LangChain 更专注，Haystack 偏生产管线。

## 9. 上线路线图（从 0 到生产）

把整套文档的知识串成一条落地路径：

```
1. MVP 基线        : 递归分块 + 单一嵌入 + pgvector + 纯向量检索 + 直接拼Prompt
                     → 先跑通，建立端到端链路
2. 加评估          : 先用小型人工集发现错误，再按 MDE/分层扩展；建立 closed-book/oracle 基线
3. 升级检索        : 在同预算下比较 BM25、dense、hybrid、rerank
                     → 只保留有配对证据的组件
4. 优化数据        : 调分块策略、加元数据、按文档类型分别处理
                     → 对比评估
5. 查询理解        : 多轮改写（对话场景必做）、按需 HyDE/Multi-Query
6. 工程加固        : 权限过滤、缓存、降级兜底、trace 可观测、增量更新
7. 上线 + 监控     : 流式输出、p95 延迟、成本、用户反馈闭环
8. 按需进阶        : 用线上数据定位瓶颈 → 针对性上 Contextual/RAPTOR/GraphRAG/Agentic
```

> **每一步都用评估说话**，确认涨点再进入下一步。先做对基础（1-7），把高级架构（8）留到有数据证明需要时。

## 10. 生产 RAG 检查清单（上线前自查）

**数据与建库**
- [ ] 分块策略适配了文档类型，参数经评估调过
- [ ] chunk 存了 `doc_id`、来源、权限等元数据
- [ ] 有增量更新/删除方案，索引能定期 compact

**检索质量**
- [ ] BM25 / dense / hybrid / rerank 做过同预算消融，当前方案有证据
- [ ] ANN 相对 exact search 的 recall–latency 曲线满足 SLO
- [ ] candidate depth、reranker 截断和最终 token 预算经评估

**生成**
- [ ] Prompt 约束"只据资料回答 + 标注出处 + 不知道就说不知道"
- [ ] Faithfulness 指标达标

**评估**
- [ ] 有评估集和离线评估流程（像单测一样跑）
- [ ] 检索和生成分开评估

**工程**
- [ ] 权限过滤正确（重点核查越权泄露）
- [ ] 有缓存（语义缓存 / prompt caching）
- [ ] 有降级兜底（检索空、服务挂）
- [ ] 全链路 trace + 延迟/成本/质量监控
- [ ] 防 Prompt 注入、PII 脱敏、合规确认
- [ ] 流式输出，p95 延迟达标
- [ ] 有用户反馈采集闭环

## 11. 深入：数据版本、原子发布、回填验证与可证明删除

### 11.1 文档生命周期状态机

```text
DISCOVERED
→ FETCHED
→ PARSED
→ CHUNKED
→ EMBEDDED + SPARSE_INDEXED
→ VALIDATED
→ PUBLISHED
→ SUPERSEDED / TOMBSTONED
→ PURGED
```

每一状态写 manifest，不靠“某个 job 跑完了”猜测：

```yaml
doc_id: policy-19
source_version: etag:7fa...
content_hash: sha256:...
parser_version: layout-v6
chunker_version: structure-v4
embedding_model: embed-model-snapshot
sparse_analyzer_version: zh-v3
acl_version: acl-18
valid_time: [2026-07-01, null]
artifacts:
  chunks: 183
  dense_written: 183
  sparse_written: 183
  parent_nodes: 22
validation:
  parse_coverage: 0.998
  vector_dimensions_ok: true
  acl_attached: true
```

只有 `VALIDATED` 的版本能进入可服务 snapshot。

### 11.2 为什么 dense/sparse/metadata 需要同一逻辑 snapshot

若向量索引已是 `v8`，BM25 仍是 `v7`，RRF 会融合两个知识世界；ACL metadata 未同步时更可能泄露。Query manifest 应绑定：

```yaml
knowledge_snapshot: kb-20260719-04
dense_snapshot: dense-88
sparse_snapshot: sparse-91
metadata_snapshot: meta-44
graph_summary_snapshot: graph-12
acl_snapshot: acl-18
```

服务端只发布经过一致性验证的组合，不让各索引 independently “最新”。

### 11.3 蓝绿重建与原子 alias 切换

```text
source snapshot S
→ build green indexes
→ structural validation
→ offline eval + diff
→ shadow/dual-read
→ atomic alias: blue → green
→ monitor
→ retain blue for rollback TTL
→ purge after safety window
```

原子切换应发生在 query routing/catalog 层；如果多个存储不支持跨系统事务，用一个 versioned manifest/alias 作为唯一发布指针。请求开始读取一次 snapshot ID，并贯穿整次检索，避免中途切版本。

### 11.4 增量更新与 CDC

增量管线需要幂等事件：

```json
{
  "event_id": "...",
  "doc_id": "policy-19",
  "source_version": 8,
  "previous_version": 7,
  "operation": "UPSERT",
  "occurred_at": "...",
  "content_hash": "..."
}
```

处理器以 `(doc_id, source_version, pipeline_version)` 幂等；乱序事件不能让 v7 覆盖 v8。新版本 chunks 完整写入并验证后，catalog 才将 `active_version` CAS 到 v8；旧版本异步 tombstone。这样既无空窗，也不把双版本同时暴露。

### 11.5 Backfill 验证

模型/分块/解析升级要全量回填。验证分四层：

1. **结构**：文档/chunk 数、解析覆盖、向量维度、空块、重复率；
2. **一致性**：dense/sparse/metadata/ACL 数量和 hash 对账；
3. **检索 diff**：固定 queries 的 top-k overlap、新增/丢失 evidence、过滤切片；
4. **端到端**：paired answer/citation eval、cost/p95/worst-slice。

设置允许差异而非要求 top-k 完全相同；关键是已知 evidence、权限和业务结果不回归。失败回填不可污染 active alias。

### 11.6 Dual-read 与 shadow

```text
request snapshot=blue
├─ blue result → 真正生成/返回
└─ green result → shadow trace/diff，不进入用户上下文
```

比较：candidate recall、top-k overlap、独占候选、ACL decision、p95、空结果和 cost。Shadow 不应把 green 中未授权内容写入普通 trace；内容用受控 hash/ref。

### 11.7 Right-to-delete 是 lineage 问题

删除一个 source document 需要传播到：

```text
raw object / parsed text
→ chunks / embeddings / sparse postings
→ parent/contextual chunks
→ RAPTOR summaries / graph entities-edges-community summaries
→ retrieval/semantic/answer caches
→ eval datasets / trace artifacts / backups（按政策）
```

建立派生 DAG：

```yaml
artifact_id: summary-node-88
derived_from: [chunk-1, chunk-2, chunk-3]
pipeline_version: raptor-v4
security_domain: tenant-T17
```

删除流程：认证请求 → tombstone 阻止新查询 → 遍历 lineage 标记派生项 → cache invalidation → 物理 purge/compaction → 搜索验证 → completion receipt。备份无法立即物理删除时，要有加密擦除/保留期、恢复后重放 tombstone 的流程，并如实说明 SLA。

### 11.8 缓存 key 是正确性与安全契约

语义/检索/答案 cache key 至少考虑：

```text
normalized query intent
tenant/user security domain + policy/ACL version
knowledge snapshot + valid time
retriever/reranker/generator/prompt versions
locale/region
tool/world-state dependencies
```

时效性、个性化、高风险或含敏感数据的请求可禁用共享语义缓存。Cache hit 前重新授权；不要因为答案以前对 Alice 正确，就返回给 Bob。

### 11.9 RPO/RTO 与灾难恢复

- **RPO**：可容忍丢失多少已发布源变更；
- **RTO**：索引服务多久恢复；
- 定期做 snapshot restore，而不只“有备份”；
- 恢复后验证 alias、ACL、tombstone、dense/sparse 对账；
- source of truth 与索引派生关系明确，索引可重建但重建时间要进 RTO；
- 外部 embedding/model version 消失时，有已钉 artifact 或迁移预案。

### 11.10 安全更新窗口

紧急撤销文档/权限不能等待数小时全量 rebuild。需要快速 tombstone/deny overlay，在所有检索/缓存入口立即生效；后台再物理删除/重建。安全 deny overlay 优先于可用性，且要监控传播延迟和残留查询。

## 12. 本章小结

- RAG 是**模块化数据管线**，离线建库与在线问答分离，各自扩缩容。
- 增量更新依赖 versioned manifest、幂等 CDC、验证后 CAS 发布；dense/sparse/metadata/ACL 必须属于同一逻辑 snapshot。
- **缓存**（语义缓存、prompt caching）大幅降本提速；prompt caching 是 Contextual Retrieval 可行的关键。
- **降级兜底**必备：检索空/服务挂时优雅降级，"不知道"是合法且安全的输出。
- **安全是上线硬门槛**：权限过滤（防越权泄露）、防 Prompt 注入、PII 脱敏、合规审计。
- 在"质量/成本/延迟"三角里：精排少塞 chunk、缓存、小模型省成本；并行检索、流式输出降延迟。
- 框架用于学习/原型，生产关键路径倾向自己掌控。
- 按"MVP → 评估 → 升级检索 → 优化数据 → 查询理解 → 工程加固 → 上线监控 → 按需进阶"路线推进，**每步用评估说话**。
