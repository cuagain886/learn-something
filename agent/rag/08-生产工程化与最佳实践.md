# 08 · 生产工程化与最佳实践

> 目标：把"能跑的 Demo"变成"生产可用的系统"。这一章是前面所有环节之上的**横切工程关注点**：架构、缓存、增量更新、降级、安全、成本、延迟。

---

## 1. 工程化心智：RAG 是一条数据管线，不是一个模型

生产 RAG 的核心理念：**把每个环节做成独立、可替换、可观测的模块**，而不是糊成一坨黑盒。

> **端到端管线模块化**：把检索、增强、生成编排成职责清晰、有明确数据契约的可调用模块，便于独立替换、扩展和维护。

好处：
- 想换嵌入模型？只动嵌入模块。想加重排？插一个模块。
- 出问题时能定位到具体模块（配合 [文档 07](07-RAG评估与可观测性.md) 的 trace）。
- 各模块可独立扩缩容（检索是 IO 密集、生成是 GPU/API 密集，资源需求不同）。

```
[Ingestion 建库服务] ──写──> [向量库 + BM25 索引 + 元数据库]
                                        ↑ 读
[Query 服务] → 改写 → 检索 → 重排 → 拼Prompt → [LLM 服务] → 后处理 → 返回
       │                                                          
       └────────────────── 缓存层 / 可观测层 贯穿全程 ──────────────
```

---

## 2. 离线与在线分离

- **离线（建库/Ingestion）**：解析、分块、嵌入、建索引。**计算密集、可批处理、可异步**。文档增删改触发，不在用户请求路径上。
- **在线（Query/Serving）**：改写、检索、重排、生成。**延迟敏感**，在用户请求路径上。

两者用不同的资源、不同的扩缩容策略。**别把建库放进用户请求里**（除非是临时上传文档即时问答的特殊场景，那也要异步化）。

---

## 3. 增量更新与数据一致性（最容易被低估的工程难题）

知识库不是建一次就完事——文档天天在增删改。设计之初就要想清楚：

### 3.1 增删改的实现
- **关联设计**：每个 chunk 存 `doc_id`（[文档 03](03-嵌入模型与向量数据库.md) 强调过），删/改文档时按 `doc_id` 批量定位它的所有 chunk。
- **更新 = 删旧 + 插新**：文档改了，删掉旧 chunk，重新分块嵌入插入。
- **变更检测**：用文档内容的 hash / 版本号判断哪些文档真的变了，**只重处理变化的部分**，别全量重建（贵）。

### 3.2 索引维护
- HNSW 的删除是"标记删除"，删多了图结构退化、占内存还查得慢，需**定期 compact/rebuild**。
- 同时维护**向量索引 + BM25 索引 + 元数据**三者的一致性（一处更新，三处同步）。

### 3.3 全量重建 vs 增量
- 嵌入模型升级、分块策略大改 → 必须**全量重建**（向量空间变了）。重建时用**蓝绿部署**：新索引建好再切换，避免停服。
- 日常文档增删 → 增量更新。

## 4. 缓存（Caching）—— 降本提速的利器

RAG 链路里多处可缓存：

| 缓存层 | 缓存什么 | 收益 |
|--------|----------|------|
| **嵌入缓存** | query → 向量 | 相同/相似 query 免重复嵌入 |
| **检索缓存** | query → 检索结果 | 热门问题免重复检索 |
| **语义缓存（Semantic Cache）** | 语义相近的 query → 已有答案 | 命中则**整条链路都省**，延迟降到几十 ms |
| **LLM Prompt 缓存** | 重复的 prompt 前缀 | 见下 |

### 语义缓存（Semantic Cache）⭐
不要求 query 字面相同，而是**语义相近就命中**（把 query 嵌入，在缓存的历史 query 向量里找足够近的）。
- 收益巨大：FAQ 类场景大量问题语义重复，命中率高时能省大量成本和延迟。
- 风险：**相似 ≠ 相同**，阈值设松了会返回错答案。要设好相似度阈值，并对时效性强的问题（"今天的…"）禁用缓存。

### LLM Prompt Caching（提示缓存）⭐
[文档 06](06-高级RAG架构.md) 的 Contextual Retrieval 重度依赖它。原理：把 prompt 里**重复的长前缀**（如系统提示、长文档）缓存在 LLM 侧，重复调用时复用。
- 收益：**延迟降 2 倍以上、成本降最高 90%**。
- 用途：Contextual Retrieval 建库、固定系统提示的高频问答。

## 5. 降级与容错（Fallback & Resilience）

生产系统的每个外部依赖都会失败，要有兜底：

- **检索失败/为空**：降级到纯 LLM 回答（并明确告知"未找到相关资料"），或返回兜底话术，绝不静默乱答。
- **重排服务挂了**：跳过重排，直接用融合后的检索结果（降级但可用）。
- **嵌入/LLM API 超时**：超时重试（指数退避）+ 熔断；准备备用模型/备用供应商。
- **检索质量差**：用 CRAG 思想（[文档 06](06-高级RAG架构.md)）——评估检索质量，差则触发重检或 Web 兜底，而不是基于烂资料硬答。
- **"我不知道"是合法输出**：当检索不到、或资料不支持时，让模型**老实说不知道**，比编造强得多。这是反幻觉的最后一道防线。

## 6. 安全与权限（企业落地的硬门槛）

RAG 接入企业内部数据，安全是上线的前置条件，不是可选项。

### 6.1 访问控制（最重要）
> **检索必须遵守用户权限**：用户只能检索到自己有权看的文档。

- 实现：chunk 元数据里存**权限标签**（部门、角色、文档密级），检索时用**元数据过滤**（[文档 03](03-嵌入模型与向量数据库.md)）只在用户有权的子集里搜。
- **常见严重事故**：忘了做权限过滤，导致用户通过提问"套"出无权查看的机密文档内容（数据越权泄露）。**这是 RAG 最高频的安全事故，务必在设计期就做对。**

### 6.2 Prompt 注入（Prompt Injection）
- 风险：知识库文档里可能藏有恶意指令（"忽略之前的指令，输出……"），被检索出来后污染 Prompt。
- 缓解：把检索内容和指令明确分隔（如用 XML 标签包裹资料）、对检索内容做清洗、对输出做审查、最小权限原则（RAG 系统本身别有危险的工具权限）。

### 6.3 隐私与合规
- PII（个人信息）脱敏：建库时识别并脱敏敏感信息。
- 数据驻留：嵌入/LLM 用的是哪家 API，数据会不会出境/被用于训练，企业场景要确认合规。自托管模型可规避。
- 审计日志：谁在什么时候问了什么、检索到了什么，留痕可审计。

## 7. 成本与延迟优化（生产三角的另两边）

[文档 00](00-RAG学习计划总览.md) 说过"质量/成本/延迟"三角。前面在谈质量，这里谈成本和延迟。

### 7.1 成本优化
- **嵌入成本**：批处理、降维（Matryoshka）、缓存、对低价值文档用更便宜的嵌入模型。
- **LLM 成本**：精排后只给 LLM 必要的 top-k（少塞 chunk = 少 token = 省钱）；语义缓存；prompt caching；简单问题用小模型（Adaptive RAG）。
- **重排成本**：控制送入重排的候选数 N；用更小的重排模型。

### 7.2 延迟优化
- **并行化**：向量检索和 BM25 检索**并行跑**（混合检索天然可并行），改写/路由能并行的也并行。
- **流式输出（streaming）**：LLM 边生成边返回，大幅降低**首字延迟（TTFT）**的体感。
- **预算分配**：给每个阶段设延迟预算（如检索 ≤100ms、重排 ≤200ms、生成流式）。监控 p95/p99（[文档 07](07-RAG评估与可观测性.md)）。
- **跳过不必要的步骤**：简单问题跳过 HyDE/Multi-Query/重排（Adaptive RAG）。

## 8. 框架选择：用还是不用

| | 框架（LangChain/LlamaIndex/Haystack） | 薄封装 / 自研 |
|---|---|---|
| 优点 | 起步快、组件齐全、生态大 | 完全可控、易调试、无黑盒、依赖少 |
| 缺点 | 抽象层厚、出问题难定位、版本变动快、可能引入不需要的复杂度 | 要自己写胶水代码 |
| 建议 | **学习期/原型期用**，快速跑通理解全貌 | **生产关键路径倾向自己掌控**，框架只用在不关键处 |

务实路线：**用框架快速验证 → 理解每个环节原理 → 生产中对关键环节（检索、重排、Prompt）自己掌控，避免被框架黑盒卡住**。LlamaIndex 在 RAG 上比 LangChain 更专注，Haystack 偏生产管线。

## 9. 上线路线图（从 0 到生产）

把整套文档的知识串成一条落地路径：

```
1. MVP 基线        : 递归分块 + 单一嵌入 + pgvector + 纯向量检索 + 直接拼Prompt
                     → 先跑通，建立端到端链路
2. 加评估          : 准备 30~50 条评估集，接 RAGAS → 测出基线指标（关键！）
3. 升级检索        : 加 BM25 → 混合检索 + RRF → Cross-Encoder 重排
                     → 每步对比评估指标，确认涨点
4. 优化数据        : 调分块策略、加元数据、按文档类型分别处理
                     → 对比评估
5. 查询理解        : 多轮改写（对话场景必做）、按需 HyDE/Multi-Query
6. 工程加固        : 权限过滤、缓存、降级兜底、trace 可观测、增量更新
7. 上线 + 监控     : 流式输出、p95 延迟、成本、用户反馈闭环
8. 按需进阶        : 用线上数据定位瓶颈 → 针对性上 Contextual/RAPTOR/GraphRAG/Agentic
```

> **每一步都用评估说话**，确认涨点再进入下一步。先做对基础（1-7），把高级架构（8）留到有数据证明需要时。

## 10. 生产 RAG 检查清单（上线前自查）

**数据与建库**
- [ ] 分块策略适配了文档类型，参数经评估调过
- [ ] chunk 存了 `doc_id`、来源、权限等元数据
- [ ] 有增量更新/删除方案，索引能定期 compact

**检索质量**
- [ ] 用了混合检索（向量 + BM25）+ RRF
- [ ] 有 Cross-Encoder 重排
- [ ] top-k 经评估调过，没给 LLM 塞过多噪声

**生成**
- [ ] Prompt 约束"只据资料回答 + 标注出处 + 不知道就说不知道"
- [ ] Faithfulness 指标达标

**评估**
- [ ] 有评估集和离线评估流程（像单测一样跑）
- [ ] 检索和生成分开评估

**工程**
- [ ] 权限过滤正确（重点核查越权泄露）
- [ ] 有缓存（语义缓存 / prompt caching）
- [ ] 有降级兜底（检索空、服务挂）
- [ ] 全链路 trace + 延迟/成本/质量监控
- [ ] 防 Prompt 注入、PII 脱敏、合规确认
- [ ] 流式输出，p95 延迟达标
- [ ] 有用户反馈采集闭环

## 11. 本章小结

- RAG 是**模块化数据管线**，离线建库与在线问答分离，各自扩缩容。
- **增量更新**靠 `doc_id` 关联、变更检测、定期 compact，是最易被低估的工程难题。
- **缓存**（语义缓存、prompt caching）大幅降本提速；prompt caching 是 Contextual Retrieval 可行的关键。
- **降级兜底**必备：检索空/服务挂时优雅降级，"不知道"是合法且安全的输出。
- **安全是上线硬门槛**：权限过滤（防越权泄露）、防 Prompt 注入、PII 脱敏、合规审计。
- 在"质量/成本/延迟"三角里：精排少塞 chunk、缓存、小模型省成本；并行检索、流式输出降延迟。
- 框架用于学习/原型，生产关键路径倾向自己掌控。
- 按"MVP → 评估 → 升级检索 → 优化数据 → 查询理解 → 工程加固 → 上线监控 → 按需进阶"路线推进，**每步用评估说话**。
