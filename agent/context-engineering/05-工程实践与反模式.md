# 05 · 工程实践：可重放的上下文系统与证据驱动诊断

> 目标：把 MCP、上下文装配、记忆和压缩做成一个**可重放、可消融、可审计**的生产子系统。面试时不只会说“减少 token”，而能说明数据契约、不变量、故障定位、因果实验和安全边界。

---

## 1. 先纠正架构：上下文不是系统状态本身

模型在第 (k) 步看到的 prompt，只是系统状态对本轮决策的一次**有预算投影**：

\[
C_k=A(S_k, q_k, B_k, P_k)
\]

- (S_k)：外部持久状态，包括事件日志、任务状态、世界快照、artifact、记忆和审批。
- (q_k)：当前决策问题，例如“选择下一工具”或“生成最终回答”。
- (B_k)：本轮 token、延迟和成本预算。
- (P_k)：权限、信任、新鲜度、地域和数据保留策略。
- (A)：确定性的 context assembler；输出 (C_k) 及 manifest。

这一定义带来三个重要结论：

1. **窗口不是事实源。** compaction 后仍应能从 event/artifact store 回取原文。
2. **任务恢复不能依赖模型回忆。** checkpoint 记录机器可验证状态和已提交副作用。
3. **上下文选择本身是可测试组件。** 同一个 (S_k,q_k) 应能离线重放不同装配策略。

### 1.1 六类外部状态不要混在一段聊天历史里

| 存储 | 保存什么 | 一致性要求 | 典型生命周期 |
|------|----------|------------|--------------|
| Event log | 用户输入、工具请求/结果、审批、状态迁移 | append-only、可排序、可去重 | 一次任务及审计期 |
| Task state | 当前节点、计划 DAG、owner、lease、重试计数 | 乐观锁/CAS、checkpoint | 一次执行 |
| World snapshot | 外部系统已观测状态及版本 | 来源、observed time、freshness | 随外部世界变化 |
| Artifact store | 网页、文件、代码、报告等大对象 | URI、hash、权限、版本 | 任务或组织保留期 |
| Long-term memory | 经治理后可跨任务复用的事实/经验 | valid time、supersedes、删除传播 | 用户/组织级 |
| Policy/tool registry | 不可覆盖策略、工具 schema、能力与风险级别 | 版本固定、签名/发布流程 | 随部署版本变化 |

把这些都序列化为“过去对话摘要”，会丢掉事务状态、版本、来源和删除能力。

## 2. Context block：装配器的最小数据契约

进入窗口的内容不能只是字符串。每个 block 至少携带：

```yaml
context_block:
  block_id: cb_0192
  kind: policy | goal | plan | evidence | memory | tool_schema | recent_event | summary
  content_ref: inline | artifact://task-7/web-2#L40-L72
  content_hash: sha256:...
  source:
    producer: crm.read_customer
    principal: user_123
    authority: crm_customer_record
  trust: trusted_control | trusted_data | untrusted_external
  instruction_authority: system | developer | user | none
  observed_at: 2026-07-19T10:02:00+08:00
  valid_from: 2026-07-01T00:00:00+08:00
  expires_at: 2026-07-19T10:07:00+08:00
  scope: {tenant: t_9, user: u_3, task: task_7}
  sensitivity: internal
  token_count: 284
  priority: 80
  dependencies: [cb_0188]
  selected_because: "current refund decision needs account tier"
```

这里最容易混淆的是：

- `trust` 表示数据来源可信程度，**不授予指令权限**。可信 CRM 字段仍只是数据。
- `observed_at` 是系统何时看到它；`valid_from/to` 是事实何时在世界中成立。
- `content_ref + hash` 允许摘要按需回源并验证内容没有漂移。
- `scope` 用于装配前隔离，不能先全局检索、再寄希望于模型忽略别人的数据。

### 2.1 装配不变量

生产装配器应以代码强制以下条件：

1. 不可覆盖 policy、用户当前目标、未决审批和已提交副作用不能被静默裁掉。
2. assistant tool call 与对应 tool result 作为一个事务块保留或删除。
3. 同一事实冲突先按 source authority、版本和时间解析；无法解析时显式标记 `unknown/conflict`。
4. 过期证据不能静默参与高风险决策；应刷新、降权或要求人工确认。
5. block 必须通过 tenant/user/task scope 过滤，再参与相关性排序。
6. 外部数据中的文字不因进入高优先级位置而获得更高指令权限。
7. 裁剪必须稳定：相同输入、策略版本与 tokenizer 产生相同 manifest/hash。

## 3. 一个确定性的装配算法

先记预算，而不是先拼字符串再截断：

\[
B_{input}=W-B_{output}-B_{reasoning}-B_{tool\_result}-B_{safety}
\]

其中工具可能返回大对象，`B_tool_result` 不能默认成零。一个可实现的流程如下：

```python
def assemble(snapshot, query, budget, policy_version):
    candidates = []
    candidates += load_protected_policy(policy_version)
    candidates += load_goal_plan_commitments(snapshot.task_id)
    candidates += discover_minimal_tools(query, snapshot.allowed_capabilities)
    candidates += retrieve_evidence(query, scope=snapshot.scope)
    candidates += retrieve_memory(query, scope=snapshot.scope)
    candidates += recent_complete_transactions(snapshot.event_log)
    candidates += summaries_with_source_refs(snapshot.older_events)

    candidates = enforce_scope(candidates)
    candidates = resolve_version_time_conflicts(candidates)
    candidates = mark_taint_and_instruction_authority(candidates)
    candidates = rerank_for_current_decision(candidates, query)

    selected, rejected = budgeted_pack(
        protected=protected(candidates),
        optional=optional(candidates),
        token_budget=budget.input,
        atomic_groups=tool_transactions(candidates),
    )
    assert_context_invariants(selected)
    return render(selected), build_manifest(selected, rejected)
```

`budgeted_pack` 不是普通 top-k：它近似一个带约束的 knapsack 问题。相关性高但重复的十个 chunk，不一定比一条目标约束和一条权威证据更有价值。可以按以下顺序实现基线：

1. 先放 protected blocks；超预算则失败并升级，绝不截 policy。
2. 为当前动作只暴露最小工具集；大目录使用 tool search/deferred loading。
3. 对证据先去重、聚类、冲突解析，再按边际信息增益选择。
4. 保留近期完整事务；旧事件用可回源摘要。
5. 记录每个未选 block 的原因：scope、expired、duplicate、low score 或 budget cutoff。

### 3.1 Manifest 是调试现场，不是完整 prompt 日志的同义词

一次装配 trace 至少记录：

```json
{
  "context_run_id": "ctx_81",
  "task_id": "task_7",
  "step": 12,
  "assembler_version": "4.3.1",
  "policy_version": "refund-2026-07-01",
  "model_snapshot": "pinned-model-id",
  "tokenizer_version": "...",
  "input_budget": 48000,
  "selected_block_ids": ["cb_1", "cb_7", "cb_9"],
  "rejected": [{"id": "cb_8", "reason": "expired"}],
  "context_hash": "sha256:...",
  "redaction_profile": "prod-sensitive-v2"
}
```

高敏场景未必能长期保存完整 prompt；可以保存受控 artifact 引用、hash、block 元数据和脱敏预览。trace 用于重放模型的**可见输入和外部动作**，不要求记录或暴露模型隐藏的 chain-of-thought。

## 4. 证据驱动的诊断：从“它忘了”走到可证伪假设

“模型能力不行”“上下文太长”都不是根因。诊断顺序应是：

```text
稳定复现 → 定位首次错误步骤 → 查看当步 manifest/事件/版本
        → 提出互斥假设 → 用重放或消融区分 → 修复 → 回归集固化
```

### 4.1 症状—证据—实验矩阵

| 症状 | 可区分的假设 | 先查什么 | 最小判别实验 |
|------|--------------|----------|--------------|
| 忘记用户硬约束 | block 未入选；摘要丢失；已入选但位置/表达失败 | selected/rejected、摘要引用、token 位置 | 强制注入原约束；原文 vs 摘要；位置置换 |
| 引用错误事实 | 检索漏召回；来源低权威；证据过期；模型未利用 | candidate recall、authority、TTL、引用对应 | oracle evidence；移除冲突源；刷新后重放 |
| 调错工具 | 目标 schema 含糊；目录过大；权限过滤后工具不可用 | 当步 tool catalog/hash、参数错误类型 | 最小目录 vs 全目录；改 schema 不改模型 |
| 工具循环 | completion predicate 不清；同一错误无新信息；结果未进状态 | 重复 call signature、state diff、error class | 设置 progress invariant；相同错误禁止无界重试 |
| 摘要后性能突降 | 否定/数值/未决项丢失；递归误差；原文无法回取 | summary coverage、source refs、compaction depth | full history vs 单次摘要 vs 递归摘要 |
| 记住了错误偏好 | 写入 precision 低；实体错配；旧事实未 supersede | write candidate、policy verdict、entity/version chain | 关闭自动写入；加入用户确认；时间冲突样例 |
| 跨用户泄露 | scope 过滤晚于检索；cache key 不含租户；共享摘要污染 | query filter、cache key、lineage | tenant sentinel 与对抗检索测试 |
| 恢复后重复执行 | checkpoint 缺 idempotency key；把摘要当事务状态 | event/receipt、work item status、attempt | 在各阶段注入 crash，验证 effect 至多一次 |
| 成本突然升高 | 工具目录/历史膨胀；缓存失效；检索 top-k 漂移 | block token 分布、cached tokens、catalog hash | 固定 workload 比较版本前后 token 分解 |

### 4.2 Counterfactual replay 的边界

离线重放可以替换 context、模型或策略，比较“如果当时看到 oracle evidence 会怎样”。但有副作用工具不能直接重放到生产：

- PURE/READ 工具可用固定快照或 recorded response。
- 写工具使用 sandbox/dry-run，或只重放到“拟议动作”阶段。
- `OUTCOME_UNKNOWN` 不可伪造为失败；必须用下游 receipt/查询对账。
- 外部世界变化时，记录“历史快照重放”和“当前世界重新执行”是两种不同实验。

## 5. 评测：同时测 selection、representation 和 downstream outcome

上下文系统有三层问题：候选信息是否存在、装配器是否选中、模型是否正确利用。只测最终答案会把三者混在一起。

### 5.1 分层指标

| 层 | 关键指标 | 解释 |
|----|----------|------|
| Candidate | evidence recall、tool availability、freshness coverage | 正确证据/工具是否进入候选池 |
| Selection | protected-block recall、evidence precision/recall、conflict resolution accuracy | 装配器选得是否正确 |
| Representation | summary claim fidelity、constraint recall、citation mapping | 压缩/渲染有没有改变含义 |
| Utilization | answer groundedness、tool choice/argument accuracy、abstention | 模型有没有用对可见信息 |
| End-to-end | task success、risk-weighted error、human escalation | 最终业务结果 |
| Efficiency | input/cached/output token、步骤数、p50/p95 latency、cost | 资源代价和尾延迟 |

几个可操作的定义：

\[
ConstraintRecall=\frac{\#\text{输出中满足的硬约束}}{\#\text{适用硬约束}}
\]

\[
FreshnessViolationRate=\frac{\#\text{使用过期证据的高风险决策}}{\#\text{高风险决策}}
\]

\[
ContextEfficiency=\frac{\text{成功任务数}}{\text{百万输入 token}}
\]

`ContextEfficiency` 只能与成功率、风险和延迟共同看；单独优化会鼓励删掉必要证据。

### 5.2 必做的消融与压力测试

1. **Leave-one-component-out**：分别去掉目标、计划、记忆、RAG、摘要或最近事务。
2. **位置置换**：保持内容不变，只交换证据在头/中/尾的位置。
3. **Distractor scaling**：逐步增加相似但无关的 chunk，画出性能—token 曲线。
4. **冲突/陈旧注入**：放入不同权威级别、valid time 和 observed time 的矛盾事实。
5. **摘要深度**：原文、一次压缩、二次递归压缩，分别测 claim/constraint fidelity。
6. **工具目录缩放**：全量工具、namespace、deferred loading，比较工具选择和输入 token。
7. **Crash matrix**：在工具调用前、提交中、回填前后杀进程，验证 checkpoint 与幂等恢复。
8. **安全 sentinel**：跨租户 canary、注入文本、敏感字段和记忆投毒样例。

对照实验保持模型快照、采样参数、工具响应、任务集合和预算相同。优先使用 paired comparison；报告 bootstrap 置信区间，二元 paired outcome 可用 McNemar 检验。按任务长度、风险级别、工具数和是否需要记忆分层，避免平均数掩盖长尾失败。

### 5.3 一个评测样例应保存什么

```yaml
case:
  id: refund_temporal_conflict_017
  initial_state_snapshot: snapshot://eval/017
  query: "给客户退款并说明原因"
  required_blocks: [policy_refund_limit, latest_payment_status]
  forbidden_blocks: [other_tenant_profile]
  expected_action:
    tool: refund.propose
    constraints: {amount_lte: 500, requires_approval_if_vip: true}
  oracle_evidence: [crm_v4, ledger_v9]
  graders:
    - deterministic_policy_checker
    - tool_argument_checker
    - citation_checker
  risk_weight: 5
```

LLM-as-a-judge 可以评价开放式表达，但金额、权限、引用、schema、租户和副作用必须优先用确定性 grader。评测集还要版本化，防止 prompt/model 针对固定样例过拟合。

## 6. 安全：把 provenance/taint 贯穿整条数据流

结构化分隔符能改善模型理解，却不是安全边界。安全控制应分布在五个位置：

| 控制点 | 主要风险 | 确定性控制 |
|--------|----------|------------|
| Ingest | 恶意网页、伪造来源、敏感信息 | 来源认证、内容类型/大小限制、恶意载荷扫描、DLP 标记 |
| Store | 串户、错误长期固化、无法删除 | scope ACL、加密、写入门、lineage、TTL/retention |
| Assemble | 高权重注入、陈旧/冲突证据、缓存串域 | instruction authority、source policy、freshness、cache security domain |
| Act | 越权工具、参数注入、不可逆副作用 | capability、参数校验、额度、审批、幂等键、sandbox |
| Output | 泄密、未经证实的结论 | DLP/redaction、citation、风险分级、人工复核 |

### 6.1 记忆写入门

候选记忆不能因模型说“请记住”就直接 commit：

```text
candidate extraction
 → instruction/data 分类
 → tenant/entity 解析
 → sensitivity 与 retention policy
 → source authority / valid time / conflict
 → 去重或生成 supersedes 链
 → 必要时用户确认
 → atomic commit + lineage + audit
```

程序性记忆风险更高：一条“以后运行脚本时关闭校验”的外部文本，不能被自动提升为跨任务规则。程序性规则应走代码/配置发布流程，或至少要求受信来源、审批、版本和回滚。

### 6.2 数据删除必须沿 lineage 传播

删除一条原始消息时，要查找它派生的 chunk、embedding、摘要、用户 profile、缓存和离线训练/评测副本。若法律或产品策略不允许删除某类审计记录，应在收集前明确最小字段和保留期，而不是事后才发现无法彻底清理。

## 7. 生产数据模型：最少要能回答五个问题

发生事故时，系统必须回答：当时世界状态是什么、模型看到了什么、为什么选这些、执行了什么、如何恢复。可从以下表开始：

```text
task_run(task_id, status, owner, lease_until, state_version, policy_version)
event(event_id, task_id, seq, type, payload_ref, idempotency_key, created_at)
artifact(artifact_id, uri, hash, media_type, scope, sensitivity, lineage)
memory(memory_id, entity, claim, valid_time, observed_at, source_ref,
       supersedes, sensitivity, status, version)
context_run(context_run_id, task_id, step, assembler_version, model_snapshot,
            selected_ids, rejected_reasons, token_breakdown, context_hash)
tool_attempt(attempt_id, task_id, tool_version, args_hash, effect_type,
             idempotency_key, outcome, receipt_ref)
```

五个必须能查询的问题：

1. 哪个 source/version 支撑了这个 claim？
2. 为什么某个 block 被选中或裁掉？
3. 这个工具动作是否已提交，receipt 在哪里？
4. 某条错误/敏感源派生出了哪些 memory、summary 和 cache？
5. 用原策略和新策略重放时，首次分歧发生在哪一步？

### 7.1 并发与版本

多个 worker 或 Agent 同时写任务/记忆时，需要 `expected_version` 或 CAS：

```text
UPDATE task_run
SET state = new_state, state_version = state_version + 1
WHERE task_id = ? AND state_version = expected_version;
```

更新行数为 0 表示状态已变化，应重读并重新规划，不能覆盖。对记忆也一样：新偏好写入时应引用所替代的版本，避免两个并发会话互相“最后写入者获胜”而不留冲突证据。

## 8. 深度案例：退款 Agent 为什么答对了却仍不可靠

任务：“客户说昨天被重复扣款，请退款 300 元。”一种表面成功的实现把聊天、CRM 搜索结果和退款工具都塞进 prompt，模型调用成功。面试追问应继续拆：

1. **权威状态**：CRM 显示投诉，账本才是扣款权威源；必须读账本最新版本。
2. **时间语义**：“昨天”按客户时区解析；`observed_at` 不等于扣款 `valid_time`。
3. **动作语义**：先 `refund.propose` 还是直接 `refund.commit`？300 元是否需要审批？
4. **幂等性**：用户重试、进程崩溃或工具超时时，使用业务 idempotency key 避免双退。
5. **结果未知**：提交后连接断开，不能直接重试；先按 receipt/key 对账。
6. **上下文**：工具返回大账单时只选目标交易和必要邻近记录，保留 artifact/hash。
7. **记忆**：投诉是本次事件，不应自动写成“该客户经常被重复扣款”的长期画像。
8. **评测**：不仅检查最终文本，还检查权威证据、金额、工具参数、审批、至多一次 effect 和跨租户隔离。

这说明“最终答对一次”只是样例成功；可靠系统必须让每一步都可验证和恢复。

## 9. 反模式及其机制性原因

| 反模式 | 机制性问题 | 替代方案 |
|--------|------------|----------|
| 把全量历史塞给模型 | 成本线性增长、噪声与位置敏感、无法治理删除 | 事件外置、protected blocks、近期事务、可回源摘要 |
| 按消息数截断 | 单条工具结果大小不定，且可能拆散 call/result | token 预算 + atomic transaction groups |
| 摘要作为唯一真相源 | 有损且无法验证，递归误差累积 | 原事件/artifact 保留，摘要携带引用与版本 |
| 所有记忆都进向量库 | 时间、冲突、精确字段和删除语义丢失 | 结构化 claim store + lexical/vector/graph 混合检索 |
| 先全局检索再让模型过滤租户 | 已在候选或 prompt 阶段泄露 | scope/ACL 在检索查询前强制 |
| 标签包住外部文本就算防注入 | 模型仍会解释其中指令 | taint + instruction authority + action control plane |
| 只看最终成功率 | 无法区分候选、选择、表示和利用故障 | 分层指标 + oracle/消融/重放 |
| 只追缓存命中率 | 可能缓存旧 policy 或跨安全域复用 | policy/tool/data/security-domain 版本入 key |
| 用 compaction 恢复任务 | 摘要不包含可靠事务状态 | durable checkpoint + event/receipt reconciliation |
| 记录隐藏推理作为审计依据 | 不稳定、不可验证且可能不提供 | 记录可见输入、结构化决策理由、证据与动作 |

---

## 10. 落地路线：每一步都有退出标准

1. **事件与 trace**：先记录 tool request/result、artifact、token 分解和 model/tool 版本。退出标准：可定位首次错误步骤。
2. **确定性装配器**：实现 block schema、scope、protected blocks、完整事务裁剪和 manifest。退出标准：相同快照可稳定重放。
3. **预算与工具发现**：预留输出/工具预算，按需暴露工具。退出标准：目录增长时成功率、token 和 p95 有曲线。
4. **摘要/卸载**：引入可回源 artifact 与 fidelity eval。退出标准：长任务收益的置信区间不以约束召回下降换取。
5. **长期记忆**：先做一个高价值 memory type，加入写入门、时间/冲突/删除。退出标准：五层记忆 eval 与污染恢复演练通过。
6. **安全和 durable execution**：capability、DLP、审批、幂等、outcome reconciliation。退出标准：注入、跨租户、crash matrix 通过。
7. **线上闭环**：shadow/canary、风险分层采样、版本回滚。退出标准：质量、风险、成本和 p95 同时在 SLO 内。

框架和模型更换不应改变这些退出标准；它们是系统能力，而不是某个 SDK 的 feature checklist。
