# 04 · 上下文管理技巧

> 目标：掌握在有限窗口里"放对信息"的具体手段——滑动窗口、分层摘要、记忆卸载、压缩、Prompt Caching。这些是 [文档 02](02-上下文工程基础.md) 原则的落地工具。

---

## 1. 问题回顾

[文档 02](02-上下文工程基础.md) 说窗口是稀缺预算、[文档 03](03-Agent记忆系统.md) 讲了记忆。但还有个最棘手的具体问题：**Agent 的执行历史（思考-行动-观察）随步数线性增长**，几步之后就撑爆窗口。本章就是治这个的工具箱。

```
失控的历史：  step1 + step2 + step3 + ... + stepN  → 线性膨胀 → 爆窗口
管理后：     [最近几步原文] + [更早的摘要] + [卸载到外部、需要时取回]
```

---

## 2. 滑动窗口（Sliding Window）

最简单：只保留最近 N 轮/消息或最近 M token，更早的丢弃。按“消息数”并不稳定：一条工具结果可能比十轮短对话更长。

```
窗口大小=N：  只保留最近 N 条 → [msg(k-N+1) ... msg(k)]
```

- **优点**：实现极简、token 可控、延迟稳定。
- **缺点**：**会丢掉早期重要信息**（如最初的任务目标、关键约束）。
- **改进**：保护不可丢的 policy/目标/约束/当前计划，按 token 预算保留最近的**完整调用事务**。不能把 assistant tool call 留下却裁掉对应 result，或反过来。
- **适用**：闲聊式、上下文依赖不强、近期信息最重要的场景。

---

## 3. 分层摘要（Hierarchical Summarization）⭐

不丢弃旧历史，而是**把它压成摘要**，保留信息、节省 token。

```
最近的：     保留原文（细节完整）
较早的：     压成简短摘要
更早的：     摘要的摘要（再压一层）
```

- **原理**：越久远的历史，越只需要"要点"而非"原文"。分层摘要让上下文里**近处清晰、远处概要**，兼顾细节和全局。
- **实现**：在 token 阈值触发 compaction，把旧事件压缩为带结构和引用的摘要；原始事件/产物仍保存在外部，摘要不是唯一事实源。
- **代价**：每次摘要是额外的 LLM 调用；摘要可能丢失后来才发现重要的细节。
- **适用**：长对话、长程任务（客服长会话、长篇研究）。
- 这和 [rag/06](../rag/06-高级RAG架构.md) 的 RAPTOR 思想相通——分层组织信息，按需取不同粒度。

### 3.1 摘要是有损变换，要测误差传播

令原历史为 \(H\)，摘要器为 \(C\)，后续任务为 \(q\)。需要关注的不是摘要“读起来不错”，而是：

\[
\Delta_q = Score(q,H)-Score(q,C(H))
\]

递归摘要会组合误差：`C(C(H1), C(H2))` 可能逐层丢掉否定词、数值、未决问题和来源。安全做法：

- policy、用户硬约束、已提交副作用、未决审批不进入自由文本摘要，结构化保留。
- 摘要中的 claim 携带原 event/artifact 引用。
- 保存 `summary_version`、覆盖事件范围和生成器版本。
- 用 constraint recall、claim fidelity、unresolved-item recall 做回归测试。
- 模型对摘要不确定时可以按引用取回原文，而不是继续猜。

## 4. 记忆卸载（Memory Offloading）⭐

**把不常用/暂时不需要的信息从上下文移到外部存储，需要时再取回。**

```
上下文里只留"当前必需" → 其余卸载到外部（文件/向量库/记忆系统）→ 需要时按需检索回来
```

- **本质**：上下文 = 快而小的"工作台"，外部 = 大而慢的"仓库"。只把当前要用的放工作台上。
- **典型做法**：
  - 把长工具结果（如一大段网页、一个大文件）存到外部，上下文里只留一个"引用/摘要"，需要细节时再取。
  - 把阶段性成果写入外部（如草稿文件），后续步骤需要时读回。
  - 与 [文档 03](03-Agent记忆系统.md) 的长期记忆是同一机制（记忆就是一种卸载）。
- **适用**：长任务、工具返回体积大、需要处理超出窗口的数据量。

> 这正是 MemGPT/Letta（[文档 03](03-Agent记忆系统.md)）的核心思想：像操作系统管理内存与磁盘那样，管理"上下文窗口 ↔ 外部存储"的换入换出。

### 4.1 卸载后必须保留可寻址索引

```yaml
artifact_ref:
  id: art_991
  uri: artifact://research/raw/web-17
  sha256: "..."
  media_type: text/html
  created_by: tool_call_77
  observed_at: "2026-07-19T11:40:00+08:00"
  summary: "包含公司 2025 年审计财务数据"
  access_scope: task_123
```

引用必须能验证内容哈希、权限和版本。只在摘要里写“详细信息已存文件”会形成不可恢复的悬空记忆。

## 5. 压缩（Compression）

压缩几乎总是**有损或改变可利用性**。目标是用更少 token 保留当前任务需要的信息，而不是宣称语义完全不变。

- **提示压缩工具（如 LLMLingua）**：用算法/小模型删除预测为低价值的 token；跨模型、跨语言和带代码/schema 的输入可能表现不同，必须做任务级保真测试。
- **裁剪工具结果**：去掉工具返回里的无关字段、冗长 ID、重复内容（[agent-core/02](../agent-core/02-工具使用ToolUse.md) 的"返回值对模型友好"）。
- **结构化代替自然语言**：有时用紧凑的结构化格式比啰嗦的自然语言省 token。
- **适用**：上下文接近窗口上限、对成本敏感的高频场景。

## 6. Prompt Caching（提示缓存）⭐ 省成本利器

不是减少 token，而是**让重复的 token 不重复计费/计算**。

> **原理**：把 prompt 里**重复的长前缀**（系统提示、工具定义、长文档、固定示例）缓存在 LLM 侧；后续调用复用缓存的前缀，**只为变化的部分付费/计算**。

- **收益**：对重复前缀占比高且命中稳定的工作负载可显著降本降延迟；具体折扣、最小可缓存长度、TTL 与写入溢价依模型供应商和版本变化，应以当期官方计价与压测为准。
- **适用场景**：
  - Agent 每步都带相同的系统提示 + 工具定义 → 缓存它们。
  - 反复基于同一份长文档问答 → 缓存文档。
  - [rag/06](../rag/06-高级RAG架构.md) 的 **Contextual Retrieval** 建库正是靠它把成本压下来。
- **工程要点**：了解供应商是隐式前缀缓存还是显式 cache boundary；把稳定内容放在可复用区域，监控 read/write cached tokens、命中率、TTL、租户隔离和缓存失效。产品支持与计价会变化，以当期官方文档为准。

### 6.1 缓存正确性不只是命中率

需要防止：

- policy/tool schema 已升级，旧前缀仍被复用。
- 把用户 A 的敏感上下文通过错误 cache key 复用给用户 B。
- prompt 内容相同但授权主体、区域或数据版本不同。
- 只优化 cache hit，导致大量无关固定内容长期占据窗口。

应用级缓存键至少纳入：`tenant/user scope`、policy version、tool catalog hash、model snapshot、data/artifact version 和安全域。供应商内部 prompt cache 通常不由应用读取明文，但应用仍要保证发送前的上下文边界正确。

## 7. 怎么组合这些技巧（决策指南）

这些不是互斥的，实际是组合使用：

```
固定部分（系统提示+工具定义）  → Prompt Caching（省成本）
近期历史                      → 保留原文（滑动窗口的"尾"）
较早历史                      → 分层摘要（压缩保信息）
任务目标/关键约束             → 固定保留在头部 + 周期重申
大体积工具结果/阶段成果       → 记忆卸载到外部，引用 + 按需取回
长期事实/偏好/经验           → 长期记忆（文档03），按需检索回填
接近窗口上限时                → 压缩（LLMLingua）兜底
```

> 选择依据还是 [文档 02](02-上下文工程基础.md) 的原则：**最少够用、高信噪比、关键信息显眼、按需取回。** 这些技巧都是为这几条原则服务的手段。

### 7.1 一个确定性的装配/裁剪顺序

```text
1. 预留输出、reasoning、tool result 与安全余量
2. 放入不可覆盖 policy / 用户目标 / 当前计划 / 已提交副作用
3. 选择当前步骤的最小工具集合
4. 检索带 provenance/TTL 的任务证据与记忆
5. 放最近的完整调用事务
6. 用摘要索引更早事件，必要时按引用回取原文
7. 超预算时按 priority 裁剪，并记录被裁掉的 block IDs
8. 生成 context manifest 和 hash，随 trace 保存
```

若第 2 步已经超过预算，不能静默截断 policy；应降低任务范围、换模型/窗口、拆阶段或停止。

### 7.2 Compaction 与 checkpoint 的边界

- compaction 解决“下一次模型调用看什么”。
- checkpoint 解决“进程崩溃后从哪个任务状态恢复”。

恢复时可以重新构造 context，但不能用摘要推断已提交外部动作。长任务设计详见 [长任务与跨上下文连续性](../systems-engineering/04-长任务与跨上下文连续性.md)。

## 8. 常见坑

- **只用朴素滑动窗口** → 丢掉最初的目标和关键约束。要固定头部 + 滑动尾部。
- **摘要过度/过频** → 丢失后来才需要的细节；也增加 LLM 调用成本。
- **卸载了却不知道何时取回** → Agent "忘了"外部有这条信息。要在上下文留"索引/引用"。
- **Prompt Caching 把变化内容放前面** → 前缀不一致，缓存永远不命中。固定内容务必放前部。
- **压缩压过头** → 删掉了有用信息，效果下降。
- **按消息数裁剪，拆散 tool call/result** → 协议序列无效或模型误判工具未完成。
- **摘要成为唯一事实源** → 后来发现遗漏时无法回取原文。
- **cache key 不含租户/策略/工具版本** → 串户或复用陈旧控制信息。
- **用 compaction 代替 checkpoint** → 文本看似恢复，真实副作用和 work item 已丢失。
- **堆砌技巧不评估** → 不知道哪个真有用。用 [INDEX 阶段6](../INDEX.md) 的评估验证。

## 9. 本章小结

- 治"历史线性膨胀"的工具箱：滑动窗口、分层摘要、记忆卸载、压缩、Prompt Caching。
- **滑动窗口**：留最近 N 条，最好"固定头部（目标）+ 滑动尾部（近期）"。
- **分层摘要**：旧历史压成摘要，近处清晰远处概要，保信息省 token。
- **记忆卸载**：上下文只留当前必需，其余移到外部按需取回（Letta/MemGPT 的核心）。
- **压缩**（LLMLingua 等）：同样信息更少 token；裁剪工具结果。
- **压缩**是有损变换，要用 constraint/claim/代码/schema 保真测试验证。
- **Prompt Caching**：重复前缀缓存复用；固定内容放前部，并监控缓存命中率、读写 token 价格和 p95 延迟，不把供应商“最高可达”数字当容量承诺。
- 实战是**组合使用**，全部服务于"最少够用、高信噪比、关键信息显眼"的原则。
