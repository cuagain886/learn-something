# 04 · 上下文管理技巧

> 目标：掌握在有限窗口里"放对信息"的具体手段——滑动窗口、分层摘要、记忆卸载、压缩、Prompt Caching。这些是 [文档 02](02-上下文工程基础.md) 原则的落地工具。

---

## 1. 问题回顾

[文档 02](02-上下文工程基础.md) 说窗口是稀缺预算、[文档 03](03-Agent记忆系统.md) 讲了记忆。但还有个最棘手的具体问题：**Agent 的执行历史（思考-行动-观察）随步数线性增长**，几步之后就撑爆窗口。本章就是治这个的工具箱。

```
失控的历史：  step1 + step2 + step3 + ... + stepN  → 线性膨胀 → 爆窗口
管理后：     [最近几步原文] + [更早的摘要] + [卸载到外部、需要时取回]
```

---

## 2. 滑动窗口（Sliding Window）

最简单：**只保留最近 N 轮/N 条消息**，更早的丢弃。

```
窗口大小=N：  只保留最近 N 条 → [msg(k-N+1) ... msg(k)]
```

- **优点**：实现极简、token 可控、延迟稳定。
- **缺点**：**会丢掉早期重要信息**（如最初的任务目标、关键约束）。
- **改进**：**固定头部 + 滑动尾部**——永远保留系统提示和任务目标（头），加最近 N 条（尾），丢中间。这缓解了"忘了目标"的问题（呼应 [文档 02](02-上下文工程基础.md) 的"重申目标"）。
- **适用**：闲聊式、上下文依赖不强、近期信息最重要的场景。

---

## 3. 分层摘要（Hierarchical Summarization）⭐

不丢弃旧历史，而是**把它压成摘要**，保留信息、节省 token。

```
最近的：     保留原文（细节完整）
较早的：     压成简短摘要
更早的：     摘要的摘要（再压一层）
```

- **原理**：越久远的历史，越只需要"要点"而非"原文"。分层摘要让上下文里**近处清晰、远处概要**，兼顾细节和全局。
- **实现**：每隔 K 步/超过阈值时，用 LLM 把较早的历史段落总结成摘要，替换原文。
- **代价**：每次摘要是额外的 LLM 调用；摘要可能丢失后来才发现重要的细节。
- **适用**：长对话、长程任务（客服长会话、长篇研究）。
- 这和 [rag/06](../rag/06-高级RAG架构.md) 的 RAPTOR 思想相通——分层组织信息，按需取不同粒度。

---

## 4. 记忆卸载（Memory Offloading）⭐

**把不常用/暂时不需要的信息从上下文移到外部存储，需要时再取回。**

```
上下文里只留"当前必需" → 其余卸载到外部（文件/向量库/记忆系统）→ 需要时按需检索回来
```

- **本质**：上下文 = 快而小的"工作台"，外部 = 大而慢的"仓库"。只把当前要用的放工作台上。
- **典型做法**：
  - 把长工具结果（如一大段网页、一个大文件）存到外部，上下文里只留一个"引用/摘要"，需要细节时再取。
  - 把阶段性成果写入外部（如草稿文件），后续步骤需要时读回。
  - 与 [文档 03](03-Agent记忆系统.md) 的长期记忆是同一机制（记忆就是一种卸载）。
- **适用**：长任务、工具返回体积大、需要处理超出窗口的数据量。

> 这正是 MemGPT/Letta（[文档 03](03-Agent记忆系统.md)）的核心思想：像操作系统管理内存与磁盘那样，管理"上下文窗口 ↔ 外部存储"的换入换出。

---

## 5. 压缩（Compression）

在不改变信息的前提下，**用更少的 token 表达同样的内容**。

- **提示压缩工具（如 LLMLingua）**：用算法/小模型识别并删除 prompt 里冗余、低信息量的 token，压缩后再喂给大模型，token 大幅减少而效果损失可控。
- **裁剪工具结果**：去掉工具返回里的无关字段、冗长 ID、重复内容（[agent-core/02](../agent-core/02-工具使用ToolUse.md) 的"返回值对模型友好"）。
- **结构化代替自然语言**：有时用紧凑的结构化格式比啰嗦的自然语言省 token。
- **适用**：上下文接近窗口上限、对成本敏感的高频场景。

---

## 6. Prompt Caching（提示缓存）⭐ 省成本利器

不是减少 token，而是**让重复的 token 不重复计费/计算**。

> **原理**：把 prompt 里**重复的长前缀**（系统提示、工具定义、长文档、固定示例）缓存在 LLM 侧；后续调用复用缓存的前缀，**只为变化的部分付费/计算**。

- **收益**：**延迟降 2 倍以上、成本降最高 90%**（对前缀大、调用频繁的场景）。
- **适用场景**：
  - Agent 每步都带相同的系统提示 + 工具定义 → 缓存它们。
  - 反复基于同一份长文档问答 → 缓存文档。
  - [rag/06](../rag/06-高级RAG架构.md) 的 **Contextual Retrieval** 建库正是靠它把成本压下来。
- **工程要点**：把**固定不变的内容放在 prompt 前部**（缓存命中要求前缀一致），变化的内容放后部。Claude/Gemini/OpenAI 的 API 都支持。

---

## 7. 怎么组合这些技巧（决策指南）

这些不是互斥的，实际是组合使用：

```
固定部分（系统提示+工具定义）  → Prompt Caching（省成本）
近期历史                      → 保留原文（滑动窗口的"尾"）
较早历史                      → 分层摘要（压缩保信息）
任务目标/关键约束             → 固定保留在头部 + 周期重申
大体积工具结果/阶段成果       → 记忆卸载到外部，引用 + 按需取回
长期事实/偏好/经验           → 长期记忆（文档03），按需检索回填
接近窗口上限时                → 压缩（LLMLingua）兜底
```

> 选择依据还是 [文档 02](02-上下文工程基础.md) 的原则：**最少够用、高信噪比、关键信息显眼、按需取回。** 这些技巧都是为这几条原则服务的手段。

---

## 8. 常见坑

- **只用朴素滑动窗口** → 丢掉最初的目标和关键约束。要固定头部 + 滑动尾部。
- **摘要过度/过频** → 丢失后来才需要的细节；也增加 LLM 调用成本。
- **卸载了却不知道何时取回** → Agent "忘了"外部有这条信息。要在上下文留"索引/引用"。
- **Prompt Caching 把变化内容放前面** → 前缀不一致，缓存永远不命中。固定内容务必放前部。
- **压缩压过头** → 删掉了有用信息，效果下降。
- **堆砌技巧不评估** → 不知道哪个真有用。用 [INDEX 阶段6](../INDEX.md) 的评估验证。

---

## 9. 本章小结

- 治"历史线性膨胀"的工具箱：滑动窗口、分层摘要、记忆卸载、压缩、Prompt Caching。
- **滑动窗口**：留最近 N 条，最好"固定头部（目标）+ 滑动尾部（近期）"。
- **分层摘要**：旧历史压成摘要，近处清晰远处概要，保信息省 token。
- **记忆卸载**：上下文只留当前必需，其余移到外部按需取回（Letta/MemGPT 的核心）。
- **压缩**（LLMLingua 等）：同样信息更少 token；裁剪工具结果。
- **Prompt Caching**：重复前缀缓存复用，**降本最高 90%、延迟降 2 倍+**；固定内容放前部。
- 实战是**组合使用**，全部服务于"最少够用、高信噪比、关键信息显眼"的原则。
