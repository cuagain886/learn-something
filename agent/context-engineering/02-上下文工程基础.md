# 02 · 上下文工程基础

> 目标：理解为什么"上下文工程"是 2026 Agent 可靠性的头号命门。读完能讲清"窗口即预算"、上下文的组成、以及"迷失在中间/上下文腐烂"等失败的根源。

---

## 1. 什么是上下文工程

> **上下文工程（Context Engineering）**：系统化地决定——在 Agent 的**每一步**，把**哪些信息、以什么形式、以什么顺序**，装进模型那个**有限的上下文窗口**里。

它是 Prompt 工程在 Agent 时代的升级：
- **Prompt 工程**关注"怎么写好一句指令"（静态、单次）。
- **上下文工程**关注"在一个多步、长程、动态的 Agent 运行中，怎么持续地把对的信息流式喂给模型"（动态、贯穿全程）。

上下文工程是 Agent harness 的核心组成，但“最核心”不是可独立验证的排名。更精确的结论是：模型只能根据实际送入本轮的 token、可访问工具和外部状态投影做决策，因此 context assembly 是影响系统策略的直接变量之一。

---

## 2. 为什么它是长任务的关键控制面 ⭐

多步 Agent 的上下文会随着每次工具调用增长；窗口截断、摘要、检索和状态恢复又会改变模型下一步实际看到的信息。这里不存在跨任务通用的失败占比，应该在自己的评测集上分别诊断漂移、遗漏、污染与陈旧状态。

为什么 Agent 特别容易栽在这上面？因为 Agent 是**多步循环**（[agent-core/01](../agent-core/01-Agent循环与ReAct.md)）：
- 每一步都往上下文里塞新东西（思考、工具调用、观察结果）。
- 步数一多，上下文要么**爆窗口**，要么**塞满噪声**，模型逐渐“忘了最初的目标”或被无关信息带偏。发生率随模型、任务、上下文装配器和工具观察质量而变，必须用重复试验测量。

**上下文工程就是治这个病的。**

---

## 3. 核心认知：窗口是"预算"，不是"仓库" ⭐⭐

最重要的心智转变：

> 上下文窗口不是"能塞多少塞多少"的仓库，而是**稀缺、昂贵、且越满越不准**的预算。

三个"越满越糟"的理由：

### 3.1 越满越贵、越慢
- 按 token 计费，上下文越长，每次调用越贵。Agent 多步循环会把成本乘以步数。
- 上下文越长，首字延迟（TTFT）越高，体验越差。

### 3.2 迷失在中间（Lost in the Middle）⭐
“Lost in the Middle”研究在特定模型与多文档任务上观察到 U 型位置效应：相关信息位于开头或结尾时常优于中间。但位置效应随模型、长度和任务变化，不能把“中间等于没放”当通用定律。正确做法是用位置扰动测试自己的模型，并减少模型必须跨越的无关内容。

### 3.3 上下文腐烂 / 噪声干扰（Context Rot）
塞进越多无关信息，模型越容易被噪声带偏、分心、产生幻觉。**信噪比比信息量更重要。**

> 结论：上下文工程的核心动作是**做选择、排序、压缩和来源标注**。关键信息要稳定、可定位，但具体位置应由目标模型的消融实验决定。

### 3.4 Context budget 可以显式记账

若窗口上限为 \(W\)，要为输出和安全余量预留空间：

\[
B_{input}=W-B_{output}-B_{reasoning/reserve}-B_{safety}
\]

输入预算再分给：

\[
B_{input}=B_{instructions}+B_{tools}+B_{task}+B_{evidence}+B_{history}+B_{memory}
\]

这不是要求固定百分比，而是要求 context assembler 在超预算时有确定的裁剪优先级。否则通常由字符串拼接顺序偶然决定谁被截断。

## 4. Agent 上下文窗口里到底有什么（组成解剖）

一个 Agent 在某一步，窗口里通常装着这些"预算项"：

```
┌─────────────────────────────────────────────┐
│ ① 系统提示 / 角色设定（相对固定）              │  ← 可缓存（Prompt Caching）
│ ② 工具定义（当前可用的工具 schema）            │  ← 工具多就裁剪
│ ③ 任务目标 / 用户请求                          │  ← 要"重申"防遗忘
│ ④ 长期记忆检索结果（相关的历史/事实）          │  ← 按需检索，不是全塞
│ ⑤ RAG 检索的知识 chunk                         │  ← 重排后只放 top-k
│ ⑥ 对话/执行历史（之前的思考-行动-观察）         │  ← 最容易爆，要压缩
│ ⑦ 当前这一步的输入                             │
└─────────────────────────────────────────────┘
        ↑ 这些加起来不能超过窗口预算，且信噪比要高
```

上下文工程就是**管理这七项的取舍**：哪些固定（可缓存）、哪些动态检索、哪些要压缩、哪些要裁剪、什么放最显眼的位置。

- ⑥（历史）是**最容易失控**的——它随步数线性增长。[文档 04](04-上下文管理技巧.md) 的滑动窗口、摘要、卸载主要在治它。
- ④⑤（记忆和 RAG）的核心是**"按需取回最相关的少量"**，而不是全量塞。这就是为什么 [文档 03](03-Agent记忆系统.md) 说"记忆即 RAG"。
- ①②可借助 **Prompt Caching** 省成本（[文档 04](04-上下文管理技巧.md)）。

## 5. 上下文工程的几条原则

1. **最少够用（Minimal Sufficient Context）**：每一步只放完成它所需的最少信息。先问"这条信息这一步用得到吗？"
2. **高信噪比**：宁可少而精，不要多而杂。无关信息是负债不是资产。
3. **关键信息放显眼处**：重要指令/约束/目标放开头或结尾，避开"中间盲区"。
4. **重申目标（Goal Reiteration）**：长循环中周期性把"当前总目标"重新放进上下文，防止计划放弃/漂移。
5. **结构化、可区分**：用清晰的分隔（标签、标题）区分"指令 / 资料 / 历史 / 工具结果"，让模型不混淆，也降低 prompt 注入风险。
6. **动态而非静态**：根据当前步骤的需要动态组装上下文，而不是每步都用同一个臃肿模板。

### 5.1 Context manifest：让每个 token 块有身份

不要只拼一个大字符串。给进入上下文的 block 维护 manifest：

```yaml
context_manifest:
  - id: system_policy_v17
    kind: instruction
    trust: trusted
    priority: must_keep
    version: 17
    tokens: 820
  - id: order_O123_v42
    kind: world_fact
    trust: tool_verified
    observed_at: "2026-07-19T10:30:00+08:00"
    stale_after: "5m"
    provenance: "orders.get/O-123"
    tokens: 210
  - id: web_9
    kind: external_evidence
    trust: untrusted
    provenance: "https://example.org/..."
    tokens: 640
```

它支持：预算审计、来源追踪、TTL、新旧版本冲突、敏感数据脱敏和逐块消融。没有 manifest 时，“上下文工程”很容易退化成难以解释的 prompt 拼接。

### 5.2 四种冲突要在装配前解决

| 冲突 | 例子 | 决策依据 |
|------|------|----------|
| 指令冲突 | 用户要求绕过系统策略 | 指令层级与不可覆盖策略 |
| 事实冲突 | CRM 与账务系统状态不同 | source authority、版本、新鲜度、对账 |
| 时间冲突 | 用户旧偏好与新偏好 | valid time / observed time / supersedes |
| 范围冲突 | 项目规则与子目录规则不同 | 作用域与更具体规则 |

不能把冲突的两段文本一起塞给模型后说“请自行判断”。控制面应先把可确定的优先级和版本关系解析出来，把真正不确定项显式标成 unknown。

### 5.3 指令与数据分隔是提示，不是安全边界

XML 标签、Markdown 围栏和“以下内容仅供参考”能改善可读性，但模型仍可能受数据中的指令影响。外部内容必须保留 provenance/taint，危险动作还要经过权限、DLP、审批和参数校验。上下文排版不能替代安全控制。

## 6. 上下文工程 vs 单纯加大窗口

"模型窗口越来越大（百万 token），是不是就不用做上下文工程了？" —— **不是。**

- **成本/延迟**：百万 token 每步都塞满，成本和延迟无法接受（Agent 还要乘以步数）。
- **迷失在中间**：窗口大不代表中间信息被用好，塞满反而更糟。
- **信噪比**：大窗口塞更多噪声，干扰更严重。

> 大窗口让上下文工程**更从容**（有余量放更多检索结果），但**不取代**它。核心仍是"放对的、放少的"。这和 [rag/01](../rag/01-RAG基础与核心原理.md) 讲"长上下文不取代 RAG"是同一个道理。

### 6.1 Long context、RAG 与外部状态各解决不同问题

| 手段 | 解决 | 不解决 |
|------|------|--------|
| 长窗口 | 单次可见 token 上限 | 新鲜度、权限、状态恢复、证据选择 |
| RAG/记忆检索 | 从大集合中选择候选证据 | 检索遗漏、写入污染、世界状态事务 |
| 外部任务状态 | checkpoint、所有权、版本、恢复 | 模型本轮需要看到哪些 token |

长任务需要三者组合。把 checkpoint 序列化成一段摘要再塞回窗口，不等于恢复了副作用状态和未完成 work item。

## 7. 如何证明某种上下文策略更好

建立同一任务、同一模型、同一工具预算的 paired eval，分别改变：

1. 去掉某类 block，做 leave-one-component-out 消融。
2. 打乱证据位置，测 position sensitivity。
3. 注入陈旧/冲突证据，测 source/version 处理。
4. 比较原文、一次摘要、递归摘要，测 constraint/claim 保真。
5. 对 tool catalog 做全量 vs deferred loading，测选择准确率和 token。

指标至少包括最终任务成功、关键约束保留、证据召回/引用正确、工具选择、输入 token、p95 延迟和成本。只看“回答更流畅”不能证明 context assembly 正确。

## 8. 常见坑

- **把窗口当仓库，能塞就塞** → 又贵又慢又被噪声带偏。头号误区。
- **关键约束埋在上下文中间** → 迷失在中间，模型看漏。
- **长循环不重申目标** → 计划放弃、上下文漂移。
- **历史不做处理、线性堆积** → 几步后就爆窗口。
- **指令和资料不分隔** → 模型混淆，且易被注入。
- **把分隔标签当注入防线** → 标签只能帮助模型理解，不能阻止越权动作。
- **没有 block 级 provenance/TTL** → 无法解释陈旧事实或删除敏感数据。
- **冲突留给模型自由裁决** → source authority 与版本规则没有进入确定性控制面。
- **以为大窗口能解决一切** → 忽视信噪比，反而更差。

## 9. 本章小结

- **上下文工程 = 系统化决定“每一步把哪些信息、怎样装进有限窗口”**。它把单次 Prompt 设计扩展为持续的选择、压缩、权限、版本和状态投影问题。
- **上下文问题要分型测量**——约束遗漏、证据遗漏、摘要失真、状态陈旧和噪声污染需要不同修复手段。
- **窗口是预算不是仓库**：越满越贵、越慢、越易"迷失在中间"、越被噪声干扰。**多 ≠ 好，信噪比 > 信息量。**
- Agent 上下文由系统提示/工具定义/目标/记忆/RAG/历史/当前输入等组成，**历史最易失控**，记忆和 RAG 要"按需取少量"。
- 原则：最少够用、高信噪比、结构化区分、动态组装；具体位置效应要用目标模型验证。
- Context manifest 为每个 block 记录类型、信任、版本、新鲜度、来源、敏感级别与 token，才能审计和消融。
- 大窗口让上下文工程更从容，但不取代它。
